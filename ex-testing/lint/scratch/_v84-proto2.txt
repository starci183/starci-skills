CONFLICT br.audit.erasure.right (done) -> br.audit.retention rev=2 because: retention promises a line is never lost within 400 days; a verified erasure request can arrive on day one of that window and must still take effect immediately, so the two rules cannot both be satisfied by 'keep everything, always, for 400 days' - retention has to mean the line's existence and chain position, not the readability of every field in it.
CONFLICT data.audit.log-line (done) -> br.task.delete.final rev=1 because: stays-gone requires a deleted task's identifier to resolve to nothing anywhere, now and after a restart, but target here is exactly that identifier, kept byte-for-byte in a task.deleted line for the full retention window - append-only forbids scrubbing it, so a task's identifier does resolve to something for as long as the line is readable, through the log's own read and export paths.
CONFLICT contract.plan.create-precondition (done) -> fr.task.create rev=(none) because: fr.task.create's mainFlow creates a task for any non-empty title with no precondition step and no dependency on this contract, so its done state and this contract's consumerObligations describe two different, currently incompatible realities for the same code path.
CONFLICT data.recur.occurrence (done) -> sds.task.completion-state rev=(none) because: an occurrence's lifecycle has five states because a rule can end under it (materialised can become orphaned); sds.task.completion-state models exactly two (open, complete) for a task with no such ending, and this feature does not own that record to widen its state machine. Extending data.task.task's fields (see extends above) does not extend that state machine.
