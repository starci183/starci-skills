# Read-only Work metadata core

`validateWorkspace(root)` is synchronous and returns `{ok,errors,warnings,nodes,resources}`. Each diagnostic has `code,path,message`; paths are workspace-relative. Node summaries expose `id,path,kind,required,state,effectiveState,specDigest,inputDigest,eligible,children`. Resources expose only `id,path,kind,revision`. No metadata bodies, account details or credentials are printed. Unknown extension data stays untouched on disk and participates in semantic hashes. `canonicalJSON(value)`, `sha256(bytesOrString)` and `profiles` are also exported.

Metadata `.yaml` files contain **JSON syntax only**, a YAML-compatible subset. `node.md` starts with `---`, a JSON object, `---`, then nonempty Markdown specifying scope and observable acceptance. Unsupported YAML is rejected, never guessed. The shape reference is [work.schema.json](../schemas/work.schema.json); executable completion profiles have their single home in [profiles.json](../schemas/profiles.json). The core reads allowed keys from the published schema and rejects unknown keys in reserved metadata objects, including nested completion, assertions, bindings, assets and provenance. A typo such as `dependOn` cannot silently bypass the dependency gate. Arbitrary namespaced data is allowed inside `extensions` and resource `details`; those fields do not become executable dependency instructions. Node operational timestamps are explicitly allowed by the schema. Schema shape alone is not completion verification.

## Layout and identity

The argument is the `.work` directory, containing `workspace.yaml`. Resources live under `_resources/**/resource.yaml`. Arbitrary business directories contain `node.md`; the nearest ancestor node defines the parent. A parent cannot store state or completion. Evidence uses `evidence/<id>/manifest.yaml` under a node or business directory, referenced by stable metadata ID. Global IDs are unique across workspace, nodes, resources and evidence; directory names are not IDs. Intermediate folders without nodes are permitted. `evidence`, `assets` and `_resources` are reserved artifact/resource directory roles: a `node.md` anywhere below them is rejected and never enters the completion tree. `_local` and `.git` are ignored. Canonical symlinks and path traversal are rejected; secrets stay outside this root, referenced by sealed provider aliases in resource details. Known plaintext credential fields are rejected recursively in every metadata type, including workspace extensions. This is a conservative key check, not comprehensive secret detection in arbitrary prose or disguised values. The validator does not fetch remote assets or resolve secrets.

## Digests and effective state

`specDigest` covers all node metadata except `state`, `completion`, `blocker`, `naReason`, `timestamps`, `createdAt`, `updatedAt`, plus normalized Markdown body. Unknown extension fields are included conservatively. `inputDigest` additionally binds workspace metadata, ancestor specifications and their referenced inputs, recursively referenced nodes/dependencies/resources, and descendants for branches. Node paths are excluded so a rename preserving hierarchy and IDs does not invalidate proof. Resource metadata, including its explicit revision and details, is bound in full. Resource-to-resource links inside arbitrary details are not interpreted; reference every applicable resource from the consuming node. No field hidden inside extension prose is automatically a dependency.

Changing only completion or state does not mechanically alter a digest. Dependency eligibility is still checked separately: a completed consumer requires its own and inherited ancestor `dependsOn` targets to be effectively `done` or reasoned `na`. `refs` bind semantic inputs but do not imply execution order. A changed specification/resource yields `stale` completion and fails validation until actual re-verification; never overwrite a digest merely to clear the gate.

Declared leaf states: `todo`, `doing`, `blocked`, `done`, `na`. Effective states additionally include `stale` and `invalid`. N/A requires a reason and is not evidence of passing. Required children drive parent rollup; all N/A becomes N/A, mixed done/N/A becomes done, otherwise invalid/blocked/stale/doing/todo applies. An all-optional branch is N/A, not certified done; unfinished optional work produces a warning. Shared metadata/evidence integrity errors fail closed for all nodes. Unknown leaf kinds remain readable with warnings but cannot earn `done`; supported profiles must be implemented and tested before certifying new kinds.

## Completion profiles

Every supported done leaf declares nonempty `assertions:[id]`. Completion is `{inputDigest,evidence:[evidenceId],codeRefs?:[{repository,commit}]}`. Evidence must explicitly bind that node and its current inputs, report overall pass, contain nonempty passing observations, and cover every declared assertion ID. A failed, missing, not-run or inconclusive assertion cannot become done. Hashes establish binding and byte integrity, **not the truth of an observation**.

One run bundle can serve multiple leaves without copying screenshots: retain its primary `nodeId,inputDigest`, then add `bindings:[{nodeId,inputDigest}]` for additional consumers. Every bound node ID must resolve and appear only once (including the primary); each consumer is checked against its own current digest and declared assertions. Store the manifest and assets once at the flow's `evidence/<id>/` and reference the same evidence ID from each appropriate leaf. An unlisted consumer cannot reuse the proof. Changing one consumer makes that consumer stale, not an unrelated binding whose inputs still match. Overall failure or corrupted assets invalidates the shared bundle for all consumers.

Implementation and release require repository resource IDs and full lowercase 40/64-hex commit SHAs. Those resource IDs must be in node `refs`; every selected evidence record must carry corresponding `codeRefs`. The core does not check Git object existence, ancestry, remote publication or commit origin. Record original versus integrated commits in explicit extensions when required; do not equate one commit binding with deployed code.

Operators must refresh applicable repository and environment resource revisions from actual inspected code/build state before validation. This core does not watch source files or deployments. A changed Git HEAD or remote runtime is not automatically detected if metadata is left unchanged; hashes cannot repair stale or fabricated inputs. `eligible` means structurally valid with satisfied own/inherited prerequisites, not user approval or authority to execute.

UAT evidence requires `provenance:{environment,actor,servedVersions,tool,capturedAt,servedVersionEvidence}` or `anonymous:true` instead of actor. Environment and actor resolve to resources of kinds `environment` and `identity`. Each served version is `{repository,commit,artifact}`: an actual observed immutable image/build identity, not a copied source HEAD. `servedVersionEvidence` identifies a passing assertion explaining the runtime version observation. Environment, actor and repository IDs must be included in node refs for invalidation. The core verifies declared binding, not the external endpoint; an operator must inspect the actual served target and capture tool-derived observations. A fabricated build label can pass structural checks and must be caught by tool evidence and review.

`uat.ui` additionally requires hashed local PNG/JPEG/WebP image bytes. Image recognition checks file signatures only, not complete image decoding, correct rendering, authenticity, viewport or freshness. The operator must open and examine the image. `uat.ux` requires at least one passing assertion marked `kind:"behavior"`; screenshot-only evidence cannot suffice. Observation semantics and assertion adequacy require review.

Evidence assets are relative normalized paths under their evidence directory with SHA-256; missing files, mismatched hashes, absolute paths, traversal and symlinks are rejected. Remote-only evidence cannot be certified in this implementation. No command runs, no account is created, no state is repaired and no next op is dispatched by validation.

## Minimal authoring sequence

Author source requirements/resources and a `todo` leaf with declared assertions. Call validation to obtain its current `inputDigest`. Execute only the approved op, save real evidence with that digest and actual code/runtime binding. Set completion only after reviewing passing proof; revalidate. These steps are operator responsibilities, not an automatic chain. Examples and tests use synthetic observations and must not be cited as product acceptance.
