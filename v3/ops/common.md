# One-op execution protocol

This English document and the selected English operator document are runtime authority. Read both completely. Same-stem `.vi.md` files are human mirrors. Read only domain references the selected scope actually needs; legacy operator files document compatibility, never restore their session, request/response, automatic-next or approval loops.

## Selection and authority

One task has one purpose and may select several independent pieces. One invocation executes one operator against its explicit target set and specific observable goal. A user-approved group may contain several ops, but completing one does not dispatch another. A catalogue entry is a contract, not an execution engine or permission grant.

Use the current request and accepted business nodes as intent authority; observed source, runtime and evidence describe facts. Label proposed values, examples, unknowns and contradictions explicitly. Never infer requirements from old behavior, invent a missing actor/route/repository/rule/test result, or turn a screenshot into proof of persistence. A newly proposed path can be written inside an authorized scope, but must be labelled proposed, not claimed to exist.

At entry, state in the conversation: specific goal, selected node IDs, bounded source/resource writes and done-when. Reuse the user's existing explicit approval for that scope. Ask only about a material missing business decision, unresolved conflict, new external effect or wider ownership. Do not demand a request file, response file, session folder, approval token or another confirmation simply because an op started. An execution request does not authorize unrelated deployment, account creation, billing, push, deletion or force operations.

Inspect applicable repository instructions, the current `.work` root and exact repository identities before writes. Preserve unrelated dirty changes. Inspect dependencies and existing valid pieces; choose only requested eligible unfinished/suspended pieces, never the first unchecked node blindly. A missing prerequisite blocks the affected piece, not an invitation to run a prerequisite op. If several pieces are explicitly selected for parallel work, verify disjoint mutable paths, resources, sessions and test data first. Three independent selected UAT flows can use three agents when that parallel dispatch is authorized and available; three is not a mandatory count for every task. Shared dependencies remain shared reads. An agent owns its target nodes, not the entire parent tree.

## Dependency graph and scope ownership

The actual dependency graph belongs in `.work`, not in an operator's next-step list. The directory tree is containment/completion; `dependsOn:[nodeId]` declares prerequisite work and requires effective `done`. `na` is not a completed account, chat module or other prerequisite. `refs:[nodeOrResourceId]` binds semantic inputs and freshness but does not require completion or imply execution order. Resource `files` bind actual local source artifacts. Neither a prose dependency nor an operator name implicitly creates a graph edge.

For example, one approved scope can declare art direction → UI design → frontend → UAT; another can declare module work dependent on account and chat pieces; another business → architecture → implementation → UAT. These are example data relationships, not universal chains to insert into every task. Store each prerequisite's stable node ID in its consumer's `dependsOn`, and source/requirement/resource IDs in `refs` where their changes affect the consumer. Unrelated pieces stay unrelated.

Only an explicitly selected goal/scope/planning or retirement op changes the selected scope graph. Other ops read their node's own and inherited graph and perform the selected job only. They cannot silently add/drop dependencies, refs, required flags or acceptance scope to run or earn pass. When a required declared prerequisite is missing/not done, report the exact IDs and stop the affected piece. If the graph itself is incomplete/wrong, propose a separately selected scope update; do not dispatch a prerequisite op or repair the graph as an implementation/UAT convenience. A source artifact producer may update its owned resource/files within the existing graph, but may not attach new consumers.

## Path and field contract

Paths below are templates, not discovered locations. Resolve `<business>`, `<piece>`, resource slugs and repository IDs from the selected workspace. Never persist literal angle-bracket placeholders or guess a path by similar name. `N` means the selected node directory, `E` means `N/evidence/<unique-evidence-id>`, `R` means `.work/_resources/<category>/<slug>`. Resolve symlinks and keep writes within the authorized roots.

Metadata uses JSON syntax, a YAML-compatible subset, in `workspace.yaml`, `resource.yaml`, evidence `manifest.yaml`, and JSON front matter inside `node.md`. This release does not parse arbitrary YAML. Consult the actual schemas under `v3/schemas/` for accepted core fields; rich domain content belongs in Markdown body or namespaced `extensions`, never ad hoc root fields.

| Destination | Fields or content | Writer / invariant |
| --- | --- | --- |
| `.work/workspace.yaml` | `schema: work/workspace@1`, stable `id`; declared workspace extensions if needed | Initialize only if this workspace is new; do not replace an existing identity. |
| `N/node.md` front matter | `schema: work/node@1`, stable `id`, `kind`, `required`, `dependsOn`, `refs`, `assertions`; leaf `state` | Scope/graph fields belong to the selected scope/planning change. Consumer ops read them unchanged; `refs` contains resolvable node/resource IDs, not a copied document. |
| `N/node.md` body | Specific purpose, scope/exclusions, authority citations, observable done-when; the operator's domain tables | Current specification, not a transcript. IDs survive renames. Child directories define the tree. |
| `N/node.md` leaf metadata | `blocker` when blocked, `naReason` for `na`, `completion` for accepted evidence | Use core schema shapes. Parents store no state/completion. `todo`, `doing`, `blocked`, `done`, `na` are persisted leaf states; freshness/rollup is derived. |
| `N/node.md` `extensions.work3` | Domain-specific structured data explicitly described in the selected op; version/domain must be named if another consumer depends on it | Not a second progress ledger. Extension data is retained, but not automatically semantically certified by core. |
| `R/resource.yaml` | `schema: work/resource@1`, stable `id`, `kind`, `owner`, `revision`, `details`; optional `files:[{path}]` | One canonical shared resource. Files are normalized local paths relative to the resource directory; the core hashes actual bytes. No authored `sha256` field inside `files`. Update only owned source fields; runtime observations belong in evidence. |
| `E/manifest.yaml` | `schema: work/evidence@1`, `id`, `nodeId`, `inputDigest`, `outcome`, `assertions:[{id,outcome,observation}]`, `assets:[{path,sha256}]`; applicable `provenance`, `codeRefs`, `extensions` | Write actual outcomes `pass`, `fail`, `not-run`, `inconclusive`. Every required assertion needs an actual observation. Assets use paths inside E and hash actual final bytes. |
| `E/*` | Actual captured images, redacted tool output, test results, measurements and other files named by the op | Store durable evidence, not every conversational input/output. Do not overwrite a sealed evidence bundle. Keep failures needed to explain current defects. |
| `.work/_local/` | Ephemeral cache, scratch, machine-local checkout/session handles | Ignored; never the sole copy of acceptance evidence or custody. No secret may enter tracked documents merely because it was first in scratch. |
| Product repository paths | The selected op's actual discovered/planned source write ceiling | Source changes stay in source; `.work` links repo and revision. Do not copy product source into the completion tree. |

Folders such as `business`, `architecture`, `implementation`, `uat`, `release`, `operations` are sensible roles, not a fixed depth or mandatory stage list. Add a new domain as a new node/resource kind plus its explicit contract. Existing IDs and core fields need not change. An unknown kind can be retained but is not automatically approved by a known profile.

Accepted art direction/design assets are source inputs: store them in the selected design resource directory and declare `files:[{"path":"assets/direction.png"}]` using the real filename. Consuming UI design/frontend nodes reference that resource explicitly. Captured output screenshots remain evidence assets under an evidence bundle; replacing a screenshot alone does not change approved design authority or imply a redesign. Promoting an observed screenshot to a new design source requires an explicit scope/design decision and source resource binding, never silent reuse as intent.

Validation detects changed bytes of declared resource files and transitively derives `suspended` for affected completed nodes; old completion, commits and evidence remain intact. Unlinked source resources do not suspend unrelated work. `suspended` is derived, not a persisted leaf state; `STALE_*` diagnostic names may explain why a proof no longer applies. Do not relabel old completion done, erase its history, or auto-rerun consumers. Report impact and run only the next separately selected eligible op. Changes in unbound external source/runtime state still require actual inspection and resource revision updates; this is not a background file/deployment watcher.

## Evidence, completion and commits

Before executing, establish the selected node's current `inputDigest` using the read-only validator. Finish semantic edits before collecting evidence: changed body, requirements, dependency or resource revisions change the input being proved. Never hand-invent a digest. Do not mark an implementation `done` because a plan completed. Do not mark a verification leaf `done` when its required assertions failed even though the checking operation itself returned a useful finished report.

Treat node Markdown body and `extensions` as specification inputs. A consumer op does not rewrite the selected scope/graph even before verification. After freezing the verification digest, write observations, current defects, commit mapping, untested assertions and cleanup results into `E/result.md` and the operator-specific evidence files, never back into semantic node prose. Post-proof node writes are only `state`, `blocker`, `completion` (or allowed operational timestamps). A changed expected outcome is a separately selected specification update requiring new verification, not an output note. Planning/specification ops finish their selected semantic body/graph first, then collect review proof against its final digest.

Source/resource-producing ops use two distinct moments: inspect approved expected intent before effects, then finalize actual source/resource facts within scope and compute the final verification digest before checking the resulting postconditions. Update selected canonical identity/version/resource metadata before this final proof; never change expected rules to fit those facts. A resource evidence pointer, if needed, uses a preallocated stable evidence ID finalized before the digest, with no claim of passing until proof exists; prefer node completion for current evidence selection. Never embed a resource's own evidence-content hash or update its semantic observation pointer after freezing proof. If relevant source, resource or spec changes during checks, rerun affected verification against the new actual inputs; never just replace a digest to clear a stale result.

Completion writes `completion.inputDigest`, `completion.evidence` (evidence IDs) and `completion.codeRefs:[{repository,commit}]` for implementation/release profiles, with repository resource IDs and full actual Git SHAs. Every selected evidence bundle also carries matching `codeRefs`, and those repository IDs are included in node `refs`. A release may reuse actual inspected source commits; it does not need a new source commit just to deploy. Run validation after binding. Evidence integrity checks show that bytes and references agree; they cannot prove an agent genuinely observed what it wrote. Actual tool-derived artifacts plus explicit inspection/review are still necessary. Never claim that this system eliminates hallucinations.

For a pure local artifact/content task with no repository or source-code acceptance, use an `operations` leaf instead of pretending to satisfy the `implementation` profile. Record the actual artifact/proof and the absence of a product commit. This does not exempt real code delivery from its implementation profile. Refresh applicable repository/environment resource revisions from actual inspected source/build state before validating: the core does not watch Git HEAD or live deployment drift.

Every changed code piece has a scoped local commit when the user's task includes committing. Stage exact files, inspect staged diff, run applicable checks and record the real SHA; no blanket `git add .`, amend, force or unrelated changes. A logical piece can require multiple commits or repositories; record them all rather than inventing one universal SHA. When committing is not authorized, report an uncommitted source delivery and do not forge code completion. An unchanged implementation can bind an existing inspected commit and prove it without an empty commit. Documentation/evidence commits belong to the canonical `.work` repository, not imaginary product commits.

Keep origin commit, integration/cherry-pick commit, tested commit and deployed immutable artifact distinct. `completion.codeRefs` binds the delivered code; detailed mapping belongs in `E/lineage.json` or `E/result.md`, with evidence-level `extensions.work3.lineage` references when useful. Verify mapping with actual Git diff/ancestry and changed-path tests; ancestry alone does not prove later changes preserved behavior. A commit cannot contain its own SHA in its own bytes: commit the implementation, then update `.work` metadata in a separate evidence/documentation commit if tracked in the same repository.

Git is edit history. `.work` keeps current specifications and indispensable evidence, not duplicate request/response histories. Deleting a task or temporary Git worktree must not remove the only images, evidence or account references. External artifact stores need an existing durable object identity and integrity reference; a URI that nobody can retrieve is unverified, not a passing local asset.

## Browser and UAT protocol

Inspect the available browser capability before choosing a driver. Use the applicable installed browser skill and its allowed tools, or a real installed Playwright/Chromium workflow when permitted. Read that skill fully when used. Do not assume a binary, browser session, bridge or screenshot capability exists. A missing browser blocks browser evidence; generated mockups, static fixtures and an API-only script are not substitute browser UAT.

Bind environment resource revision, expected origin, actual physical target where relevant, observed served FE/BE versions, configuration generation, actor resource or explicit anonymous access, and fixture namespace. Exact UAT provenance is `{environment, actor, servedVersions, tool, capturedAt, servedVersionEvidence}`, replacing actor with `anonymous:true` for anonymous access. `environment` resolves to resource kind `environment`, actor to `identity`, and each `servedVersions` entry is `{repository,commit,artifact}` with resource kind `repository`, full actual commit and observed immutable image/build identity. `servedVersionEvidence` is the ID of a passing assertion describing the actual runtime-version check. Include all environment/actor/repository resources in consuming node `refs`; include other input resources such as fixtures/design explicitly because links inside `details` are not transitive core dependencies. Store additional observations in `E/runtime.json` / evidence extensions, not unknown root fields. HEAD in a source checkout is not proof that the browser loaded that build. Check declared health/version evidence and actual page/network behavior; a successful redirect to a 404 or sign-in screen is not successful product login.

One actual run can support several leaves without copying images. Store its bundle once, for example under the flow's `evidence/<id>/`. Preserve primary `nodeId,inputDigest`; additional consumers use manifest `bindings:[{nodeId,inputDigest}]`. Each consumer explicitly references this evidence ID and covers its own assertions/current digest. No unstated consumer may reuse it; failure or corruption of a shared bundle affects all its consumers. A UI leaf still needs actual image assets; a UX leaf still needs at least one passing assertion with `kind:"behavior"`. Binding and byte integrity are not proof of the observation's truth.

Keep three claims separate: appearance (actual image inspected at named viewport/theme), interaction (controls/actions and feedback observed), persistence/authorization (read-back, reload/resume and applicable negative checks). Drive actual rendered controls for UI journeys. Discover locators from observed DOM/accessibility state; never invent selectors or hide failed steps. API/DB probes may corroborate persistence but must not perform the action being claimed as a successful UI action.

Each browser context/session is isolated for parallel actors and flows. Mutable data namespaces must also be disjoint; separate tabs alone do not isolate cookies or data. Shared accounts may be read-only where safe; do not create extra accounts automatically. Credentials resolve through approved custody at use time. Store account aliases/provider subject/roles/member refs, not plaintext credentials, tokens, cookies, raw storage state or secret-bearing traces. Inspect/redact evidence before tracking it; keep masking provenance and hash the delivered masked bytes.

## Bounded finish and blockers

Reuse matching current resources; inspect before changing uncertain state. Stop after repeated identical failure when no new diagnosis or authorized alternative remains. An uncertain external mutation is reconciled read-only before any retry. Do not weaken expected outcomes, skip failed checks, or change `required`/`na` to obtain a green parent.

Record a blocker with the actual missing fact, affected node, last relevant observation and required owner decision/action. Continue other explicitly selected independent pieces only if safe. No automatic repair, deployment, next op or agent spawn follows a failure. Finish with result, changed node IDs/files, real commits, tested/untested extent, evidence and the precise remaining gap; keep the conversation response compact. Mention an available next op as a suggestion only, then stop.
