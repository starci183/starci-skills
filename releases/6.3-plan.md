# StarCi Skills 6.3 release plan

## Outcome

Make proactive UX→UI design and evidence-complete UAT executable in the existing v6 operator system. Flow Audit compiles coverage; Behavior, UX, and UI keep independent verdicts; Product UAT coordinates conflict-safe parallel case-runs, user actions, repair, retest, and user approval.

## Lifecycle

```text
feedback + product intent
  → behavior envelope
  → UX brainstorm: journey + failure/recovery + container ownership
  → preliminary flow coverage
  → UI brainstorm: composition + render states + responsive matrix
  → final coverage/resource freeze
  → implementation + lower gates + visual fidelity
  → parallel UAT cases
  → root-cause repair
  → fresh retest
  → USER APPROVE UAT <review-hash>
```

UX precedes UI. UI cannot change journey order, interaction-container ownership, API semantics, or business policy. Flow coverage may be preliminarily compiled after UX and is frozen after UI exposes the final reachable render-state/viewport matrix.

## Operator architecture

| Operator | Role | Verdicts |
| --- | --- | --- |
| `test/flow-coverage-audit` | Compile the smallest complete feature flow set, state graph, recovery-equivalent representative cases, delegated lower tests, fixtures, resources, conflicts | `ready/findings/blocked` |
| `test/behavior-audit` | Prove business outcome and side effects through read-only verification | `passed/failed/blocked` |
| `test/ux-audit` | Prove orientation, validation feedback, container behavior, recovery, refresh/resume, completion | `passed/failed/blocked` |
| `test/ui-audit` | Prove composition, state rendering, responsive behavior, overflow, accessibility, Grammar fidelity | `passed/failed/suspense/blocked` |
| `fe/product-uat` | Join passed lenses, semantic proof, result finality, cleanup, root repair/retest, user-review handoff | existing typed repair routes + final approval |

The existing `test/ui-quality-audit` remains a low-level browser-quality delivery guard for maintenance/reconcile skills. It is not the v6.3 product UI verdict.

## Happy/unhappy compiler

The canonical happy case is separate. Unhappy examples merge only when start/pre-failure state, semantic owner, side effect, recovery action, terminal state, and fault scope are all equal. Client validation permutations may delegate to lower tests only with no request, no side effect, one correction, one terminal, and complete schema/component proof.

Feature coverage uses the smallest complete flow set. Create a sibling flow only when actor/entry, business outcome/terminal, semantic owner/side-effect boundary, or recovery topology changes. The normal flow budget is one to five representative cases; every excess case needs a distinct signature or high-risk transition. Readiness means zero uncovered transitions and zero equivalent sibling flow candidates, not a large case count.

Always split business refusal, security/auth, stale/expired, concurrency/idempotency, rate-limit, transport/infrastructure, realtime, or different recovery. A recoverable unhappy case ends at success, not at its error screenshot.

## Parallel execution

Each case-run owns a fresh account, one agent-bound browser-session lease, origin, mailbox/query namespace, mutable fixture namespace, artifact directory, and locks. Reruns use new accounts. Resource classes are safe, partitioned, and exclusive. Shared server stop/start is exclusive; prefer a case-local fault proxy. One coordinator owns case classification; one writer owns each deduplicated root cause. `REQUIRE_USER_ACTION` temporarily transfers the exact leased session to the user and returns control to the same runner after `USER ACTION COMPLETE <action-id>`.

## Evidence and review

The canonical product tree is defined in `uat/README.md`. Each feature has `INDEX.md` plus `feature.json`; each flow has `review.md` plus `review.json`; each case has one intent file; each run is immutable. Full-viewport screenshots prove entry, material commitment, material feedback, recovery, terminal, and every meaningful responsive branch. Region crops are supplementary.

User feedback is hash-bound. UI SUSPENSE requires an exact situation, authorities checked, finite question, and owner. Closure requires user decision, authority promotion when applicable, source repair, fresh discovering checkpoint, full recovery, all occurrences, canonical happy smoke, zero SUSPENSE, zero pending REQUIRE_USER_ACTION, and zero open correction.
