# StarCi Skills 2.2.1 — user workflow topology evidence

Opened: 2026-09-05. Final verification: 2026-09-06. Target: the `.claude` runtime in
`starci183/starci-skills`.

## Demand and contract

The missing distinction was above operator execution. A person may ask one native task to own one
complete, independently confirmable workflow, or may explicitly ask one native task to track several
independently owned task/worktree workflows. Calling the first form `isolated` collided with the
existing per-operator `isolated` mode; calling the second `controller` described an implementation
role rather than the working relationship. The public topology names are therefore `solo` and
`coordinated`.

`resources/orchestrator.json#workflowTopologies` is the single policy home. `solo` is the default.
`coordinated` is selected only from user demand for at least two independent workflows or an explicit
tracker; one chain's operators, fan-out branches, nested exchanges and three worker slots remain
solo internals. Ordinary two-way native task messages are sufficient for assignments, status,
evidence references, feedback, resource ownership and wake conditions; there is no typed message
envelope. Each peer still owns a normal solo StarCi session. Closing uses `workflow.verify`, whose
normal local matched receipt binds every frozen peer goal to its original session, actual full Git
head and complete accepted evidence, including the original operator-specific law. No cross-session
receipt import was added.

## Occurrence 2 — independent coordination pressure

The independent five-task retrospective at
`tests/evidence/20260904-codex-five-tasks-retrospective.md#cross-mission-coordination-by-chat`
records three mission roots exchanging 102, 35 and 38 task messages to agree SHAs, leases and file
boundaries. The tasks had no explicit topology or dedicated tracker, so peers polled one another in
prose and each root invented its own coordination notes. This is a second independent occurrence of
the coordination problem, not a second observed dedicated-coordinator topology. It supports the
need for a named owner and compact peer index while showing that ordinary messages were already a
sufficient transport; the Nivo occurrence above supplies the exact final shape.

The earlier 2.2 release integration (`tests/evidence/20260905-starci-2.2-release.md`) also exercised a
root integrating three isolated worktrees, but those workers were within one native task. It is an
adjacent stress case, not counted as a second coordinated topology occurrence.

## Executable change

- `scripts/session-open.mjs` records the selected mode at `state.json.topology.mode`; omitted demand
  defaults to `solo`, an unconfirmed draft may follow corrected demand, and an activated mission
  refuses a topology change. Host reuse now includes host kind, so equal Codex and Claude ids cannot
  cross-reuse or race under different locks.
- `scripts/workflow-topology.mjs` reads names, default, peer bounds and terminal-head behavior from
  the one policy record rather than copying them. `scripts/validate-resources.mjs` keeps topology
  names disjoint from operator execution modes and resolves the policy's evidence citation.
- `scripts/validate-request.mjs` refuses coordinated dispatch until at least two peer task ids are
  tracked; `scripts/validate-session.mjs` additionally requires a non-null peer head at completion.
  Explicit solo execution refuses peer entries. Earlier v2.2.0 states without `topology` remain
  readable but cannot dispatch or close until `session-open` migrates them.
- `templates/step/state.schema.json` types the additive topology record and reuses `brief.peers`; no
  message envelope, worker lifecycle protocol or new operator execution mode was added.
- `workflow.verify` supplies the previously missing lawful portfolio receipt owner. Its frozen peer
  snapshot records exact child goals and coordinator done-when coverage. Its verifier resolves live
  or retained originals, validates their complete sessions and each proving operator's own law,
  checks request/evidence hashes and real Git objects/current heads, and compares the local report
  with those reread originals. Missing or changing evidence remains a refusal. A retained original
  is replayed as evidence, never as a newly dispatched request; a live peer in closing requires normal
  close recovery. The ordinary local done-when/attempt/retention gates remain intact.
- Live coordinator feedback caught an execution-profile mismatch in the first verification cut:
  an inline Sol-bound verifier could not truthfully run on an Astra coordinator. The verifier now
  dispatches an isolated `sol-reviewer` worker inside the same coordinator session, chain, ledger,
  lease and three-slot budget. No additional native task or user-level workflow is created, and the
  root keeps its actual profile. Each frozen peer requires explicit live or retained context aliases;
  both may be bound through normal retention, but broad roots, untracked siblings and nested aliases
  cannot widen that inventory. A same-session slot regression checks the unchanged host binding.
- A dangling `else` in the shared JSON-schema checker had prevented schema-valued
  `additionalProperties` from checking map values; braces fix the gate, with dedicated regressions.
  New retained state uses a traversal-free compact reference relative to the archive namespace.
- `scripts/workflow-topology.spec.mjs` covers the exact names, default, demand selection, message
  boundary, peer bounds, terminal heads and v2.2.0 migration boundary.
  `scripts/v22-runtime.spec.mjs` covers persistence, clean-draft reselection, active-mission refusal,
  legacy migration and host-kind isolation through the real session-open path.
- `scripts/workflow-verification.spec.mjs` also runs as the new operator self-test. Its synthetic
  two-peer portfolio validates original operator semantics and a coordinator's terminal local
  receipt, including after retention. Mutations refuse narrated success, changed assignments/goals,
  unproven or nonexistent heads, unfinished peers, forged reports and even resealed evidence that
  fails the original operator law. This is runtime integration proof, not a claim of live Nivo UAT.

## Version decision

`UPDATE.md` normally classifies a new concept and template section as at least a minor release, and
an older installed tree cannot validate the added closed-schema property. The user explicitly
directed the exact version `2.2.1`. This is therefore a recorded user-authorized numbering exception,
not precedent that this document-shape change is an ordinary patch under the standing release rule.
