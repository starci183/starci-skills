# Idempotency

## LOADS

| Alias | Target | Kind | Why |
|---|---|---|---|
| `@canon-be` | `@starci/eslint-canon-be` | npm package | the published backend machine this record cites |

## Record

The input is an accepted command, job or webhook that may be delivered more than once. This pattern
does not decide whether the business action is desirable. It decides how one logical request gets a
stable key, how that key is claimed before an effect, how a completed result is replayed, and how
scope, retention and failure are made explicit.

## Law

Idempotency means repeating one logical operation produces one business effect and the same observable
result. It requires durable coordination at the boundary where the effect begins; a process map,
consumer offset or "the client will not retry" is not durable evidence.

The key is the identity of the logical operation, not a random value generated by the server on each
attempt. A durable claim must win atomically before an external or irreversible effect. Completion
stores the result that later attempts replay. A failed claim has an explicit retryable or terminal
meaning and retention window.

## Situation codes

| Code | Situation | What the source must look like |
|---|---|---|
| `IDEMP-1` | A caller, webhook or job needs a repeat identity | A stable key is supplied or deterministically derived from caller/job identity and operation scope; it is validated and never regenerated per retry |
| `IDEMP-2` | The effect must be claimed before it runs | A unique durable claim is inserted/locked atomically before the effect, with owner/status/lease or equivalent. Forbidden: effect first, marker later |
| `IDEMP-3` | A duplicate arrives after completion | The completed result/status is durable and returned for the same key; the effect is not run again and a duplicate cannot invent a new response |
| `IDEMP-4` | Scope, retention and failure semantics are chosen | Key namespace, tenant/actor scope, expiry/retention, payload mismatch, retryable failure and terminal failure are explicit |
| `IDEMP-5` | One-effect behaviour needs proof | A test submits the same key concurrently and after completion, asserts one effect and the same result, using real durable storage at the claim boundary |

## Reading an accepted shape

1. Name the logical operation and its retried delivery sources.
2. Resolve the key (`IDEMP-1`), then the pre-effect durable claim (`IDEMP-2`), replay (`IDEMP-3`),
   lifecycle (`IDEMP-4`) and proof (`IDEMP-5`).
3. Ask whether two different valid commands are being serialized. If so, use `CONCURRENCY`, not an
   idempotency key. Ask whether the duplicate is a broker envelope or CDC row; that belongs to
   `DELIVERY`/`CDC` unless it is also the business command boundary.

## `IDEMP-1` — the logical request has a stable key

**What it emits.** A required idempotency key from the caller, webhook event id, or durable job
identity, combined with an operation/version and tenant scope. The server may normalize but may not
replace it with `randomUUID()` on each attempt.

**Boundary.** Not `CONCURRENCY-1`: this identifies repeats of one command, not two different commands
competing for a quota. Not `DELIVERY-1`/`CDC-2`: a transport envelope or consumer group identifies
delivery, not necessarily the business effect. Not async retry: retry must carry the same key.

## `IDEMP-2` — claim before effect

**What it emits.** An atomic unique insert or claim transition in durable storage before payment,
email, grant, enqueue, provider call or other irreversible effect. A concurrent claimant receives a
pending/duplicate outcome rather than running the effect.

**Boundary.** Not `DATA-4`: transaction-manager propagation governs atomic writes, while this code
orders a durable claim before an external effect. Not `DELIVERY-4`/`CDC-4`: message digest claims are
transport/projection dedupe and must not be reused as the business claim without an explicit mapping.
Not async retry: a retry may reclaim an expired lease only under the declared lifecycle.

## `IDEMP-3` — replay the recorded result

**What it emits.** Completion stores a stable status and the response/result (or a canonical result
reference). A later same-key request validates the request fingerprint and returns that stored result;
it does not call the effect again.

**Boundary.** Not `CACHE-2`: a replay record is correctness state and must survive cache eviction;
cache is derived data. Not `CONCURRENCY-2`: a stale row conflict is not a duplicate command. Not
`DELIVERY-5`/`TESTING-2`: the result is runtime behaviour; the test still must assert the one effect.

## `IDEMP-4` — lifecycle semantics are part of the key contract

**What it emits.** Explicit namespace/scope, request fingerprint mismatch error, retention/TTL,
pending lease expiry, retryable versus terminal failure, and whether failure is replayed or reclaimable.
No response body is stored before it is safe, and sensitive payloads are not retained accidentally.

**Boundary.** Not async retries: retry budget/backoff is delivery policy; idempotency lifecycle says
what a repeated key means. Not `CACHE-4`: idempotency retention is correctness retention, not freshness.

## `IDEMP-5` — the proof runs the duplicate

**What it emits.** A spec/e2e launches concurrent same-key attempts from a barrier, then repeats the
key after completion and asserts one durable effect plus byte/value-equivalent results. It does not
mock the claim store or call a handler directly in place of the production boundary.

**Boundary.** Not `TESTING-5`/`TESTING-6`: branch and call assertions do not prove a durable one-effect
property. Not `CONCURRENCY-4`: that test uses competing state transitions, while this uses the same
logical key and effect. Not `DELIVERY-6`/`CDC-7`: broker fan-out/projection tests do not prove the
business claim.

## Inputs

| Input | Evidence required |
|---|---|
| operation | Logical command/job/webhook and irreversible effect |
| key | Caller/job identity, normalized and scoped |
| claim | Durable unique record, owner and status |
| result | Stored completion response or canonical reference |
| lifecycle | Retention, lease, mismatch and failure policy |
| proof | Same-key concurrent and replayed test |

## Rules

1. A retry carries the same logical key.
2. Claim happens durably before the effect.
3. Completion is replayable and request fingerprints cannot silently change.
4. Scope, retention and error semantics are explicit.
5. One-effect proof uses real durable coordination.
6. Transport/CDC dedupe, concurrency arbitration, async retry and testing lane rules remain separate.

## Exceptions

- **Pure read.** No irreversible effect means no idempotency record; caching a read is `CACHE`.
- **Naturally idempotent write.** A deterministic upsert may satisfy the effect property, but the key
  and proof are still required when callers need the original result or external side effects exist.
- **Expired claim.** Reclaim is allowed only after an explicit lease/retention policy and a safe
  determination that the prior owner cannot still perform the effect.
