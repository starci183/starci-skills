# orca-tree

Lane L of `1.0.0-alpha.2`. The ledger's hierarchy was right the whole time; the
Orca tree beside it was not.

## Practiced

The owner opened the Orca sidebar on the `nivo-backend` ledger and read the
rows out loud (`fable.md` → `orca-hierarchy`, 2026-09-23):

- **Two `[Kernel] wf-nivo-workspace-provision`.** The kernel signal named
  `term_d2f101cf`; `term_aef50872`, titled "Kernel orchestration for…", was
  still connected and in no signal. The kernel job was on attempt 4.
- **A settled op still at the root.** Two `[Op] interface.implement`
  gpt-5.6-luna rows, 18h old, ticked, sitting at the sidebar root instead of
  under a kernel — `interface.implement a19` had succeeded through managed
  worker `ctx_427183f`.
- **A failed op whose terminal was still open.** `[Op] interface.audit`
  showing "Idle" under the kernel: job `interface.audit a4` failed at 15:52,
  its dispatch `ctx_23ab4762` was rejected at worker-start, and
  `term_b6fa4c43` was still there.
- **Provider titles instead of ours.** "devin.exe: Kernel orchestration
  for…" — `[Kernel] <wf>` only ever reached a Task display name.

`node scripts/kernel/api.mjs hierarchy --workflow <id>` disagreed with all of
it: every op read `parent = agent:kernel:<wf>`. Two projections of one
workflow, and only one of them was being looked at.

## Observed

Reading the code on 2026-09-23 (`fable.md` → "Root cause chính xác") gave three
causes, not four symptoms:

1. **`scripts/kernel/start-workflow.mjs:563-565`** — the restart ran
   `UPDATE jobs SET payload_json=?` with a freshly built object, replacing the
   kernel job's whole payload. `orca.runId` died with the old seat, so the next
   dispatch's `ensureWorkflowRun` (`scripts/kernel/api.mjs:1465`) found no Run
   and `run-create`d a second one. Old Tasks in the old Run, new Tasks in the
   new Run: that is the two-tree sidebar, and it also explains the rows at the
   root — a Task whose Run is bound to a terminal that no longer exists has
   nowhere to hang.
2. **`scripts/kernel/start-workflow.mjs:438-455`** — the stale-kernel block
   only called `releaseManagedWorker` for a managed dispatch. A
   command-terminal kernel (`launch: terminal` — Devin, Codex, Qwen) was never
   `terminal-close`d. The signal was deleted and the job marked `stopped`, so
   the ledger stopped knowing about a terminal that kept running. Second
   `[Kernel]` row.
3. **`createOperationTask` (`scripts/kernel/api.mjs:1506`)** — Tasks were
   created with `--run` and `--from` but never the `--parent` flag
   `modules/host/orca/calls.yaml` has declared all along, so the tree was
   inferred from the Run alone and cause 1 was enough to break it.

Two more, found while fixing those:

4. `rejectDispatch` released the lease and failed the job but closed nothing.
   The terminal or worker the attempt had already created outlived the
   refusal — the "Idle" `[Op]` row.
5. `cmdSettle` stopped and released the managed worker and never touched the
   Task. Every finished operation stayed an open Task in the Run.

The shape of the whole thing: `.claude` **did** enforce the hierarchy at
creation and **did not** enforce it continuously. Nothing in the repo compared
the ledger with `terminal-list`, so the drift was only ever visible to a human
looking at a sidebar.

## Derived

One rule, written once in `modules/kernel/start-workflow.yaml` (`orcaTree`),
cited by `modules/kernel/dispatch.yaml` and `modules/kernel/api.yaml`:

> A workflow has exactly one live kernel terminal; its Orca Run is created once
> and survives kernel restarts; every operation Task is created in that Run
> with the CURRENT kernel terminal as `from` and as `parent`; a job that ends
> (settle, reject, finish) leaves no live terminal, worker or open Task; a
> kernel restart closes the previous kernel terminal before the new one is
> recorded.

Where each clause is now true:

| Clause | Enforced in |
|---|---|
| the Run is created once and survives restarts | `scripts/kernel/start-workflow.mjs` — the restart merges the new seat OVER the previous payload, so `orca.runId` / `hierarchy.runtime.runId` survive while route, attempt and `terminalHandle` are replaced |
| exactly one live kernel terminal | same file — the stale-kernel block `terminal-close`s a command-terminal kernel before the replacement is recorded; a refused close is a `kernel-stale-terminal-unclosed` event plus an open incident, and the restart still proceeds |
| Task in that Run, current kernel as `from` and `parent` | `createOperationTask` passes `parent: kernelHandle`; titles are written at creation (`[Kernel] <wf>`, `[Op] <op> a<n> · <wf>`) instead of the provider's auto-summary |
| a reject leaves nothing | `rejectDispatch` closes the terminal or worker the attempt created, once, before the refusal is written, and records `terminalClosed` on the result and the `dispatch-rejected` event |
| a settle/finish leaves nothing | `cmdSettle` closes the worker and then the Task (`task-update --status done`, `taskClosed` on the receipt and payload); `cmdFinish` closes the kernel terminal and every Task no settle reached |
| detectable when it is not true | `scripts/checks/check-orca-tree.mjs` — `DUPLICATE_KERNEL`, `ORPHAN_TERMINAL`, `DEAD_KERNEL`, `TASK_OUTSIDE_RUN`; `scripts/supervisor/poll.mjs` prints the same findings every cycle |

`scripts/api/orca/task-update.mjs` is restored (Lane D deleted it as uncalled —
it has a caller now), converted to `orcaCall`, and `modules/host/orca/calls.yaml`
declares `task-update` again as a `kind: mutation`.

Two smaller standards fell out:

- **A containment effect belongs in the step that records the refusal.**
  `rejectCommand` used to close the terminal and then call `rejectDispatch`,
  which meant the close was an effect nothing wrote down. Now the close runs
  inside `rejectDispatch` and its answer is a field on the event.
- **A contract that only holds at creation is not enforced.** The three causes
  were all "true at `t=0`, false at `t=1`". A check that reads the durable
  state and the host at the same time is the only thing that notices.

## Open

- **Can Orca archive Tasks automatically?** No. `modules/host/orca/api.yaml`
  `publicCommands` lists no archive verb anywhere in the inventory —
  `orchestration task-update` is the only Task-state write StarCi may issue, so
  `--status done` is the whole of "closed" that we can ask for. Whether Orca's
  sidebar then hides a done Task is a rendering decision on Orca's side that a
  stubbed host cannot answer; it needs one look at a real sidebar after a
  settle. If it does not hide them, closure is bookkeeping and a finished
  workflow still accumulates rows — worth asking the Orca side for a
  `task-archive`.
- **Is `run-use` needed?** No, and it stays deleted. It binds a Run to the
  *calling terminal's* session; StarCi never relies on that, because every
  orchestration call passes `--run <id>` explicitly and now `--parent`/`--from`
  as well. A restart therefore has nothing to re-bind: the Run id is durable on
  the kernel job and the new terminal names it per call. `run-use` would only
  matter if a Task could be created without `--run`, which
  `modules/host/orca/calls.yaml` makes impossible (`required: [spec, run]`).
- **`TASK_OUTSIDE_RUN` has no repair path.** The check reports a Task in a Run
  the workflow no longer uses; nothing moves it. Reparenting may not be
  expressible in the Orca API at all — the honest fallback is closing the
  stale Task, which `api finish` already does at the end of a workflow but
  nothing does mid-flight.
- **Orphan detection is scoped by title.** A terminal counts as ours when the
  ledger names its handle or its title starts with `[Kernel] ` / `[Op] `. A
  StarCi terminal whose title a provider overwrote, on a workflow whose ledger
  row is gone, is invisible to the check. Titles being written at creation
  makes this rarer, not impossible.
