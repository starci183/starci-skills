StarCi (version in `package.json`) is a kernel-agent workflow runtime whose source tree is the runtime: `node` reads these files directly. `modules/` holds the contracts as data — `modules/goal/` goal-chain rules, `modules/kernel/` the kernel-loop and api contracts, `modules/ops/` op manifests plus the generated registry, `modules/models/` model selection, runtime pools and the per-agent spawn cards (`modules/models/agents/`), `modules/host/` the host contracts that `scripts/api/orca/` reads, `modules/quality/` the audit bar, `modules/supervisor/` the supervisor loop contract, `modules/schemas/` the canon schemas (specification bodies under `modules/schemas/spec/`). `engine/` holds the mechanism code (ledger store, SQL DDL, YAML, runtime-root, config). `scripts/` holds the executables — `scripts/goal/`, `scripts/kernel/`, `scripts/route/`, `scripts/agent/`, `scripts/api/orca/`, `scripts/context/`, `scripts/checks/` (including the `scripts/checks/spec/` validators), `scripts/example/`, `scripts/install/`. `skills/` holds the user-facing skills (canonical here; a host's `.devin/skills/` is install output), `init/` the host bootstrap template, `knowledge/` scoped reference material, `benchmark/` the model-pool evidence that routing and profile decisions cite (`expectations.yaml`, append-only `snapshots/` written by `scripts/agent/benchmark-snapshot.mjs`, owner-reviewed `findings/`; see `benchmark/README.md`), `docs/` doctrine and check guides, `examples/` and `tests/` ship with the package, `packages/` the reusable lint/grammar kits, and `bin/starci.mjs` is the entry CLI (`init | update | doctor | version | api | start | goal | validate`).

The operating model: a chat submits a goal → one long-lived `[Kernel]` LLM agent per workflow orchestrates only through `node .claude/scripts/kernel/api.mjs <command>` — the command surface is `modules/kernel/api.yaml`, which names every verb, what it reads, what it writes and when it refuses → one ephemeral `[Op]` agent per job executes exactly one operation and dies at verdict settle → the api settles truth from evidence. The Kernel reasons through immediately executable transitions, then yields when durably waiting; it never keeps a model turn alive with sleep or an internal polling loop. `scripts/kernel/watchdog.mjs` is liveness only: it wakes the same Kernel terminal on `turn-idle` and replaces one proven disconnected, on the cadence in `modules/models/runtimes.yaml` `allocation.watchdogCadenceMs`; it never chooses workflow work. Kernel and watchdog are the only runners a workflow has; every other participant is a chat in one of the three roles below.

A chat takes one of three named roles. **Trigger:** the two lifecycle entry skills — `define-goal` (owner prompt → cold-scan assess → enriched goal draft + op chain presented for the owner's explicit `ok`, then persisted into the project-owned `.starciwork/runtime.sqlite`) and `start-kernel` (plan → owner `ok` → claim a queued goal → spawn its long-lived kernel, routed via `route-model` kind `model.manageWorkflow`). **Workflow monitor:** after the kernel boots, one chat monitors one workflow per `skills/workflow-chat/` — it reads ledger projections through the api, relays the kernel's questions and open incidents to the owner verbatim, sends the owner's words back into the kernel terminal, and decides, approves and mutates nothing. **Supervisor:** when the owner asks a chat to supervise, that chat runs the loop in `modules/supervisor/supervise.yaml` — `node scripts/supervisor/poll.mjs --repo <ledger-owner>` prints one digest per cycle, the chat classifies each finding, patches `.claude` when the contract is the gap, and restarts the affected kernels through `start-workflow.mjs --goal` so they reload it. Kernels are restarted only after a landed contract change. The supervisor is the runtime-maintenance authority: it is the one role allowed to edit the installed `.claude`, and an op defect, a dispatch decision or an owner gate is never its to answer.

Kernel boundary — mandatory: the kernel agent's only mutation surface is `scripts/kernel/api.mjs`. It never writes `.starciwork/runtime.sqlite` directly, never calls `orca`, `git` or provider CLIs itself (the api owns all host mechanics), and never spawns op terminals by hand. It persists findings, plans and decisions into the ledger as they form — events and state snapshots via `api plan`/`api incident` — so a kernel that dies mid-survey loses nothing durable. Before `api enqueue` it preflights candidate `owned_paths` against the target repository's layout/lint contracts; a contradiction is an `incident`, never a dispatch. `api dispatch` attests the spawned terminal landed (prompt delivered, first model activity); an auth failure or crash is `dispatch-rejected` — the job is not running and its slot is released. `api settle` records the evidence-backed verdict `pass | fail | blocked` per `modules/kernel/verdict-contract.yaml` (the op's own report outcome is the separate `done | partial | failed | ask | blocked` enum in `scripts/kernel/report-envelope.mjs`), releases the job's leases and closes the worker terminal — a settled job leaves no live terminal behind. A re-plan persists its lineage (`replannedFrom`, blocker, path delta, routing reason). The workflow ends with `api finish`: the goal closes, the kernel exits, and its lease is released.

All projects in this standard use TypeScript, Next.js frontend and NestJS backend with the owner's Academy code patterns. Monorepo/single-source mappings do not authorize framework substitution. Read [common architecture rules](docs/architecture-rules.md) and [knowledge/architecture-rules.yaml](knowledge/architecture-rules.yaml) first. Mechanical code-pattern conformance requires executable checks with complete applicable rule/file coverage; a missing checker cannot be replaced by agent approval. Agents review design patterns and edge cases using the Markdown guidance and relevant behavior evidence.

For design review, read the applicable entries in the [enterprise design pattern catalog](docs/design-pattern-catalog.md), which owns the pattern list. Select from actual invariants; do not impose every pattern on every feature. The [source research note](docs/design-pattern-source-review-20260916.md) records Academy/Nivo observations and primary research without certifying product behavior. [Code-pattern enforcement](docs/code-pattern-enforcement.md) separately defines executable coverage and unresolved checker gaps.

Before implementation or code review, read [coding reference](knowledge/coding-reference.yaml) and the applicable pattern topics; the authored `knowledge/**/*.yaml` sources are canonical and the runtime reads them directly. Read [portable source architecture](docs/portable-source-architecture.md) and, for backend changes, [backend source pattern](docs/backend-source-pattern.md). Academy FE/BE are inspected references containing both useful patterns and debt; they do not turn historical file counts or boilerplate into requirements. Apply one ownership/dependency pattern through the applicable Nest/Next profile and verified installed APIs. Existing target-project code and passing tests do not replace this standard. Knowledge is maintained in English only.

For existing-source work, use executable checks before choosing repairs: `node .claude/scripts/checks/check-stales.mjs --work <work root> --repo <id>=<git root>` reads canonical freshness and source identities; optional `--target` values bound the inspected closure. `review.verify` modes `stales` and `lint` execute scripts and write attempt reports only. Nonzero findings never authorize source writes or completion refresh. A changed input means revalidation, not proof that its implementation must be rewritten. Repair the owned scope under its existing authority, rerun the scripts and required implementation checks, and obtain independent verification; see [docs/source-staleness.md](docs/source-staleness.md).

For FE/BE boundaries run `node .claude/scripts/checks/check-scoped-lint.mjs --profile <nest|next> --root <repository> [--architecture-config <file>] (--all | -- <files...>)` with actual project config. Mono versus separate repositories changes source resolution, not module/feature responsibilities. Explicit combined FE/BE bindings share one backend-owned Work tree. Static checks complement actual repository lint/typecheck and semantic review; they do not prove DI scope, behavior, runtime readiness or product completion. See [docs/architecture-check.md](docs/architecture-check.md) and [docs/source-layout.md](docs/source-layout.md).

Before designing or configuring any external API, service or SDK integration, read its current official documentation for the intended use. Record the primary sources and actual read date, supported authentication/account/scope/lifecycle constraints, applicable callback or webhook setup, owner-only versus workflow-owned prerequisites, and a real verification plan in the owning integration declaration. Missing research returns to the owning operation; it never becomes an unsupported credential request. The workflow prepares what its authority permits, presents researched owner input through its own Orca GUI, then verifies the provider separately from credential presence. See [docs/workflow-kernel.md](docs/workflow-kernel.md).

Fix minor form-only defects and missing flow details directly in their owning Work or product source, then re-run the affected checks. If business behavior or a code flow is wrong, return to the owning Business/SRS or Architecture/SDS workflow, revise it under current authority, and produce fresh downstream evidence; never defer the defect into a separate ledger or refresh stale proof by assertion.

For application deployment, environment bootstrap, or changes to `.stacks`, read `knowledge/application-stacks.yaml` and `docs/application-stacks.md`, which own the supported package profiles. Bind placement per application component and the selected deployment package: local processes, managed containers and separately deployed application APIs may coexist, and a declared development profile may run application processes natively while dependencies stay in Docker. Every profile accounts for the same selected components, source/build roots, endpoint contexts, ports and persistent-data custody; selecting one never grants relocation of an existing remote API, replacement of its project-selected runtime, teardown, or live-data effects. An external dependency needs an explicit owner and failure domain; network location alone does not remove its deployment ownership. Follow [docs/remote-application-api.md](docs/remote-application-api.md) for remote application APIs, including APIs hosted in Kubernetes/K3s; API consumption, application rollout and cluster administration have separate contracts and verification. Use the declared inventory, encrypted custody and lifecycle entrypoints, then run applicable static checks and actual readiness/recovery checks — static profile validation proves neither startup nor recovery. Preserve existing declarations until an authorized stack conversion, do not label an undeclared stack dual-mode capable, and remember that installing this standard neither converts nor deploys an existing app.

Select execution by scope, not by prompt count or line count. Every tracked outcome enters through `define-goal`: a small bounded request yields a short op chain, a large or unclear outcome a longer decomposed one — the same assess → plan → owner `ok` → persist gate applies to both, and underivable chains are shown as such, never filled in by hand. Questions remain read-only: an `request.analyze`-class discovery answers without mutation and claims no completion.

The operation catalog is `modules/ops/ops/*.yaml` with the generated index `modules/ops/registry.yaml` (regenerate with `node .claude/scripts/route/build-ops-registry.mjs`; never hand-edit it). One operation instance maps to exactly one ephemeral op agent — an operation is never split among several agents and never fanned out. `api dispatch` spawns the agent through `scripts/agent/lib.mjs` with the agent-card flags auto-injected, on the main checkout of the target repository with its disjoint write allowlist; a separate worktree is used only when the owner's prompt asks for one (`api dispatch --worktree`). Agent and model for every leg come from `modules/models/selection.yaml` + `runtimes.yaml` + `registry.yaml` via `scripts/route/route-model.mjs` — owner `config.yaml` pins override the default route, an explicit `--agent` flag overrides both.

Host calls go through `scripts/api/orca/`; agents never run `orca` and never read `modules/host/**`. `node scripts/checks/providers.mjs` validates the host contract; `--live` compares it with the running Orca.

Before any workflow effects, verify this skill tree first: run the applicable checks under `scripts/checks/` and stop if the source tree cannot be verified. On resumption or an entry-path error, reread the actual host bootstrap before diagnosing an installation failure: `node .claude/scripts/checks/check-entry.mjs <explicit-host> [claimed-entry]` distinguishes a missing runtime from a stale reference. A conflicting explicit instruction needs a replacement instruction from its authority, not a runtime rewrite.

The owner gates are exactly two: the entry skills' exact-`ok` approvals and the settle-time evidence verdicts. Inside an accepted goal envelope the kernel proceeds without procedural confirmations. A changed goal, widened scope/authority, missing credential, unresolved business alternative, safety block, reserved checkpoint or partial/unknown effect returns to the owner as an `api incident` or an owner ask (`decision.prepare`/`provision.ask`); validator success never manufactures an acceptance record.

Initialization seeds an untracked `config.yaml` from `config.example.yaml` only when `config.yaml` is missing; existing local config is never rewritten. Read local config for user-facing language, requested model/effort, budgets and the non-operation model pools; its shape is [config format](docs/config-format.md). Precedence is explicit `--agent` flag > `config.yaml` > route-model default. Pool selection is quota-aware before each call and still requires eligibility and qualification. Explicit task choices override the presentation defaults; pass supported model/effort preferences when dispatch is authorized, and never claim to change the current session or silently substitute unsupported settings. Runtime contracts, knowledge, and all canonical SRS/SDS content are English; config never translates canonical specifications or changes operation-agent authority. The host-local file is not part of the canonical package payload.

Resolve project bindings through `modules/schemas/workspace-routing.yaml`. Source is the host containing `.claude` and `.workspaces`; its `AGENTS.md` is the bootstrap entrypoint installed from `init/`. The selected project's backend owns the canonical `.starciwork` for BE and FE, and the runtime record inside it is the ledger `.starciwork/runtime.sqlite`. Frontend repositories contain product source, not a second StarCi workspace. Starting or preparing a project binds those locations; it does not install bootstraps or runtime copies in routed sources. Preserve host and binding when changing directories or delegating. A projectless task or a task opened directly in FE must receive the host entry and binding explicitly; do not assume host instructions were auto-loaded. Read-only questions may be answered without a job.

Before choosing feature paths, read `modules/schemas/work-layout.yaml`: it owns the record families, their paths and their schemas, and `scripts/checks/check-example-work.mjs` reads that list at gate time so the two cannot drift. One project has one bound `.starciwork`; its product catalog is `features/index.yaml`, and each actual capability owns the family folders under `features/<feature>/` that its content justifies. The layout applies recursively — every semantic scope can have `index.yaml`, child scope folders and optional `assets/**`; assets are payloads, not Work nodes, and need no index. The project/repository name is workspace metadata, never an extra folder. Shared rules, data, NFRs and cross-feature journeys have one accountable feature owner and are referenced by stable IDs from other features. Create only families with actual authorized content, keep small scopes flat, keep shared assets under one owner, and keep execution captures with their implementation/UAT scope; FE, BE and services do not create separate copies of the project workspace. New records use `.starciwork`; never create a parallel empty tree.

For product intent and target design, the current reviewed Business/SRS and Architecture/SDS payloads in `.starciwork` are the source of trust even while their delivery leaves remain `state: todo`. SRS owns required product behavior; SDS owns the target technical design that realizes it. UI, frontend, backend, tests and UAT must trace to these contracts and cannot redefine them from current code, even when tests pass. Within authorized scope, close missing cases in the owning canonical specifications, review affected consumers and refresh their reviewed context before dependent implementation resumes; do not stop at a gap report or force completion. A deliberate SRS/SDS change invalidates affected downstream proof until implementation and verification are updated, and existing `done` never forbids a necessary revision.

Canonical Work uses YAML `index.yaml` records with English structural vocabulary, English natural-language content, and direct current provenance; it contains no underscore directories, JSON, archives, histories or resource manifests. `modules/schemas/work-layout.yaml` owns the lifecycle vocabulary — which nodes author state, the state and `activity` values, and how `blockers[]` records an impediment — and a parent or dependency change invalidates affected proof without rewriting stored completion evidence. Only final reconciliation may author `done`, and only when current SRS, SDS, code, test/E2E and UAT evidence bind the same delivery revision. Missing or stale evidence leaves the affected leaf `todo` and the workflow partial or blocked.

Frontend delivery uses the closed quality loop `interface.draw → interface.implement → fresh capture → interface.audit`. Draw covers a small representative set of critical screens and derives every remaining screen from an explicit coverage map; generated direction is not exact component/render/API proof, so Grammar implementation captures and browser UAT remain separate downstream evidence. Implementation owns code and the real route×state×viewport×theme captures after its final mutation; audit is product-read-only and resolves the actual installed Grammar anatomy and tokens, so a border added around a canonically borderless card is a hard `grammar.anatomy` failure, not a taste preference. Small/local drift routes back to `interface.implement`; systemic, missing, generic or creatively inadequate direction routes to a more explicit `interface.draw`, then implementation. Each op's manifest under `modules/ops/ops/` owns its own inputs, provenance and round budget; audit never edits, redraws, captures replacement evidence or claims UAT/review acceptance. `done` never locks authorized edits: re-evaluate changed content and affected dependents without claiming stale results still pass, and do not delete useful images or videos merely because an existing folder is named evidence. See [interface audit](docs/interface-audit.md).

Ordinary automated UAT stays `uat.verify`; third-party involvement alone does not make a flow manual. A flow with a genuine non-automatable human/provider checkpoint runs `uat.assisted.prepare`, then the user runs [run-assisted-uat](skills/run-assisted-uat/SKILL.md) in an isolated visible browser, then a separate `uat.assisted.verify` rechecks the receipt independently — each op manifest owns what it freezes and what it rechecks. A human `ok` means controlled execution finished only and never sets pass. Prepare, runner and verify do not update canonical Work or runtime.sqlite; final full-chain reconciliation is the only place that may project current evidence to `done`. See [assisted UAT](docs/assisted-uat.md).

Before recording downstream delivery results, keep proof appropriate to each layer, identify what was actually tested or served, and retain useful implementation/E2E/UAT results; typed refs and dependencies form the repair graph. Do not turn examples into a mandatory file inventory or duplicate Git diffs in Work. For browser workflows, check [browser prerequisites](docs/browser-testing.md) at entry, not after implementation.

Select tests by the actual change. During edits and retries, run the affected tests and relevant lint/typecheck/build checks; do not rerun the entire repository suite per operation, poll or small fix. A required full-suite run belongs at the release checkpoint, after integration, and is reused while its tested code, dependencies and configuration remain unchanged. Preserve each run's real revision and coverage; never relabel older evidence as a new full-suite run or waive a required check. See [useful verification](docs/verify-proof.md).

Authoring SRS reads `modules/schemas/spec/srs-sections.schema.yaml` and [docs/business-srs.md](docs/business-srs.md); authoring SDS reads `modules/schemas/spec/sds-map.schema.yaml` and [docs/architecture-sds.md](docs/architecture-sds.md). Those schemas own each record's sections and required fields; `work-layout.yaml` owns where the record lives. Business defines observable outcomes, not implementation design. Architecture records source-independent design: inspect only relevant source, configuration and installed APIs to understand feasibility and transition, then independently record retain/extend/correct/replace/add target decisions from accepted SRS and quality constraints; observed code is neither design authority nor completion proof. Repository roles, paths, symbols, signatures, actual behavior, revisions and executed tests belong to Implementation and UAT. Shared design has one owner and consumers reference it by stable ID.

SRS/SDS reason proactively and broadly about realistic main, alternative, failure and edge cases plus relevant constraints for the selected implementation slice. Foreseeable material behavior, boundaries, contracts, data, authority, assumptions and decisions are clear enough to implement without guessing; record consequential unknowns instead of omitting them. This is comprehensive thinking, not a demand for theoretical perfection or exhaustive certainty before coding. Unresolved consequential business, security or data choices block affected effects, while a sufficiently decided slice proceeds to implementation/testing so concrete observations refine the design. Repair the owning SRS/SDS and affected dependencies, re-review the affected scope, preserve valid unrelated work and continue; never silently diverge or copy stale `done`.

Runtime maintenance belongs to the supervisor role above: consuming or checking an installed `.claude` does not authorize editing, upgrading or publishing it. A product workflow encountering a runtime defect reports the evidence and waits for that authority; it never repairs its own rules to unblock dispatch.
