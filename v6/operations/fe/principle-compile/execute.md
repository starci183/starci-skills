# Execute Principle compile

## LOADS

| Alias | Target | Kind | Why |
|---|---|---|---|
| `@design-principles` | `fe.design-principles` | qdrant | compile detailed product-neutral composition, boundary, hierarchy, responsive and interaction rules |

1. Run `node validate-input.mjs <input.json>`. Do not load or process an invalid artifact.
2. Verify every requested decision is an axis opened by both the selected Grammar result and source-fit result. Stop on owner substitution or a closed invariant.
3. Classify the situation into exactly one primary concern: composition, spacing-boundary, hierarchy, responsive-persistence or state-interaction.
4. Derive one decision from observable content/task structure. Explain the implementation intent at block and behavior level without emitting classes or package imports.
5. Write the nearest negative boundary. It must reject a realistic competing move, not merely say that bad design is forbidden.
6. Define proof across the relevant wide, intermediate, compact, keyboard, state and content-volume cases.
7. Scan the record for concrete package selection, business mapping, product-specific terms and complex-case ownership. Return `blocked` if any leaked into Principles.
8. Run `node validate-output.mjs <output.json>`. Emit nothing unless it passes; then advance the compiled decisions to request review and implementation planning.
