`listWorkflows(repoRoot)` (`kernel/store.mjs`) always returns `dir:null` per entry now (§8: no per-workflow

those throws `The "path" argument must be of type string. Received null` the moment a real ledger-backed
workflow reaches it (`workflow-list`/`workflow-status` on `bin/starci.mjs`, and directly in
`tests/workflow-view.spec.mjs`'s "workflow-list is one row per workflow..." once that fixture is pointed at a
real ledger). Confirmed this is the actual, sole blocker for `entry.spec.mjs`'s first test and
`workflow-view.spec.mjs`'s failing test by tracing the stack trace to `kernel/view.mjs:653` (`readLines`) and

### `hosts/headless/host.mjs`'s `providerFor` matches an alias before an exact id

`providerFor({agent,model})`'s candidate search is one `.find()` with an OR'd condition
(`id===wanted||modelOf(spec.command)===wanted`), so it returns whichever registered provider comes first in
insertion order that satisfies *either* half — never preferring an exact id match over a
happens-to-have-the-same-launch-command one. Since `codex-agent`'s own `working` profile is now
`gpt-5.6-luna` (same product change as above), `HEADLESS_PROVIDERS['codex-agent']` and
`HEADLESS_PROVIDERS['gpt-5.6-luna']` now carry the *identical* command
(`['codex','exec','--json','--model','gpt-5.6-luna']`) — and because `codex-agent` is registered first
(`model/registry.yaml`'s target order), an explicit request for `gpt-5.6-luna` by name matches `codex-agent`
on the `modelOf(spec.command)===wanted` half before ever reaching the entry actually named `gpt-5.6-luna`.
Confirmed directly: `providerFor({agent:'codex',model:'gpt-5.6-luna'})` returns `{id:'codex-agent',...}`, not
`{id:'gpt-5.6-luna',...}`. This is exactly what `tests/headless-model-registry.spec.mjs`'s
"Luna headless dispatch preserves the explicitly selected registered model" is a dedicated unit test for, and
what blocks `tests/luna-allocation.spec.mjs`'s last assertion — both correct, current, deliberately-written
assertions; the code doesn't honor its own documented contract
(`model/registry.yaml`'s own comment: "an explicit `--model gpt-5.6-luna` request still reaches the model").

--- a/hosts/headless/host.mjs
+++ b/hosts/headless/host.mjs

   const hit=wanted

+    // An exact registered id always wins first: once a pool's own working model coincides with a
+    // specific launch-only alias's model (e.g. codex-agent and gpt-5.6-luna both launch
+    // `--model gpt-5.6-luna`), matching by command alone would return whichever one happens to be
+    // registered first, never the one actually named.
+    ?entries.find(([id])=>id===wanted)??entries.find(([,spec])=>modelOf(spec.command)===wanted)??entries.find(([id])=>id===canonicalTarget(wanted))
     :entries.find(([id])=>id===HEADLESS_AGENTS[family].default);
