# Wave 3 — s7 cluster: `ledger-binding-mismatch:wf` (6) and `Missing workflow id` (3)

Starting point: `git fetch . main 2>/dev/null; git merge --ff-only main` (clean fast-forward, `038c1e4d` →
`5112c31c`, 48 files, six wave-2 branches merged). Full suite on `main` before this session: 2012 pass /
260 fail / 6 skip (per the lead).

## Method

Both error strings are thrown from guards this stream doesn't own (`kernel/store.mjs`'s `bindJournal` and
`hosts/orca/protocol.mjs`'s `required()`), so "trace to call site" meant finding every actual *failure*
carrying these messages across the full suite, not just files that mention the strings in their own
assertions (`tests/store.spec.mjs` intentionally exercises both guards and already passes). Ran a full
`npm test` first, then `grep -n "ledger-binding-mismatch\|Missing workflow id"` its output: exactly 7
`ledger-binding-mismatch:*` lines (6 are `:wf`, 1 is `:20260912-104251-kernel-spec` in a different spec not
part of this count) and exactly 3 `Missing workflow id` lines, matching the brief's counts.

## `ledger-binding-mismatch:wf` (6) — fixed

All 6 traced to the same retired pattern: a test opened a *separate* legacy `journal.sqlite` via
`openJournal({file:path.join(repo,'journal.sqlite')})` and passed it to `store.bindJournal(journal,...)`.
`kernel/store.mjs`'s `bindJournal` (line 163) correctly refuses any handle whose file isn't the store's own
ledger (`repo/.starciwork/runtime.sqlite`) — that guard is exactly right per §2 ("a generation bound to
another goal" class of protection) and was **not touched**. The bug was in the specs: they predate the
ledger-db refactor and never picked up the new pattern that `tests/store.spec.mjs` already establishes —
`openLedger({file:ledgerFileFor(repo)})`, the *same* file the store under test already opened internally.

- **`tests/kernel-engine.spec.mjs`** (5 occurrences: `journal-bound store recovers committed state…`,
  `the snapshot ledger keeps one body…`, `durable transition applies continuation…`, `durable recovery
  rejects the same job text…`, `replaying transition A after B…`). Swapped every `openJournal({file:
  path.join(repo,'journal.sqlite')})` paired with a `bindJournal` call for `openLedger({file:
  ledgerFileFor(repo)})`; added the `openLedger,ledgerFileFor` import from `kernel/ledger-db.mjs`. Left
  every *other* `openJournal` call in this file alone — the file also has ~15 tests exercising
  `kernel/journal.mjs`/`kernel/admission.mjs`/`kernel/job-bridge.mjs`/`kernel/job-worker.mjs` directly
  against a legacy journal with no `store.bindJournal` involved at all; those are a different, still-valid
  use of the legacy reader and out of this cluster.
  - One of the five (`journal-bound store recovers committed state when the JSON projection is lost`) also
    read `store.paths.state` — the fix moved forward from `store-paths-removed:continuation` was really
    `store-paths-removed:state`, i.e. a second retired-API reference on the very same line. §8 removed the
    on-disk JSON state projection entirely (there is nothing left to "tear" any more), so I ported the test's
    *intent* rather than its literal steps: it now asserts a fresh `createStore` on the same repo reads the
    latest committed state straight from the ledger, with no file dependency at all. Renamed accordingly
    (`durable state recovers from the ledger alone; a fresh store on the same repo sees the latest commit`).
  - Fixing the binding let each test run to completion for the first time, which surfaced a second, distinct
    bug: none of them ever closed the `store` object `createStore` returns. `createStore` opens its own WAL
    ledger connection and keeps it open for the store's lifetime; once `journal` pointed at the *same* file
    as that internal connection (the whole point of the fix), the still-open store handle held a lock that
    blocked each test's own `fs.rmSync(repo,{recursive:true,force:true})` cleanup with `EPERM` on Windows.
    Added the missing `store.close()` (and `reopened.close()` where a test opens a second store) calls.
- **`tests/engine-lifecycle.spec.mjs`** (1 occurrence: `owner inbox commits the actual choice and requester
  continuation once`). Same fix: `openJournal({file:path.join(root,'journal.sqlite')})` → `openLedger({file:
  ledgerFileFor(root)})`, same import swap. This one is **still red after the fix** — see below, it's now
  blocked by a real bug in a file this stream doesn't own.

## `Missing workflow id` (3) — root cause identified, not owned, diff below

All 3 (`tests/workflow-kernel.spec.mjs`: `an ask is never deferred for the decision folder another ask
holds…`, `a blocked credential ask from an older build is taken over…`, `a fill-waiting ask with no command
yet is named at the next tick…`) share one identical stack:

```
Error: Missing workflow id
    at need (hosts/orca/protocol.mjs:28:54)
    at required (hosts/orca/protocol.mjs:29:32)
    at singleTick (hosts/orca/protocol.mjs:113:20)
    at waitTick (hosts/orca/protocol.mjs:95:16)
    at runLoop (kernel/kernel.mjs:4187:18)
```

`hosts/orca/protocol.mjs`'s `singleTick` does `const workflowId=required(workflow,'workflow id')` — the
`workflow` param comes from `waitTick`'s own `workflow=null` default, so it throws unless a caller actually
passes one. `hosts/orca/protocol.mjs:204` (the CLI's `wait` verb) *does* pass `workflow:required(options.
workflow,'workflow id')`, confirming the parameter is meant to always be supplied — `singleTick` needs it to
key the wait-state `signals` row it now keeps in the ledger (§9: the old `<reports>/wait-state.json` file is
gone, replaced by a `signals` row scoped to the workflow).

The **only other caller** in the whole tree, `kernel/kernel.mjs:4187` (`runLoop`'s main wait step), never
passes `workflow` at all:

```js
const tick=waitTick(orca,{cwd:state.worktree,run:state.run,from:state.from,
  timeoutMs:inputWait?Math.min(waitTimeoutMs,5000):waitTimeoutMs,tickMs:inputWait?Math.min(tickMs,5000):tickMs,
  now,wait,wake:()=>inboxPending(store)||stopRequested(store)});
```

`state.id` is the workflow id everywhere else in `kernel.mjs` (`op.lease.workflowId!==state.id`,
`journal.events({workflowId:state.id})`, `attestationId:\`retry:${state.id}:…\``, dozens of call sites) —
it's simply missing from this one call. This is exactly the "used with none" half of the cluster's own
description: the kernel's main run loop calls into a function that now needs a workflow id to scope its
ledger-backed wait state, without supplying one.

### Exact diff requested (kernel/kernel.mjs, not owned by this stream)

```diff
-      const tick=waitTick(orca,{cwd:state.worktree,run:state.run,from:state.from,
+      const tick=waitTick(orca,{cwd:state.worktree,run:state.run,from:state.from,workflow:state.id,
         timeoutMs:inputWait?Math.min(waitTimeoutMs,5000):waitTimeoutMs,tickMs:inputWait?Math.min(tickMs,5000):tickMs,
         now,wait,wake:()=>inboxPending(store)||stopRequested(store)});
```

**Verified locally** (scratch edit, reverted before this commit — `kernel.mjs` is not in this stream's
owned-file list): with this one line added, all 3 target failures disappear. Two of the three tests then
pass outright (`a blocked credential ask from an older build…`, `a fill-waiting ask with no command yet…`).
The third (`an ask is never deferred for the decision folder another ask holds…`) fails for a completely
different, pre-existing reason (`AssertionError: only the op that edits the folder waits for the ops
holding it` — `[]` vs `['author-c']`), unrelated to workflow binding and outside this cluster.

## `owner inbox commits the actual choice…` — still red, real bug, not owned

After the binding fix above, this test fails one line later:

```
Error: store-paths-removed:inbox
    at enqueueOwnerInbox (kernel/owner-inbox.mjs:21:31)
```

`kernel/owner-inbox.mjs`'s `enqueueOwnerInbox` still does `const directory=store?.paths?.inbox;` and writes
a raw `<id>.json` file into it — §8's retired file-path API, never ported to `store.inbox.push({kind,key,
payload})`. This is **not a simple one-line port**, though, and I want to flag why rather than guess at a
fix: `enqueueOwnerInbox` has exactly one production caller in the whole tree,
`kernel/inputs-model.mjs:127`:

```js
enqueue=payload=>enqueueOwnerInbox({paths:{inbox:path.join(binding.dir,'inbox')}},payload)
```

— a *synthetic* object that is not a real store at all, just `{paths:{inbox:<a plain directory>}}`. That
caller is the owner-credential-answer UI's own local queue and is presumably still meant to write files
there (it's not clear that path is meant to go through the ledger `inbox` table at all). Meanwhile
`kernel/kernel.mjs`'s `applyInbox` (kernel.mjs, already ported) reads exclusively from `store.inbox.
pending()` — a ledger table row, never a file on disk. That means, as the code stands today:
`enqueueOwnerInbox`'s only real caller writes files that `applyInbox`'s only real reader never looks at.
Whether that's because `inputs-model.mjs`'s owner-credential flow is wired through a different consumer I
didn't trace, or because this producer/consumer pair genuinely disconnected during the 1.0.4 port, is a
judgment call for whoever owns `kernel/owner-inbox.mjs`/`kernel/inputs-model.mjs`/`kernel/kernel.mjs` — not
something I'm willing to guess at by writing a diff. Flagging the disconnect with its exact evidence instead
of proposing a fix I can't verify end to end.
