## Contract addendum picked up mid-session (merge `main`, then `starci183/s0-ledger-db` again)

Ledger identity is now a minted `meta.ledger_id` (never path-derived), `journal_mode=WAL` is the default, and
`machine.sweep` reopens each registered ledger at its last-known `ledgers.file` to confirm that identity
before trusting its leases (§5/§6/§12 of `docs/ledger-db.md`). My part:

- `superviseOnce` previously opened its own `machine` handle, ran `sweep`, and closed it immediately —
  *before* it ever opened a workflow ledger. No ledger opened during the round ever registered/refreshed
  itself on the machine, so a moved ledger's `ledgers.file` would go stale. Fixed: the machine handle now
  stays open for the whole round (still closed at the end, still only when this call opened it itself), and
  every ledger `superviseOnce` opens is opened with `openLedger({...,machine:machineHandle})`.
- No `supervisor.mjs` code path copies the ledger file (that's archive/`workflow-export`/backup, none of
  which this stream owns), so the addendum's `PRAGMA wal_checkpoint(TRUNCATE)` requirement has nothing to
  wire here. Verified against the sibling worktrees: `s0-ledger-db` already exports `checkpointLedger(handle)`
  for exactly this, and `s6-cli`'s `hosts/orca/launch.mjs` already calls
  `store.ledger.db.exec('PRAGMA wal_checkpoint(TRUNCATE)')` at its copy site.
- Fixed a test (`tests/supervisor.spec.mjs`'s machine-sweep case) that called the old
  `machine.registerLedger({file})` (path-derived id) shape; updated to the new
  `registerLedger({file,ledgerId:ledger.ledgerId})`.

## Readings I picked where the contract was ambiguous

- **`reopenLane`'s Orca call shape.** The contract says it recreates the worktree "through Orca
  `worktree-create`", but `providers/orca/calls.yaml`'s `worktree-create` only accepts
  `[repo, name, base-branch, setup, no-parent, parent-worktree]` — no flag for checking out an *existing*
  branch instead of cutting a new one from a base, and no flag for an explicit target path. I passed the
  recorded branch as `base-branch` (the closest lever the documented flags offer) and the recorded `path` as
  an extra hint a host adapter may honour, then read back whatever Orca actually reports (never assumed the
  hint was obeyed) — same discipline `openLane` already uses. This is the reading that touches the fewest
  other files (no change to `providers/orca/calls.yaml` or `hosts/headless/host.mjs`). If the real intent is
  a `worktree-create` flag that checks out an existing branch verbatim, that flag needs to land in the shared
  calls contract first; I don't own it.
- **Where `reopenLane` gets called from.** The contract's Deliver bullet says "used by the kernel when the
  recorded worktree path is absent at resume (write the call-site diff for kernel.mjs into notes for s3)."
  But a kernel process can't discover its own worktree is missing — the supervisor spawns it with
  `cwd: info.worktree`, so a missing directory fails at process-spawn time, before any kernel code runs. The
  only place that can act on a missing worktree is whoever is about to spawn the process — `supervisor.mjs`'s
  `startKernel`, which I own. I read "the kernel" here as the kernel *system*, not literally `kernel.mjs`, and
  wired it there instead of asking s3 for a call-site change. `startKernel` now checks
  `fs.existsSync(info.worktree)` before doing anything else, and calls `reopenLane` using `info.lane` (added
  to `inspectWorkflow`'s return) when it's missing.
- `scripts/runtime-modules.txt`, while not on my owned list, is required for `kernel/launch.mjs` and
  `kernel/ledger-db.mjs` (s0's) to build at all — every stream that lands a genuinely new source file will hit
  the same `assertRuntimeImportClosure` failure. Added the two entries mine needed rather than leaving the
  build broken; flagged below so nobody double-adds them and nobody else gets stuck on the same wall without
  knowing why.
