## Fixed in kernel.mjs (owned)

**`withAnchorVerified` called `ledgerDb.verifyAnchor` with the wrong second argument.**
`kernel/kernel.mjs` line ~1624 called `ledgerDb.verifyAnchor(store.ledger,{workflowId:state.id})`, but
`verifyAnchor(ledger,repoRoot)` (kernel/ledger-db.mjs) takes a **repo root string**, not an options object -
it passes it straight into `readAnchor(repoRoot)` → `anchorFileFor(repoRoot)` → `path.join(repoRoot,...)`.
Every resume hit `TypeError: The "path" argument must be of type string. Received an instance of Object`,
reported as `Workflow resume boundary is inconsistent ... ledger-behind-anchor: The "path" argument must be
of type string.` This was the root cause of:
- "a resume boundary reported inconsistent" (workflow-kernel.spec.mjs)
- "a kernel that already has its run records run-resumed; only a real bind records run-bound" (same crash, once workflow-run reaches resume)
- half of "public retry and pinned enrolled run preserve accepted history..." (workflow-kernel-shared-ledger.spec.mjs)

Fix: pass `store.repoRoot` instead.
```js
try{anchor=ledgerDb.verifyAnchor(store.ledger,store.repoRoot);}
```

## NOT fixed - real bugs in files I do not own (diffs below; none applied)

### 1. `kernel/sync.mjs` `quarantineStrays` still uses `store.dir` (always `null`)

Line ~988:
```js
const from=path.join(root,stray),to=path.join(store.dir,'strays',stamp,stray);
```
`store.dir` is always `null` on a ledger-backed store. `path.join(null,...)` throws `TypeError`, caught by
this function's own try/catch, which emits `stray-quarantine-failed` instead of `stray-quarantined` - so a
stray is *never* actually quarantined any more. Root cause of:
- "a stray is quarantined when git names the file and the validator names the reserved directory above it"
- "untracked strays that alone make the tree invalid are quarantined beside the store..."

Suggested fix (root-level `.starciwork/_local` is already excluded from the tree validator - see
`core/index.mjs` line 138 - so it's still a safe, scan-invisible destination without touching the validator):
```diff
- const from=path.join(root,stray),to=path.join(store.dir,'strays',stamp,stray);
+ const from=path.join(root,stray),to=path.join(root,'.starciwork','_local','strays',stamp,stray);
```
I ported my own test's assertion to expect `.starciwork/_local/strays` at this destination already, so this
diff alone should turn both stray tests green.

### 2. `kernel/inputs.mjs` `recoverWorkflowInputReferences` accepts an ungrounded collision

`recoverWorkflowInputReferences` (line 44) treats any `state.inputs` shaped like `{0:ref,...,phase:'ready'}`
(numeric keys + a valid `SURFACE_PHASES` value) as a genuine GUI/goal-key collision worth trusting, as long as
the recovered refs match the approved goal's `inputs`. It does not require any other grounding surface field
(`page`, `session`, `priorSession`, ...) to be present. A bare `{...arrayInputs,phase:'ready'}` - which is
exactly what an unrelated bug elsewhere could also produce by accident - is indistinguishable from a real prior
GUI session and gets silently "recovered" (`ok:true`), when the workflow-kernel.spec.mjs test
"kernel restart refuses ungrounded input recovery before launching or reading downstream inputs" expects this
exact shape to be refused (`ok:false`, `workflow-input-repair`) specifically *because* it carries no grounding
signal. Confirmed by adding a `refreshPreparation` fixture that throws if ever called: it IS called, meaning
recovery is wrongly reported as `ok:true`.

I don't own this file, so I have not guessed at the exact grounding predicate the recovery should require. My
best-supported suggestion: refuse (`refused('input-reference-ungrounded')`) unless `surface` has at least one
field beyond `phase`/`reason`/`lastCheckedAt` (i.e. `session`, `priorSession` or `page` - something a live or
very recent GUI session could only have set):
```diff
  const refs=numeric.map(key=>collided[key]);
  const validRefs=items=>...
  if(!validRefs(refs)||(state.ownerInputs!=null&&!plain(state.ownerInputs)))return refused('input-reference-shape-invalid');
+ const grounded=['session','priorSession','page'].some(key=>Object.hasOwn(surface,key));
+ if(!grounded)return refused('input-reference-ungrounded');
  const goal=store.goal()?.json??null;
```
Please sanity-check against the passing sibling test ("kernel restart recovers collided approved input refs...",
which sets `page:'synthetic-existing-page'`) before applying - that one must keep passing.

### 3. `tests/helpers/kernel-harness.mjs` `scriptedOrca`'s `check` never advances past an unconsumed report

Line ~105:
```js
const existing=live.size?new Set(store.readReports().map(item=>item.dispatchId)):new Set();
```
`store.readReports()` (kernel/store.mjs) returns every report row regardless of `consumed_at` - by design,
callers are expected to filter on `consumedAt` themselves (this is the SQL-row equivalent of the old
"rename the report file aside" consumption model; `archiveOpReport` in kernel.mjs sets `consumed_at` instead of
renaming a file). This harness never checks it, so once a dispatch's first report is written (and then
consumed/archived by the kernel, e.g. a `shared-change-refused` "report again" cycle), `existing` still
contains that dispatch id forever, and the harness never delivers the op's *next* scripted report - the op
keeps re-reporting the same first script entry every tick until `maxIterations` runs out. Root cause of:
- "a shared change naming a path of another repository is refused and the op is answered, never delegated"
  (11 duplicate `shared-change-refused` events instead of 1 - the second script entry, `outcome:'done'`, is
  never delivered)

Suggested fix:
```diff
- const existing=live.size?new Set(store.readReports().map(item=>item.dispatchId)):new Set();
+ const existing=live.size?new Set(store.readReports().filter(item=>item.consumedAt===null).map(item=>item.dispatchId)):new Set();
```

## The headless-host relaunch storm (found and fixed, not just documented)

"on the headless host a workflow runs end to end one operation at a time..." was not in the wave-4 message's
six named descriptions, but it was failing (46/49/83/92/104 launches instead of 3, growing on every re-run) and
turned out to be two real bugs in my own `headlessFake` test fixture (`tests/workflow-kernel.spec.mjs`):

1. `headlessFake`'s headless-host dispatch/mailbox table lives on real disk at
   `os.tmpdir()/starci/<workflow id>/headless`, and `setup()` fixes that workflow id to the same literal
   (`'20260912-104251-kernel-spec'`) on every call - unlike `repo`, which is a fresh tmpdir per test. Every
   previous run's stale dispatch records accumulated there forever (nothing ever cleaned that path), and each
   pile-up confused the host's own mailbox-wait liveness check into more spurious relaunches than the run
   before. Fixed: `headlessFake` now `fs.rmSync`s its `root` before use, the same fix shape as `inputScratchDir`
   in wave 2.
2. Once (1) stopped the relaunch storm, the test failed later on `mailbox.jsonl` having 0 lines instead of 3:
   the fake wrote each report straight into the ledger (bypassing the real launcher's `report` CLI, which is
   also what tells the headless host to append a mailbox message) and never fixed the resulting API-real gap -
   comment in the code (`hosts/orca/protocol.mjs is outside this stream`) explained the ledger write clearly but
   the mailbox notification was fully dropped, not just deferred. Fixed: `finish()` now also calls
   `orca.invoke('send',{...})` after `store.writeReport`, mirroring what the real report CLI does.

Both fixes are in `tests/workflow-kernel.spec.mjs`, entirely inside my ownership; no diff needed elsewhere.

### 4. `core/index.mjs` Work-tree validator does not exclude 1.0.4's new root-level kernel files

The canonical-v2 tree walker (`walk()`, ~line 124) excludes the root-level `_local` directory by name
(line 138: `if(dir===absolute&&ent.name==='_local')continue;`) but 1.0.4 replaced per-workflow `_local` file
storage with two NEW root-level files that live directly under `.starciwork/` (no longer inside any excluded
directory): `runtime.sqlite` (+`-wal`/`-shm`) and the §12 tracked anchor `ledger-anchor.json`. Every `.json`
file under the tree root is pushed to `jsonFiles` (line 145) and, once `canonicalV2` is true, reported as
`JSON_ARTIFACT` (line 182): `"Canonical Work records and results use YAML; JSON files are not accepted inside
Work."` Since `ledger-anchor.json` is written on every checkpoint and never goes away, the tree is reported
invalid **forever** on any repo using the 1.0.4 ledger, which cascades into:
- `work:custody-path-touched:.starciwork/ledger-anchor.json` candidate-quarantine refusals (the kernel's own
  anchor write looks like a candidate touching an unowned path)
- nodes that depend on another node's completion (e.g. `demo.sales.implementation.frontend.receipt` depending
  on `demo.sales.ui`) never becoming schedulable, because the tree scan they're read from is permanently red
- root cause of `tests/workflow-kernel-shared-ledger.spec.mjs`'s "the accepted slice is recorded and committed
  in the owner..." (only 1 of 3 expected ops ever completes) and the "candidate-reconciliation"/stall half of
  "public retry and pinned enrolled run preserve accepted history..."

Suggested fix - exclude the same fixed root-level filenames the way `_local` is already excluded:
```diff
       if (ent.isDirectory()) {
         ...
         continue;
       }
+     if(dir===absolute&&(ent.name==='ledger-anchor.json'||ent.name==='runtime.sqlite'||ent.name==='runtime.sqlite-wal'||ent.name==='runtime.sqlite-shm'))continue;
       let item;
       if(ent.name.toLowerCase().endsWith('.json'))jsonFiles.push(p);
```
