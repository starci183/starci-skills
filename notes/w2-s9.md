# Wave 2 — s9 cluster: kernel/inputs*.mjs, kernel/goal.mjs, kernel/amendment.mjs

Fast-forwarded onto `main` (the ten 1.0.4 branches merged). Read docs/ledger-db.md §3, 4, 8, 9, 12 before
starting, per instructions.

## Files changed

- `kernel/inputs-model.mjs`
  - `inputBinding(state,store)` now takes the live `store`, not a directory: it carries `repoRoot` instead
    of `dir` (a workflow owns no directory any more). `readInputState(binding)` opens a short-lived store
    from that binding (`createStore({repoRoot,id})`, `store.loadState()`, close) instead of reading
    `<dir>/state.json`.
  - The default `enqueue` (owner credential/decision actions) now validates with `owner-inbox.mjs`'s own
    `parseOwnerInboxCommand` and pushes straight into the ledger's `store.inbox` instead of routing through
    `enqueueOwnerInbox`'s file-based queue (which wrote `<dir>/inbox/*.json` — `store.paths.inbox` no longer
    exists to give it a directory). `applyOwnerInbox` (kernel/owner-inbox.mjs, unchanged, not owned) already
    tolerated the bare `starci/owner-action@1` shape this writes, so the kernel-side apply path needed no
    change.
- `kernel/inputs.mjs`
  - `inputScratchDir(id,repoRoot)` now keys the detached input helper's scratch directory
    (`os.tmpdir()/starci/<hash>/`) by a hash of **both** `repoRoot` and `id`, not `id` alone — two
    workflows of the same id in different repositories (routine in tests, and not impossible in practice)
    were sharing one scratch directory and reading each other's session, which read as
    `workflow-binding-changed` and got the reconciliation stuck at `starting` forever.
  - `bindingMatches` compares `repoRoot` instead of the removed `dir`.
  - `reconcileWorkflowInputs` calls `inputBinding(state,store)` (not a directory).
- `kernel/inputs-server.mjs`
  - `serveWorkflowInputs` derives its scratch directory from the session file's own path
    (`path.dirname(sessionFile)`) instead of `session.binding.dir` (gone); validates
    `session.binding.repoRoot` instead.
  - `inputFiles(dir)` drops the `lock` key: `inputs.lock` is the ledger signal `inputs-lock` (already
    landed last wave), never a file, so the dead key was actively misleading (a caller writing to it
    silently did nothing).
- `goal.md` — two unrelated-but-owned corrections that were blocking my own owned spec
  (see "Unrelated drift" below): `codex-agent` cap/model split in §3, and `interface.draw`/
  `interface.asset`'s model claim in §2 (D. DESIGN) rewritten from a literal `gpt-5.6-sol only` pin to
  "the codex-agent pool only, no fallback" with a note that the resolved model follows `write`, since
  ImageGen routing names the operation agent, not an image-model version (registry.yaml's own
  `costPolicy` already said this; the model changed under it).
- `kernel/goal.mjs`, `kernel/amendment.mjs` — **no source changes needed this wave.** Both already coded
  entirely against `store.setGoal`/`store.goal`/`store.appendEvent`/`store.saveState`/`store.readEvents`
  (amendment.mjs never touched `store.paths` to begin with), so once `main` merged stream s1's real
  `kernel/store.mjs`, both files worked unmodified. All failures in their two spec files were in the
  *tests*, not these two files.
- `tests/workflow-inputs.spec.mjs`, `tests/goal-grounds-intake-scope.spec.mjs`, `tests/workflow-amendment.spec.mjs`,
  `tests/goal-contract.spec.mjs` — ported every fixture off the removed `store.paths.*`/`store.dir` surface
  and, critically, **closed every `store` a fixture opens**: `createStore` now opens a real
  `node:sqlite` handle (`kernel/ledger-db.mjs`), and an unclosed one blocks Windows from deleting the temp
  directory in `t.after`/`finally` (`EPERM`) — this was the single largest failure category across all four
  files (see "Root cause note" below). Also: `store.inputs.get(...).bytes` is a `Uint8Array`, not a `Buffer`
  (`Buffer.from(bytes).toString('utf8')`, not `bytes.toString('utf8')`, which silently produces a
  comma-joined byte list instead of throwing).

## Root cause note: the EPERM cluster

Of the ~53 originally-failing tests in this cluster, the large majority (`workflow-inputs.spec.mjs`'s 22,
most of `goal-grounds-intake-scope.spec.mjs`'s 13, 4 of `goal-contract.spec.mjs`'s 5) trailed a **second**,
independent error once the first (the actual `store.paths`/`store.dir` API break) was fixed: an `EPERM` on
`fs.rmSync` in cleanup. `kernel/store.mjs`'s `createStore` now opens a real SQLite file
(`.starciwork/runtime.sqlite`) and every one of these fixtures' `store` was never `.close()`d before the
temp directory was removed — Windows refuses to delete a directory with an open file handle inside it. This
was invisible before 1.0.4 because the old store only touched plain files/directories, which Windows never
locks against deletion the same way. Every fixture in this cluster's four files now closes its store(s) in
`t.after`/`finally`, in the same statement (or right before) the temp directory is removed.

One instance of this pattern could **not** be fixed the same way: see "engine.mjs leaks a ledger handle"
below.

## Requests to other streams

1. **`kernel/continuation.mjs` (not owned) — the largest single external blocker.**
   `bindContinuationPath` (three call sites, lines ~177/181/198) still does
   `store.paths.continuation = <resolved path>` as a memoization cache, and `store.paths` is the new store's
   permanently-throwing Proxy (`kernel/store.mjs:114`, `store-paths-removed:continuation`). The store already
   computes a fixed canonical value at `store.continuation` (`path.join(workflowsDir, \`${workflowId}.md\`)`
   — read-only, no brief-matching). The fix: `bindContinuationPath` should stop assigning to `store.paths.*`
   and just `return` the resolved path (the explicit-override branch at line 177, the canonical-exists
   branch at line 181, and the brief-matching branch at line 198 all currently write-then-return the same
   value they're about to return anyway — dropping the assignment changes nothing observable there). Its
   one caller, `kernel/kernel.mjs:4497` (`bindContinuationPath(store,state);`, standalone, return value
   discarded), calls it purely for that now-removed side effect — whoever owns `kernel/kernel.mjs` needs to
   either capture and use the return value there or confirm nothing downstream still expects
   `store.paths.continuation`/`store.continuation` to reflect the brief-matching result (only the fixed
   canonical path is exposed by the store today). This is not a small blocker: it produced 27 of the 33
   `store-paths-removed:*` failures in a full `npm test` run (7 of them in my own
   `tests/workflow-amendment.spec.mjs`, all of which exercise the real public CLI path via
   `hosts/orca/launch.mjs`).
2. **`kernel/owner.mjs` (not owned).** `openOwnerAsk` (line 221) does
   `const file=op.dispatch?store.reportPath(op.dispatch):null; if(file&&fs.existsSync(file))fs.renameSync(file,`${file}.asked-${op.reports.length}`);`
   — an old trick to keep a settled report file from being reprocessed by renaming it, using
   `store.reportPath`, which `kernel/store.mjs` explicitly keeps as a throwing stub
   (`reportPath(){removed('reportPath');}`, per docs/ledger-db.md §8: "removed (grep all callers)"). Under
   the ledger, this needs a different signal — most likely marking the report row "asked"/consumed via
   `reports.consumed_at` (already a column, per docs §4) rather than a filesystem rename, but that read/write
   path (`store.writeReport`/`readReports`) doesn't currently expose an "asked" or "consumed" setter either,
   so this may need a small `kernel/store.mjs` addition too. Failed exactly once in my cluster
   (`tests/workflow-inputs.spec.mjs`, "kernel accepts a typed replacement report through the owning ask
   path…") but 3 more times elsewhere in the full suite.
3. **`kernel/engine.mjs` leaks the durable ledger handle `enrollEngine` opens (not owned).**
   `enrollEngine` (kernel/engine.mjs:259-277) opens its own `ledger=openLedger({file:ledgerFile,...})` and
   hands it to `store.bindJournal(ledger,generation,{...})`, which the store keeps as its *durable* binding
   for `saveState`/`transition`/etc. `store.close()` (kernel/store.mjs) only closes the handle the store
   opened for itself at construction (`const ledger=openLedger({file});` inside `createStore`) — it never
   closes `durable?.ledger`, so a workflow that called `enrollEngine` and then `store.close()` leaves that
   second connection open for the life of the process. Confirmed in
   `tests/goal-contract.spec.mjs` ("typed I/O: a record reference that resolves to nothing blocks
   dispatch…", which calls `enrollEngine` + `createEngineRuntime`): `runtime.close()` closes a **third**,
   separate handle (`kernel/job-bridge.mjs`'s own `openLedger` call inside `createJobBridge`), so even
   closing both `store` and `runtime` leaves the `enrollEngine`-opened one dangling. I could not close it
   from the test (it is never returned to the caller), so I marked that one cleanup tolerant of the specific
   `EPERM` this leak causes (`rmSyncTolerant` in `tests/goal-contract.spec.mjs`) rather than pretend a retry
   loop would ever succeed against a handle nothing releases. Likely fix: either `enrollEngine` should reuse
   the store's own already-open ledger handle instead of opening a second one to the same file (when
   `ledgerFile` resolves to the same path `store` already has open), or `store.close()` should also close
   `durable?.ledger` when it differs from its own. This is a real resource leak beyond test hygiene — every
   production process that enrolls a workflow and later closes its store leaks a SQLite connection for its
   remaining lifetime.
4. **Unrelated model-routing drift, pulled in by the merge, not part of this stream's task.** Two things in
   `model/runtimes.yaml`/`model/registry.yaml` changed since the contract's `goal.md` was written (an
   unrelated commit, "model: codex implement/write on gpt-5.6-luna (refactor alignment), verify stays sol,
   pool cap 10"): `codex-agent`'s cap (8→10, already corrected last wave) and its `write`-role model
   (`gpt-5.6-sol`→`gpt-5.6-luna`, discovered this wave via `interface.draw`/`interface.asset`, which route
   through `write` with no per-op override and so silently moved off Sol too). I corrected `goal.md` and the
   one test this broke in my own cluster (`tests/goal-contract.spec.mjs`); I did not audit every other file
   for the same drift. Anything else that asserts `gpt-5.6-sol` for a `write`-role codex-agent operation
   should be re-checked against the current `model/runtimes.yaml`.
