## Assigned cluster: `store.signal.get/set/clear` round-trip correctness

Read the actual new callers before writing any test, so the cases match what's really written, not
invented shapes:
- `kernel/common.mjs` `rulingsText`/`setRulingsText` — **string** (`RULINGS_KEY='rulings'`).
- `kernel/verify.mjs` `readValidatorMemory`/verdict writer — **string** (`validator-memory`) and **array of
  objects** (`validator-verdicts`).
- Existing coverage already had an **object** shape (`supervisor-lock` → `{role:'supervisor'}`).
- No real caller writes an explicit `{value:null}`, but I added it anyway since "every shape those callers
  use" plus "a cleared key reads back null rather than undefined" both call for covering the boundary
  between "never set," "explicitly null," and "cleared."

**Finding: no bug.** `kernel/store.mjs`'s `signal.set/get/clear` (lines ~272-284, unchanged this wave)
already handles every case correctly:
- `set` distinguishes `value===null` from any other value with an explicit check (not `!value`), so `0`,
  `false` and `''` all round-trip — not just object/array/string.
- `get` on a missing row: `bound().prepare(...).get(...)` returns `undefined`, and the ternary
  `row?{...}:null` normalizes that to `null` — never `undefined`.
- `clear` deletes the row; a subsequent `get` hits the same missing-row path, so a cleared key and a
  never-set key are indistinguishable, both `null`.
- Isolation is exactly what the `(scope,key)` primary key gives it: every real caller passes `store.id` as
  `scope`, so two different workflow stores opened on the *same* ledger file (one repo, one ledger — §1)
  never see each other's row under the same key, and clearing one never touches the other's.

Added to `tests/store.spec.mjs` (all passing, no `kernel/store.mjs` change needed):
- `signal values round-trip every shape a real caller writes: string, array, object and explicit null` —
  exercises the exact `rulings`/`validator-verdicts` shapes plus a nested-object shape, a never-set key, an
  explicitly-null value, an omitted value, and a cleared key, asserting `null` (not `undefined`) throughout.
- `signal rows are scoped per workflow: one workflow can never read or clear another's` — two `createStore`
  calls on the same repo (same ledger file), same signal key, different scopes: neither store's own-scoped
  `get` sees the other's value, explicitly reading the *other* workflow's id back out proves the scope
  column (not the calling store) is the isolation boundary, and clearing one workflow's row leaves the
  other's untouched.

## Found while verifying: a real regression in `kernel/owner-inbox.mjs` (not owned by this stream)

Per "assume any remaining failure may be a real bug of the same kind," I ran the full suite and traced
every failure that touched `kernel/store.mjs`'s call sites. `tests/engine-lifecycle.spec.mjs` failed with

the HTTP seam that queues an owner action), not a test stub. It still reads `store?.paths?.inbox` as a
directory and writes a raw `<id>.json` file into it — exactly the same shape of bug the lead already fixed
twice this wave (`reportPath`, `rulingsText`): a caller that silently degrades (`if(!directory)return
{ok:false,code:'inbox-unavailable'}`) instead of using the real §8 surface (`store.inbox.push/pending/

catching it loudly: `store.paths.inbox` now genuinely throws (my wave-1 design), so an owner action posted

## Found but out of scope: two more `ledger-binding-mismatch` failures, same family as wave 2

`tests/workflow-first-enrollment.spec.mjs` and `tests/workflow-kernel-shared-ledger.spec.mjs`'s "public
retry" tests both throw `ledger-binding-mismatch:<id>` from `kernel/store.mjs:180`'s `bindJournal` guard
(unchanged, and I did not weaken it — the check is correct, see wave 2's notes for why). This is the same
root-cause family as wave 2's finding, not a new bug in `store.mjs`:

- `tests/workflow-first-enrollment.spec.mjs` passes `'journal-file':journalFile` where
  `journalFile=path.join(root,'runtime','journal.sqlite')` — a path distinct from the store's own
  `ledgerFileFor(root)`. `kernel/kernel.mjs:4822`'s `retryJournalTarget({option:options['journal-file'],...})`
  honors that CLI-style override unconditionally when present.
- `tests/workflow-kernel-shared-ledger.spec.mjs`'s "public retry and pinned enrolled run..." test sets
  `state.engine={...,ledgerFile:journalFile,journalChosen:true,...}` with the same
  `runtime/journal.sqlite` convention, which `retryJournalTarget`'s `chosen&&previous` branch then keeps
  across `workflow-stop`/`workflow-retry`.

Unlike wave 2's cases, the call sites here (`kernel/kernel.mjs:4566` inside the real `workflow-stop`
handler, and `kernel/kernel.mjs:4831` inside the real `enrollEngine` retry path) are **production code**,
not test-only fixtures — but the *data* driving the mismatch (`journalFile`/`'journal-file'` pointing away
from `ledgerFileFor(repoRoot)`) only exists in these two tests' own setup. I did not find any real,
non-test caller that constructs a `--journal-file`/`state.engine.ledgerFile` diverging from the store's own
ledger. Given the contract (§1-§12) never describes a configurable or relocatable ledger location — it is
always exactly one file at `ledgerFileFor(repoRoot)` — I believe `kernel/kernel.mjs`'s
`retryJournalTarget`'s `option`/`chosen&&previous` override branches (and the CLI's `--journal-file` flag,
and `journalChosen`) are 1.0.3 vestiges of a "choose where your operational journal lives" feature that
1.0.4's single-ledger model retired, and these two tests are the last fixtures still exercising it.

I did not attempt this fix myself: it is a design decision in `kernel/kernel.mjs` (whether to delete the
CLI flag and the override branches entirely, or keep them for some purpose I'm not seeing), not a
mechanical substitution like wave 2's `openJournal`→`openLedger` swap, and it's real product code rather
than a test-only fixture — I'd rather flag it precisely than guess wrong on the seal wave. Whoever owns
`kernel/kernel.mjs` (likely s3) should decide whether to retire `retryJournalTarget`'s override branches
(and `--journal-file`) or give them a real, still-valid meaning under 1.0.4, then port these two tests to
match.
