# Wave 2 — s2 cluster (kernel/engine.mjs, kernel/admission.mjs)

## Summary

Fixed six distinct root causes across `kernel/admission.mjs` and `kernel/engine.mjs`. With those fixes
alone, `tests/engine-adapter.spec.mjs` is still red (still full of `NOT NULL constraint failed:
events.digest` and `EPERM` failures) because two of the biggest failure classes in this cluster's spec
list turn out to live in files this stream does not own: `kernel/jobs.mjs` and `kernel/job-bridge.mjs`.
I verified both with a temporary local patch (never committed — applied, tested, `git checkout`'d back
out every time) before writing the diffs below, so these aren't guesses: with both applied on top of my
real commits, `tests/engine-adapter.spec.mjs` goes from 4/48 to **48/48**, and
`tests/engine-lifecycle.spec.mjs`'s job-bridge-dependent tests also turn green.

## The "openLedger needs a file" cluster (21 failures, per the assignment)

All the ones inside this cluster's files were plumbing bugs of exactly the shape described: code
reaching `openLedger`/`inspectLedger`/`createJobBridge` with the wrong field name in scope, not a missing
default to invent.

- `kernel/engine.mjs`'s `enrollEngine` had `ledgerFile`/`machineFile` as **parameter-list defaults**
  (`{ledgerFile=ledgerFileFor(store.repoRoot),...}`). A parameter default is evaluated eagerly, before the
  function body's first line runs — so a caller whose `store.repoRoot` isn't set yet (or omits `store`
  data.entirely) got a `path.join(undefined,...)` `TypeError` instead of the "Settle live operation
  dispatches" guard the function is supposed to check first. Fixed by computing both inside the function
  body, after that guard (`kernel/engine.mjs` around `enrollEngine`).
- The rest were test fixtures (`tests/engine-adapter.spec.mjs`, `tests/engine-kernel-flow.spec.mjs`,
  `tests/engine-lifecycle.spec.mjs`) still building `state.engine.journalFile` or passing
  `createJobBridge({journalFile:...})` — the pre-1.0.4 field name. Ported to `ledgerFile`+`machineFile`.
  (`tests/kernel-engine.spec.mjs` and part of `tests/engine-migration.spec.mjs` also do this, but
  deliberately — see "Not this cluster" below; I left those alone.)

## Other root causes fixed in this cluster

- **`providerAdmissionView` read `ai/provider:*` capacity from the wrong database.** `admission.setCapacity`
  correctly routes `ai/*` keys to the machine DB (§6), but `providerAdmissionView` (engine.mjs) queried
  `journal.db`'s (the ledger's) `resources` table for them — always empty, so every provider always showed
  0 capacity and every model call refused with "no provider admission capacity". Reads
  `admission.machine.db` now.
- **`settled()`'s `workerOnly` release leaked machine-side leases.** It deleted a job's `ai/*`/`machine:*`
  ledger lease rows (the mirror rows §6 describes) without ever reading their `machine_ref` first, so the
  *real* reservation in the machine DB was never released — only cleared up eventually by
  `machine.sweep()`'s TTL reaping. Now reads and releases those tokens, the same pattern
  `admission.mjs`'s `release`/`settleUnknown` already use.
- **A hand-rolled event insert silently vanished.** `settleStoppedOperation`'s launch-reconciliation path
  did a raw `INSERT OR IGNORE INTO events(...)` that never set `digest`/`prev_digest`. Those columns are
  `NOT NULL` with no default (§4), and SQLite's `OR IGNORE` conflict resolution treats a `NOT NULL`
  violation as an ordinary conflict to skip — so the row was silently dropped, no error, and the job could
  never later prove itself `launched`. Replaced with `journal.appendEvent(...)`, which computes the digest
  chain correctly and is safe to call inside the already-open transaction. (This is the exact same bug
  class as the `kernel/jobs.mjs` finding below — I searched the rest of `engine.mjs` for other raw
  `INSERT INTO events`/`INSERT OR IGNORE INTO events` and this was the only one.)
- **Peer-workflow cooldown was read from a dead file.** `requestModel`'s shared-cooldown read used
  `readLoads({path:loadsFileFor(store.dir),...})`. `loadsFileFor`/`LOADS_FILE` still exist in
  `kernel/loads.mjs` but are explicitly retired (`kernel/loads.mjs`'s own comment: "Legacy name kept so
  callers still wired to `_local` resolve; nothing here ever reads or writes that path") — shared runtime
  loads live in the ledger's `runtime_loads` table now (§4). `readerOf` only opens a `path` ending in
  `.sqlite`, so the old call silently got an empty view every time, meaning a peer kernel's cooldown was
  invisible. Passes the already-open ledger handle (`ledger:journal`) directly instead.
- **`staleLeaseProof`/`unsettledGenerationJobs` called methods `inspectLedger`'s handle doesn't have.**
  `inspectLedger` (§3) only exposes `{liveRows,workflows,eventsHead,verifyChain}` beyond `db` — no
  `getJob`/`listJobs` (those are `openLedger`-only conveniences). Both functions called them anyway
  (`ledger.getJob(...)`, `ledger.listJobs()`), throwing `TypeError: ledger.listJobs is not a function`.
  Queried the rows directly off `ledger.db` instead.
- **`reserveTwoPhase`'s machine-capacity failure dropped its reason.** On success paths `reserveTwoPhase`
  returns `{ok:false,reason:...,reasons:[...]}`, but on the specific path where a machine-side (`ai/*`)
  reservation itself fails, it returns `{ok:false,reason:...}` with no `reasons` array. Every caller in
  this codebase (`job-bridge.mjs`, `engine.mjs`'s `deferJob`) treats `reasons` as *the* informative field,
  so that path silently fell back to a bare "waiting for job X" with the real cause dropped.
  `admission.mjs`'s `reserve()` now normalizes: `reasons:result.reasons??(result.reason?[result.reason]:[])`.
- **`ledgerIdOf` crashed `createAdmission` for a non-ledger-db handle.** `kernel/ledger-db.mjs`'s
  `ledgerIdOf(handle)` unconditionally queries a `meta` table; `kernel/journal.mjs`'s (the retired
  module's) own tests still pair `openJournal` directly with `createAdmission`, and that handle has no
  `meta` table at all, so `createAdmission` itself threw `no such table: meta` before doing anything.
  `admission.mjs`'s local `ledgerIdOf` wrapper now catches that and falls back to `handle.ledgerId` (`null`
  for a non-ledger-db handle) — `admission.ledgerId` is informational only, nothing keys off it inside this
  module. (This does **not** fix every place a legacy `journal.mjs` handle meets the two-phase primitives —
  see "Not this cluster" below; `reserveTwoPhase` itself has the same unconditional `meta` lookup one level
  deeper, in a function I don't own.)

## A live environment-corruption bug found along the way (not a code fix — a standing hazard)

`kernel/job-bridge.mjs`'s `close()` only closes the ledger handle (`journal.close()`), never the
admission's own machine handle when `createAdmission` opened one itself (i.e. whenever `createJobBridge`
callers don't explicitly pass a pre-opened `machine`, which is every caller today). Every test — and every
real `starci` invocation — that doesn't pass its own isolated `machineFile` falls back to the **real**
`%LOCALAPPDATA%/StarCi/runtime/machine.sqlite`, and its `ai/global` lease (and others) is never released.

I found this because it had **already exhausted** that shared file's `ai/global` capacity (10/10 leased,
permanently) from earlier test/dev activity on this machine, which was silently causing unrelated-looking
`admission.reserve` failures in tests that don't isolate `machineFile`. I deleted the polluted
`machine.sqlite`/`-wal`/`-shm` to unblock my own verification (a pure dev-machine cache file, safe to
regenerate), but **the leak itself is still there** and will re-corrupt it the next time anything runs a
test or command that doesn't pass an isolated `machineFile` through to `createJobBridge`. This isn't
hypothetical — it's the single largest cause of "unrelated" `admission.reserve` failures anyone will hit
running this suite on a machine that's exercised the kernel before. See the diff below.

I also went back through `tests/engine-adapter.spec.mjs` (my file) and made sure every `createJobBridge`
call passes its own `machineFile` — two tests didn't and were falling back to the shared global file
themselves; fixed as part of this cluster's commit, independent of the job-bridge.mjs fix below.

## Requests to other streams (verified, not guesses — see "Summary")

### `kernel/job-bridge.mjs` — `close()` leaks the machine handle (see above, high severity)

```diff
- close(){journal.close();}};
+ close(){journal.close();admission.close();}};
```

`admission.close()` (admission.mjs) already checks `ownsMachine` internally and is a no-op if the bridge's
caller passed its own `machine` handle — this is safe to add unconditionally.

### `kernel/jobs.mjs` — `complete()`'s hand-rolled event insert has the same NOT-NULL-swallowed-by-OR-IGNORE bug as the one I fixed in engine.mjs

```diff
-        db.prepare('INSERT INTO events(event_id,workflow_id,entity_type,entity_id,generation,kind,payload_json,created_at) VALUES(?,?,?,?,?,?,?,?)').run(eventId,workflowId,'job',jobId,generation,`job-${status}`,JSON.stringify({opId,attempt,result}),at);
+        journal.appendEvent({eventId,workflowId,entityType:'job',entityId:jobId,generation,kind:`job-${status}`,payload:{opId,attempt,result},createdAt:at});
```

This one is a plain `INSERT` (not `OR IGNORE`), so unlike the engine.mjs case it doesn't fail silently —
it throws `NOT NULL constraint failed: events.digest` and aborts the whole `journal.transaction`, which is
why it's the single largest failure class in `tests/engine-adapter.spec.mjs` (15 of ~44) and shows up
throughout `tests/kernel-engine.spec.mjs` too: **every** `jobs.complete()` call fails, i.e. every durable
job settlement in the whole 1.0.4 kernel. `journal.appendEvent` is safe to call from inside
`jobs.complete()`'s existing `journal.transaction(db=>{...})` callback (it only runs prepared statements
against the same `db`, no nested transaction).

`jobs.complete()` also still doesn't release a settled job's `machine_ref` leases at all (a separate,
narrower gap — repeats §6's "release" for the ledger side but never calls `machine.release`). I've worked
around this from my own files by reading `machine_ref` before calling `jobs.complete()` and releasing
after (see `kernel/engine.mjs`'s `settleJob`/`completeSettled` helpers, and the equivalent in
`kernel/job-worker.mjs`, both wave-1 work), but any caller of `jobs.complete()` outside those two files
still leaks.

## Full-suite number, and why it's below the wave's 1922/296/6 starting point on `main`

This branch's full-suite total (2002) is *lower* than the count implied by the assignment's baseline on
`main` (1922+296+6=2224) — i.e. ~222 fewer tests got enumerated at all, while the fail count is higher.
That shape (fewer total, more failing) is the signature of whole spec files crashing at **import time**
rather than at individual assertions — a file that fails to load counts as one failing "test" no matter
how many `test(...)` calls it would have registered. I confirmed this is exactly what's happening and that
none of it is downstream of anything in this commit:

- `scripts/ledger-migrate.mjs:6` does `import {journalFileFor} from '../kernel/engine.mjs'` — that export
  was deliberately removed from `engine.mjs` (docs §8: "`journalFileFor` is deleted from engine.mjs — s7's
  migrator imports it from `journal.mjs`"). This file imports it from the wrong module; every test that
  transitively imports `scripts/ledger-migrate.mjs` fails to load with
  `SyntaxError: The requested module '../kernel/engine.mjs' does not provide an export named
  'journalFileFor'`. Not a file I own or touched — it's the migration stream's script, and the fix is a
  one-line import-source change (`./journal.mjs` instead of `./engine.mjs`), per the contract's own stated
  design.
- `tests/runtime-allocator.spec.mjs:56,62,63` calls a `loadsFile(root)` that `kernel/loads.mjs` has never
  exported (only `loadsFileFor` exists, and per its own comment it's retired/dead) — every test in that
  file fails to load with `SyntaxError: ... does not provide an export named 'loadsFile'`. Not a file I
  touched; `kernel/loads.mjs` is unmodified by this commit.
- The rest of the 458 is dominated by the same handful of cross-stream root causes already itemized above
  (`kernel/jobs.mjs`'s digest bug touches essentially every job settlement in the whole suite,
  `kernel/job-bridge.mjs`'s handle leak causes cascading `EPERM`s and — worse — cross-test `admission.reserve`
  failures via the shared machine.sqlite exhaustion described above, `kernel/ledger-db.mjs`'s
  `reserveTwoPhase`/`inspectLedger` unconditional `meta` lookups, `kernel/store.mjs`'s `bindJournal`
  contract). I did not attribute all 458 line-by-line — that's more than this cluster's scope covers — but
  spot-checked broadly enough (every failure this cluster's own 5 named specs surfaced) to be confident none
  of it traces back to `kernel/engine.mjs` or `kernel/admission.mjs` after this commit.
