## Root causes found and fixed

- **`kernel/launch.mjs` — `closeStaleCoordinatorTerminals` had two real bugs**, both from its port off the
  file-based `kernel/coordinator-terminals.mjs` in an earlier session:
  1. A terminal `known` (Orca's current terminal list) no longer names was left sitting in the ledger's
     `open` record forever — never closed, never dropped. The pre-1.0.4 module's behavior (and the
     coordinator-terminals suite's own assertions) is the opposite: a terminal nobody lists any more is
     dropped from the record as "already gone," with no `close()` call spent on it.
  2. Its `closed` return had regressed from `{terminal,reason}` objects to bare strings. A caller — my own
     `kernel/terminals.mjs` and the coordinator-terminals suite — needs the `reason` to tell "we actually
     closed a live tab" from "we noticed it was already gone," and `kernel/supervisor.mjs`'s
     `stale-kernel-terminals-closed` log event expects `.terminal` on each entry.
  Both are fixed in the function itself (docstring updated to say so); every caller inside my cluster
  already matched the corrected shape once I checked them (see below), so no other call site needed
  changing.
- **`kernel/terminals.mjs` — `writeLastWordsReport` still called the removed `store.reportPath()` +
  `fs.writeFileSync`** (docs §8: `reportPath` is removed). Ported to
  `store.writeReport({dispatchId,opId,attempt,report,fromTerminal})`, the same call `kernel.mjs`'s own
  `settleFromTab` already makes. Dropped the now-unused `fs` import.
- **`kernel/terminals.mjs` — `sweepStaleTerminals` lost a filter during the same port**: the pre-1.0.4
  version excluded `reason==='coordinator terminal already gone'` entries from what it reports as swept
  (an "already gone" terminal wasn't closed by this sweep, it was already gone before the sweep started).
  The migrated version pushed every entry unconditionally. Restored the filter.
- **`kernel/coordinator-terminals.mjs` retired** (deleted, and removed from `scripts/runtime-modules.txt`):
  nothing imports it any more now that `kernel/terminals.mjs` is ledger-backed. Its only remaining importer
  was `tests/coordinator-terminals.spec.mjs`, rewritten below.
- **`kernel/startup-lock.mjs` NOT retired.** `tests/workflow-amendment.spec.mjs` still imports it
  (`acquireStartup`, `reserveStartup`), and that file is outside this cluster (its primary subjects are
  `kernel/amendment.mjs` and `kernel/kernel.mjs`, neither of mine). Checked whether it's safe to retire
  anyway: **no** — `tests/workflow-amendment.spec.mjs` currently fails 13/13, but for an entirely unrelated
  reason (`store-paths-removed:final` — its own `fixture()` helper still uses `kernel/store.mjs`'s removed
  `store.paths.*`, §8). Retiring `startup-lock.mjs` would swap that diagnostic for a `Cannot find module`
  at import time, hiding the real cause from whoever picks that file up, for zero gain (it's already 0/13).
  `tests/startup-lock.spec.mjs` (4/4, tests only `kernel/startup-lock.mjs` itself, in isolation) is left
  alone for the same reason: nothing is broken by leaving a dead-but-passing module and its test in place
  until its last real importer is gone.

## Test fixes (fixtures brought to the current, correct 1.0.4 shape)

- **`tests/runtime-allocator.spec.mjs`** — failed to load at all: `loadsFile` is not exported by
  `kernel/loads.mjs` any more (by design — there is no single "the loads file" under the ledger model, only
  `runtime_loads` rows in `.starciwork/runtime.sqlite`). Rewrote its `sharedRoot()` fixture to build a real
  ledger via `ledgerFileFor`/`openLedger` and drive it directly through the `runtime_loads` table and the
  `kernel-lock` signal, instead of a bare `runtime-loads.json` + per-workflow `kernel.lock` files. Removed
  two assertions of retired behavior: a per-workflow-directory `loadsFileFor(...)` resolving to one shared
  file (no such per-workflow resolution exists any more — the ledger lives at one fixed repo-root path), and
  an external `${file}.lock` file (SQLite's own transaction locking replaces it; the test's substantive claim
  — that two kernels writing don't lose either other's update — is still asserted, just not through a lock
  file's absence). One incidental fix: `local.allocate(...).preferredOver` is `undefined`, not `[]`, when
  there is no shared ledger at all (`kernel/schedule.mjs` only includes that key when it has one) — the old
  assertion assumed `[]`; corrected to match `kernel/schedule.mjs`'s actual (unowned, unchanged) behavior.
  **32/37 pass.** The other 5 are the pre-existing `model/runtimes.yaml` pool-cap drift from commit
  `88463e1b` (`codex-agent` `maxParallel: 10` vs the tests' assumed `8`, and `implement`/`write` now modeled
  on `gpt-5.6-luna` instead of `gpt-5.6-sol`) — confirmed by inspecting `model/runtimes.yaml` directly.
  Nothing to do with `kernel/loads.mjs`; not touched.
- **`tests/coordinator-terminals.spec.mjs`** — rewritten end to end against `kernel/launch.mjs`'s
  ledger-backed functions (`openLedger`/`ledgerFileFor`, `recordCoordinatorTerminal`,
  `closeStaleCoordinatorTerminals`, `readCoordinatorTerminals`, `readClosedCoordinatorTerminals`,
  `reserveStartup`, `bindStartupTerminal`) and a minimal store stub carrying `.ledger`/`.ledgerFile` (what
  `sweepStaleTerminals`/`startKernel` actually read of it) instead of a bare `.dir`. Two sibling-workflow
  tests needed one addition the old fixture didn't: `siblingKernelGone` reads the sibling's latest
  `state_snapshots` row, so a workflow the ledger has never heard of reads as "not this kernel's to judge"
  and its tabs are left alone regardless of any startup reservation — added a small `seedSiblingState` helper
  (`ensureWorkflow` + one `state_snapshots` insert) to give the sibling a known, unfinished state, matching
  what the old fixture's `state.json` file did. **8/8 pass.**
- **`tests/kernel-seams.spec.mjs`** — its local `stubStore` fixture predates `kernel/store.mjs`'s migration
  and had no `writeChecks` (docs §8); `kernel/kernel.mjs`'s `applyOpReport` calls it directly now. Added a
  minimal `writeChecks({opId,attempt})` (nothing in this file inspects what was written, only that the call
  doesn't throw and the surrounding events/state still land right). Two other tests built `state.engine` with
  the retired `journalFile` field and no `candidateRoot`; `releaseSettledOperationLeases` (docs: gates on
  `state.engine.ledgerFile`, not `journalFile`) and `sweepSettledCandidates`'s `candidateBaseFor` (reads
  `state.engine.candidateRoot`, falling back through `machineFile`/the real machine.sqlite location — never
  `journalFile`) were both correctly failing closed / resolving to the wrong directory against the stale
  fixture; neither function has a bug. Updated both tests' `state.engine` to `ledgerFile`/`candidateRoot`.
  **38/38 pass.** (Neither `kernel/kernel.mjs` nor `kernel/engine.mjs` was touched — both are outside this
  cluster; only the test fixtures changed.)
- **`tests/launch.spec.mjs`** (this stream's own, from wave 1) — one test asserted the old, wrong bare-string
  `closed` shape from `closeStaleCoordinatorTerminals`; corrected to `{terminal,reason}` once the function
  itself was fixed. Caught by re-running this stream's full owned suite after the launch.mjs fix, not by the
  wave-2 task's named list.
