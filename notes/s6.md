# s6 — CLI, bin, hosts: verbs over the ledger (runtime 1.0.4 §9)

## Contract addendum picked up mid-stream (commit `826894e5` on `main`, merged)

The lead landed §12 (the tracked `.starciwork/ledger-anchor.json` head) plus identity/WAL hardening in
§§2-6, and routed this stream three pieces of it directly: `ledger-verify` also verifies the anchor per
workflow and reports the named refusals; a new `ledger-anchor --write` verb regenerates the anchor from a
healthy ledger; `workflow-export` checkpoints (`wal_checkpoint(TRUNCATE)`) before it reads. All three are
implemented in `hosts/orca/launch.mjs` (below) and covered by five new cases in
`tests/cli-ledger-commands.spec.mjs`. One reading choice, since it touches a file this stream does not
own: §3's `ledgerIdOf(handle)`/`meta.ledger_id` (a minted UUID, immune to a rename/junction/UNC) has not
landed in `kernel/ledger-db.mjs` on this branch yet (only the docs commit did; `git diff` against
`starci183/s0-ledger-db` confirms the module is still the old `ledgerIdFor=sha256(realpath(file))`
shape, with no `meta` table). The anchor's `ledgerId` field and its `ledger-identity-mismatch` check are
built against the identity function that actually exists now (`ledgerIdFor`), not the not-yet-landed
`ledgerIdOf` — changes the fewest files, and the anchor's own JSON shape (`{schema,ledgerId,updatedAt,
workflows}`) does not change either way. **Once s0 lands `ledgerIdOf`/`meta`, swap the one `ledgerIdFor`
call in each of `writeAnchor`/the `ledger-verify` block for it** — everything downstream (the anchor file
shape, the mismatch check, the tests) stays the same, since a path-derived id is strictly a worse identity
than a minted one, never a different comparison shape.

## Files changed

- `hosts/orca/launch.mjs` — four new verbs and a rename, all reading/writing the ledger directly (no
  kernel, no Orca runner needed for any of them):
  - `op-contract --workflow <id> --op <op> [--attempt N] [--dispatch <id>] [--json true]`: prints
    `store.readContract(op,attempt)`'s markdown (or `{markdown,context}` with `--json`). `--attempt`
    omitted reads the latest attempt. `--dispatch`, when given, must match the contract's own
    `dispatchId` (or the contract must carry none yet) — a worker cannot read another dispatch's
    contract; refused by name, not silently served.
  - `workflow-export --id <id> --to <dir>`: calls `store.exportTo(dir)`, returns `{dir,files}`.
  - `ledger-verify --repo <root> [--id <id>]`: opens the ledger read-only (`inspectLedger`) and calls
    its `verifyChain({workflowId})` for the named workflow, or every workflow the ledger holds when
    `--id` is omitted. `ok:false` the moment one chain is broken, with `brokenAt` (the seq) per result.
  - `ledger-migrate --repo <root> [--journal-file <f>] [--machine-file <f>] [--dry-run] [--archive true]`:
    dynamic `import('../../scripts/ledger-migrate.mjs')` (per contract: "import by path; if it is not
    there yet, forward and let the missing module error name it") then calls `migrateLedger(...)`.
  - `ledger-prune`/`ledger-retire` (renamed from `journal-prune`/`journal-retire`, `--repo <root>`
    instead of `--journal-file`/`--store-root`): 1.0.4 has **one ledger per repository**, not a shared
    journal multiple store roots point into, so the old `--store-root` cross-referencing is gone.
    `ledger-prune` retires every workflow the ledger's own `workflows.finished_json` (or `--retire`)
    proves settled and has no live lease/job; `ledger-retire` removes the whole `runtime.sqlite` only
    when nothing in it is live and it has been quiet for 30 min, `--delete true` to actually remove it.
    Implemented directly against `kernel/ledger-db.mjs`'s `openLedger`/`inspectLedger` handles
    (`.workflows()`, `.retireWorkflow()`) — `kernel/journal-maintenance.mjs` (not owned by this stream)
    is no longer called from here and is now dead code from the CLI's side; see open questions.
  - The two old names are kept in the command table and refused with a one-line pointer to the new
    name and `exitCode:2` (not a thrown error) — `main()`'s two entry points (`bin/starci.mjs`'s
    forwarding block, and this file's own direct-run block) now honor a numeric `output.exitCode`
    before falling back to the `output.ok===false → 1` rule they already had.
  - `ledger-anchor --write --repo <root> [--id <id>]` (§12 addendum): regenerates
    `.starciwork/ledger-anchor.json` from a healthy ledger — one workflow with `--id`, every workflow
    otherwise. A workflow whose `verifyChain` does not pass is refused (`ledger-chain-broken`) and left
    out of the written anchor, never anchored on a guess. `--write` joins `--dry-run` as a bare boolean
    flag in `parseArgs`.
  - `ledger-verify` now also checks each workflow's `events`/`state_snapshots` against its
    `ledger-anchor.json` entry (§12): no anchor entry yet is fine (`{ok:true,checked:false}` — the
    ledger running ahead of its anchor is normal); the anchored `eventsHead` missing at its `seq`, or no
    `state_snapshots` row at or after its `generation`, is `ledger-behind-anchor`; a different
    `ledgerId` on the anchor is `ledger-identity-mismatch`; the ledger file itself gone while an anchor
    is still tracked is `ledger-missing` (returned as a structured result, not a thrown error — the
    named recovery per §12 is restoring a backup or `ledger-migrate`, never a silent fresh start). `ok`
    is now `chain.ok && anchor.ok` for every requested workflow.
  - `workflow-export` runs `store.ledger.db.exec('PRAGMA wal_checkpoint(TRUNCATE)')` before
    `store.exportTo(dir)` (§3: "every copy... runs `wal_checkpoint(TRUNCATE)` first"). Verified empirically
    that the pragma is a harmless no-op on the DELETE-mode handle this branch's `kernel/ledger-db.mjs`
    still opens by default (`{busy:0,log:-1,checkpointed:-1}`), so this is forward-compatible with s0's
    not-yet-landed WAL-by-default change without needing to branch on journal mode here.
  - `usage()` documents all seven verbs and the rename.
- `bin/starci.mjs` — `LAUNCHER_COMMANDS` gained `op-contract`, `workflow-export`, `ledger-verify`,
  `ledger-anchor`, `ledger-migrate`, `ledger-prune`, `ledger-retire` (kept `journal-prune`/`journal-retire`
  so they still reach the redirect instead of falling through to "Unknown command"); `KERNEL_HELP`
  documents them; exit-code handling mirrors launch.mjs's.
- `cli/main.mjs` — its own `help` text (asserted 1:1 against `bin/starci.mjs`'s `LAUNCHER_COMMANDS` by
  `tests/cli.spec.mjs`) gained one line per new verb plus the two renamed-old-name lines.
- `tests/cli.spec.mjs` — updated the `forwarded`/`declared` help-list assertion for the seven added names.
- `tests/cli-ledger-commands.spec.mjs` (new) — the seven verbs, exercised through `launch.mjs`'s `main()`
  directly (as `tests/orca-supervised-launch.spec.mjs` does): contract printing/JSON/dispatch-ownership
  refusal, export file layout, verify's hash-chain break (tampers a row the way `tests/ledger-db.spec.mjs`
  does) and per-workflow scoping, migrate's forwarding, prune/retire against live vs. settled rows, the
  `journal-*` redirect + exit 2, `ledger-anchor --write` (regenerate, and refuse a broken chain rather
  than anchor it), and the anchor side of `ledger-verify` (ahead-is-fine, `ledger-behind-anchor` via a
  simulated truncated restore, `ledger-missing` via a deleted ledger file with the anchor kept, and
  `ledger-identity-mismatch` via a hand-written anchor naming a different ledger).

## Known fallout in files this stream does not own (not fixed here)

- `kernel/kernel.mjs` (`kernelMain`, used by every `KERNEL_COMMANDS` verb: `workflow-run`,
  `workflow-approve`, `workflow-status`, `workflow-answer`, `workflow-amend`, `workflow-stop`, …) still
  reads `store.dir`, `store.paths.*`, `store.reportPath`/`contractPath`/`checksPath` in dozens of call
  sites (grepped: lines 142, 353, 355, 476, 665, 779-781, 1618, 1871, 2290-2322, 2426-2428, 2544-2561,
  3095-3096, 3221, 3860, 4179, 4289-4361, 4443-4476, and more). Every one of those now throws
  `store-paths-removed:<name>` against the merged `kernel/store.mjs`. This is squarely "s3 (kernel.mjs)"
  per `notes/s1.md`'s own routing ("s3 (kernel.mjs)/s6 (cli): reports.consumed_at…") and is out of this
  stream's owned files (`kernel/**`). Until s3 lands, `workflow-status`/`workflow-tail`/`workflow-ops`/
  `workflow-stop`/`workflow-answer`/`workflow-amend`/`workflow-run`/etc. are not exercisable end to end,
  and neither is `report`/`wait` if they route through kernel-held state — but the flags and wiring for
  all of them were already in place before this stream started and are untouched here (§8 says the
  store's *exported surface* is kept, so no call-site signature changed; only the backing broke).
- `kernel/view.mjs` (`buildView`, `buildList`, `buildOpsView`, `readWorkflowEvents`) still takes a
  filesystem `dir` and reads `events.jsonl`/`state.json` off disk; under the ledger `store.dir` is
  `null` and there is no such directory. Same routing question as above — not kernel/kernel.mjs but
  still `kernel/**`, still not owned by this stream.
- Both of the above are why this stream did **not** touch the `report` verb
  (`hosts/orca/protocol.mjs`'s `reportOutcome`), despite the contract listing it under this stream's
  deliverables ("`report` verb: writes `reports` via the store"). `reportOutcome` currently writes
  through `kernel/reports.mjs`'s file-based `reportPath`/`reportsDirectory`/`buildReport` (not owned by
  this stream), and it is keyed by `--run` (the Orca Run id), never `--workflow`/`--id` — but the
  ledger's `reports` table is keyed by `workflow_id`. There is no documented run→workflow_id mapping in
  `docs/ledger-db.md` or `notes/s1.md`, and guessing one (e.g. treating `--run` as the workflow id, or
  adding a new required flag) would touch a command every other stream's tests call by its current
  flags. Per the contract's own instruction to "pick the reading that changes the fewest other files"
  when a shape is ambiguous, I left `report`/`wait` as they are rather than reshape a heavily-depended-on
  verb on a guess. **Open question for the lead below.**

## Open questions

1. **`report`'s workflow identity.** `starci report --run <run> --dispatch <dispatch> ...` has no
   `--workflow`/`--id` flag today, but the ledger's `reports` table is `FOREIGN KEY workflow_id`. Is
   `--run` meant to *become* the workflow id (kernel launches nested Runs 1:1 per workflow already, so
   this may already hold in practice), or does `report` need a new flag the kernel passes through? I did
   not guess; `hosts/orca/protocol.mjs`'s `reportOutcome` is unchanged pending this answer.
2. **The blanket `_local` grep (§11).** `grep -rn "_local" kernel/ cli/ bin/ hosts/` is specified to
   return only `ledger-migrate`/`workflow-export`/docs, but this stream's owned files carry two
   unrelated, pre-existing `_local` usages that are a different feature entirely (the "Work v3"
   file-tree workspace system in `cli/main.mjs` — `init`/`audit-legacy`'s `_local`/`_workflows`
   exclusions — and `bin/starci-skills.mjs`'s installer path filters), not the 1.0.4 workflow-kernel
   ledger this contract is about. I left both alone: ripping out an unrelated, working feature's own
   directory convention to satisfy a literal repo-wide grep seemed like exactly the kind of invented
   reinterpretation the contract says not to do. Picked the reading that changes nothing there; flagging
   for the lead to confirm the grep is scoped to the workflow-kernel `_local/workflows` subtree in
   intent, not literal.
3. **`hosts/headless/host.mjs`'s `headlessRoot()` fallback.** Its last-resort root (before `--root`, a
   bound store dir, `STARCI_HEADLESS_ROOT`, or `--reports-dir` are known) is still
   `<repo>/.starciwork/_local/headless` — scratch space for the headless host's own table/mailbox/logs,
   not workflow *state*, but still a `_local` write from a file this stream owns, which the strict rule
   reads as a violation. I did not change it: `tests/orca-headless.spec.mjs` (not owned by this stream)
   asserts on that exact path (`headlessRoot({cwd,env:{}}).endsWith(path.join('.starciwork','_local','headless'))`,
   line ~373), and changing the fallback without being able to update that test would trade one failure
   for another I cannot fix myself. Flagging for the lead: if this should move (e.g. under
   `os.tmpdir()/starci/headless/<repo-hash>`, matching §9's dispatch-context-file precedent), the test
   needs to move with it — happy to do both once the redirect is confirmed.
4. **`kernel/journal-maintenance.mjs`** is now unreferenced from this stream's files (superseded by the
   ledger-native `pruneLedger`/`retireLedger` in `hosts/orca/launch.mjs`, which need no cross-repo
   `--store-root` concept since 1.0.4 has one ledger per repository). Left the module itself alone
   (`kernel/**`, not owned here); it may be dead code repo-wide now, or another caller still needs it —
   worth a repo-wide grep by the lead before deletion.
