## `tests/w1-reconcile.spec.mjs` — still 0/5, blocked on two bugs outside this stream's files

Added `maxRetries`/`retryDelay` to `gitRepo()`'s own cleanup (matches this stream's other hygiene fixes;
verified it does *not* by itself fix anything here - the underlying leaks are real, not transient). Diagnosed
precisely with a throwaway repro script (never committed) rather than guessing:

- **4 tests**: unchanged from wave 2 - `kernel/continuation.mjs`'s `bindContinuationPath` still writes to
  the removed `store.paths.continuation` setter. The 3-line diff I gave in `notes/w2-s8.md` has not landed.
  Repeating it here since it's still the blocker:
  ```diff
  -    assertContinuationTarget(root,target);store.paths.continuation=target;return target;
  +    assertContinuationTarget(root,target);return target;
     }
     const canonical=path.join(workflows,`${id}.md`);
     assertContinuationTarget(root,canonical);
  -  if(fs.existsSync(canonical)){store.paths.continuation=canonical;return canonical;}
  +  if(fs.existsSync(canonical))return canonical;
     ...
  -  store.paths.continuation=matched.length===1?matched[0]:canonical;assertContinuationTarget(root,store.paths.continuation);return store.paths.continuation;
  +  const bound=matched.length===1?matched[0]:canonical;assertContinuationTarget(root,bound);return bound;
  ```
- **1 test** ("candidate custody lost..."): the `NOT NULL constraint failed: events.digest` bug from
  wave 2 is gone (someone fixed `kernel/jobs.mjs`'s `complete()` - thank you), which let this test's real
  code path run further and surface a **new, high-impact bug**: `kernel/job-bridge.mjs`'s `createJobBridge`
  opens its own `admission` (`createAdmission({journal,machineFile:machinePath,now})`, which internally
  `openMachine`s its own handle since no `machine` option is passed), but the bridge's `close()` only closes
  `journal`:
  ```js
  // kernel/job-bridge.mjs, current:
  return {journal,admission,request,poll(...){...},close(){journal.close();}};
  ```
  Every `createEngineRuntime(...).close()` therefore leaks `admission`'s machine.sqlite handle. Most callers
  never notice because the default `machineFile` (`machineFileFor()`) points at
  `%LOCALAPPDATA%/StarCi/runtime/machine.sqlite`, outside any test's own temp dir, so the leak doesn't block
  *that* test's cleanup - it just accumulates process-wide. This test passes an explicit
  `machineFile` inside its own temp dir (a legitimate, self-contained-test thing to do), which is exactly
  what makes the leak visible as an EPERM on that dir. **I traced the same failure signature to
  `tests/engine-adapter.spec.mjs` (88 EPERM instances in this wave's full run, up from 42 in wave 2) and
  `tests/engine-kernel-flow.spec.mjs` (4) - both set a custom `machineFile` too, so this one-line fix is
  very likely the single largest remaining EPERM contributor in the whole suite.** Exact diff:
  ```diff
  -  return {journal,admission,request,poll(...){...},close(){journal.close();}};
  +  return {journal,admission,request,poll(...){...},close(){admission.close();journal.close();}};
  ```
  (`admission.close()` already exists and does the right thing: `close(){if(ownsMachine)machine.close();}`
  in `kernel/admission.mjs` - `ownsMachine` is `true` here since `createJobBridge` never passes its own
  `machine` handle into `createAdmission`.)

Neither file is in this stream's list; both diffs are written here per this wave's instruction rather than
applied.
