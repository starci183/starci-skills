# w2-s4 — continuation boundary / candidate bridge, wave 2

## Cluster

`kernel/continuation.mjs` and `kernel/candidate-bridge.mjs` — the `store.dir`/`store.paths` null-path
family ("The paths[0] argument must be of type string. Received null" / "path ... Received null").

## Root-cause fixes made (my files)

`kernel/store.mjs` (merged from wave 1, now `store.dir=null` and `store.paths` is a proxy that throws on
every access) removed three things `kernel/continuation.mjs` still read/wrote:

- `bindContinuationPath`/`continuationPath` wrote `store.paths.continuation=…` as a side-channel cache of the
  resolved path (canonical or a "friendly" alternate). No caller reads it back that way any more — `kernel.mjs`
  reads the fixed `store.continuation` property directly (see `runtimeManagedFiles()` and the
  `workflow-run`/resume-boundary error text) — so the fix is to stop writing it and just return the resolved
  path locally, which is what every caller already used.
- `buildContinuationBrief` read `store.paths.state` for a "Projected state" row. There is no projected state
  file any more (§8: `saveState`/`loadState` are ledger-only, `project()` is removed) — removed the row rather
  than inventing a path that doesn't exist.
- `buildContinuationBrief` read `store.paths.final` to point an operator at the final report file. The final
  report is a ledger row now (`signals` key `'final-report'`, written by `kernel.mjs:3106`,
  `store.signal.set(store.id,'final-report',{value:final})`), so the replacement is
  `store.signal?.get?.(store.id,'final-report')?.value` — a ledger read, guarded with optional chaining so a
  minimal test double without `.signal` still works.
- `buildContinuationBrief`'s "Durable ledger" row now falls back to `store.ledgerFile` when `ledgerView.file`
  is null (first boot, no ledger file yet), instead of only ever reading the (removed) `store.paths.state`.

Test fixtures in `tests/workflow-continuation.spec.mjs` updated to match: `store.paths.continuation` →
`store.continuation` (2 tests), and `t.after` hooks now call `store.close()` before `fs.rmSync` on the temp
dir — `createStore` now opens a real WAL-mode sqlite handle, and Windows refuses to delete a directory that
still has an open handle under it (`EPERM`) if the handle isn't closed first.

## Found while verifying, but NOT in my files — request to whoever owns kernel.mjs

`kernel/kernel.mjs:1621-1628`, `withAnchorVerified`:

```js
const withAnchorVerified=(boundary,store,state)=>{
  if(typeof ledgerDb.verifyAnchor!=='function')return boundary;
  let anchor;
  try{anchor=ledgerDb.verifyAnchor(store.ledger,{workflowId:state.id});}
  ...
```

`ledgerDb.verifyAnchor`'s real signature (`kernel/ledger-db.mjs`, docs §12) is `verifyAnchor(ledger, repoRoot)`
— the second argument is the **repo root string**, not an options object. Passing `{workflowId:state.id}`
means `verifyAnchor` calls `readAnchor(repoRoot)` → `anchorFileFor(repoRoot)` →
`path.join(repoRoot,'.starciwork','ledger-anchor.json')` with `repoRoot` bound to that object, which throws
`TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received an instance of Object`
inside `path.join`. `withAnchorVerified`'s own `catch` turns that into a **finding**, not a re-thrown crash, so
it doesn't look like an exception at the call site — it surfaces as a boundary finding with
`code:'ledger-behind-anchor'` (the catch-all default in the `code` ternary, since the caught error's `.code` is
`undefined`, not one of the three real anchor reasons) and `detail` equal to the raw TypeError message. Every
`reconcileContinuationPreflight`/`workflow-run` resume-boundary check after the **first** `store.saveState()`
call for a repo hits this (an anchor file exists as soon as one checkpoint has been written), so this is not a
narrow edge case.

**Fix**: pass the repo root, not an options object:

```diff
-  try{anchor=ledgerDb.verifyAnchor(store.ledger,{workflowId:state.id});}
+  try{anchor=ledgerDb.verifyAnchor(store.ledger,store.repoRoot);}
```

`store.repoRoot` is already the field `verifyAnchor`'s second parameter wants (same value
`anchorFileFor`/`ledgerFileFor` are joined against in `kernel/ledger-db.mjs` and in my own
`kernel/continuation.mjs`'s `readLedger`/`anchorRepoRoot`). No other change is needed — `verifyAnchor`
already returns `{ok:false,reason,workflowId}` shaped exactly for the three real §12 codes, so the `code`
ternary and `detail` fallback in `withAnchorVerified` still work once the call itself stops throwing.

I did not make this edit: `kernel/kernel.mjs` is not in my owned cluster.

## Second bug found while verifying, also not in my files — request to whoever owns kernel/jobs.mjs

After patching the above locally (scratch only, reverted) to isolate it, a second, more consequential bug
surfaced underneath it. `kernel/jobs.mjs:35`, `createJobs(...).complete(...)`:

```js
db.prepare('INSERT INTO events(event_id,workflow_id,entity_type,entity_id,generation,kind,payload_json,created_at) VALUES(?,?,?,?,?,?,?,?)')
  .run(eventId,workflowId,'job',jobId,generation,`job-${status}`,JSON.stringify({opId,attempt,result}),at);
```

This raw INSERT never supplies `prev_digest`/`digest`, but `docs/ledger-db.md` §4's `events` table has
`digest TEXT NOT NULL` (the hash-chain link every row must carry). Every call to `jobs.complete(...)` — i.e.
every job settlement, success, failure or cancellation anywhere in the kernel — throws
`SqliteError: NOT NULL constraint failed: events.digest` inside the surrounding `journal.transaction(...)`,
which rolls the whole transaction back. The caller (`releaseSettledOperationLeases` in `kernel/kernel.mjs`,
and anywhere else that calls `settleJob`/`jobs.complete`) catches the thrown error and records it as a mundane
per-op refusal (`op.leaseReleaseRefused`), so nothing crashes visibly — a settled job's lease and status
update simply never commit, silently, every time. I found this by instrumenting a scratch reproduction (not
committed) of `reconcileContinuationPreflight`'s job-release path and reading the persisted
`op.leaseReleaseRefused` field it left behind: `"NOT NULL constraint failed: events.digest"`.

**Fix**: use the ledger handle's own `appendEvent`, which already computes `prev_digest`/`digest` correctly
(same helper `kernel/store.mjs` uses), instead of a raw INSERT. `journal` in this closure is the full
`openLedger(...)` handle (confirmed via its caller, `settleGenerationLeases` in `kernel/engine.mjs`, which
passes `pair.ledger` from `openPair`), so `journal.appendEvent` is already in scope and safe to call from
inside `journal.transaction(db=>{…})` — `appendEvent` does its own `db.prepare(...).run(...)` without opening
a nested transaction:

```diff
-        db.prepare('INSERT INTO events(event_id,workflow_id,entity_type,entity_id,generation,kind,payload_json,created_at) VALUES(?,?,?,?,?,?,?,?)').run(eventId,workflowId,'job',jobId,generation,`job-${status}`,JSON.stringify({opId,attempt,result}),at);
+        journal.appendEvent({eventId,workflowId,entityType:'job',entityId:jobId,generation,kind:`job-${status}`,payload:{opId,attempt,result},createdAt:at});
```

I did not make this edit: `kernel/jobs.mjs` is not in my owned cluster.

## Third bug found while verifying, also not in my files — request to whoever owns kernel/engine.mjs

`kernel/engine.mjs:84-91`, `staleLeaseProof(...)`:

```js
export function staleLeaseProof({ledgerFile,journalFile,lease}={}){
  const file=ledgerFile??journalFile;
  if(!file||!fs.existsSync(file)||!lease?.jobId)return null;
  const ledger=inspectLedger({file});
  try{
    const job=ledger.getJob(lease.jobId);
    ...
```

`inspectLedger` (`kernel/ledger-db.mjs`, §3: "Read-only, no migration, what an operator inspection and the
candidate bridge use") returns a narrower handle than `openLedger` — it exposes
`{schema,file,path,db,readOnly,ledgerId,version,liveRows,workflows,eventsHead,verifyChain,close}`, **not**
`getJob`/`listJobs` (those only exist on the read-write `openLedger` handle, per `kernel/ledger-db.mjs`'s own
source). My own `kernel/candidate-bridge.mjs` follows this correctly everywhere it calls `inspectLedger` — it
always queries `ledger.db.prepare(...)` directly, never a high-level convenience method. `staleLeaseProof`
instead calls `ledger.getJob(lease.jobId)`, which throws `TypeError: ledger.getJob is not a function` the
first time it runs against a real `inspectLedger` handle (as opposed to a full `openLedger` one it may have
been written/tested against). This is called from `kernel/kernel.mjs`'s `workflow-retry` handler
(`staleLeaseProof({journalFile:state.engine?.journalFile,lease:op.lease})` for every op with a lease), so any
retry on a workflow with at least one leased op hits it.

**Fix**: query the row directly, matching the read-only-handle convention used everywhere else against
`inspectLedger`:

```diff
-    const job=ledger.getJob(lease.jobId);
+    const job=ledger.db.prepare('SELECT * FROM jobs WHERE job_id=?').get(lease.jobId);
```

(Only `job.status` is read afterward, so the raw row is sufficient — no need for the `payload`/`result` JSON
parsing `getJob`'s wrapper does on the read-write handle.)

I did not make this edit: `kernel/engine.mjs` is not in my owned cluster.

## What this blocks in my named specs

With all three bugs above still live, four tests in `tests/workflow-continuation.spec.mjs` that exercise
`kernelMain('workflow-run'|'workflow-retry', …)` on a workflow that has already called `store.saveState()`
once cannot pass no matter what I do to `continuation.mjs`/`candidate-bridge.mjs` — every crash happens inside
files I don't own, before or underneath my boundary code's own (correct) result:

- `public same-ID stop, run recovery and retry use a real journal without discarding unknown or staged work`
  — blocked on bug 1 (`kernel.mjs:1624`).
- `public retry durably stages same-generation late-report recovery before its early return` — blocked on
  bug 3 (`engine.mjs:86`, reached via `workflow-retry`'s stale-lease check before bug 1's path).
- `public retry re-admits a completed report without replacing its candidate writer or model attempt` —
  same, bug 3.
- `public stop, valid-pin retry and pinned same-ID run preserve accepted history while completing remaining
  work` — blocked on bug 1 first; would very likely also hit bug 2 once past it, since it drives real
  operation settlement through `jobs.complete`.

I ported all four fixtures off the retired `journalFile`/`openJournal(journal.mjs)`/`store.reportPath`/
`store.dir` shape onto `ledgerFile`/`openLedger`/`store.writeReport`/`store.signal` (real replacements, same
pattern as the rest of this cluster) so that once the three fixes above land, these tests exercise the real
1.0.4 path end to end. I did not weaken any assertion or change what they expect, with one exception I want to
flag explicitly rather than bury: in "public retry durably stages same-generation late-report recovery…" the
original fixture wrote a stale `state.json` after the retry call and asserted a fresh read still showed the
pre-recovery pin digest, to prove `reconcileContinuationPreflight` upgrades a lagging on-disk projection. That
projection doesn't exist any more (§8: `saveState`/`loadState` are ledger-only, `project()` removed; the
retry's own early return already durably saves the adopted pin before returning), so there is no longer a
"stale cache" state for that step to construct — I removed the stale-write step and changed that one
`assert.equal(reloaded.engine.runtimePin.digest, …)` to the value that's honestly there (`pin.digest`, not
`'a'.repeat(64)`) immediately after retry, keeping the rest of the assertions (late-report identity
re-derivation, lease/candidate/terminal continuity) unchanged. That is a narrowing of what the fixture
simulates, not a loosening of what it checks — I flag it so whoever reviews this doesn't need to hunt for it.

I confirmed the `withAnchorVerified` fix alone clears the anchor-crash symptom (scratch-patched locally,
reverted, not committed) but could not verify all four pass end-to-end without editing files outside my
cluster, which this wave's contract asks me not to do.
