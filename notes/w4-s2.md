# Wave 4 (final) — s2 cluster: tests/engine-migration.spec.mjs, tests/engine-lifecycle.spec.mjs

## The premise check, as instructed

"Both are about a state carrying journalFile but no ledgerFile being treated as ledger-unmigrated and
failing closed" — checked this against the actual code before touching either file, per the wave's own
instruction. It's **not** what either cluster's remaining failures are about:

- `kernel/common.mjs`'s `predatesEngineSchema` already implements exactly that check
  (`typeof state.engine.journalFile==='string' && typeof state.engine.ledgerFile!=='string'`), and its own
  docstring says so in nearly the same words as §8.
- `kernel/continuation.mjs` and `kernel/kernel.mjs` already consume it correctly for fail-closed behavior
  (`continuation.mjs`: `{ok:false,reason:'ledger-unmigrated',...}`; `kernel.mjs:4900`:
  `need(!predatesEngineSchema(state), ...)` blocking retry).

So this premise, while true of the *contract*, wasn't the cause of any of the six failures the two named
specs actually had. Reading the real errors instead turned up three separate, real bugs — one of which
*is* about `predatesEngineSchema`, just not the direction the premise implied (see below). Fixed what was
mine (both test files, all six failures accounted for), diffed the rest.

## What was fixed (both test files, mine)

### `tests/engine-migration.spec.mjs`

1. **Version literal.** `assert.equal(pkg.version,'1.0.0')` — the real, correctly-reported version is
   `1.0.4` (this is the seal wave). `ENGINE_VERSION` itself was never wrong; only the test's pinned
   literal was stale. Updated to `1.0.4`.

2. **`predatesEngineSchema`'s own contract, inverted.** The test asserted
   `predatesEngineSchema({engine:{schema:ENGINE_SCHEMA,journalFile:'j'}})===false`. Per §8's last
   paragraph *and* the function's own docstring ("a numbered pre-schema marker **or** a state that still
   names the retired journal (journalFile without ledgerFile)"), a schema tag alone does not clear the
   ledger-unmigrated case — the two conditions are independently sufficient, not both required. The real
   code (unchanged, correct) returns `true` here. Fixed the assertion to `true`, and added the missing
   contrasting case (`schema` + `ledgerFile` → `false`) so both arms of the "or" are actually pinned by
   this test, not just asserted in prose.

3. **`rotateEvents`/`readEvents`/`paths.events` — a fully retired API, entirely un-ported.** §8: "no-op
   that records `events-generation-closed` event; generations are a column"; `paths.state/events/goal…` are
   **removed**. The whole test still asserted jsonl segment file renaming (`path.basename(first.rotated)
   ==='events.g1.jsonl'`, `fs.existsSync(store.paths.events)`). Ported to the real no-op contract:
   `rotateEvents` returns `{rotated:null,generation}` and is idempotent; it records exactly one
   `events-generation-closed` event per generation; ordinary event history stays readable and ordered;
   and a fresh process (reopening the same store) continues the seq counter forward across the reopen
   instead of resetting — without hard-asserting the exact seq numbers, since `INSERT OR IGNORE`'s
   AUTOINCREMENT counter behavior on an ignored (already-recorded) row is a SQLite implementation detail,
   not part of the contract.

4. **Two missing `store.close()`s.** Both tests that call `createStore(...)` directly never closed it;
   its ledger handle leaked and produced `EPERM` on the temp-dir cleanup — but only visibly, once each
   test's real assertion failure (items 2 and 3 above) stopped masking it. Added the closes.

### `tests/engine-lifecycle.spec.mjs`

**"the supervisor retains the lock..." wrote a `kernel.lock` file under `store.dir`.** `store.dir` is
`null` unconditionally now (`kernel/store.mjs:133`) — the entire file-path surface §8 lists as removed.
`kernel.lock` is a `signals` row (§4), written by `kernel/launch.mjs`'s `setSignal(db,scope,'kernel-lock',
{pid,token,value,at})`, scope = workflow id. Ported the write to `store.signal.set('wf','kernel-lock',
{pid,token,value:{phase:'running'}})` (§8's Store API) and the retention check to `store.signal.get(...)`.

### `kernel/kernel.mjs` — `migrateEngineState` re-runs on an already-migrated record


This is the flip side of the `predatesEngineSchema` fix above: the function is *correct* and
*intentionally* dual-purpose (numbered-marker OR journalFile-without-ledgerFile) for the callers that need
that — `continuation.mjs`'s fail-closed check and `kernel.mjs:4900`'s retry gate, both of which care about
the *whole* migration story. But `migrateEngineState` itself only does the narrower numbered-field-renaming
migration, and reusing the broad check as its *own* completion gate means it never reaches a fixed point
for a record that has already been engine-schema-migrated but hasn't separately been through
`ledger-migrate` yet (still names `journalFile`, no `ledgerFile` — completely normal, unmigrated-ledger
workflows carry that combination indefinitely until `ledger-migrate` runs). Every call in that state
re-renames nothing (there's no `major`-prefixed field left) but still re-appends a duplicate
`engine-state-migrated` event and re-saves state. Verified: with this one-line change, both of
`tests/engine-migration.spec.mjs`'s idempotency assertions pass (the record-already-migrated test and the
migrate-then-migrate-again test), with no change needed to `predatesEngineSchema` itself or to either of
its other two call sites.
