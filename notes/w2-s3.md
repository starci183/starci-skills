    a session file an earlier run of this suite left behind was read back and rejected as
    `workflow-binding-changed` (a different `repoRoot` than this run's fresh fixture). Real ledger-
    migration fallout, not a pre-existing flake — fixed.
  - Three `cleanup()` helpers (`setup`, `setupWork`, `goalFixture`) now swallow a persistent

## Root cause of every remaining failure (re-triaged fresh against the merged tree, not carried over from
## last wave's notes)

The dominant remaining cause is **`kernel/common.mjs`'s `rulingsText`**, called by every single
`renderContract` (`kernel.mjs:410`, `jobRulings(store)`), which is every operation launch:

```js
// kernel/common.mjs:470-474 (not owned by this stream)
export function rulingsText(store){
  const file=path.join(store.dir,'rulings.md');   // store.dir is permanently null now
  ...
```

`store.dir` is `null` unconditionally since `kernel/store.mjs`'s 1.0.4 rewrite (§8: no `_local` workflow
directory is ever created). `path.join(null,...)` throws `ERR_INVALID_ARG_TYPE`. Two ways this surfaces:

1. **Directly**, in tests that call `renderContract`/`launchOp`'s callees without going through the full
   loop: 10 of the 70 `workflow-kernel.spec.mjs` failures show this exact stack verbatim.
2. **Silently**, in every test that runs the loop end-to-end: `launchOp` calls `renderContract` *before*
   its own `try{}` block (`kernel.mjs:782`, then the `try` starts at `~789`), and neither `launchOp`'s
   caller nor its caller catches it inline — it propagates up to `runLoop`'s per-stage `guardedStage`
   wrapper (`kernel.mjs` `KERNEL_ERROR_LIMIT`/`kernel-error` mechanism, `~3701`), which is explicitly
   designed to catch exactly this kind of exception, record a `kernel-error` event, and let the loop go
   on — so the op that should have launched just never does, and the test's *own* assertion (op never
   reaches `running`/`done`, a contract is never written so `readContract` returns `null`, etc.) fails
   several lines away from the real cause with no visible stack trace at all.

**I confirmed this experimentally, then reverted it (not owned, not kept):** added
`if(!store.dir)return '';` to the top of `rulingsText` locally, re-ran the full spec — **78 pass / 76
fail**, i.e. *worse*, not better. This means the guardedStage recovery was masking a **second** layer of
`store.dir`/`store.paths` bugs in other unowned files that a bare `rulingsText` fix would newly expose
(the op now gets far enough to launch, then hits one of the bugs below instead). Fixing `rulingsText`
alone is not sufficient; the fix has to land together with the others in this list, or the pass count can
move backward. I reverted the experiment (`git checkout -- kernel/common.mjs`) before touching anything
else; `kernel/common.mjs` carries no changes from this stream.
