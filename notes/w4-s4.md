## Real bug found and fixed (my file: kernel/candidate-bridge.mjs)

**The tracked §12 anchor (`.starciwork/ledger-anchor.json`) was not excluded from candidate observation the
way the untracked ledger files are.** `store.saveState()` rewrites the anchor on every checkpoint (this is
by design — §12: "written inside the same store call that commits a checkpoint"). A candidate freeze that
runs `reconcileStoppedNativeRetryLease`/`freezeCandidate` after any `saveState` call — i.e. essentially any
retry that adopts and re-settles a durable job — saw the anchor's byte change as an observed `.starciwork`
path outside the operation's allowlist, and `freezeSingleDetectionCandidate` correctly (per its own rule)
classified an unexplained `.starciwork` change as `custody-path-touched`, quarantining the candidate with
`custody-path-touched:.starciwork/ledger-anchor.json`. Confirmed by instrumenting the failing test
(`tests/workflow-continuation.spec.mjs`'s "public retry durably stages same-generation late-report
recovery…") and reading the `pending.reasons` a `reconcileStoppedNativeRetryLease` failure carries.

Root cause: `kernel/candidate-bridge.mjs`'s `ledgerRecord(file)` (used by `runtimeLocalPaths` to skip
inventorying the ledger files entirely, since diffing a live-growing sqlite file is never meaningful) only
matched `runtime.sqlite`/`-journal`/`-wal`/`-shm` — not the anchor file, which is exactly the same class of
kernel-owned churn, just a second file added to `.starciwork` after the sqlite exclusion was written (§12
landed in a later wave-1 addendum than the original `.starciwork/**` exclusion).

Fix (applied): extended `ledgerRecord`'s pattern to also match `.starciwork/ledger-anchor.json`, and added the
anchor filename alongside the sqlite files in `DEFAULT_EXCLUDED` (candidate references/oracle paths) and
`LEDGER_HOUSEKEEPING_FILES` (belt-and-braces for any caller that still inventories it). New regression test:
`tests/candidate-bridge.spec.mjs`: "the tracked ledger anchor is invisible to candidate observation, exactly
like the untracked ledger files" — writes and rewrites the anchor file mid-candidate and asserts the freeze
still seals and never reports it.

## Still blocked, not my file — same bug reported in wave 2, still unfixed

`kernel/kernel.mjs:1621-1628`, `withAnchorVerified`, calls `ledgerDb.verifyAnchor(store.ledger,{workflowId:state.id})`.
`verifyAnchor`'s real signature (`kernel/ledger-db.mjs`, docs §12) is `verifyAnchor(ledger, repoRoot)` — the
second argument must be the repo root **string**, not an options object. Passing `{workflowId:state.id}` makes
`path.join(repoRoot,'.starciwork','ledger-anchor.json')` throw
`TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received an instance of Object`,
which `withAnchorVerified`'s own `catch` turns into a boundary finding with `code:'ledger-behind-anchor'`
(the ternary's catch-all default, since the caught error's `.code` is `undefined`) instead of a thrown crash —
so it reads as an ordinary anchor failure at every call site, not an exception.

I found and wrote up this exact bug, with this exact fix, in `notes/w2-s4.md` during wave 2. It is still
unfixed on `main` as of this wave. Restating it here in case the wave-2 note was missed, since it is now the
sole remaining blocker for 2 of my 3 named `tests/workflow-continuation.spec.mjs` failures:

```diff
-  try{anchor=ledgerDb.verifyAnchor(store.ledger,{workflowId:state.id});}
+  try{anchor=ledgerDb.verifyAnchor(store.ledger,store.repoRoot);}
```

`store.repoRoot` is the exact value `anchorFileFor`/`ledgerFileFor` are joined against everywhere else this
is called correctly (including my own `kernel/continuation.mjs`'s `readLedger`/`anchorRepoRoot`). No other
change needed — `verifyAnchor` already returns `{ok:false,reason,workflowId}` shaped for the three real §12
codes once the call itself stops throwing.

Blocked tests in my named spec (both fail with the identical `ledger-behind-anchor: The "path" argument must
be of type string. Received an instance of Object` message, from `kernel.mjs:4905`'s resume-boundary check):
- `public same-ID stop, run recovery and retry use a real journal without discarding unknown or staged work`
- `public stop, valid-pin retry and pinned same-ID run preserve accepted history while completing remaining work`

I did not make this edit: `kernel/kernel.mjs` is not in my owned cluster.

## Two real bugs found and fixed — stale retired-API test fixtures (my file: tests/disk-headroom.spec.mjs)

Both `tests/disk-headroom.spec.mjs` failures were the fixture driving a retired API shape, not a code bug —
ported per this wave's instruction ("if the spec drives a retired API, port the spec").

1. **`assertHeadroom`'s test fixture measured the wrong fields.** `kernel/kernel.mjs`'s `assertHeadroom` (line
   4442-4447) measures `[store.ledgerFile, state.worktree, ...(isEnrolled(state)?[state.engine.machineFile]:[])]`
   — the real 1.0.4 disk locations a workflow writes (the shared ledger file, the worktree, and — once
   enrolled — the cross-ledger machine db). The test's fake `store`/`state` still carried the retired
   `store.dir`/`state.engine.journalFile` fields, which `assertHeadroom` no longer reads at all, so those two
   measured paths came back `undefined`. Fixed by giving the fixture `store.ledgerFile` and
   `state.engine.machineFile` instead, and updating the expected `disk-headroom-exhausted` event's `volumes`
   to the three real paths in order.
2. **`inspectWorkflow`'s test fixture wrote to the retired `_local` file layout.** `kernel/supervisor.mjs`'s
   `inspectWorkflow(entry,…)` reads `entry.state` directly (`const state=entry.state??null`) — it no longer
   reads `entry.dir/state.json` off disk (`.starciwork/_local` is retired kernel authority the supervisor
   never touches). The test wrote `state.json`/`events.jsonl` under
   `.starciwork/_local/workflows/wf/` and passed `{id:'wf',dir}` with no `.state`, so `inspectWorkflow` saw
   `state=null` and `supervisorAction` short-circuited on `!info.approved` before ever reaching the headroom
   check being tested — the reported `{action:'leave',reason:'not approved'}` instead of the expected headroom
   refusal. Fixed by building a real ledger via `createStore`/`saveState`/`appendEvent` (same as `superviseOnce`
   itself does through `listWorkflows`) and reading the entry back with `listWorkflows(root)`, matching exactly
   how the production call path constructs `entry` for `inspectWorkflow`.

Both fixes keep every original assertion's intent (disk-below-threshold refusal, one exhaustion event, no
spawn while full, restart once the disk clears) — nothing was loosened or reinterpreted, only the fixture's
plumbing was ported off retired fields/files onto their real 1.0.4 replacements.

## store-paths-removed:continuation — one remaining occurrence found and fixed

`tests/continuation-binding.spec.mjs:59` still read `store.paths.continuation` (throws
`store-paths-removed:continuation` against the real `kernel/store.mjs`). `kernel/continuation.mjs` itself has
been clean of this since wave 2 (`bindContinuationPath` returns the resolved path locally instead of writing
it back to `store.paths.continuation`; `kernel.mjs` reads `store.continuation` directly). This one test line
regressed back to the old shape during a wave-2/3 merge — `tests/continuation-binding.spec.mjs`'s shared
`fixture(t)` was independently patched by another wave-2 stream (`w2-s8`, per its own notes) for the
`store.close()`/EPERM half of the same cluster, using an older base that predated my `store.continuation`
rename, and the merge kept their base text for that one line. Re-applied: `store.paths.continuation` →
`store.continuation`. Swept the whole repo for any other occurrence — none remain outside this one file,
`notes/*.md` (historical, left as-is), and `tests/store.spec.mjs` (see below, not a bug).

**Not a bug, no action taken**: `tests/store.spec.mjs` also uses `store.paths.continuation`/`store.paths.final`,
but `kernel/store.mjs` now special-cases exactly those two keys in its `paths` Proxy (get **and** set) as "a
real, working surface, not a guard" per its own comment — `store.paths.continuation` defaults to
`store.continuation` and accepts a sticky override; `store.paths.final` returns a `ledger://final-report/<id>`
reference string. This is a deliberate, working feature of `store.mjs` (not mine to touch), verified by
`node --test tests/store.spec.mjs` — 21/21 pass. `kernel/continuation.mjs` doesn't need to use it (it computes
the resolved path locally and reads the final-report value straight off `store.signal`), and nothing requires
it to; the two designs coexist without conflict. I did not change `kernel/continuation.mjs` to adopt the
restored setter — the wave's own framing ("`store.continuation` is canonical; `store.paths.continuation`
writing is the bug shape to look for") confirms the direction already taken in wave 2 is the intended one.
