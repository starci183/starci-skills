## Root cause 1 — real leaked store handles (the same species of bug as job-bridge.mjs)

`tests/workflow-kernel-lanes.spec.mjs` never closed the `store` handles it opened directly (bypassing
`kernelMain`'s own `openedStores`-tracked auto-close, since `runLoop`/`approve` are called with an
already-loaded `store`+`state`, not through `kernelMain`):

- Three inline reads — `createStore({...}).loadState()`, `createStore({...}).readEvents()`, and (after
  porting `run.goal.goal` below) a `store.goal()` read — each opened a store and never closed it.
- `walked()`'s own `store`, kept alive for the whole test body (`run.store.readEvents()`,
  `run.store.signal.get(...)`, etc. after `walked()` returns), was never closed at all.

Fixed with a `withStore(run,fn)` helper (open, run, close) for the three one-off reads, and by giving
`fixture(t)` an `onClose(fn)` registration that `walked()`'s store uses.

## Root cause 2 — `t.after` hooks run in *registration* order, not reverse order

First attempt used `t.after(()=>store.close())` directly inside `walked()`, expecting it to run before
`fixture()`'s own `t.after(()=>fs.rmSync(root,...))` (registered earlier, since `fixture()` runs first). It
didn't: I verified directly (`node -e "test('x',t=>{t.after(()=>console.log('a'));t.after(()=>console.log('b'));})"`)
that Node's test runner runs `after` hooks in the order they were *registered*, not reverse order. So
`fixture()`'s removal — registered first — always ran *before* `walked()`'s close — registered second — and
the directory removal hit a still-open SQLite handle every time. This is why a first pass of
`maxRetries`/`retryDelay` padding on the `rmSync` call did nothing: it wasn't a timing lag, the handle was
never going to close before the removal ran, no matter how long the removal waited.

Fixed by moving the closing responsibility into `fixture()` itself: it now keeps a `closers` array, exposes
`onClose(fn)` to push onto it, and its own single `t.after` runs every registered closer *before* removing
the directory — so ordering no longer depends on which function called `t.after` first. Kept the
`Atomics.wait` settle + `maxRetries`/`retryDelay` padding too, as a second line of defense against the
ordinary Windows SQLite-close lag (a real, separate, already-documented quirk from waves 1–3) now that the
handles are actually closed before it runs.

`tests/helpers/kernel-harness.mjs` (shared with other specs, per the brief's warning) was checked and is not
where either bug lives: `scriptedOrca` takes an already-open `store` from its caller and never creates or
holds one of its own — nothing to fix there.

## Root cause 3 — two assertions still read the retired `_local` file shape

- `const page=fs.readFileSync(run.goal.goal,'utf8');` — `kernelMain('workflow-goal',...)`'s return has no
  `.goal` file-path field any more (goal.md is not a file; §8's `store.goal()` reads the `goals` table row
  directly). Ported to `withStore(run,store=>store.goal().markdown)`.
- Two `git status --porcelain` assertions expected `'?? .starciwork/_local/'` after a workflow ran. The
  ledger leaves four untracked files instead of one directory (WAL mode is the §3 default):
  `ledger-anchor.json`, `runtime.sqlite`, `runtime.sqlite-shm`, `runtime.sqlite-wal`. Captured as a
  `LEDGER_UNTRACKED` constant and used in both assertions, in the order git itself reports them
  (alphabetical within the untracked group).
