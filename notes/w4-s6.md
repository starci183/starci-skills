## `singleTick`/`waitTick` now receiving both `store` and `workflow` (as flagged)

`kernel/kernel.mjs`'s internal call now passes `store,workflow:state.id` together. `hosts/orca/protocol.mjs`
was silently preferring `givenStore.id` whenever both were given, never checking the two agreed — a mismatch
would have been reported against whichever workflow the store happened to be, not the one the caller named
and not refused. Added an explicit consistency guard to both `reportOutcome` and `singleTick`: when both
`store` and `workflow` are given, they must name the same workflow, or the call is refused
(`need(workflow===givenStore.id, ...)`) rather than one silently winning. The real call site
(`kernel.mjs`'s `store`/`state.id` pair) satisfies this by construction — verified by every named spec
still passing after adding the guard.

## `tests/orca-headless.spec.mjs` (3) — two were one real bug, one was a retired-API test

### 1–2. `gpt-5.6-sol` requests silently launched `gpt-5.6-luna` (a real product bug)

Both "a dead pid is a dead worker..." and "providerFor maps the launcher's agent and model..." asked for
`--model gpt-5.6-sol` and got a spawned `codex exec --model gpt-5.6-luna` back — not test/data drift, a real
resolution bug in `models/functions.mjs`'s `headlessProvidersFromRegistry`. It built each target's "other
role" headless lines from `registry.targets[id].profiles` alone (`working`/`reasoning` — the only two roles
`model/registry.yaml`'s own target shape carries), but the *actual* per-role model map a provider-window
pool launches from is `model/runtimes.yaml`'s five-role `models: {implement, verify, write, decide, plan}`
(`kernel/schedule.mjs`'s `loadRuntimes()`). The `codex-agent` pool decides on `gpt-6-astra`, implements/
writes on `gpt-5.6-luna` and **verifies on `gpt-5.6-sol`** — a role `registry.targets.codex-agent.profiles`
never names, so no headless line for that exact model ever existed. `providerFor`'s lookup then fell through
its `id===wanted` and `modelOf(command)===wanted` misses to `canonicalTarget('gpt-5.6-sol')` →
`'codex-agent'` → that target's own **working**-model command line (`gpt-5.6-luna`), silently substituting a
model the caller never asked for. Confirmed with a fixed comment in the code itself
("codex-agent decides on gpt-6-astra but implements on gpt-5.6-sol" — stale since the `gpt-5.6-luna`
rename, and it names exactly this gap).

Fixed `headlessProvidersFromRegistry` to take an optional `runtimes` map (the pool's own role→model map,
`model/runtimes.json`'s `.runtimes`) and enumerate every distinct model from **both** sources when building
each target's `<id>~<model>` lines, not the registry's narrower profile pair alone. Passed
`readDistJson('model','runtimes.json').runtimes` at `HEADLESS_PROVIDERS`'s construction. Backward compatible
(third param defaults to `{}`; `tests/headless-model-registry.spec.mjs`'s synthetic-registry test, which
calls the two-arg form directly, is unaffected and still passes).

That exposed a second bug in `providerFor` itself (`hosts/headless/host.mjs`), pre-existing and not part of
my named three but caught while verifying the fix above didn't regress `tests/headless-model-registry.spec.mjs`
(confirmed via `git stash` isolation on `models/functions.mjs` that it already failed identically before
today's change): `entries.find(([id,spec])=>id===wanted||modelOf(spec.command)===wanted)` treats an exact
target-id match and an incidental command-model match as equally good, so `Object.entries` insertion order
alone decided which one won whenever both existed — `codex-agent`'s own command already ends in
`--model gpt-5.6-luna` (its working model) and is declared before the literal `gpt-5.6-luna` target in
`model/registry.yaml`, so an explicit request for `gpt-5.6-luna` matched `codex-agent` by `modelOf` before
ever reaching the id match, attesting the wrong target id (functionally harmless for that one case, since
both commands are identical, but wrong identity, and unsafe in general — a future target sharing a model
with a pool's working default would silently attest as the pool). Reordered to check every entry for an
exact `id===wanted` match first, across the whole set, before falling back to a command-model match.

### 3. `inspectWorkflow` no longer reads a workflow directory off disk (ported the spec)

`kernel/supervisor.mjs`'s `inspectWorkflow(entry, {ledger, ...})` was already ported: `entry.state` is
read directly (no `entry.dir/state.json` read at all any more — confirmed against its one production call
site, `kernel/supervisor.mjs`'s own round loop, which gets `entry` from `listWorkflows(repoRoot)` -
`{id, dir:null, state, updatedAt}` per §8 - and passes a real `ledger` handle alongside it). The test still
wrote a raw `_local/workflows/w1/state.json` file and called `inspectWorkflow({id,dir})`, expecting the
function to read the file itself - the retired calling convention. Ported: construct the loaded `state`
object directly and pass it as `entry.state` (`{id:'w1', dir:null, state}`), matching what the real
supervisor loop already hands the function. No `ledger` needed for this test's two assertions (`hostAdapter`
round-tripping through `state.hostAdapter`), since every `ledger?.db` read inside `inspectWorkflow` already
degrades gracefully to its default when no ledger is given.
