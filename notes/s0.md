## Contract addendum: minted identity, WAL by default, checkpoint, §12 anchor (826894e5, merged 2ae95d3d)

Landed and committed first, per the lead's priority instruction, before anything else this session:

- `meta(key,value)` table, seeded once at creation (never rewritten after): `ledger_id` = `crypto.randomUUID()`,
  `schema`, `created_at`. `journal_mode` is also a `meta` key but is **kept in step on every open** (an
  `INSERT … ON CONFLICT DO UPDATE`), not seeded-once-only — that's what lets `inspectLedger`/an operator see
  the DELETE fallback happen on a later open even though the row already existed. `ledgerIdOf(handle)` reads
  the row directly off `handle.db`; every place that used to compute an id from the path (`openLedger`'s own
  `ledgerId`, `inspectLedger`'s, `reserveTwoPhase`'s `machine.registerLedger` call) now reads it from `meta`
  instead. The old path-hash `ledgerIdFor(file)` export is gone — §3's export list no longer lists it, and
  `machine.registerLedger({file,ledgerId})` now requires the caller's `ledgerId` explicitly (no path fallback).
- `openLedger`/`openMachine` default to `journal_mode=WAL`, `busyTimeoutMs=15000`. A request that doesn't
  actually report `wal` back from the PRAGMA falls back to `DELETE` (never throws), and the fallback is what
  gets written to `meta.journal_mode`. **Gotcha found and fixed**: `PRAGMA auto_vacuum=INCREMENTAL` is a
  no-op if it runs *after* `journal_mode` has already switched to `WAL` — SQLite only accepts it on a
  database it still considers pristine. The old code set journal_mode first (inside `openDb`) and
  auto_vacuum second (inside `migrateLedger`), which was fine under the old DELETE default but silently
  dropped `auto_vacuum` to 0 once WAL became the default. Fixed by moving `auto_vacuum=INCREMENTAL` into
  `openDb`, before the journal_mode PRAGMA, gated by a new `autoVacuum:true` passed only from `openLedger`
  (machine.sqlite has no auto_vacuum requirement per §5). Caught by the spec's own schema test, not by
  inspection — worth flagging in case another stream copies this open sequence.
- I also **removed the old version gate** (`sqliteAtLeast(sqliteVersion,'3.51.3')`) that used to block WAL
  entirely below that version. The bundled `node:sqlite` here reports `3.50.4` and `PRAGMA journal_mode=WAL`
  works perfectly on it (verified directly) — the gate was stricter than reality and would have forced every
  ledger onto DELETE by default, defeating the point of this addendum. The fallback is now decided purely by
  what the PRAGMA reports back, matching §3's literal wording.
- `checkpointLedger(handle)` / `handle.checkpoint()` run `PRAGMA wal_checkpoint(TRUNCATE)` and return
  `{ok,busy,logFrames,checkpointedFrames}`. Exposed on both the ledger and machine handles; exported
  standalone for callers holding just a handle (archive/export/backup streams).
- `machine.sweep()`'s orphan check now requires the inspected ledger's `meta.ledger_id` to match the group
  it's sweeping — added one line (`if(inspection.ledgerId!==ledgerId)continue`) inside the existing per-ledger
  loop. Without it, a machine row registered against a path that now holds an unrelated fresh ledger (same
  path, different bytes) would have been wrongly released, since the old code only checked "did this open
  succeed", not "is this actually the same ledger".
- §12 anchor: `anchorFileFor(repoRoot)` → `.starciwork/ledger-anchor.json`. `readAnchor` returns `null` when
  untracked. `writeAnchor` reads-modifies-writes one workflow's head (merging with whatever else is already
  tracked), atomically via a `.tmp` sibling + `fs.renameSync`, and throws `ledger-identity-mismatch` itself if
  asked to write a `ledgerId` that doesn't match an anchor already on disk (defensive; §12 only requires this
  check from `verifyAnchor`, but it's cheap insurance against a second, unrelated ledger corrupting the
  tracked file). `verifyAnchor(ledger,repoRoot)`: no tracked anchor (or one with an empty `workflows` map) is
  `{ok:true}` — the legitimate first boot; `ledger` falsy/no `.db` with a tracked anchor present is
  `ledger-missing`; an id mismatch is `ledger-identity-mismatch`; per anchored workflow, a missing event at
  the anchored `(seq,digest)` or no `state_snapshots` row at or after the anchored `generation` is
  `ledger-behind-anchor`.
- §4 `inputs` table added to `LEDGER_DDL` verbatim (markdown backticks stripped from its comment — they
  terminate a JS template literal).
- `inputs.put/get/list/materialise` implemented on the ledger handle so the store stream's §8 methods can
  delegate: `put` computes `sha256` over the bytes and returns `{ref:'ledger://inputs/<wf>/<key>#sha256=<hex>',sha256}`;
  `get`/`materialise` read through `readInput(db,{workflowId,key})` which recomputes the digest and throws
  `input-digest-mismatch` on drift (spec asserts both paths refuse). `list` returns metadata + `ref`.
- `retireWorkflow` now also drops `inputs` rows — required for the `workflows` FK on plain retire.
- Note for the store stream: `node:sqlite` returns BLOBs as `Uint8Array`, not `Buffer`.

## Readings I picked where the contract was ambiguous

- `appendEvent`/`enqueueJob` **auto-`ensureWorkflow`**: `events.workflow_id`/`jobs.workflow_id` are FK'd to
  `workflows`, and no 1.0.3 caller ever creates a workflows row first. Without this, every ported caller
  fails with a raw FK error. `ensureWorkflow` is also exported as a module function `(db,{...})` so it is
  callable inside a `transaction` body.
- `journalWorkflows` is ported under the name **`ledgerWorkflows`** and now also scans the `workflows`
  registry table (a registered workflow with no operational rows still shows).
- `retireWorkflow` keeps journal semantics but removes every `workflow_id`-keyed row (`goals`, `reports`,
  `contracts`, `checks`, `inbox`, `signals` by scope) and then the `workflows` row itself — required because
  the children FK-reference it. Under `preserveRuntimeCustody` the `workflows` row stays: the retained
  snapshot references it.
- `releaseTwoPhase(ledger,machine,{jobId,status,result})`: deletes lease rows, then with `status` settles
  the job (`status`+`result_json`, clears `lease_token`/`deadline`); without `status` it only clears fencing,
  mirroring `admission.release`. Machine `machine_ref`s are released after the ledger commit.
- `machine.release` accepts a token string or an array; `machine.reserve` accepts `ttlMs` (or `ttl` per the
  §6 pseudocode); `sweep({inspectLedger})` is injectable and skips ledgers whose file cannot be inspected
  (their TTL still owns the rows — fail closed).
- `runtimeRootFor` is duplicated one-line locally (same formula as `engine.mjs`) so `ledger-db.mjs` never
  imports the engine — engine will import this module, and a cycle on a `const` arrow is TDZ-fragile.

## Requests to other streams

- **Whoever ports `admission.mjs`**: `admission.reserve` currently inserts `leases` rows and only then sets
  `jobs.lease_token`. Under `leases_match_job` that order now aborts with `lease-identity-drift`. Set
  `lease_token` on the job first, then insert lease rows (the order `reserveTwoPhase` uses).
- `reserveTwoPhase` requires an existing job to be `queued` with matching identity (throws otherwise), or
  inserts it as `leased` when absent. Repo-scoped `leases` are capacity-checked against ledger `resources`
  counting only unexpired leases.
- **Whoever owns `store.mjs`'s `saveState`/checkpoint path (§8/§12)**: this stream only exports the anchor
  primitives (`readAnchor`/`writeAnchor`/`verifyAnchor`) and the checkpoint helper
  (`checkpointLedger`/`handle.checkpoint()`); it does not call them anywhere itself. §12 says the anchor is
  "written inside the same store call that commits a checkpoint" — that wiring (call `writeAnchor` right
  after the ledger transaction that writes a `state_snapshots` row commits, with `repoRoot`, the just-opened
  ledger's `ledgerId`, the workflow id, the new generation, the checkpoint's `checkpoint_id`, `eventsHead()`
  and the event `seq`) belongs in `store.mjs`/`saveState`, not here — §8 is store's file, not mine.
- **Whoever owns the continuation boundary / `ledger-migrate` / `workflow-export`**: `verifyAnchor(ledger,
  repoRoot)` should run right after `openLedger`/`inspectLedger` and before trusting the file, per §12's
  "verified at the continuation boundary". A `ledger-missing` refusal's named recovery is restoring a backup
  or `ledger-migrate`, never a fresh `openLedger` — don't just retry the open.
- Any copy path (archive, `workflow-export`, backup, supervisor snapshot) must call `checkpointLedger(handle)`
  (or `handle.checkpoint()`) on the same handle immediately before copying `runtime.sqlite`, and copy that
  file alone — never `-wal`/`-shm` (§3, §7's glob already scopes the allowlist refusal to `runtime.sqlite*`).
- The exact diff needed elsewhere: none — this stream needed no changes outside its owned files.
