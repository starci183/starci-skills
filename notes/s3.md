# s3 — kernel.mjs: every file surface becomes a store call (runtime 1.0.4)

## Files changed

- `kernel/kernel.mjs` (own file; five commits, see `git log --oneline` on this branch):
  - **Reports**: `archiveOpReport` marks `reports.consumed_at` via `store.ledger.db` raw SQL instead of
    renaming/deleting a file (contract's exact suggestion). `stageAnsweredDecisionLateReport`/
    `lateReportReplayMatches` read via `store.readReports()` and hash the `reports.report_json` bytes
    (`reportDigest` helper) instead of a report file's sha256. The kernel's own synthesized reports
    (`applyOpReport`'s tab-read fallback) call `store.writeReport(...)`. `readmitCompletedReportRetry`/
    the retry-recovery path return the dispatch id in place of a file path where the old code surfaced
    `store.reportPath(...)`.
  - **Contracts**: `launchOp` calls `store.writeContract({opId,attempt,dispatchId,markdown})` instead of
    `fs.writeFileSync(store.contractPath(...))`. Dropped `op.contractFile`/`op.contractFile`-based
    pointer; `operationSpec(workflowId,op,contract)` (signature changed - was `operationSpec(op,contract)`)
    points an oversized contract at `starci op-contract --workflow <id> --op <op> --attempt <n>` instead
    of a file path (matches §9's worker IPC exactly, and s6 confirms `op-contract` was built to this
    signature).
  - **Checks**: the audit-measurement and machine-verify checks writes (`checksPath('<op>-audit')`,
    `checksPath('<op>-kernel')`) become `store.writeChecks({opId:'<op>-audit'|'<op>-kernel',attempt,checks})`.
  - **Inbox**: `queueInbox`/`applyInbox` use `store.inbox.push/pending/settle` instead of writing/reading/
    deleting JSON files in a directory. Settle status is `'applied'` for every processed item (matching
    the old code's unconditional file removal before/after handling - nothing was ever "rejected" at the
    file level, only via `inbox-rejected`/`inbox-ignored` *events*, which are unchanged).
  - **Signals**: `kernel.lock`/`stop.flag`/`launch.json`/`final-report.json`/`supervisor.lock` move onto
    the `signals` table. `final-report.json` specifically becomes `store.signal.set(id,'final-report',
    {value:final})`; `state.finished.report` is now `true` (a marker, not a path or the whole report -
    the report itself would otherwise duplicate into every state snapshot forever) and the
    `workflow-status` reader reads back via `store.signal.get(id,'final-report')?.value`.
  - Once `kernel/launch.mjs` landed (s5), replaced this stream's own hand-rolled, simplified kernel-lock/
    supervisor-lock/launch-signal code with calls into it (`reserveStartup`/`acquireStartup`/
    `releaseStartup`/`inspectStartup`/`readSupervisor`/`readLaunch`), restoring the full
    launching/launching-child/launching-native reservation state machine `startup-lock.mjs` had, so
    `terminals.mjs`/`supervisor.mjs` (launch.mjs's other callers, once they're wired to it) see the same
    rows this stream's kernel-lock writes.
  - **`journalFile` → `ledgerFile`/`machineFile`**: ported every call site once s2 landed the real
    `engine.mjs` rewrite (`settleGenerationLeases`/`staleLeaseProof`/`prepareGenerationRetry`'s keyword
    args; `openJournal({file:state.engine.journalFile})` → `openLedger({file:state.engine.ledgerFile})`,
    aliased at the import (`const {openLedger:openJournal}=ledgerDb`) to keep the diff small; the
    candidate-base and "machine-local root" `path.dirname(...)` sites → `candidateBaseFor(state)` /
    `state.engine.machineFile`; `retryJournalTarget`'s `journalFileFor()` fallback → `ledgerFileFor
    (store.repoRoot)`, repo-scoped, matching `enrollEngine`'s own default - this was an explicit open
    question in s2's notes and I answered it by using the same default `enrollEngine` uses).
  - `kernelMain`'s `storeRootFor` (shared-ledger routing: does this workflow live in this repo or its
    owning repo?) used to check `fs.existsSync(_local/workflows/<id>/state.json)`; that file never
    exists now, so it always fell through to the wrong root. Replaced with a `workflowKnownAt(root,id)`
    helper that opens the ledger read-only (`inspectLedger`) and checks the `workflows` table.
  - `kernelMain` now closes every store it opens (tracked in an `openedStores` array, closed in a
    `finally` around a renamed inner `kernelMainDispatch`) before returning: a CLI command is one
    self-contained unit of work, and a caller inside one long-lived process (this test suite, potentially
    a future daemon) must not accumulate open sqlite handles across commands - this was the direct cause
    of Windows `EPERM` on temp-dir cleanup in several owned tests until fixed.
  - Independent-review validation receipts move off `store.dir/evidence/...` (gone) to a non-`_local`
    corner of `.starciwork` beside the ledger (`kernelEvidenceRoot = <repoRoot>/.starciwork/kernel-
    evidence/<workflowId>`) - a real file, not ephemeral, because the write-once-per-attempt immutability
    check is a real integrity property, not something a tmpdir stand-in should degrade.
  - `renderContract`'s worker-facing check-control file (`checksFile`) moves to
    `os.tmpdir()/starci/<op>-<attempt>.checks.json` (ephemeral kernel-IPC transport, like the dispatch
    context file per §9), and the rendered report command gains `--workflow ${state.id}` (see "answers to
    other streams' open questions" below) and drops `--reports-dir` (no directory to name any more).
    **Found and fixed a real bug while doing this**: an earlier commit on this branch removed the
    `reportsDir` local but missed the one place that still referenced it in the report-command template
    literal, so every real `renderContract` call would have thrown `reportsDir is not defined` building
    the launch spec. Fixed in the same commit as the `--workflow` addition.
  - `state.dir`/`store.dir` are `null` everywhere now (no `_local` workflow directory is ever created);
    `createWorkflowState`'s `dir` field, the allocator's shared-loads/budget wiring (now
    `shared:{path:store.ledgerFile,...}` per s5's ledger-backed `kernel/loads.mjs`, `budget:{path:
    <repoRoot>/.starciwork}` per s9's real convention for `runtime-budget.json`) and every `dir:store.dir`
    CLI-response field (now `dir:store.ledgerFile`) were updated to match. (I initially stood a tmpdir
    convention in for the loads/budget root before s5 landed the real ledger-backed API; removed that
    stand-in once the real thing existed - see commit history if the intermediate step matters.)
  - `reconcileContinuationPreflight` now calls `ledgerDb.verifyAnchor` (imported as a namespace,
    `ledgerDb.verifyAnchor?.(...)`, so it activates automatically once s0 ships it without needing another
    edit here) before trusting a resumed boundary, folding a `ledger-behind-anchor`/`ledger-missing`/
    `ledger-identity-mismatch` refusal into the existing `continuationBoundary` findings shape instead of
    a silent fresh start at generation 0 - the lead's contract-addendum instruction to this stream.
- `tests/workflow-kernel.spec.mjs`, `tests/w1-reconcile.spec.mjs`, `tests/workflow-kernel-shared-ledger.
  spec.mjs` (own files): ported every fixture off the removed `store.paths.*`/`reportPath`/`contractPath`/
  `checksPath` and off raw `fs` writes to `kernel.lock`/`stop.flag`/inbox files, onto `store.goal()`/
  `store.signal.*`/`store.inbox.*`/`store.writeReport`/`writeContract`/`writeChecks`/`readContract`/
  `readChecks`/`readReports`, matching kernel.mjs's own migration line for line. `scriptedOrca`'s and
  `headlessFake`'s "worker writes a report" step now calls `store.writeReport(...)` directly instead of
  writing a report file `acceptReports` would have picked up (§9 says the real worker path goes through
  `starci report`, which nothing has wired to the ledger yet - see "Blocked on other streams" - so the
  fixtures simulate the *end state* `starci report` will eventually produce, which is what these tests
  actually need to exercise: the kernel's own consumption of `store.readReports()`, not the CLI's file→
  ledger bridge). `state.engine`/journal fixtures in `w1-reconcile.spec.mjs` and the shared-ledger spec's
  enrolled-runtime test carry `ledgerFile`/`machineFile` instead of `journalFile`. Closed every store/
  ledger handle these tests open in their own cleanup (`t.after`), for the same Windows-`EPERM` reason as
  `kernelMain` above.
- `tests/helpers/kernel-harness.mjs` (**not on my owned list** - a shared fixture also used by `tests/
  goal-contract.spec.mjs` and `tests/workflow-kernel-lanes.spec.mjs`, neither owned by this stream): its
  `scriptedOrca` had the identical `reportsDir`-based report-file-write this stream's own local copy in
  `workflow-kernel.spec.mjs` had, and `tests/workflow-kernel-shared-ledger.spec.mjs` (owned) depends on
  it. Ported it the same way. The two other consumers were already calling it with `store.paths.reports`
  (which throws regardless of my change, since `store.mjs` removed `.paths` independently of this edit),

## Every remaining failure in the three owned specs, by root cause

1. **`kernel/terminals.mjs:261`** (owned by s5, explicitly flagged unmigrated in `notes/s5.md`'s "Open
   questions": *"It's on my owned list, but... it will break outright the moment store.mjs drops paths.
   state/dir"*) still does `fs.existsSync(path.join(store.paths.reports,...))` - throws `store-paths-
   removed:reports` immediately. This is called from inside `kernel.mjs`'s own sweep/dispatch-check paths
   (`sweepStaleTerminals` and friends), so it very likely also explains the broader scatter of `Cannot
   read properties of undefined ('status'|'kind'|'id'|...)` failures across otherwise-unrelated tests
   (an op search coming back empty because its launch silently failed inside a swallowed exception from
   this call - kernel.mjs's launch path deliberately never lets a launch failure crash the loop, so the
   *symptom* surfaces several lines away from the *cause*). I did not chase every one of these
   individually to confirm the causal chain for each - they share the same shape (an op the test expects
   to exist/progress is instead absent/stuck) and the one common thread I could find in the ones I did
   check was launch failing silently. Once `terminals.mjs` is ported (its own owner, s5, already has the
   fix pattern ready in `kernel/launch.mjs`'s `readCoordinatorTerminals`/`closeStaleCoordinatorTerminals`/
   etc.), I'd expect most of this bucket to clear without any further change on this end.
2. **`kernel/job-bridge.mjs`** (not owned by this stream - s2's notes name it "likely s4-boundary-bridge")
   still calls `openJournal({file:journalFile})` from the retired `kernel/journal.mjs` with no `journalFile`
   in scope (its own param is not named that), so `createEngineRuntime` throws `openJournal needs a file`
   the moment any test enrolls the durable engine. This is **all 5** of `w1-reconcile.spec.mjs`'s
   failures (every one of them enrolls the engine via `createEngineRuntime`) and is exactly s2's own
   "Blocked on other streams" item #2, reproduced independently here against the merged tree. s2's notes
   give the exact requested `createJobBridge({ledgerFile,machineFile,...})` shape.
3. **`kernel/continuation.mjs`'s `bindContinuationPath`/`storeRepoRoot`** (owned by s4; **not** the
   function s4's `verifyAnchor` addendum touched, and not mentioned anywhere in `notes/s4.md` - a real
   gap, not a stale note): `storeRepoRoot=store=>path.dirname(path.dirname(path.dirname(path.dirname
   (store.dir))))` - four levels of `dirname` on a value that is permanently `null` now. Throws
   `TypeError: path argument must be of type string...Received null` from `kernel.mjs`'s `open(id)`
   helper (used by essentially every resuming `kernelMain` command: `workflow-run`, `workflow-status`,
   `workflow-amend`, `workflow-retry`, ...). Exact one-line fix, since `store.repoRoot` is the same value
   this function is trying to reconstruct: `const storeRepoRoot=store=>store.repoRoot;`. This is the
   single highest-value fix left in the whole ten-stream tree by failure count - it's what's actually
   behind "the launcher commands reach one workflow directory in the owner" and "public retry and pinned
   enrolled run..." in the shared-ledger spec, and very likely a chunk of `workflow-kernel.spec.mjs`'s
   remaining 75 too, though I did not have time to re-audit that file's failures against this specific
   cause after finding it late in the session.
4. A handful of individual `workflow-kernel.spec.mjs` failures I looked at directly and could not
   attribute to (1)-(3): "the kernel-owned ledger paths are protected..." (`harness.store.readContract
   (nodeId)` returns `null` - a `work.author` op whose contract genuinely never got written for a reason
   I did not trace to the end; a sibling test using the same `readContract(UI)`/`readContract(CART)`
   pattern against a similarly-shaped fixture passes, so the API itself is not the problem) and a couple
   more in the same family. I'm reporting these as open rather than root-caused; they may be downstream of
   (1)-(3) too, or may be genuinely narrower bugs in a corner of the Work-ledger flow I didn't have
   remaining budget to isolate.
