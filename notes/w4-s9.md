## Root causes and fixes, all in `tests/workflow-amendment.spec.mjs`

1. **`fixture()` still enrolled every workflow with `state.engine.journalFile`** (the pre-1.0.4 field
   name) and opened a *separate* `journal.sqlite` via the retired `kernel/journal.mjs`'s `openJournal` to
   seed a `jobs`/`leases` row. `kernel/kernel.mjs` locally aliases `kernel/ledger-db.mjs`'s `openLedger`
   as `openJournal` (`const {ledgerFileFor,openLedger:openJournal}=ledgerDb;`) and reads
   `state.engine.ledgerFile` exclusively (`kernel/kernel.mjs:4566,4590,4452`) — a state carrying only
   `journalFile` makes it call `openLedger({file:undefined})`, which throws `openLedger needs a file`
   deep inside the real CLI dispatch (`kernelMainDispatch`). Fixed: `state.engine.ledgerFile` is set to
   `store.ledgerFile` (the exact file `store` already has open — one ledger, not two), and the
   `jobs`/`leases` seed rows are inserted straight into `store.ledger.db` (the schema is column-for-column
   identical to the retired journal's for these two tables, so the INSERT statements themselves needed no
   change). This alone fixed 6 of the 7 failing tests.
2. **`f.store.dir` for a fake `kernel.lock` file** (test "public stop and same-ID amendment…", to prove
   `workflow-amend` refuses while a kernel is still running) — `store.dir` is `null` under 1.0.4.
   `kernel.lock` is the ledger's `kernel-lock` signal now, held through the same startup-row state machine
   `kernel/launch.mjs` exports (`reserveStartup`→`acquireStartup`→`releaseStartup`) — exactly what a
   *different* test in this same file ("public amendment reclaims a dead running startup row…") already
   used correctly. Ported this test to the same pattern instead of inventing a second one.
3. **Two direct `f.store.paths.state`/`store.paths.state` reads/writes**, both genuinely retired surface
   (docs/ledger-db.md §8: `paths.state/…` removed; anything that needs state reads `loadState()`):
   - *"sequential, stale-projection and replayed amendments…"* wrote a stale `state.json` snapshot
     mid-test to prove the kernel was immune to it. Checked what that immunity actually rested on: for an
     **enrolled** workflow, `open()`'s `store.loadState()` was always durable-bound and read the journal,
     never the plain projection file — the file was a side channel for humans, and the pre-1.0.4 test's
     entire point was proving the kernel never reads it. Under 1.0.4 there is no parallel projection left
     to go stale (the ledger row *is* the record), and the only writers that can touch it go through
     `saveState`, itself serialized by the same startup-row lock `workflow-amend` holds across its own
     reload/apply/save (kernel.mjs's own comment on `acquireKernelLock` says so). I confirmed this by
     tracing what injecting a raw, out-of-band `state_snapshots` row *would* do: `loadState()` always takes
     the newest row by insertion order with no other integrity check, so a raw insert bypassing the
     kernel's own write protocol absolutely would get picked up as current — but that isn't a "concurrent
     writer" scenario the kernel is designed to defend against (no real writer ever bypasses
     `saveState`/the lock this way); it would be indistinguishable from hand-editing the SQLite file with a
     text editor. Injecting it would produce a failure that *looks* like a lost-update bug but proves
     nothing about the kernel — so I did not add it. Removed the now-inapplicable file write and its
     "stale projection" framing (test renamed to `'sequential and replayed amendments compose every prior
     operation grant without a lost update'`), kept every substantive assertion (both amendments' grants
     present after the second call, replay is idempotent) — those never depended on the file write to be
     true.
   - *"a legacy amendment reloads the final controller checkpoint…"* is the *other* half of the same
     invariant, and this one **does** correspond to something still real under 1.0.4: `open()` reads state
     once (`kernel.mjs:4490`), then `workflow-amend` reads it *again* after acquiring the startup lock
     (`kernel.mjs:4593`, `Object.assign(state,durable)`) specifically so a write that lands in the gap
     between those two reads is not lost. The pre-1.0.4 test proved this by monkey-patching
     `fs.readFileSync` in a `--import`-preloaded child process to swap `state.json`'s bytes right after the
     first read returned. Ported the same idea one layer down, onto the one chokepoint every ledger read
     now goes through: the preload patches `DatabaseSync.prototype.prepare` (`node:sqlite`, used directly
     by `kernel/ledger-db.mjs`) to detect the first `SELECT … FROM state_snapshots … ORDER BY snapshot_id
     DESC` for the target workflow, let it return its real (first) result untouched, then insert the
     "final controller checkpoint" as a new row — so only the *second* read (post-lock) sees it. First
     attempt used `createRequire(import.meta.url)` to reach `node:sqlite`, which throws for a `data:` URL
     module (`import.meta.url` isn't a real file path there); switched to a plain `import {DatabaseSync}
     from 'node:sqlite'` (the preload is already loaded as ESM — `import` statements were accepted before
     that line ever ran). Kept every original assertion (the accepted receipt, the final decision and the
     new `controllerFinalCheckpoint` field all survive, exactly the invariant being proven).
4. Confirmed `kernel/amendment.mjs` needed no changes: it never imports `startup-lock.mjs`/`launch.mjs`
   and never touches `store.paths`; every one of its own functions already reads and writes exclusively
   through `store.saveState`/`store.appendEvent`/`store.readEvents`, which is why the file passed
   unmodified.

## Addendum from the lead (runtime-tree hygiene)

The lead traced the real root cause one level deeper than I had: `fixture()`'s `t.after` called
`store.close()` **before** `fs.rmSync`, so while `store.close()` was throwing `store-paths-removed:final`
(before my fix above), the temp directory was never removed at all — and because the fixture also
`mkdtemp`s into `process.cwd()` (the runtime tree itself, `.claude`) rather than `os.tmpdir()`, thirteen
`.workflow-amendment-test-*` roots and a live `.starciwork/` accumulated *inside the runtime this repo
ships*, not in a throwaway temp location. The lead swept the accumulated debris and added
`tests/runtime-tree-hygiene.spec.mjs` as a permanent gate (fails while any spec mkdtemps into the runtime
tree, or while any such leftover directory exists), naming `workflow-amendment.spec.mjs` as one of two
remaining offenders (`orca-headless.spec.mjs` is the other, not owned by this stream).

Fixed both halves in `fixture()`:
- `root=fs.mkdtempSync(path.join(os.tmpdir(),'starci-workflow-amendment-'))` instead of
  `path.join(process.cwd(),'.workflow-amendment-test-')`.
- `t.after(()=>{try{store.close();}catch{}fs.rmSync(root,{recursive:true,force:true});})` — cleanup no
  longer depends on `close()` succeeding; `rmSync` always runs. Dropped the two `assert.equal`/`assert.ok`
  checks on `root`'s location that only made sense when it lived under `process.cwd()`.

Also re-checked `store-paths-removed:final` itself, since the lead named it "the real failure": by this
point `kernel/store.mjs`'s `paths` Proxy had itself been fixed (by another stream, in between my wave-4
commit and this addendum) to properly support `paths.continuation` and `paths.final` (`` `ledger://final-
report/${workflowId}` ``) instead of throwing for those two keys specifically — confirmed via
`tests/store.spec.mjs:41`, which now asserts exactly that value. My own wave-4 fixture had worked around
the then-throwing property with a synthetic placeholder string (`'signal:final-report'`); replaced it with
the real `store.paths.final` now that the API behind it exists, rather than leaving a workaround in place
once the thing it was working around was fixed. Grepped the whole tree for any other `.paths.final` use:
none outside `tests/store.spec.mjs` and this one line.

`node --test tests/workflow-amendment.spec.mjs` → still 13/13 after both changes.
`node --test tests/runtime-tree-hygiene.spec.mjs` → `workflow-amendment.spec.mjs` no longer named in
either check (only `orca-headless.spec.mjs` remains, not mine).
`npm test` (full suite, after this addendum's fix): **2268 tests, 2208 pass, 54 fail, 6 skip** — zero
`workflow-amendment` matches in the failure list.
