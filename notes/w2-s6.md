## Root cause found and fixed

The lead's port of `hosts/orca/protocol.mjs`'s `report`/`wait` onto `store.writeReport`/`readReports`
(§8/§9, `--workflow` now required) left `singleTick` referencing two names that no longer exist:
`directory` (never assigned — the old `reportsDirectory(cwd,run,reportsDir)` call was deleted but the
`path.join(directory,'wait-state.json')` line below it was not) and, by extension, a `wait-state.json`
file with nowhere left to live now that `store.paths.*` is gone (§8: "paths.state/events/goal… removed").
This was a `ReferenceError`/broken-state bug in production code, not a test-only drift, and it is why
every `waitTick`-driven test failed with "Missing workflow id" one line before the real crash (the
`required(workflow,...)` in `withStore`/`createStore` fired before the broken line was ever reached).

Fix, in `hosts/orca/protocol.mjs`:
- The delivery cursor + seen-report set (`wait-state.json`) now lives in one `signals` row, keyed
  `wait-state:<run>`, scoped to the workflow (`store.signal.set(workflowId, 'wait-state:'+run, {value})`) —
  the same table `kernel-lock`/`stop` already use for small keyed operational records that are not
  workflow state, so no schema change was needed. `singleTick` opens the workflow's store once (report
  rows + the signal row + the final write), instead of the dead `readJson(stateFile,...)`/`writeJson(...)`.
- Removed the now-dead `withStore` helper (nothing called it after the fix — `singleTick` opens its own
  store directly) and the now-dead `writeJson` (only used by the removed `wait-state.json` write).
- `usage()` in `hosts/orca/launch.mjs` and the help text in `cli/main.mjs` still documented `report`/`wait`
  with the retired `--reports-dir <dir>` flag and no `--workflow`; updated both to the real flags
  (`--workflow <workflow-id>` required, `[--op <op>] [--attempt N]` new on `report`).

Retired the three dead exports from `kernel/reports.mjs` per instruction (`reportsDirectory`, `reportPath`,
`readReports(directory)` — the file-based ones; `store.readReports()` is a different function on a
different module and is unaffected): grepped every `from '.../kernel/reports.mjs'` import in the repo
first and confirmed only `tests/reports.spec.mjs` used any of the three (no production code did — the
port to `store.writeReport`/`readReports` was already complete on the production side). Removed the now-
unused `fs` import from `kernel/reports.mjs` alongside them.

## Not rooted in this cluster (fix belongs elsewhere — diffs below, not applied)

### 1. `scripts/ledger-migrate.mjs` imports a name `kernel/engine.mjs` no longer exports

`tests/cli-ledger-commands.spec.mjs`'s `ledger-migrate forwards to scripts/ledger-migrate.mjs...` test
crashes the whole `ledger-migrate` verb (via `hosts/orca/launch.mjs`'s dynamic
`import('../../scripts/ledger-migrate.mjs')`):

```
SyntaxError: The requested module '../kernel/engine.mjs' does not provide an export named 'journalFileFor'
```

`journalFileFor` was removed from `kernel/engine.mjs` when s2 ported engine/admission onto
`kernel/ledger-db.mjs`'s two-phase reservation (journal.sqlite is fully retired; `git log -p --follow --
kernel/engine.mjs` shows the export deleted in `ba273836 kernel(s2): port engine/admission to ledger-db
two-phase reservation`). Its only use in `scripts/ledger-migrate.mjs` was as the default value of the
already-optional `--journal-file` flag (§10: `starci ledger-migrate --repo <root> [--journal-file <old>]
[--dry-run]` — there is no more canonical journal.sqlite location to default to under 1.0.4 anyway).
Neither file is in this cluster (`scripts/`, `kernel/engine.mjs`); the exact fix is a two-line diff in
`scripts/ledger-migrate.mjs`:

```diff
 import {inspectJournal} from '../kernel/journal.mjs';
-import {journalFileFor} from '../kernel/engine.mjs';
 import {pidAlive} from '../kernel/loads.mjs';
 ...
-export async function migrateLedger({repoRoot,journalFile=journalFileFor(),machineFile=machineFileFor(),dryRun=false,archive=false,now=Date.now,pidAliveFn=pidAlive}={}){
+export async function migrateLedger({repoRoot,journalFile=null,machineFile=machineFileFor(),dryRun=false,archive=false,now=Date.now,pidAliveFn=pidAlive}={}){
```

(`journalFile=null` then flows into `journalFile&&fs.existsSync(journalFile)?inspectJournal(...):null`
a few lines down, which already handles a falsy `journalFile` correctly — confirmed by reading the rest
of the function.)

### 2. Model-registry drift (`gpt-5.6-luna` vs `gpt-5.6-sol`), pre-existing, not this cluster's data

`tests/orca-headless.spec.mjs`'s "a dead pid is a dead worker..." and "providerFor maps the launcher's
agent and model..." both expect `gpt-5.6-sol` and observe `gpt-5.6-luna`. This is the exact drift
`notes/s0.md` (wave 1) already flagged as unrelated to the ledger-db work and outside every stream's
owned files ("None of these touch kernel/ledger-db.mjs... or any file this stream owns"). Root cause is
in `model/registry.yaml`/`model/codex.yaml`/`model/runtimes.yaml` (which pool a `codex-agent` request
resolves to first) — none of which are `hosts/orca/*`, `kernel/reports.mjs`, or `cli/`. Not touched.

### 3. `kernel/supervisor.mjs`'s `inspectWorkflow` no longer reads the fixture this test writes

`tests/orca-headless.spec.mjs`'s "the supervisor starts the next kernel of a headless workflow..." writes
a raw `.starciwork/_local/workflows/w1/state.json` file by hand and expects
`inspectWorkflow({id:'w1',dir}).hostAdapter` to read `'headless'` back out of it; it reads `null` instead.
`inspectWorkflow`/`startKernel` are exported by `kernel/supervisor.mjs`, not this cluster. Given §1 ("the
kernel never writes or reads `.starciwork/_local` again") this looks like `inspectWorkflow` was correctly
ported to read the ledger and the *test* fixture is the one still writing the pre-1.0.4 file shape — but
confirming that, and writing a ledger-backed fixture in its place, needs `kernel/supervisor.mjs`'s current
`inspectWorkflow` signature, which is out of this cluster to read closely. Flagging for whichever stream
owns `kernel/supervisor.mjs` rather than guessing at its ledger-backed shape from outside.
