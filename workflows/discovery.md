# Goal discovery and project workflow storage

Before confirmation, render the reviewed discovery with `node scripts/session-open.mjs preview <session>` according to [interaction.json#scopePresentation](../resources/interaction.json).

The executable contract is [delivery.json](../resources/delivery.json), [goal-discovery](../templates/kinds/goal-discovery.schema.json), and [workflow-root.mjs](../scripts/workflow-root.mjs). The runtime stays under Source. A project declares one workflow owner role in `.workspaces/projects/<project>/workflow.json`; its hydrated canonical route resolves Workflow. All routed repositories of that project share this workflow evidence home. The central runtime, route declarations and environment declarations remain Source-owned.

Open the draft ledger before discovery. Read-only inspection of declared route files and repository identity establishes actual route patterns, generalized code ownership, repository heads, verification reach, final destinations and remaining material decisions. Discovery does not create an implementation worktree. Use `session-open.mjs discover` to record the reviewed result. The goal-discovery schema records one planned or justified not-applicable handoff disposition per delivery lane, including inputs, outputs, owner, dependencies and verification. The planner derives applicable operators from those impacts and the operator contracts. A handoff stage plans future implementation and evidence without authorizing product writes, runtime operation or publication.

Confirmation binds the exact scope hash. An opening-scope claim retains the user's actual statement and excerpts explicitly covering the goal, impact, destination, stage and verification; a vague instruction or task creation is insufficient. A scope-answer instead records the displayed scope hash with the actual answer reference. A bank approval remains bound to the unchanged approved bank. The gate checks source bindings and unresolved decisions before activation. Already authorized complete scope needs no repeated routine approval.

Old sessions and UAT runs are historical records, never current execution authority or completion proof. Archive them outside active workflow coordinates, retain product source and actual user decisions, then open a fresh current session and produce current plans, requests and UAT evidence. There is no in-place migration or original-contract replay adapter. Relocation and retirement markers deny writes to retired roots. The current wire contract remains starci/v2.2; runtimeRevision 3 and the current owner, topology and frozen discovery gates govern execution.

A planned read-only prerequisite may bind a declared route outside product code impact only when its concrete goal enables a confirmed delivery operator whose authored required Context names that role. The bind remains `checkout: routed`, carries no declared write roots or environment writes, and verifies the actual portable/hydrated route and canonical Git checkout. It adds no repository to discovery and grants no product source writes; those still require the confirmed code-impact role. `scripts/mission-scope.mjs#readOnlyPrerequisiteBinding` enforces this boundary.

A coordinated mission may retain a peer-executed impact through the goal-discovery schema's `producer` selector: the original session, impact id and sealed mission address. Copy its actual role, routes, code, behavior, tags and evidence. This keeps the full product scope visible while assigning local closing evidence to `workflow.verify`; it grants the coordinator no product source writes and does not require duplicate product generation. Confirmation and new admission verify that the selected original mission remains current. A later authorized execution extraction keeps these original goals and accepted receipts; the coordination commands described in [README.md](README.md) derive only the selected subset for its new owner, without another user approval for the same authorized decomposition.
