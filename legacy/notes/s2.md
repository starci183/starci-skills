## Contract addendum (2026-09-17, docs/ledger-db.md @ 826894e5 — meta-uuid identity, WAL default, §12 anchor)

Merged `main` (brought `826894e5` in) and re-read §§2-6 and the new §12. My part, per the lead's message:

- **Key the machine side by `ledgerIdOf(ledger)`, never a realpath digest.** `admission.mjs` had exactly
  one place doing this itself: `const ledgerId=journal.ledgerId??ledgerIdFor(journal.path??journal.file)`
  — the fallback used `ledgerIdFor` (realpath digest). Fixed: `admission.mjs` now imports `ledger-db.mjs`
  as a namespace (`import * as ledgerDb`) and computes ledger identity through a local `ledgerIdOf(handle)`
  that calls `ledgerDb.ledgerIdOf(handle)` when the linked module exports it, falling back to
  `handle.ledgerId` (what `openLedger` already sets today) only because **`kernel/ledger-db.mjs` itself
  hasn't shipped `ledgerIdOf`/`meta.ledger_id` yet** — see "still on s0's older module" below. The
  namespace import means this resolves to the real meta-based function automatically the moment s0 ships
  it, with no further change on this end; it never computes a path digest itself either way. Added a spec
  (`admission.spec.mjs`, "admission keys the machine side by the ledger's own identity...") pinning that
  `admission.ledgerId` is exactly the handle's own identity, not something this module derived.
  `engine.mjs`/`job-worker.mjs` never computed a ledger id themselves (they only pass handles through), so
  nothing else to change there.
- **`verifyAnchor` at the continuation boundary.** I do not own it — `kernel/continuation.mjs` is not in
  s2's file list. The exact call requested is below under "Requests to other streams".

**Still on s0's older module contract, not mine to fix:** the linked `kernel/ledger-db.mjs` (the file s0
delivered before this docs change landed) still has `ledgerIdFor(file)` computing a realpath sha256, no
`meta` table, `openLedger`/`openMachine` defaulting to `journalMode='DELETE'`/`busyTimeoutMs=5000` (docs
now say WAL-by-default/15000), and no `verifyAnchor`/`ledgerIdOf`/`ledger-anchor.json` writing at all.
`starci183/s0-ledger-db`'s tip (`2ae95d3d`) is only a merge of `main`'s docs commit, not a reimplementation
— re-merge this branch again once s0 pushes the actual §3/§4/§5/§12 module update.

## Files changed

- `kernel/admission.mjs` — rewritten. `reserve`/`release`/`settleUnknown`/`expire` all run through
  `reserveTwoPhase`/`releaseTwoPhase` from `kernel/ledger-db.mjs` (the real module s0 landed on
  `starci183/s0-ledger-db`, merged into this branch twice — see "Merges" below). Repo-scoped resources
  stay ledger-only; `ai/*` and `machine:*` needs split off to the machine DB (`machineScoped()`, defined
  locally here since `ledger-db.mjs` doesn't export it — see requests below). Budgets aren't known to the
  two-phase primitives (§6 of the contract only covers leases), so they're reserved/returned around the
  `reserveTwoPhase` call in a second ledger transaction, and fully unwound — leases released, job put back
  to `queued` — on a partial budget failure, so nothing is ever left half-held. A `status==='queued'`
  precheck avoids `reserveTwoPhase`'s `need()` throw on a job that isn't queued, restoring the old
  contract of returning `{ok:false,reasons:[...]}` instead of throwing (this matters: `kernel/jobs.mjs`'s
  `claimNext` calls `admission.reserve` with no try/catch, so a throw there would crash the claim loop
  under an ordinary claim race). `runExpire()` (the old `expire()` transaction) now also runs at the top
  of every `reserve()`, matching pre-1.0.4 behavior — dropped in the earlier scratch-API pass, caught by
  the new admission spec.
- `kernel/engine.mjs` — `enrollEngine` now opens the machine DB, then the ledger registered against it
  (`openLedger({file,now,machine})`, which self-registers via `machine.registerLedger`), writes
  `state.engine.{ledgerFile,machineFile}` (`journalFile` is gone, `journalFileFor` is deleted per
  contract), and binds the store to the ledger handle. `settleGenerationLeases`, `staleLeaseProof`,
  `settleNeverStartedModelJobs`, `unsettledGenerationJobs`, `prepareGenerationRetry` each open a
  ledger+machine pair per call (`openPair`/`closePair`) and settle jobs through a local `settleJob`
  helper that reads a job's `machine_ref` leases *before* `jobs.complete()` (kernel/jobs.mjs, not owned)
  drops the rows, then releases them — `jobs.complete()` itself has no idea `machine_ref` exists, so
  without this wrapper every model/operation job settlement would leak its `ai/*`/`machine:*` machine
  lease forever. `createEngineRuntime`'s `createJobBridge(...)` call is repointed at `ledgerFile`/
  `machineFile` (job-bridge.mjs itself is not ported — see requests). All other `journal`/`admission`
  methods used through `createEngineRuntime` (reserveOperation, reservationPhase, settleStoppedOperation,
  settled, launched, pulse, …) needed no change beyond what the earlier pass already did: they call
  generic `journal.*`/`admission.*` methods that work the same whether `journal` is a ledger-db handle
  opened by `enrollEngine`/`createJobBridge` or (in the standalone module functions) by `openPair`.
- `kernel/job-worker.mjs` — the detached wrapper (`runDurableJob`) now opens the ledger via `openLedger`
  registered against its own `openMachine` handle (`ledgerFile`/`journalFile` alias, `machineFile`
  optional), and settles jobs through the same machine_ref-release wrapper pattern as engine.mjs
  (`completeSettled`), for the same reason: `jobs.complete()` doesn't release machine leases on its own.
- `tests/admission.spec.mjs` (new) — the admission-only cases ported off `tests/kernel-engine.spec.mjs`
  (not owned; see below) onto `openLedger`/`openMachine`, plus everything §6/§11 of the contract asks
  for: two-phase machine-capacity failure leaves 0 ledger leases and 0 machine leases; a crash simulated
  between release's two phases (ledger commit, then `machine.release`) is swept clean by `machine.sweep`;
  plus three more (`ai/*` vs repo-scoped capacity routing to the right DB; a partial budget failure
  rolling back a successful two-phase reserve; the `leases_match_job` trigger surfacing as
  `lease-identity-drift`). All 8 pass in isolation.
- `tests/engine-adapter.spec.mjs`, `tests/w5-retry-coverage.spec.mjs` — mechanically ported off
  `state.engine.journalFile` / bridge `journalFile:` params onto `ledgerFile`+`machineFile`. The two
  `w5-retry-coverage` tests that only needed a journal handle to seed fixture jobs now open
  `openLedger`/`openMachine` directly instead of going through `createJobBridge`, so they no longer
  depend on job-bridge.mjs at all.

`kernel/kernel.mjs:3` imports `journalFileFor` from `./engine.mjs`. Per contract: *"`journalFileFor` is
deleted from engine.mjs (s7's migrator imports it from journal.mjs)"* — and it is deleted, on purpose.
Since `kernel.mjs` still imports it, **every test file that transitively imports `kernel/kernel.mjs`
fails to load at all** (`SyntaxError: The requested module './engine.mjs' does not provide an export
named 'journalFileFor'`). That's the large majority of the suite, including both of my own
`engine-adapter`/`w5-retry-coverage` specs.

Fix: drop `journalFileFor` from that import line; import it from `./journal.mjs` instead if `kernel.mjs`
still needs the *old* journal path for something journal.mjs-specific, or from `./ledger-db.mjs`'s
`ledgerFileFor` if what it actually needs is "where does a fresh workflow's ledger file live."

Once that line loads, `kernel.mjs` has extensive further `state.engine.journalFile` / `openJournal`
usage that needs the same 1.0.4 port this stream did for `engine.mjs`/`admission.mjs`/`job-worker.mjs`.
Call sites (grepped, not exhaustive beyond this file):

### 2. `kernel/job-bridge.mjs` (not owned — likely s4-boundary-bridge)

Still entirely on the retired `kernel/journal.mjs` (`openJournal({file:journalFile})`,
`createAdmission({journal,now})` with no machine). `journal.mjs`'s `leases` table has no `machine_ref`
column and no `leases_match_job` trigger, so as soon as anything calls `bridge.request(...)` → 
`admission.reserve(...)` → `reserveTwoPhase`'s `INSERT INTO leases(...,machine_ref)`, it will throw
`no such column: machine_ref` — a hard break, not a silent one, until this is ported.

Requested shape (this is what `kernel/engine.mjs`'s `createEngineRuntime` now calls):

```js
export function createJobBridge({ledgerFile,machineFile,now=Date.now,spawnChild=spawn,workerFile=...,eligibility,beforeSpawn=null}={}){
  const machine=openMachine({file:machineFile??machineFileFor(),now});
  const journal=openLedger({file:ledgerFile,now,machine});
  const admission=createAdmission({journal,machine,now});
  ...
  return {journal,machine,admission,request,poll,close(){journal.close();machine.close();}};
}
```

`kernel/job-worker.mjs` (mine) already accepts `ledgerFile`/`machineFile` (with `journalFile` kept as a
legacy alias) for the detached wrapper's own connection, and spawns
`[workerFile, journal.path, jobId, leaseToken]` positionally — that part of the contract is unaffected by
this rename, only `createJobBridge`'s own signature needs to change. `kernel/job-model-worker.mjs` (not
owned, spawned by `job-worker.mjs`'s `runModelWithHeartbeat` with a bare file path) will need the same
`openJournal`→`openLedger`+`openMachine` port; I pass it whatever ledger path I'm given today
(positionally, unchanged), so it isn't newly broken by this stream, but it's still on the old journal.

### 3. `kernel/jobs.mjs` (not owned)

`complete()` deletes `leases` rows and updates `jobs` directly by raw SQL; it never reads or releases
`machine_ref`. Every caller of `jobs.complete()` that isn't going through my `settleJob`/`completeSettled`
wrappers (i.e. any caller outside `kernel/engine.mjs` and `kernel/job-worker.mjs`, both mine) leaks the
job's `ai/*`/`machine:*` machine lease until `machine.sweep()`'s TTL reaping catches it. Requested fix:
mirror the pattern already in this stream's two files — read `machine_ref` leases for the job before the
delete, release them after a successful commit. `createJobs({journal,admission,...})` would need a
`machine` handle threaded through for this (today it only takes `journal`/`admission`).

### 5. `kernel/continuation.mjs` (not owned) — `verifyAnchor` at the continuation boundary

Per the 2026-09-17 contract addendum (docs §12): a restored, rolled-back or rewritten ledger must fail
closed instead of resuming. `continuationBoundary(state,{journalView=readJournal(state),controller})` is
the continuation boundary today, and it's still entirely on the retired `kernel/journal.mjs`
(`readJournal` at `continuation.mjs:29` calls `inspectJournal({file:state.engine.journalFile})`; that
whole helper needs the same `state.engine.journalFile`→`ledgerFile`/`inspectJournal`→`inspectLedger` port
every other stream's `state.engine.journalFile` reader needs). Once it's reading the ledger, the requested
call — using `findings.push`/`issue(code,detail,identity)`, the pattern every other check in that function
already uses — is, once per workflow, right after (or folded into) the ledger-open step:

```js
const anchor=verifyAnchor({repoRoot:/* the ledger's repo root, i.e. path.dirname(path.dirname(ledgerFile)) */,
  ledger /* the open or inspected ledger handle */, workflowId:state.id});
if(!anchor.ok)issue(anchor.code /* 'ledger-behind-anchor' | 'ledger-missing' | 'ledger-identity-mismatch' */,
  anchor.detail??anchor.reason,{});
```

`verifyAnchor` itself isn't shipped by `kernel/ledger-db.mjs` yet either (see "still on s0's older module"
above) — docs §12 names the three fail-closed codes and what each checks (anchor's `eventsHead`/`seq`
must exist in `events`; `state_snapshots` must hold a checkpoint at or after the anchor's `generation`;
`meta.ledger_id` must match the anchor's `ledgerId`), but doesn't give the function's exact call shape, so
I'm not inventing one — whoever owns `continuation.mjs` and whoever finishes `ledger-db.mjs` should agree
on it together. The important part for the continuation boundary specifically: it must run per-workflow,
before anything treats `journalView.snapshot`/durable state as resumable, and a failure must become a
`findings` entry (or an equivalent fail-closed refusal) rather than being swallowed — the same way every
other invariant in that function already reports rather than throws, so the boundary keeps surfacing every
problem it finds instead of stopping at the first one.

## Open questions

- `kernel.mjs:4807`'s `journalFileFor()` fallback for `retryJournalTarget` — is the post-1.0.4
  equivalent `ledgerFileFor(repoRoot)` (repo-scoped, matching `enrollEngine`'s default), or does
  `--journal-file`/relocation still want a machine-local default? I didn't touch `kernel.mjs` (not
  owned) so I'm not answering this myself; flagged above for whoever ports it.
- `kernel/ledger-db.mjs` doesn't export a `machineScoped(key)` helper even though the machine/ledger
  split (`ai/*`, `machine:*` vs everything else) is exactly the kind of thing every caller needs
  consistently. I defined it locally in `admission.mjs` (one line) rather than ask for an s0 change, per
  "pick the reading that changes the fewest other files." If another stream needs the same predicate,
  it'd be worth s0 exporting it from `ledger-db.mjs` instead of it being copied around.
- Budgets (`budgets`/`setBudget`/`budget_reservations`) aren't mentioned anywhere in
  `docs/ledger-db.md` §6's two-phase design, only in §4's schema. I kept them fully working (see
  `admission.mjs`'s `reserveBudgets`/`returnBudgets`), reserved/returned around the two-phase call rather
  than inside it, since `reserveTwoPhase`/`releaseTwoPhase` know nothing about them and I don't own
  `ledger-db.mjs`. This is a real atomicity seam (two ledger transactions instead of one) but every
  failure path is still fully unwound, verified by the "partial budget failure" spec.
