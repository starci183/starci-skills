# s4 — continuation boundary, candidate bridge, custody boundary

## Files changed

- `kernel/continuation.mjs` — `readLedger`/`continuationBoundary` read `state.engine.ledgerFile` via
  `inspectLedger`/`verifyChain`/`verifyAnchor` instead of `journalFile`/`inspectJournal`. New fail-closed
  reasons: `ledger-unmigrated` (journalFile present, no ledgerFile), `ledger-chain-broken` (`verifyChain`
  fails), `ledger-head-mismatch` (live event head newer than the latest snapshot's `events_head` and no live
  kernel-lock signal), and the §12 anchor trio `ledger-missing` / `ledger-identity-mismatch` /
  `ledger-behind-anchor` (via `verifyAnchor`, checked before the hash chain — the anchor is what makes a
  self-consistent-but-restored ledger detectable at all). `readController` reads the `kernel-lock` signal
  from the ledger's `signals` table instead of `kernel.lock`. Retained the 1.0.2 rule that a lease binds
  `job.generation`, not the current enrollment.
- `kernel/common.mjs` — `predatesEngineSchema` is true for any state carrying `journalFile` without
  `ledgerFile` (in addition to the old numbered-marker check). New `coversLedgerScope(entry)`, used by both
  the candidate-bridge guard and `candidate-roots.mjs`'s allowlist compiler: refuses `.starciwork`,
  `.starciwork/**`, and `runtime.sqlite`/`-journal`/`-wal`/`-shm`.
- `kernel/candidate-bridge.mjs` —
  - `durableProjection`/`lastCustodySeq`/`custodyReceipt`/writer records now read the ledger via
    `inspectLedger`/`ledgerFileFor`, not `inspectJournal`. `journalFile` fields renamed to `ledgerFile`
    throughout (including the two-generation-transition path in `currentRuntimeWriter`).
  - `runtimeWriters(root,ownWorkflow,git)` is rebuilt: instead of scanning
    `.starciwork/_local/workflows/<id>/state.json` files on disk, it queries every workflow's latest
    `state_snapshots` row directly from this repo's one shared ledger (`ledgerFileFor(root)`), since 1.0.4
    puts every workflow of a repo in the same `runtime.sqlite`.
  - `runtimeInternal`/`DEFAULT_EXCLUDED` now exclude the whole `.starciwork` subtree (previously only
    `_local`); `runtimeLocalPaths` walks all of `.starciwork` except the ledger record files themselves
    (`ledgerRecord()`), which are never inventoried — their custody comes from the allowlist refusal, not
    post-hoc diffing.
  - New custody classification in `freezeSingleDetectionCandidate`: an observed `.starciwork` change outside
    the operation's allowlist is `custody-path-touched` (`source:`/`work:` prefixed), never
    `outside-allowlist` or ordinary scope drift.
  - `housekeepingFiles(identity)` — **see the fix below**, this went through two shapes in this branch's
    history.
  - `beginSingleDetectionCandidate` refuses any allowlist entry with `coversLedgerScope` before doing
    anything else (`scope-covers-ledger`).
- `kernel/candidate-roots.mjs` — `candidateRootBindings`'s `add()` refuses an `allowlist` entry that
  `coversLedgerScope` (same reason string), independent of the candidate-bridge check, since this is the
  "allowlist compiler" referenced in §7 for the multi-root path (there is no `kernel/scope.mjs`; I looked and
  confirmed it doesn't exist — this function is where raw allowlist entries get compiled into routed
  bindings, so it's the right place).
- `scripts/runtime-modules.txt` — added `kernel/ledger-db.mjs`. It was missing from the build's runtime
  module inventory after s0 landed the file, which made `ensure-build.mjs` (and therefore `node --test`
  against anything importing `kernel/chains.mjs`/`core/runtime-root.mjs`) fail for **every** stream, not just
  s4. One-line, purely additive; flagged here in case another stream's branch also touches this file.
- Tests ported from journal to ledger fixtures: `tests/workflow-continuation.spec.mjs`,
  `tests/candidate-bridge.spec.mjs`, `tests/candidate-multi-root.spec.mjs` (details below).

## A regression I introduced and then fixed on this same branch

First pass at `housekeepingFiles(identity)` assumed the *target* 1.0.4 shape was already true everywhere —
that the kernel's only `.starciwork` footprint is the ledger record — and dropped the old per-identity
exemption for the current operation's own `_local/workflows/<id>/{state,events,checks,reports}` files. That
assumption is correct for my own files but **not yet true of `store.mjs`/`kernel.mjs`/`engine.mjs`**, which on
this branch still project state to `.starciwork/_local/workflows/<id>/…` on every save. With the exemption
gone, any real kernel+store retry/stop/reconcile cycle saw its own ordinary housekeeping writes as
`custody-path-touched` and refused to seal, which broke `tests/w1-reconcile.spec.mjs` (not mine),
`tests/workflow-kernel-shared-ledger.spec.mjs` (not mine), and one case in my own
`workflow-continuation.spec.mjs`. Fixed by restoring the named-identity exemption (state.json, events.jsonl,
kernel.lock, stop.flag, this op's checks/reports, and the ledger-wide supervisor.lock/runtime-loads/
runtime-budget/supervisor.log files) **in addition to** the ledger record files — everything else under
`.starciwork`, including a stray file under the current workflow's own `_local` tree, still classifies as
custody evidence. Once `store.mjs` stops writing `_local` this list simply goes unused; nothing else needs to
change here when that lands. Verified against `tests/w1-reconcile.spec.mjs` (5/5 pass) and
`tests/workflow-kernel-shared-ledger.spec.mjs` (4/5 pass, the 5th is the cross-stream block below) after the
fix.
