## Root-cause finding: only 2 of the 5 named errors are store.mjs's fault

I traced every one of the 5 named error strings to its actual throw site and caller before touching
anything. Two are genuine §8 API gaps in `kernel/store.mjs` (fixed here). Three throw through code paths
that never touch `kernel/store.mjs` at all, or that store.mjs already serves correctly for every real
production caller — the failures are in test fixtures (and in one case a foreign file's own hand-rolled
stub) that predate 1.0.4 and were never ported. I did not "fix" those by loosening a guard or editing a
test to paper over broken behaviour; I verified the real fix by applying it locally, confirmed the named
error drops to 0, then reverted the non-owned files and pasted the verified diff below.

## Fixed in this stream (kernel/store.mjs)

### `store-paths-removed:final` (13) and `store-paths-removed:continuation` (17-19)

Real callers, not test stubs: `kernel/continuation.mjs`'s `bindContinuationPath` does
`store.paths.continuation=target` (three call sites, to bind the *resolved* projection target — an
explicit override, an existing canonical file, or a friendly-identity match — none of which is just the
fixed `store.continuation` string), and `buildContinuationBrief` reads `` `Inspect the final report at
${store.paths.final}` ``. Neither `continuation` nor `final` has a dedicated method anywhere in §8's table
(the table's `paths.state/events/goal…` row covers what's replaced by `goal()`/`loadState()`/etc.; it never
named these two). That's the actual gap: not a missing guard, a missing surface.

Fix (`kernel/store.mjs`, in the `paths` Proxy): `continuation` is now a real get/set — get returns
`continuationOverride ?? api.continuation` (the canonical default), set resolves and stores an override,
exactly matching how `continuation.mjs` already uses it. `final` is a real get-only, returning
`` `ledger://final-report/${workflowId}` `` — a stable reference in the same `ledger://` scheme §4 already
uses for `inputs`, backed by the existing `signal` `'final-report'` key (`kernel/kernel.mjs:3106` already
writes there: `store.signal.set(store.id,'final-report',{value:final})`). Every other `paths.*` key is
untouched and still throws `store-paths-removed:<name>`.

Added a spec case to `tests/store.spec.mjs` (`opening a store...` test) asserting the new real surface;
removed `final`/`continuation` from the list of keys expected to throw (they're no longer removed, they're
real).

Verified: `grep -c "store-paths-removed:final\|store-paths-removed:continuation"` on a full `npm test` run
is 0/0 after this fix (was 13 and ~17-19 before). `tests/store.spec.mjs` 21/21 green.

## Not this stream's fault — root cause, verified fix, reverted from my worktree

For each of the three below I made the change locally in the *foreign* file, ran the exact test, confirmed
the named error count dropped to 0, then `git checkout --` the file (never committed — not mine to touch)
and paste the verified diff here per the wave-2 instruction.

### `store.writeChecks is not a function` (5) — `tests/kernel-seams.spec.mjs`

All 5 are `tests/kernel-seams.spec.mjs`'s own local `stubStore(dir)` fixture (not `createStore` — a
hand-rolled object), still shaped for 1.0.3 (`paths`, `checksPath`, `contractPath`, `reportPath`). Real
`kernel/store.mjs` has had `writeChecks`/`readChecks` since wave 1; `kernel/kernel.mjs:2435`
(`applyOpReport`) calling `store.writeChecks(...)` is correct against the real store.

Verified fix (`tests/kernel-seams.spec.mjs`, in `stubStore`):
```diff
     readReports(){return [];},
     checksPath:id=>path.join(dir,'checks',`${id}.json`),
     contractPath:id=>path.join(dir,'contracts',`${id}.md`),
-    reportPath:dispatch=>path.join(dir,'reports',`${dispatch}.json`)};
+    reportPath:dispatch=>path.join(dir,'reports',`${dispatch}.json`),
+    writeChecks(){},
+    readChecks(){return null;}};
```
Result: `node --test tests/kernel-seams.spec.mjs` → 0 occurrences of the named error (was 5); 36/38 pass (2
unrelated pre-existing failures, not this error). This is a two-line, low-risk diff — whoever owns this
file (kernel.mjs/kernel-seams, likely s3) should be able to land it directly.

### `ledger-binding-mismatch:wf` (10) — `tests/kernel-engine.spec.mjs`, `tests/w1-reconcile.spec.mjs`, `tests/engine-lifecycle.spec.mjs`

`store.bindJournal`'s file-identity check (`kernel/store.mjs:163`, unchanged by me) is correct: it refuses
when the handle it's given isn't opened on the *same* ledger file the store itself opened. I confirmed this
against real production code — `kernel/engine.mjs:enrollEngine` defaults `ledgerFile` to
`ledgerFileFor(store.repoRoot)`, i.e. always the store's own file. These three test files instead construct
a *separate* `journal.sqlite`/`runtime/journal.sqlite` path via the retired `openJournal` (`kernel/journal.mjs`)
and bind that mismatched handle — pre-1.0.4 fixtures never ported to the single-ledger model. Loosening the
check to tolerate a different file would silently defeat §2's whole point ("everything a workflow needs
lives in one file"), so I did not touch `bindJournal`.

Verified fix — swap the mismatched `openJournal`+separate-path construction for `openLedger`+`ledgerFileFor`
on the store's own repo root, in every call site that feeds a handle to `store.bindJournal`:

**`tests/kernel-engine.spec.mjs`** — add `import {openLedger,ledgerFileFor} from '../kernel/ledger-db.mjs';`
after the `journal.mjs` import, then replace every `openJournal({file:path.join(repo,'journal.sqlite')})`
with `openLedger({file:ledgerFileFor(repo)})` (6 occurrences, lines ~172, 177, 196, 203, 208, 213 — all the
ones using the `repo` variable; leave the `dir`/`temporary()`-scoped `openJournal` calls elsewhere in the
same file alone, they test `journal.mjs` itself, unrelated to store binding). Note: one of these tests
(`journal-bound store recovers committed state...`, line ~172) *also* uses `store.paths.state` — a
genuinely-removed key with no replacement (§8 explicit) — so fixing the binding alone won't turn that one
test green; it needs its own rewrite (drop the JSON-projection-torn-file assertion, use `loadState()`), out
of scope for this diff.

**`tests/w1-reconcile.spec.mjs`** — add the same import, then:
```diff
-  const journalFile=path.join(root,'runtime','journal.sqlite'),machineFile=path.join(root,'runtime','machine.sqlite');
+  const journalFile=ledgerFileFor(work),machineFile=path.join(root,'runtime','machine.sqlite');
```
and change `heldLease`/`jobStatus` (the two helpers reading `journalFile` for assertions) from
`openJournal({file:journalFile})` to `openLedger({file:journalFile})` (their `.db`/`.getJob` calls are
otherwise identical across both modules).

**`tests/engine-lifecycle.spec.mjs`** — add the same import, then:
```diff
-  const root=fixture(t),store=createStore({repoRoot:root,id:'wf'}),journal=openJournal({file:path.join(root,'journal.sqlite')});
+  const root=fixture(t),store=createStore({repoRoot:root,id:'wf'}),journal=openLedger({file:ledgerFileFor(root)});
```
(leave the file's *other* `openJournal`/`openJournalForStale` import and usage alone — that one tests
`engine.mjs`'s `staleLeaseProof` against a raw journal-shaped file directly, never binds a store to it.)

Result after all three: `grep -c ledger-binding-mismatch` across all three files is 0 (was 10). Remaining
failures in those files after the fix are pre-existing and unrelated (an `inspectLedger` handle missing
`getJob` in `kernel/engine.mjs:86`'s `staleLeaseProof`, an `events.digest NOT NULL` constraint in
`kernel/jobs.mjs:35`, `no such table: meta` in `kernel/admission.mjs`, a runtime-pin assertion, EPERM
cleanup races) — none of them are this cluster's error string, so out of scope here.

### `Missing workflow id` (12) — `hosts/orca/protocol.mjs` callers

All 12 throw inside `hosts/orca/protocol.mjs`'s own `required(workflow,'workflow id')` (lines 29-30,
41/108), never inside `kernel/store.mjs`. `reportOutcome`/`waitTick` now require a `workflow` id to open a
real ledger-backed store (`createStore({repoRoot:repositoryRoot(cwd),id:workflowId})`) — this is real,
correct 1.0.4 behaviour (§9: workers give/take data through the CLI against the workflow's own ledger rows).
The callers are three pre-1.0.4 test files that never pass `workflow` and, worse, still assert against a
`reportsDir` file-based API (`reportsDir:path.join(store,'reports')`, reading raw `ctx_*.json` files back
off disk) that no longer exists — `reportsDir` isn't even in `reportOutcome`'s destructured parameter list
any more (`hosts/orca/protocol.mjs:40`), so it's silently ignored today.

I did not attempt a mechanical one-line diff here: unlike the other two clusters, this isn't a single
substitution. `tests/reports.spec.mjs` (8 of the 12) points `cwd` at the shared `fixtures/orca/agentos-r14-sales`
directory in this repo, which is wrong to reuse as a `createStore` repo root now that reporting is
ledger-backed (it would open/pollute that fixture's own `.starciwork/runtime.sqlite`) — it needs an isolated
temp repo per test, a `workflow` id, and its raw-file assertions (`fs.readFileSync(path.join(dir,'ctx_op.json'))`)
replaced with `store.readReports()`. `tests/orca-headless.spec.mjs` (1) and `tests/workflow-kernel.spec.mjs`
(3) need the analogous `workflow:` field threaded through from whatever store/workflow id each fixture
already tracks. This is a fixture redesign for whoever owns `hosts/orca/protocol.mjs` and these three test
files (routes to s6-cli by the `hosts/orca` path), not a diff I can respons­ibly write blind for files I
don't own and haven't traced end-to-end.

## Bonus finding, unrelated to the 5 named clusters: `tests/continuation-binding.spec.mjs` never closes its store

While verifying the `continuation`/`final` fix I found this file's `fixture(t)` opens
`createStore({repoRoot:root,id:'wf-one'})` and never calls `store.close()` before `t.after()` removes the
temp dir — a latent Windows EPERM-on-cleanup bug, independent of my change (I confirmed it reproduces on
the pre-fix tree too, just non-deterministically, since before my fix most of the 6 tests threw before doing
enough file I/O to hit the race; after my fix all 6 run to completion and hit it every time). Verified
one-line fix, reverted (not my file):
```diff
   const store=createStore({repoRoot:root,id:'wf-one'}),folder=path.join(root,'workflows');
+  t.after(()=>store.close());
```
placed alongside the existing `t.after(()=>fs.rmSync(root,...))`. Not one of my named clusters, so I left it
alone and am only flagging it here in case the owning stream wants the one-liner.
