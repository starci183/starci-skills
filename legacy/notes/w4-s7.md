### `kernel/view.mjs`'s `buildView` was never ported off the retired `_local` file layout — `workflow-status`/`workflow-tail`/`workflow-ops` are broken for every workflow, not just migrated ones

**Reproduction** (fixture: a realistic `_local/workflows/<id>/` directory with a complete `state.json` —
`kernel:'starci/workflow-kernel@1'`, `ops:[]`, `ledger:[]`, etc. — plus an old-schema `journal.sqlite` with
one settled job, mirroring `tests/ledger-migrate.spec.mjs`'s own fixture shape):

```
$ node bin/starci.mjs ledger-migrate --repo <fixture> --journal-file <fixture>/journal.sqlite
{"schema":"starci/ledger-migrate@1","ok":true,"workflows":[{"id":"…","imported":{…}}],"skipped":[],"refused":[]}

$ node bin/starci.mjs ledger-verify --repo <fixture>
{"schema":"starci/ledger-verify@1","ok":true,"results":[{"workflowId":"…","ok":true,"checked":3,"brokenAt":null,
  "anchor":{"ok":true,"checked":true,"reason":null}}]}                                    ← chain intact, anchor matches

$ node bin/starci.mjs ledger-migrate --repo <fixture> --journal-file <fixture>/journal.sqlite   (second run)
{"ok":true,"workflows":[],"skipped":[{"id":"…","reason":"already-migrated"}],"refused":[]}     ← clean no-op

$ cd <fixture> && node bin/starci.mjs workflow-status --id <id>
{"ok":false,"error":{"message":"No workflow state in <fixture>/.starciwork/runtime.sqlite"}}   ← BROKEN
```

Isolated the failure to the view layer, not the kernel or the migration, by calling `kernelMain` directly:

```js
const {kernelMain}=await import('./kernel/kernel.mjs');
kernelMain('workflow-status',{id:'…'},{cwd:'<fixture>'});
// → {phase:'run', approved:true, dir:'<fixture>/.starciwork/runtime.sqlite', id:'…'}   ← correct, reads the ledger fine
```

**Root cause**: `hosts/orca/launch.mjs`'s `workflow-status` dispatch (not owned) does

```js
const status=kernelMain(command,options,{orca:runner,cwd,wait});
const view=buildView({repoRoot:repositoryRoot(cwd),id:required(options.id,'workflow id'),dir:status.dir??null});
```

`status.dir` is `store.ledgerFile` — the path to `runtime.sqlite`, a *file* — because `kernel/kernel.mjs`'s
`kernelMainDispatch` (already ported) returns `dir:store.ledgerFile` for `workflow-status`
(kernel.mjs:4868), and `kernel/store.mjs`'s `dir` field is `null` under 1.0.4 (no `_local` directory is ever
created any more). But `kernel/view.mjs`'s `buildView` (not owned) was never ported at all — its own
docstring still says "every number below is derived from the workflow's own files: `state.json`,
`events.jsonl`, `kernel.lock`, `stop.flag`…", and its body does exactly that:

```js
export function buildView({repoRoot,id,now=Date.now(),dir:given=null}){
  const dir=given?path.resolve(given):workflowDir(repoRoot,id);
  const state=readJson(path.join(dir,'state.json'));   // path.join(<a .sqlite file>, 'state.json') → never exists
  need(plain(state),`No workflow state in ${dir…}`);
  const events=readJsonLines(path.join(dir,'events.jsonl'));
  …
```

When `dir` is given (the ledger file path, as every real caller now supplies), `path.join` treats it as a
directory and joins `state.json` onto it — a path that can never exist, since `dir` is a file. The `need()`
throws exactly the "No workflow state" message observed. This is not fixture-specific: `state.dir` is
*always* `null` post-1.0.4 and `kernelMainDispatch` *always* passes `dir:store.ledgerFile` for
`workflow-status`/`workflow-tail`/`workflow-ops` (`hosts/orca/launch.mjs:1010,1015,1040`, all three read
`status.dir` the same way) — so this breaks **every** workflow under 1.0.4, freshly created or migrated,
not something specific to the migration path. `workflow-list` is unaffected (it calls `listWorkflows` from
`kernel/store.mjs` directly, already ledger-based).

**Corroborating evidence this is a known-stale test, not a fixture mistake on my part**:
`tests/workflow-view.spec.mjs` currently passes 11/12 (the one failure, `workflow-list`, is unrelated) — but
every one of its `buildView(...)` calls omits `dir` entirely (`buildView({repoRoot,id,now:NOW})`), which
makes `buildView` fall back to `workflowDir(repoRoot,id)` — the *old* `_local/workflows/<id>` path — and the
test's own fixtures write real files there by hand. The test is internally consistent with `buildView`'s
actual (unported) behavior, so it stays green; it just never exercises the real caller's `dir:store.
ledgerFile` argument, so it never caught this. Two halves of the same feature were ported on different
schedules and the seam between them was never driven end to end until this wave's CLI exercise.

**Contract citation**: `docs/ledger-db.md` §2 states outright: *"Archive = copy one file. Inspect = `SELECT`.
`workflow-ops`, `workflow-tail`, `workflow-status` are views."* — i.e. these three commands were always
meant to read the ledger by `SELECT`, never by file. `kernel/view.mjs` contradicts that today.

**Not attempting a fix here.** `kernel/view.mjs` is a large module (~450+ lines) with several file-based
concerns beyond `state.json`/`events.jsonl` — `kernel.lock`/`stop.flag` (now `signals` rows per §4, same
migration `setRulingsText`/rulings just went through per this wave's brief), validator verdicts, and
`supervisor.log` (which §2's own reasoning suggests may legitimately *stay* a file: "the supervisor's log is
an audit stream beside the ledger, never state"). A correct port needs to sort out, table by table, which
of these move to `SELECT`s against the ledger and which stay files, and I don't own the file or have the
context to make that call safely inside this wave. Flagging with full reproduction and root cause instead
of proposing a diff I can't verify end to end. **This blocks `workflow-status`, `workflow-tail` and
`workflow-ops` for the sealed 1.0.4 runtime and should be treated as pre-seal-blocking**, not a
nice-to-have — it is the primary way an operator or the supervisor inspects a running or migrated workflow.

## What this wave otherwise verified (this stream's own scope: migration is solid)

Built a fixture at a temp path (not committed) mirroring `tests/ledger-migrate.spec.mjs`'s own shape: a
`_local/workflows/<id>/` directory (`goal.md`, `goal.json`, a complete `state.json` including `kernel`,
`ops`, `ledger`, `decisions`, `amendments`, `scope`, `lane`, `engine.journalFile`, one `events.jsonl`, one
report) plus an old-schema `journal.sqlite` (`openJournal`, one settled job, one `job-succeeded` event).

1. **`node bin/starci.mjs ledger-migrate --repo <fixture> --journal-file <fixture>/journal.sqlite`** →
   `ok:true`, one workflow imported (`events:3, snapshots:1, jobs:1, reports:1, goals:1`), nothing refused.
   **This required rebuilding `.dist/`** (`node scripts/ensure-build.mjs` → `{"ok":true,"stale":[],
   "files":500,"rebuilt":true}`) — before that, `bin/starci.mjs` imports `../.dist/hosts/orca/launch.mjs`
   (the *sealed* build, not live source: see `bin/starci.mjs:64`), and the checked-out `.dist/` predated the
   `scripts/runtime-modules.txt` fix the lead already made on `main`, so it didn't even recognize the
   `ledger-*` commands (its own usage text omitted all five of them). This is exactly the class of gap the
   brief warned about ("anything that only works through the script but not through `node bin/starci.mjs`")
   — the *source* fix already landed, but a worktree's stale `.dist/` hides it until rebuilt. Worth the lead
   confirming the seal process always rebuilds `.dist` from a clean state rather than trusting whatever is
   checked out.
2. **`node bin/starci.mjs ledger-verify --repo <fixture>`** → `ok:true`, `checked:3, brokenAt:null`
   (intact hash chain), `anchor:{ok:true,checked:true,reason:null}` (anchor matches).
3. **`node bin/starci.mjs ledger-migrate` a second time, same args** → `ok:true, workflows:[],
   skipped:[{"id":"…","reason":"already-migrated"}], refused:[]` — confirmed no-op via the real CLI, not just
   the script.
4. **`node bin/starci.mjs workflow-status --id <id>`** (cwd set to the fixture repo) → fails; see the
   `kernel/view.mjs` finding above. Isolated to the view layer only — `kernelMain('workflow-status',…)`
   called directly returns the correct `phase`/`approved`/`id`/`dir`, proving the ledger itself, the
   migrated state, and the kernel's own read path are all correct; only the rendering step is broken.
