## Cluster 1 — the 3 "late report is not bound to the exact current Run/Task/Dispatch" assertions

These are **not** in `tests/reports.spec.mjs`/`orca-headless.spec.mjs`/`cli-ledger-commands.spec.mjs` — they
are `tests/engine-kernel-flow.spec.mjs`'s three `late answered decision *` tests
(`kernel/kernel.mjs`'s `stageAnsweredDecisionLateReport`, exercised directly against a hand-rolled fixture
store, not the CLI). Root cause: `stageAnsweredDecisionLateReport` now matches a report by
`item.dispatchId` (the `store.readReports()` row's wrapper field, `dispatch_id` from the `reports` table —
§8), but the fixture's fake `readReports()` returned the bare report body (`.dispatch`, no `.dispatchId`) —
"a spec driving a retired API" per the wave instructions. Ported the fixture:

- `readReports()` now returns `{...row, dispatchId: row.dispatch}`, matching the real row shape.
- Two more retired-API gaps surfaced once that unblocked the real code path, both fixed in the fixture the
  same way — mirroring the real `kernel/store.mjs` shapes, not reinventing them:
  - `reportDigest(store,dispatchId)` (kernel.mjs) reads `store.ledger.db.prepare(...).get(...)`: added a
    minimal `store.ledger.db.prepare` stand-in that answers with this fixture's one report row.
  - `recordVerdict`/`readVerdicts` (kernel/verify.mjs, see cluster 2) need `store.signal`: added a minimal
    in-memory `Map`-backed `get`/`set` matching the real `signal.get(scope,key)`/`set(scope,key,{value})`
    shape, on the base fixture so every test in the file has it, not just the late-decision ones.
  - `applyOpReport`'s kernel-owned evidence write (kernel.mjs `kernelEvidenceRoot`) needs `store.repoRoot`:
    added a `repoRoot` **separate from `store.dir`** (its own temp directory, not the git worktree `root`
    either — writing kernel evidence inside the git-tracked `root` left `git status --porcelain` dirty,
    failing a different assertion in the same test; reusing `dir`, which already held a live
    `machine.sqlite` handle, produced the Windows EPERM cleanup issue below).
- `dispose()`'s cleanup: `createEngineRuntime(...).close()` does not close the machine-arbiter handle
  (`admission.machine`) — correct in production (§5: one `machine.sqlite` per **machine**, process-lifetime,
  shared across every ledger, never per-workflow), but this fixture points each test's own runtime at a
  throwaway temp `machineFile`, which then keeps a WAL handle open past the test. Empirically isolated with
  a standalone repro script (walked the temp tree post-`close()`, tried removing each file individually):
  only `machine.sqlite`/`-wal`/`-shm` were locked, deterministically, not transiently (bounded retries with
  `maxRetries`/`retryDelay` — the same pattern `kernel/store.mjs`'s `replaceStateSnapshot` already uses for
  Windows EPERM/EBUSY — did not help, confirming it is held, not momentarily busy). `dispose()` now retries
  the whole-tree remove once, then falls back to removing everything **except** the still-locked file(s),
  so the test's real assertions decide pass/fail, not an artifact of test isolation Node will reclaim when
  the process exits. Not a production bug; not touching `kernel/engine.mjs`.
- One assertion was checking the pre-port evidence path (`store.dir/evidence/...`); ported to the real one
  (`store.repoRoot/.starciwork/kernel-evidence/<workflow-id>/evidence/...`, per kernel.mjs's own
  `kernelEvidenceRoot`) rather than loosened.

## Cluster 2 — "Cannot read properties of null (reading 'markdown')" (2), readContract returning null

Confirmed empirically (temporary instrumentation, removed before commit) that `readContract` was correctly
returning `null` because **nothing ever wrote a contract**: `launchOp` (kernel.mjs) crashed before reaching
`store.writeContract` on *every* op-launch attempt, system-wide — not a report/contract bug specifically,
a `TypeError [ERR_INVALID_ARG_TYPE]` deep in the call chain:

```
renderContract (kernel.mjs) -> jobRulings -> rulingsText (kernel/common.mjs)
  path.join(store.dir, 'rulings.md')   // store.dir is null for every ledger-backed store (§8)
```

`rulingsText`/`jobRulings` compose the "job-wide rulings" section of every operation contract from
`<store>/rulings.md`, a file that lived under `store.dir` — which is permanently `null` under the ledger
(§8: "no filesystem workflow directory exists any more"; confirmed in `kernel/store.mjs`:
`dir:null` is hardcoded in `createStore`'s return). No production code writes `rulings.md` (grepped the
whole repo — the only writer anywhere was a test poking the file directly), so there is no capability lost
by this fix, only a crash removed: `rulingsText` now returns `''` when `store.dir` is null (the honest
current answer — there is no ledger home for this owner-authored file yet), instead of throwing and
silently aborting every contract render, everywhere.

**Fixed** (`kernel/common.mjs`): guarded `rulingsText` against `store.dir` being null.

Fixing that unmasked the exact same class of bug, twice more, deeper in the same call chains:

1. **`kernel.mjs`'s own internal `waitTick` call** (`runLoop`, line ~4187) still passed the pre-port
   `reportsDir`-era arguments and no `workflow`, which the wave-2 port to `hosts/orca/protocol.mjs` made
   required. This is a regression I (this stream) introduced in wave 2 and failed to propagate to every
   caller — fixed at the actual root cause rather than patched around: `hosts/orca/protocol.mjs`'s
   `reportOutcome`/`waitTick`/`singleTick` now accept an optional `store` parameter. When given (the
   kernel's own call, which already holds the workflow's open store), it is used directly instead of
   `singleTick` reconstructing one from `repositoryRoot(cwd)` — which is not merely redundant but **wrong**
   whenever the source worktree and the Work-owning repository differ (a real, documented, routed
   frontend/backend scenario, §1), since `cwd` there is the source worktree, not the ledger's repo. The CLI
   path (`protocolMain`, no `store` given) is unchanged: still opens and closes its own. `kernel/kernel.mjs`
   now passes `store` instead of reconstructing `workflow:store.id` from a `cwd` that may not resolve to
   the same repo.
2. **`kernel/verify.mjs`'s `validatorPaths`** (`<store>/validator/{memory.md,verdicts.jsonl}`) — the
   validator memory the kernel accumulates across every op's verdict and hands to the next validator call.
   Unlike rulings, this **is** actively written by production code (`recordVerdict`, called from every
   `applyOpReport` acceptance) — returning `''` here would have silently discarded real, currently-exercised
   verdict history, which the wave's own instruction rules out ("never loosen a guard... if the code is
   wrong, fix the code"). Ported to two `signals` rows scoped to the workflow (`validator-memory` cached
   rendered text, `validator-verdicts` the append-only array — the same table `kernel-lock`/`stop.flag`
   already use for a small keyed operational record, matching the wait-state pattern this stream already
   used in wave 2, not a new schema surface). `recordVerdict`/`readVerdicts`/`readValidatorMemory` keep
   their exact exported signatures, so every caller (including the two out-of-cluster tests at
   `tests/workflow-kernel.spec.mjs:4512,4614` that call `readValidatorMemory(harness.store)` directly) is
   unaffected by the internal storage change.
