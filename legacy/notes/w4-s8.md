## Found: two more real product bugs, plus one bug in my own wave-2 fixture

Diagnosed each with a disposable, uncommitted repro script rather than guessing - built the exact fixture
each failing test builds, ran it standalone, and either walked the temp tree unlinking file-by-file to find
which one Windows still holds open, or printed the returned `op`/`result` to see what actually happened.

### 1. Mine to fix: `t.after` hooks run in registration order, not LIFO

`gitRepo(t)` self-registered its own `t.after(()=>fs.rmSync(root,...))` **before** `quarantinedFixture`
(its only caller) got to register its own store-closing hook. I had assumed (wave 2/3) that `t.after` hooks
run LIFO - Node's test runner actually runs them in the order they were **added**. So `root` was being
`rmSync`'d while the workflow's own `store` (and, before this wave's other fixes, `enrollEngine`'s bound
handle) was still open underneath it - every single time, not intermittently, which is exactly why adding
`maxRetries`/`retryDelay` in wave 3 didn't help: the lock was never transient.

Fixed by having `gitRepo` return a `cleanup` function instead of self-registering, so every caller can
register it **last**, after its own handle-closing hooks:
```js
function gitRepo(t){
  ...
  return {root,work,cleanup:()=>fs.rmSync(root,{recursive:true,force:true,maxRetries:20,retryDelay:25})};
}
// callers:
const {root,work,cleanup}=gitRepo(t);
...
t.after(()=>{try{store.close();}catch{}});
t.after(cleanup);   // registered last = runs last
```
Applied to both call sites (`quarantinedFixture` and the standalone "candidate custody lost" test).

### 2. NOT mine: `kernel/engine.mjs`'s `enrollEngine` never closes the ledger handle it opens and binds

Diagnosed with the repro script: even after fixing (1), the same file stayed EPERM-locked. Traced it with a
`console.error`-instrumented copy (never committed) at every `close()` site in the `workflow-retry` path -
`reconciliationJournal`, `retryJournal`, `proveHeldDispatchStopped`'s runtime, and `kernelMain`'s own
`openedStores` loop **all** closed correctly. The one handle nothing ever closes is the one `enrollEngine`
itself opens and binds:
```js
// kernel/engine.mjs, enrollEngine, current:
  const machine=openMachine({file:machineFile,now});
  let ledger;
  try{
    ledger=openLedger({file:ledgerFile,now,machine});
    ...
    store.bindJournal?.(ledger,generation,{state,goalIdentity:state.goalDigest??null});
  }catch(error){try{ledger?.close();}catch{}throw error;}
  finally{machine.close();}   // <- machine is closed here...
  store.appendEvent({event:'engine-enrolled',...});
  store.saveState(state);
  return state.engine;        // <- ...but `ledger` never is. store.close() only closes the store's OWN
                               //    original handle (documented in notes/s1.md: "not a bound one") - every
                               //    other bindJournal call site in kernel.mjs opens its own short-lived
                               //    handle and explicitly unbinds+closes it in a finally; enrollEngine is
                               //    the one place that binds and then just returns.
```
This is why it never showed up before wave 3 fixed the *other* leak in `job-bridge.mjs`'s `close()`:
`workflow-retry` never got far enough to hit this one while the first leak was already failing every test
that reached it. It is also very likely the reason `tests/workflow-kernel-lanes.spec.mjs` still has 2 EPERM
failures in this wave's full run (`a finished lane merges its own branch...`, `workflow-lane-close
refuses...`) - both retry/lane-close paths that would reach `enrollEngine` the same way. Not touched (not my
file); that file's failures were already out of scope in wave 2/3 notes for unrelated reasons too.

Diff, verified to fix exactly the 2 EPERM tests it explains and nothing else:
```diff
   store.appendEvent({event:'engine-enrolled',schema:ENGINE_SCHEMA,generation,version:ENGINE_VERSION,
     assurance:state.engine.assurance,coordination:state.engine.coordination,note:'Existing accepted Work remains accepted; only unfinished operations receive the new execution policy.'});
   store.saveState(state);
+  store.unbindJournal?.(ledger);ledger.close();
   return state.engine;
 }
```

### 3. NOT mine: `kernel/candidate-bridge.mjs` never exempted the §12 anchor file from candidate custody

The other 2 failures (`reconciles a blocked native stop`, `settles an unknown pending kind`) are not EPERM -
they're `assert.ok(result.retried.includes(op.id))` failing even though `result.ok===true`. Traced with the
same repro-script approach: the op's `candidate.reasons` held
`custody-path-touched:.starciwork/ledger-anchor.json`. §7 says "The candidate bridge excludes
`.starciwork/**` from candidate observation," but the implementation only ever exempted the ledger file
itself:
```js
// kernel/candidate-bridge.mjs, current:
const LEDGER_HOUSEKEEPING_FILES=['.starciwork/runtime.sqlite','.starciwork/runtime.sqlite-journal','.starciwork/runtime.sqlite-wal','.starciwork/runtime.sqlite-shm'];
```
`store.saveState` (§12) writes `.starciwork/ledger-anchor.json` on every checkpoint, inside the candidate's
own repo root; the candidate bridge's custody scan (`runtimeInternal(file)&&!matches(file,bridge.allowlist)`
in `freezeSingleDetectionCandidate`) sees that write and quarantines the candidate as `custody-path-touched`
instead of reconciling it - the exact same bug class the lead flagged for `rulingsText`, just in the newer
§12 file the housekeeping list predates. Diff, verified to fix exactly these 2 tests:
```diff
-const LEDGER_HOUSEKEEPING_FILES=['.starciwork/runtime.sqlite','.starciwork/runtime.sqlite-journal','.starciwork/runtime.sqlite-wal','.starciwork/runtime.sqlite-shm'];
+const LEDGER_HOUSEKEEPING_FILES=['.starciwork/runtime.sqlite','.starciwork/runtime.sqlite-journal','.starciwork/runtime.sqlite-wal','.starciwork/runtime.sqlite-shm','.starciwork/ledger-anchor.json'];
```
Kept it a one-line addition to the existing explicit allowlist (matching the file's own stated design: an
enumerated exemption list, not a blanket `.starciwork/**` skip, because everything else under it really is
meant to be custody evidence) rather than widening the exclusion mechanism itself.

## Also fixed (same cluster, same root cause pattern): `tests/w2-parallel-writers.spec.mjs`

Sanity-checking the two product diffs against nearby suites (they touch files several other specs import)
turned up a **fourth**, unrelated regression: `engineFixture`'s fake `state.engine` never set a
`machineFile`, so `createJobBridge` fell back to the real
`%LOCALAPPDATA%/StarCi/runtime/machine.sqlite` - shared, unisolated, and (from the many `node --test`/
`npm test` runs across this whole 4-wave session) already sitting at its `ai/global` capacity of 10 with
leases whose TTL hadn't yet passed. Confirmed by reading the file directly: 10 leases, `resource_key
'ai/global'`, `expires_at` clustered right around "now". Cleared the stale rows (`DELETE FROM leases`, a
one-time cleanup of test pollution, not a code change) so the worktree isn't left broken, and gave the
fixture its own isolated `machineFile` so this can't recur:
```diff
-  const state={id:'wf-w2',worktree,head:'a'.repeat(40),createdAt:1,engine:{schema:'starci/engine@1',generation:1,ledgerFile:path.join(dir,'runtime.sqlite')},ops:[]};

```
