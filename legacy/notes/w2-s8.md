# w2-s8 — test hygiene across the suite (EPERM / leaked handle cluster)

Wave 2: the ten 1.0.4 branches are merged into `main`. Full suite on `main`: 1922 pass / 296 fail / 6 skip
(my own first run after `git merge --ff-only main` + `npm install`, which restored a `typescript`
devDependency this worktree started without: **1923 pass / 295 fail / 6 skip** — one unaffected test's
flake between the lead's run and mine).

## Cluster

"18 failures are EPERM on Windows temp cleanup... the cause is an open SQLite handle at rm time." Plus
`tests/w1-reconcile.spec.mjs` (5) and `tests/w2-parallel-writers.spec.mjs` (4).

## Root causes found and fixed (all in files this stream owns or that the cluster explicitly named)

1. **A `createStore`/`openLedger` result was never `.close()`d before `fs.rmSync` on its temp dir.** On
   Windows a live sqlite handle (WAL mode holds `-wal`/`-shm` too) keeps the file open; the `rmSync` throws
   `EPERM`, and — because JS lets a `finally` block's own throw silently replace whatever the `try` block
   was about to throw — this can also *mask* the test's real failure reason behind an unrelated `EPERM`.
   - `tests/goal-grounds-intake-scope.spec.mjs`: `setup()`'s `harness.cleanup()` now closes the store it
     opened; five standalone `createStore`+`tree.cleanup()` sites now close their store first (careful to
     hoist `let store;` *outside* the `try{}` — a `const` declared inside `try{}` is not visible from
     `finally{}`, a bug I made and caught in my own first pass here). **Fixed all 13 failures in this file**
     (12 EPERM directly, one more that only surfaced because store-paths-removed:goal / a ledger:// input-ref
     mismatch were masked by cascading EPERM cleanup fallout — see "found but not fixed" below).
   - `tests/workflow-store.spec.mjs`: same close-the-handle fix across all six `createStore` call sites.
     Removes the EPERM; the file's five remaining failures are real, pre-existing `store.paths`/
     `reportPath`/`listWorkflows` mismatches against the fully-removed 1.0.3 file API this file still tests
     (see "found but not fixed").
   - `tests/continuation-binding.spec.mjs`: its one shared `fixture(t)` now closes the store it opens.
     Removes the EPERM; five remaining failures are the `kernel/continuation.mjs` bug below (not this
     cluster's fix).
2. **`tests/w1-reconcile.spec.mjs` — the real bug was not a missing `.close()`, it was two ledger files.**
   `quarantinedFixture()` opened the engine runtime's own ledger on a second, repo-external
   `<tmp>/runtime/journal.sqlite`, while the store it also created opened its own ledger at
   `ledgerFileFor(work)` (`<work>/.starciwork/runtime.sqlite`) — the pre-1.0.4 two-file shape. Under 1.0.4
   there is one ledger per repo (§3/§8): `store.bindJournal(handle,...)` refuses a handle on a different file
   as `ledger-binding-mismatch:<id>`, which is exactly what all 5 tests in this file were hitting. Fixed by
   pointing the engine's ledger at `ledgerFileFor(work)` too (same file as the store), and porting the
   file's own `heldLease`/`jobStatus` helpers off the retired `kernel/journal.mjs`'s `openJournal` (a
   different schema, `operational-journal@1`) onto `kernel/ledger-db.mjs`'s `inspectLedger` (the real
   `ledger-db@1` schema the shared file now holds). Also added the missing `store.close()` in every test
   (`t.after` in `quarantinedFixture`, plus the standalone 5th test). This removed `ledger-binding-mismatch`
   from all 5 tests and unmasked two real, out-of-cluster bugs — see below.
3. **`tests/w2-parallel-writers.spec.mjs` — a stale field name, not a leak.** `engineFixture()`'s fake
   `state.engine` carried `journalFile`; `kernel/engine.mjs` reads `state.engine.ledgerFile` (§8's rename).
   One-line fix. **12/12 pass now** (was 8/12).

## Helper added (as asked): leaking one is now impossible

`tests/_ledger-fixture.mjs` gained `trackHandles(t)` and `withLedger(...,({...,track})=>...)`'s new `track`:
closes every tracked handle, in reverse acquisition order, before `t.after`'s own cleanup — the same
`fixture(t)`/`fx.track(handle)` shape s1 already proved in `tests/store.spec.mjs`, generalized into the
shared fixture so it's not reinvented per file. Not retrofitted onto the five files fixed above (their
existing `try/finally`/`t.after` shapes were simpler to patch in place than to convert); available for any
spec written from here on, or for a future pass that wants to consolidate.

## Found but NOT fixed — outside this cluster, precise diffs for the owning streams

**`kernel/continuation.mjs`'s `bindContinuationPath` still writes to the removed `store.paths` setter.**
`kernel/store.mjs`'s `paths` is a Proxy that throws `store-paths-removed:<name>` on every get *and* set
(s1's 1.0.4 store API). `bindContinuationPath` (owned by the boundary-bridge/candidate-bridge stream) uses
`store.paths.continuation` as a scratch variable to hold its own return value in three places. This breaks
every caller unconditionally, not just this stream's tests: I found it independently from three different
files (`tests/w1-reconcile.spec.mjs`, `tests/continuation-binding.spec.mjs` — 5 of its 6 tests fail on this
alone — and `tests/workflow-kernel-lanes.spec.mjs`). Exact fix, `kernel/continuation.mjs`:

```diff
   if(typeof explicit==='string'&&explicit.trim()){
     const target=path.resolve(root,explicit),relative=path.relative(workflows,target);
     if(relative.startsWith('..')||path.isAbsolute(relative)||path.extname(target).toLowerCase()!=='.md')throw Error('Public continuation binding must be a Markdown file under workflows/');
-    assertContinuationTarget(root,target);store.paths.continuation=target;return target;
+    assertContinuationTarget(root,target);return target;
   }
   const canonical=path.join(workflows,`${id}.md`);
   assertContinuationTarget(root,canonical);
-  if(fs.existsSync(canonical)){store.paths.continuation=canonical;return canonical;}
+  if(fs.existsSync(canonical))return canonical;
   ...
-  store.paths.continuation=matched.length===1?matched[0]:canonical;assertContinuationTarget(root,store.paths.continuation);return store.paths.continuation;
+  const bound=matched.length===1?matched[0]:canonical;assertContinuationTarget(root,bound);return bound;
```
(the function already returns its result directly in every branch; `store.paths.continuation` was never
read back by any caller in this codebase — it was purely a now-broken way to stash a local before returning
it.)

**`kernel/jobs.mjs`'s `complete()` inserts an `events` row without the hash-chain columns.** §4's `events`
table has `digest TEXT NOT NULL` (and `prev_digest`), computed as
`sha256((prev_digest ?? '') + event_id + kind + payload_json + created_at)`. `createJobs({journal,...}).
complete()` (owned by the engine-admission stream) does a raw `INSERT INTO events(...)` with no digest at
all, so any job settlement through this path throws `NOT NULL constraint failed: events.digest`
(`tests/w1-reconcile.spec.mjs`'s "candidate custody lost..." test hits it via `acceptReports` →
`engine.mjs`'s `settled` → `jobs.mjs`'s `complete`). The `journal` parameter passed into `createJobs` is
already a `kernel/ledger-db.mjs` `openLedger` handle (via `createJobBridge`), which exposes a correctly
hash-chained `appendEvent` — the fix is to use it instead of hand-rolling the insert, from *inside* the same
`journal.transaction(db=>{...})` callback (safe: `appendEvent` operates on the same open connection, not a
new transaction). `kernel/jobs.mjs`:

```diff
         const at=now();db.prepare('UPDATE jobs SET status=?,result_json=?,lease_token=NULL,deadline=NULL,updated_at=? WHERE job_id=?').run(status,JSON.stringify(result),at,jobId);
-        db.prepare('INSERT INTO events(event_id,workflow_id,entity_type,entity_id,generation,kind,payload_json,created_at) VALUES(?,?,?,?,?,?,?,?)').run(eventId,workflowId,'job',jobId,generation,`job-${status}`,JSON.stringify({opId,attempt,result}),at);
+        journal.appendEvent({eventId,workflowId,entityType:'job',entityId:jobId,generation,kind:`job-${status}`,payload:{opId,attempt,result},createdAt:at});
         return {ok:true,duplicate:false,status};
```

**A test debris pattern from `tests/workflow-amendment.spec.mjs` leaks `.workflow-amendment-test-*`
directories into the repo's working directory** (not `os.tmpdir()`) — I found a dozen of these sitting in
this checkout mid-suite-run and removed them (untracked, never committed). Different flavor of hygiene bug
(wrong root, not a handle leak) in a file this stream doesn't own (`kernel.mjs`/`journal.mjs` heavy,
matches the engine-admission/kernel domain); flagging rather than fixing.
