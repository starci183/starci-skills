Every genuinely-in-cluster failure had the identical shape: a fixture builds its handle with `openJournal`
from `kernel/journal.mjs`, then drives 1.0.4 admission, jobs or the job bridge through it.
`reserveTwoPhase` unconditionally keys the machine side by `ledger.ledgerId ?? ledgerIdOf(ledger)` (docs
§5/§6) — a journal handle has no `meta` table, so every such call throws `no such table: meta`. Fixed by
porting each fixture's handle-construction to `openLedger`, never by touching `reserveTwoPhase` or
`ledgerIdOf` (per the brief: that identity check is exactly what stops an orphaned machine lease surviving a
moved ledger).

`kernel/ledger-db.mjs` carries **no diff** from this wave — every fix landed in the four test files.

## What stayed on `openJournal`, and why

Per the brief: "keep on openJournal only the tests that genuinely assert kernel/journal.mjs's own
behaviour, because that module still exists for one reason: the migrator reads old files with it."

- `tests/kernel-engine.spec.mjs`: "journal defaults to DELETE/FULL, persists across reopen..." and "WAL is
  opt-in and gated by the embedded SQLite fix level" assert journal.mjs's *own* defaults (`DELETE` by
  default, `allowWal`-gated WAL) — behavior ledger-db.mjs deliberately does not share (WAL by default, no
  `allowWal` param at all since wave 1). Also left "model jobs fail explicit without an eligibility policy"
  alone: it calls `createAdmission({journal})` on a journal handle too, but never reaches `.reserve()` (throws
  earlier, on the eligibility check) so it was never actually broken - not touched, since it wasn't failing.
- `tests/journal-retention.spec.mjs`: the constants test, both `compactSnapshots` tests, "finished
  shared-store custody...", and "a journal created by this build gives freed pages back on its own" test
  journal.mjs's own compaction/vacuum/retirement directly, no admission involved - left alone (already
  passing). "journal-prune retires what the store roots prove settled..." tests
  `kernel/journal-maintenance.mjs`, which is explicitly journal.mjs-only tooling (docs §1) - its *subject*
  correctly stays on `openJournal`; only its setup (which used `createAdmission`+`.reserve` just to mark one
  job "live") needed to stop routing through admission.mjs. Replaced with a raw `UPDATE`+`INSERT` on
  `jobs`/`leases` matching exactly the row shape `admission.reserve` would have left - the test's own subject
  never touches ledger-db.mjs at all.

## Two assertions ported to intentional, already-documented 1.0.4 behavior

`tests/kernel-engine.spec.mjs`'s "an expired lease becomes effect_unknown before capacity is reused" expected
a second `ai/global` reservation to fail while the first sat unreconciled - the pre-split journal-only
semantics, where one db saw both the job status and the capacity. `tests/admission.spec.mjs` (already merged,
not mine) proves side-by-side that this is intentionally *different* now: a repo-scoped resource's capacity
excludes expired rows in `reserveTwoPhase`'s own query, and `ai/*` capacity is TTL-swept by the machine
arbiter on every `reserve`, in both cases independent of whether the ledger job has been reconciled. I nearly
"fixed" `machine.reserve()`'s inline expiry sweep to make the *old* assertion pass by construction before
finding that comment and reverting - `kernel/ledger-db.mjs` carries no diff from this wave, confirmed with
`git diff --stat`. Renamed the test and fixed the assertion instead. Separately found and fixed the reason the
symptom looked like a hang in the first place: the test's fake `now` only reached `admission`'s own clock, not
`journal.now` (which `reserveTwoPhase` actually uses for `expires_at`) - `withLedger` needed a `now` option
threaded to `openLedger`, matching `tests/admission.spec.mjs`'s own `withPair` helper.

"bridge relaunches only a valid staged completion with the original lease" read the spawned worker's lease
token off `launches[0][1].at(-1)`; `kernel/job-bridge.mjs`'s spawn call (already updated by an earlier wave)
appends the machine file path after the lease token now, so the token is the second-to-last argv element, not
the last.

## Isolation bug this porting surfaced (fixed in the tests, not the module)

Every one of these fixtures' `createAdmission({journal})` calls, across all four files, defaulted to the real
`%LOCALAPPDATA%/StarCi/runtime/machine.sqlite` (docs §1's actual default location) rather than naming a
`machineFile`. Once the `no such table: meta` crash stopped masking it, tests started interfering with each
other's `ai/*` capacity within a run, and even leaked leases into the real default location between separate
`node --test` invocations during this session (confirmed and cleaned up: a `machine.sqlite` created minutes
earlier by my own debugging, holding stale `ai/global` leases that starved a later, unrelated reservation).
Every ported fixture now takes an explicit `machineFile` in its own sibling temp directory (never nested
inside the test's own `dir` - an unclosed WAL handle there blocks that directory's own `fs.rmSync` on
Windows). `tests/kernel-engine.spec.mjs` got a `temporaryMachineFile()` helper; `tests/engine-migration.spec.mjs`
and `tests/journal-retention.spec.mjs` got the same pattern inline/as a one-off helper.

Also added `store.close()` calls the bindJournal-based tests were missing (a `createStore` opens its own
internal ledger handle per docs §8's "a store is a session, closed by its caller" - four tests in
`tests/kernel-engine.spec.mjs` never called it, which also blocked their own `fs.rmSync` cleanup on Windows).

## Two retired-API tests, ported to their closest 1.0.4 equivalent

- `tests/kernel-engine.spec.mjs`'s "journal-bound store recovers committed state when the JSON projection is
  lost" wrote to `store.paths.state`, removed outright by §8 (no JSON projection exists under 1.0.4 at all).
  Renamed and rewritten to the equivalent property: a second, freshly opened `createStore` for the same
  workflow - no in-process cache of its own - still reads the exact durably committed state.
- `tests/engine-lifecycle.spec.mjs`'s "owner inbox..." test's own "replay" step wrote a raw file into
  `store.paths.inbox`; replaced with a second `store.inbox.push` of the identical job payload (§8's actual
  replacement for that removed path).

## Not mine: unrelated pre-existing failures in the same four files

None of these touch `kernel/journal.mjs`, `kernel/ledger-db.mjs`, or an `openJournal`/`openLedger` handle at
all - confirmed by reading each one's actual stack trace/assertion before deciding not to touch it:

- `tests/engine-migration.spec.mjs`: "the engine version is the package version..." hardcodes
  `assert.equal(pkg.version,'1.0.0')`; `package.json` is now at `1.0.4` (bumped by another stream). "migration
  renames the numbered fields..." and "a record already on the schema is untouched..." both get
  `{migrated:true,...}` from `migrateEngineState` (kernel/kernel.mjs) where they expect `{migrated:false}` on
  an already-migrated record - an idempotency regression in that function, unrelated to any ledger/journal
  handle. "the event log rotates by generation..." reads `store.rotateEvents(1).rotated` as a file path;
  under §8 `rotateEvents` is a no-op recording an event, so `.rotated` is `null` now - a `kernel/store.mjs`
  API-retirement test, not a journal/ledger fixture.
- `tests/engine-lifecycle.spec.mjs`: "the supervisor retains the lock until the former kernel is confirmed
  dead" does `path.join(store.dir,'kernel.lock')`; `store.dir` is deliberately `null` under §8 (replaced by
  `signal.set/get/clear`) - `kernel/supervisor.mjs`'s kernel-lock handling was never updated to the new
  signal API.
