## Root causes found and fixed (in owned files)

1. **`tests/ledger-migrate.spec.mjs` didn't load at all** — `scripts/ledger-migrate.mjs` imported
   `journalFileFor` from `kernel/engine.mjs`, which no longer exports it. The s2 (engine/admission) stream's
   port to ledger-db two-phase reservation retired `journalFile` as a real file path inside `engine.mjs`
   (there, `journalFile` is now just the pre-1.0.4 *parameter name* for `ledgerFile`, per `engine.mjs:42`'s
   own comment) and dropped the function that resolved the legacy `journal.sqlite` path, since `engine.mjs`
   never needs that path anymore. The migrator still does — it's the one remaining reader of the retired
   file. Fix: moved `journalFileFor` (`path.join(runtimeRootFor(env),'journal.sqlite')`) into
   `kernel/journal.mjs`, the legacy-journal module and the migrator's last caller, duplicating
   `runtimeRootFor` locally exactly as `kernel/ledger-db.mjs` already does ("kept local so this module never
   imports the engine"). Updated the migrator's import accordingly. Verified with `git log -p` that this was
   the function's original body before it was removed from `engine.mjs`.

2. **Meta/anchor duplication** — s0 has now landed real `meta` seeding and §12 anchor support in
   `kernel/ledger-db.mjs` (`openLedger` seeds `ledger_id`/`schema`/`created_at`/`journal_mode` itself on
   create and keeps `journal_mode` in step on every open; exports `ledgerIdOf`, `writeAnchor`, `readAnchor`,
   `verifyAnchor`, `anchorFileFor`). This session's branch still carried last wave's hand-rolled
   `seedMeta`/`writeAnchorEntry` duplicates in `scripts/ledger-migrate.mjs`, written before that landed.
   Removed them; the migrator now reads `ledger.ledgerId` straight off the handle `openLedger` already
   returns and calls the module's own `writeAnchor(repoRoot,{ledgerId,workflowId,generation,checkpointId,
   eventsHead,seq,at})` after each workflow's transaction commits (unchanged ordering: anchor write always
   follows the commit it describes, per §12). Also fixed `machineApply`'s `machine.registerLedger(...)` call:
   the signature changed from `registerLedger({file})` (which used to derive `ledgerId` from the path itself)
   to `registerLedger({file,ledgerId})` (§5: `ledgerId` is always the ledger's own `meta.ledger_id`, never
   path-derived) — the migrator now passes the ledger's `ledgerId` through explicitly.
   `writeAnchor` requires a non-null `checkpointId` (`need(...)`, throws otherwise), unlike last wave's
   local version which tolerated `null`; the migrator now only calls it when `anchorCheckpoint(plan)` found
   one (state.json's import checkpoint, or the newest old-journal snapshot) — a workflow with neither (no
   `state.json`, no journal snapshots) still imports everything else, it just gets no anchor entry, same as
   it would get none from a fresh non-migrated workflow with no checkpoint yet.
   **No merge of `starci183/s0-ledger-db` was needed this session** — `main` at `f2dfbf7a` already carries
   everything from that branch (`git log --oneline starci183/s7-migrate..starci183/s0-ledger-db` is empty
   after the ff-only merge onto `main`).

3. **`tests/ledger-migrate.spec.mjs` stale assertions** — updated to match the corrected behavior above, not
   to hide it: `journal_mode` now asserts `'wal'` (§3's new default; was asserting the old `'delete'`
   default from before WAL became default) and the now-nonexistent `<ledgerFile>#meta` migrations-row
   assertion was dropped (the migrator no longer writes that row since it no longer seeds meta itself).

4. **`tests/journal-retention.spec.mjs`: 1 of 4 fixed — a leaked ledger handle blocked Windows cleanup.**
   `stateAt()` (a local test helper) called `createStore({repoRoot,id})` and `.saveState(...)` but never
   `.close()`d the returned store. `createStore` (kernel/store.mjs, not owned) opens a real `openLedger`
   handle in WAL mode and keeps it open for the store's lifetime — every one of `stateAt`'s six call sites
   discards the return value, so the handle just leaked for the rest of the test. On Windows, WAL's open
   file handle on `repo/.starciwork/runtime.sqlite` blocked the `t.after` hook's `fs.rmSync(dir,{recursive:
   true,force:true})` with `EPERM` (not `ENOENT` — a real lock, not a missing-file race). Fixed by having
   `stateAt` close the store immediately after saving.

## Remaining 3 failures in `tests/journal-retention.spec.mjs` — cross-file, not fixable from owned files

All three (`retired generations lose their settled jobs and events…`, `a workflow is retired whole only
when nothing of it is live…`, `journal-prune retires what the store roots prove settled…`) fail identically:

```
Error: no such table: meta
    at Module.ledgerIdOf (kernel/ledger-db.mjs:29:20)
    at ledgerIdOf (kernel/admission.mjs:15:75)
    at createAdmission (kernel/admission.mjs:35:18)
```

Each test calls `createAdmission({journal})` where `journal` is a **legacy `openJournal()` handle**
(`kernel/journal.mjs`, my file — deliberately, since these tests exercise the retired `journal.sqlite`'s own
retention/pruning semantics through the journal API, exactly as the file's own docstring says: "exercised
through the journal's own API"). `journal.sqlite`'s schema (`starci/operational-journal@1`) never had a
`meta` table — that concept is ledger-only (§4). `createAdmission` (kernel/admission.mjs:31-35, not owned)
unconditionally calls `ledgerIdOf(journal)` at setup time to have a ledger id ready for machine-scoped
(`ai/*`) reservations, which these tests do exercise (`admission.reserve({...,resources:[{key:'ai/global',
units:1}]})`). `admission.mjs`'s own `ledgerIdOf` wrapper (line 15) has a comment saying it falls back to
`handle.ledgerId` "until [`ledgerDb.ledgerIdOf`] lands" — it has now landed, so the wrapper always takes the
`ledgerDb.ledgerIdOf(handle)` branch, which (kernel/ledger-db.mjs:26-30) runs an unguarded
`SELECT value FROM meta WHERE key='ledger_id'` with no fallback for a handle whose `db` isn't a ledger at
all. That raw SQLite error is the crash.

**This is not something fixable inside `scripts/ledger-migrate.mjs` or `kernel/journal*.mjs`.** The tests are
correctly exercising real retention/admission behavior against a real legacy journal, which is a supported
combination per `kernel/journal.mjs`'s own docstring (the module "backs `scripts/ledger-migrate.mjs`, the
pruning maintenance verbs and the historical specs"). The bug is that `ledgerIdOf` (kernel/ledger-db.mjs,
§3, "The ledger's own identity, from its `meta` row") isn't safe to call on something that isn't a ledger —
it should answer "this isn't a ledger" (`null`), not throw a raw `SQL logic error`.

### What I tried, and what it actually surfaces (kernel/ledger-db.mjs / kernel/admission.mjs, neither owned)

I patched a scratch (uncommitted, reverted before this note was finalized) copy of `kernel/ledger-db.mjs`'s
`ledgerIdOf` to stop throwing on a handle with no `meta` table:

```diff
 export function ledgerIdOf(handle){
   need(handle?.db,'ledgerIdOf needs a handle');
-  return handle.db.prepare("SELECT value FROM meta WHERE key='ledger_id'").get()?.value??null;
+  try{return handle.db.prepare("SELECT value FROM meta WHERE key='ledger_id'").get()?.value??null;}
+  catch{return null;}
 }
```

This is a real, no-guard-loosened bug fix on its own — `ledgerIdOf`'s job per its docstring is to answer "the
ledger's own identity, from its `meta` row," and a handle whose `db` isn't a ledger at all should answer
"none" (`null`), not throw a raw `SQL logic error`. It clears the crash at `createAdmission`'s setup line
(`kernel/admission.mjs:35`). **But it only gets one layer deeper, not through**: `admission.reserve(...)` for
the `ai/global` resource these tests use then fails a *different* way —

```
Error: registerLedger needs the ledger meta.ledger_id
    at need (kernel/ledger-db.mjs:20:40)
    at Object.registerLedger (kernel/ledger-db.mjs:424:7)
    at reserveTwoPhase (kernel/ledger-db.mjs:492:28)
    at kernel/admission.mjs:75:22
```

`reserveTwoPhase` (kernel/ledger-db.mjs) calls `machine.registerLedger({file:ledger.path,ledgerId:
ledger.ledgerId??ledgerIdOf(ledger)})` — with the fix above, `ledgerIdOf(journal)` now returns `null` instead
of throwing, but `null` still fails `registerLedger`'s own `need(ledgerId,...)` guard (§5's whole point:
`ledgerId` is never allowed to be empty in the machine DB, since a missing/synthetic id is exactly the kind
of path-derived-identity bug §5 retired). So a *legacy journal* handle genuinely cannot register with the
machine arbiter under the new meta-based identity model — there is no `meta.ledger_id` for it to have, by
design (journal.sqlite never had `meta`, and per docs §1/§2 it is retired and read-only for audit).

**This is a real design question, not a one-line fix, and it belongs to whoever owns `kernel/admission.mjs`
(the identity-fallback comment at line 9-15 is that stream's own transitional shim) or `kernel/ledger-db.mjs`
(§5's admission).** Two directions I can see, neither of which I'll choose for another stream's file:
- `admission.mjs`'s local `ledgerIdOf` wrapper could fall back to a stable identity derived from the
  handle's own `.path` (mirroring the pre-§5 `ledgerIdFor(file)=sha256(realpath).slice(0,16)` this whole
  redesign retired for *modern* ledgers) specifically for a handle that provably isn't a ledger — legacy
  journals are frozen/read-only, so the rename/junction/UNC concerns that motivated moving off path-derived
  ids for live ledgers don't really apply to something nobody will ever move again.
- Or these `journal-retention.spec.mjs` tests' use of `createAdmission({journal:<legacy journal handle>})`
  for a resource that needs the machine DB (`ai/*`) is simply retired functionality dressed as a still-green
  test, and the tests should be told (by whoever owns admission.mjs's contract) that machine-scoped admission
  on a bare legacy journal is no longer supported — which is a statement about `admission.mjs`'s contract,
  not something I can decide by editing a test in a file I don't own to route around the failure.

Both the one-line `ledgerIdOf` fix above and a decision on one of these two directions are needed together
to actually turn the 3 remaining failures green; I'm flagging the fully-traced chain rather than half of it.
