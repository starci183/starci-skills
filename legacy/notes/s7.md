# s7 — migration: `_local` + old journal → ledger (§10)

## Files changed

- `scripts/ledger-migrate.mjs` (new) — `migrateLedger({repoRoot,journalFile,machineFile,dryRun,archive,now,pidAliveFn})`
  per §10, exported and runnable as `node scripts/ledger-migrate.mjs --repo <root> [--journal-file <f>]
  [--machine-file <f>] [--dry-run] [--archive true]`. Per workflow directory under
  `_local/workflows/<id>/`: folds `goal.md`+`goal.json` → `goals` rev, `events.g*.jsonl` then `events.jsonl`
  → `events` (digest-chained, original `seq` kept in `payload_json._seq`), `state.json` → the newest
  `state_snapshots` checkpoint (`state.engine.journalFile` rewritten to `ledgerFile`+`machineFile`),
  `reports/contracts/checks/inbox` → their tables, plus the retired journal's `jobs/leases/events/
  state_snapshots/incidents/budget_reservations` for that workflow id (`ai/*` leases mirrored to the machine
  DB, `machine_ref` set on the paired ledger lease). Idempotent via one `migrations` row per source path
  (`_local/workflows/<id>` and `<journalFile>#<id>`); a second run skips recorded sources. Refuses
  (writes nothing for that workflow) on a live `kernel.lock` pid or an old-journal unsettled job behind
  `state.json`'s generation (`kernel-reconcile-required`). `--archive true` moves the directory to
  `_local/workflows-archive/<id>.migrated`; nothing is ever deleted.
  **This session's addition**: picked up the §4 `inputs` table contract addendum (merged from
  `s0-ledger-db`, itself picked up from `main`) — `goal.mjs`'s `stageExternalInputs` copies owner files
  under `_local/inputs/<id>/<n>-<basename>` before this refactor, and those bytes now import into the
  ledger `inputs` table via `ledger.inputs.put`, read off the `ref`/`sourceRef` entries declared in
  `state.json`/`goal.json` (deduped across the two, since both carry the same array), keyed by
  `goal.revision`. A declared ref whose file the directory no longer holds is reported per-workflow as
  `inputsLost:[{key,reason:'input-file-missing'}]` — a loss, not a refusal, per docs/ledger-db.md:161-162.
  The import is recorded in `migrations` (`kind:'workflow-inputs'`) for idempotency/audit, and
  `workflows.updated_at` is restored after `inputs.put`'s internal `ensureWorkflow` call touches it (it
  writes its own `now()`, which would otherwise clobber the value computed from the workflow's real event
  history). `imported` summary counts gained an `inputs` field (count of bytes imported); this is additive,
  nothing else in the repo parses the summary JSON's shape strictly.
  **Second addendum this session** (lead's §4/§12 contract change, docs merged from `main` at `826894e5`):
  `kernel/ledger-db.mjs` does not yet create the `meta` table, mint a `randomUUID` `ledger_id`, or write
  `.starciwork/ledger-anchor.json` — that part of the doc is ahead of s0's module (confirmed: `git show
  starci183/s0-ledger-db:kernel/ledger-db.mjs` still has neither `meta` nor `ledgerIdOf`). Per the lead's
  explicit assignment, the migrator does both directly since it is the process that actually creates
  `runtime.sqlite` on a first run:
  - `seedMeta(db,{now})`: `CREATE TABLE IF NOT EXISTS meta(key TEXT PRIMARY KEY, value TEXT NOT NULL)` (the
    exact §4 shape), then only if no `ledger_id` row exists yet, inserts `ledger_id` (`crypto.randomUUID()`),
    `schema` (`LEDGER_SCHEMA` import, `'starci/ledger-db@1'`), `created_at` (`now()`), `journal_mode` (read
    back from `PRAGMA journal_mode`, lowercased to `'wal'|'delete'` per the doc). Called once per ledger, at
    ledger-open time, gated by a `<ledgerFile>#meta` row in `migrations` (same pattern as the existing
    `#shared` journal-bootstrap key) — a second run does not reseed, and the `IF NOT EXISTS`/`ledger_id`
    check makes it harmless even once `kernel/ledger-db.mjs` grows its own seeding.
  - `writeAnchorEntry`/`anchorCheckpoint`: for every workflow imported, after its ledger transaction commits
    (§12: the anchor is written only after the commit it describes, never before), reads back
    `.starciwork/ledger-anchor.json` if it exists, merges in `{generation, checkpointId, eventsHead, seq,
    at}` for that workflow (`checkpointId`/`generation` from the imported `state.json` checkpoint when one
    exists, else the newest old-journal snapshot; `eventsHead`/`seq` are the digest chain's tail and the
    `lastInsertRowid` of the last event inserted, both now returned by `ledgerApply`), and replaces the file
    atomically (write to a temp file beside it, then `renameSync`). Recorded under `<dir>#anchor` in
    `migrations` so a second run — already a no-op for the workflow via the existing `<dir>` key — leaves the
    anchor file untouched too, matching the lead's "records both in migrations" instruction literally (two
    keys: `#meta` once per ledger, `#anchor` once per workflow).
- `kernel/journal.mjs` — unchanged except a top-of-file comment marking it retired-but-kept as the legacy
  reader `ledger-migrate` and the historical specs depend on; no new writers were added, nothing deleted

## Open questions

- The §10 prompt text (line 26 of the brief) enumerates the `imported` summary fields without `inputs`; the
  keystone doc (`docs/ledger-db.md:161-162`, a later addendum merged from `main` via `s0-ledger-db`) requires
  importing the `_local/inputs/<id>/` directory and recording losses. I added `inputs` (a count) and
  `inputsLost` (an array, only present when non-empty) to the workflow summary entry rather than inventing a
  different shape — additive, and nothing else in the repo parses this JSON strictly. If the lead wants a
  different field name/shape, it's isolated to the `imported`/`inputsLost` construction at the end of the
  per-workflow loop in `migrateLedger`.
- `ensureWorkflow` (kernel/ledger-db.mjs, not owned here) unconditionally bumps `workflows.updated_at` to its
  own `now()` on every call, including from `inputs.put`. `ledgerApply` now restores the correct
  `updated_at` after the inputs loop; flagging in case another stream also calls `ensureWorkflow`/`inputs.put`
  outside a full workflow-row rewrite and hits the same clobber.
- The `<dir>#anchor` migrations row is written in its own tiny follow-up transaction, after the anchor file
  write, which is itself after the main per-workflow transaction commits (so the anchor file write is never
  inside the transaction it describes, per §12's stated safety direction). This leaves a narrow crash window
  where the main import committed (including the `<dir>` workflow-dir migrations row) but the anchor file
  write or its `#anchor` record did not complete — on retry that workflow is already `already-migrated` and
  is never revisited, so a crash exactly there would permanently skip its anchor. Given the anchor write is
  a local file write with no network or missing-directory risk (the parent dir is created first), I judged
  this an acceptable, low-probability gap rather than restructuring the per-workflow atomicity model to cover
  it; flagging in case the lead wants `starci ledger-anchor --write` (§12, mentioned as regenerating the
  anchor "from a healthy ledger") to be the documented recovery instead of a migrator-side guarantee.
