## (a) `no such table: meta`

**What I built, as asked**: `migrateLedger` now checks the schema itself, not just `user_version`, because
`meta` (and the digest-chain trigger from (b)) were added to `LEDGER_DDL` without a version bump in wave 1 —
`user_version=1` cannot tell a fresh v1 file from one built before either landed. On an existing v1 ledger
missing `meta`, it creates just that table (`META_TABLE_DDL`, a shared constant — see the self-caught
regression below) and seeds `ledger_id`/`schema`/`created_at` exactly as a fresh create does, and separately
backfills the digest-chain trigger if it's missing too. No other row is touched. New spec:
`openLedger migrates a v1 file that predates meta, preserving every row and retrofitting the digest trigger`
— builds a hand-written pre-addendum schema (every §4 table except `meta`, `digest TEXT NOT NULL` with no
default, no trigger), seeds a workflow + event row directly, opens it with `openLedger`, and asserts: a fresh
identity is minted, `meta.schema`/`meta.journal_mode` are correct, the pre-existing workflow/event rows are
byte-identical, the trigger is retrofitted, and a second open never re-seeds (`ledger_id` stays stable).

**Why the count is still 18, and that's not a ledger-db.mjs bug**: I traced all 18 occurrences in the actual
suite — none of them touch a v1-without-meta ledger file at all. Every one is
`kernel/admission.mjs:15` (`ledgerIdOf`) calling `ledgerDb.ledgerIdOf(handle)` where `handle` is a
`kernel/journal.mjs` `openJournal()` handle (the pre-1.0.4, `operational-journal@1` schema, kept only for the
migrator per docs §1) — never a `ledger-db.mjs` handle at all, so it never has, and never should have, a
`meta` table. `admission.mjs`'s own comment (lines 9-14, still present) explains the *intended* behavior:
fall back to `handle.ledgerId` until `ledgerDb.ledgerIdOf` ships. It shipped in wave 1, so the `typeof
ledgerDb.ledgerIdOf==='function'` branch is always taken now and the promised fallback never triggers — this
regressed the moment wave 1 added the export, independent of anything in wave 2. I confirmed with
`node --test tests/admission.spec.mjs` (all 9 pass — every call there uses a real ledger handle) and by
reading every failing call site's stack trace (all fall through `openJournal → createAdmission →
admission.mjs:15`, e.g. `tests/kernel-engine.spec.mjs`, `tests/journal-retention.spec.mjs`,
`tests/engine-migration.spec.mjs`, `tests/engine-lifecycle.spec.mjs`).

## (b) `NOT NULL constraint failed: events.digest`

**Root cause, found**: `kernel/jobs.mjs:35` —
`db.prepare('INSERT INTO events(event_id,workflow_id,entity_type,entity_id,generation,kind,payload_json,created_at) VALUES(...)').run(...)`
— a column list that omits `prev_digest` and `digest` entirely. Not a file I own.

**Fix, at the root, inside my file**: rather than chase this (and any other) caller, the chain is now
enforced by the `events` table itself. `digest` gets `DEFAULT ''` (still `NOT NULL`, so an omitted column
can never trip the constraint) and a new `AFTER INSERT` trigger, `events_digest_chain`, recomputes both
`prev_digest` and `digest` from the workflow's own history for every row, regardless of what the INSERT
supplied — via a `starci_sha256` SQL function registered on the connection
(`db.function('starci_sha256',{deterministic:true},...)`, `node:sqlite`'s `DatabaseSync.function`) that
mirrors the existing `digestOf` formula exactly. The trigger is part of `LEDGER_DDL` for new ledgers and
retrofitted by the (a) migration for old ones. New spec:
`the events table computes its own hash chain even when an insert omits prev_digest and digest entirely` —
inserts two rows with `kernel/jobs.mjs`'s exact column list and asserts the resulting chain both differs
from `''`/`null` correctly and passes `verifyChain`.

Signature count: **15 → 0**, confirmed by `grep -c "NOT NULL constraint failed: events.digest"` on the full
suite log both before and after.

## (c) `ledger.listJobs is not a function`

**Root cause**: `kernel/engine.mjs`'s `unsettledGenerationJobs` (and `staleLeaseProof`, same shape) opens a
ledger read-only via `inspectLedger` and then calls `.listJobs()` / `.getJob()` on it — but `inspectLedger`'s
returned handle only ever exposed `liveRows`/`workflows`/`eventsHead`/`verifyChain`. An inspection is meant to
be a full read of the ledger (§3), not a lesser one, so the gap was in my own file.

**Fix**: pulled the read-only accessor set (`liveRows`, `workflows`, `eventsHead`, `verifyChain`, `getJob`,
`listJobs`, `events`) into one `readAccessors(db)` factory shared by both `inspectLedger` and `openLedger`'s
handle (also removing the duplicated inline definitions `openLedger` used to carry). New spec:
`inspectLedger exposes the same job and event read surface as openLedger`.

Signature count: **2 → 0**.

## Self-caught regression (fixed before committing)

Verifying the fix, `tests/execution-contracts.spec.mjs`'s
`ledger-db schema catalog names exactly the tables kernel/ledger-db.mjs creates` newly failed. That test
statically regexes this file's *source text* for `CREATE TABLE (\w+)` to build the table catalog it checks
against `schemas/ledger-db.schema.yaml` — a real safety net, not a test to work around. My (a) fix's backfill
branch had a second, literal `CREATE TABLE meta(...)` string outside `LEDGER_DDL` (to create just that one
table on an old file), and the regex picked it up as a spurious extra `meta` entry appended to the tail of
the match list, landing in `machineTables` instead of `ledgerTables` (everything after the source's one
`ledgers` token is bucketed as machine). Fixed by hoisting `META_TABLE_DDL` into its own constant, referenced
by both `LEDGER_DDL` (as `${META_TABLE_DDL};`, so the source text is unaffected) and the backfill branch
(`db.exec(META_TABLE_DDL)`), so the literal `CREATE TABLE meta` text appears exactly once in the file.
Verified with `node -e` running the same regex against the fixed source: the match list now matches the
schema exactly, and the spec test passes.
