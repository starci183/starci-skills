## The defect, measured

The Nivo Setup re-audit at 0.4.11 (session `20260905-130417-nivo-environment.preflight`,
`step-13/parallel-2`, capture `module-setup-vi-wide`) measured the page heading stamped `FONT-4` at
36px / 40px and the section heading stamped `FONT-3` at 30px / 36px; the same nodes at 0.4.9
(`step-7/parallel-2`, `module-setup-read-only-vi-wide`) measured 20px / 28px and 16px / 24px. Every
other text node in those records is byte-identical between the two captures, and
`packages/grammar/src/core/primitive/Heading/index.tsx` did not change between 0.4.9 and 0.4.11.

The component was never the defect. `Heading` renders through the vendor's `Typography.Heading`
(`@heroui/react` 3.2.4), which adds `typography typography--h<level>`, and the vendor sheet
(`@heroui/styles`, `components` layer) sizes `.typography--h1` at `text-4xl` (36px), `.typography--h2`
at `text-3xl` (30px). Against that the family fielded only Tailwind utility classes on the component
(`text-xl`, `text-base`, `text-sm`, `text-xs`, `text-4xl`), and a utility class exists only where the
consumer's Tailwind build scans this package's dist. nivo-fe's `globals.css` scans
`../../node_modules/@starci/grammar/dist` relative to `apps/app/src/app`, i.e. the app-local
`apps/app/node_modules/@starci/grammar`. At 0.4.9 that nested copy existed because the workspace root
still held 0.4.8, so the scan found the package and `text-xl` (utilities layer) beat the vendor. The
0.4.11 consume bumped every manifest to one version, npm hoisted the package to the root
`node_modules`, the app-local copy disappeared, the scan found nothing, the utilities were never
generated, and the vendor's sizes rendered under the family's stamps. So 0.4.10/0.4.11 changed nothing
in the Heading; they changed where the consumer's install put the package, and the family's stamp had
never been backed by the family's own sheet.

## The repair (package commit 67680f82)

`packages/grammar/src/common/styles.css` now draws the FONT scale off the attributes `Heading`
already emits, `[data-component="Heading"][data-scale][data-level]`, under `.grammar-common-root`:
FONT-4 1.25rem / 1.75rem, FONT-3 1rem / 1.5rem, FONT-2 0.875rem / 1.25rem, FONT-1 0.75rem / 1rem,
FONT-6 2.25rem / 1.25, each with the recipe's weight and the `tracking-tight` `font.md` gives FONT-4
and FONT-6 alone. This is what `.starci-core-text[data-size]` has always done for `Text`. No class,
markup, JSX or prop changed; `Heading/index.tsx` is untouched, which the operator's projection gate
would have refused anyway.

Two rulings the receipt records:

- `!important` on the standard levels. The Grammar sheet lives in `@layer starci-grammar-common`;
  nivo-fe imports it after `@heroui/styles` (family layer outranks the vendor's), starci-academy-fe
  imports it before Tailwind and HeroUI (vendor outranks the family). Layer rank alone cannot decide
  the winner in both orders, and the sheet already uses `!important` where it must beat the vendor
  (`.starci-core-tabs .tabs__tab`, `.starci-core-input-resting-*`). The values re-state what the
  utilities carry, so a consumer whose scan still finds the package sees nothing move.
- Only FONT-6's size is important. `offset-pop/styles.css:72` re-cuts the display heading with its
  own `font-weight: 900`, `letter-spacing: -.045em`, `line-height: .96` as normal declarations in a
  later family layer; a blanket `!important` would have silently overridden all three. The display
  rhythm stays a normal declaration, so in an import order where the vendor's layer outranks the
  family's, the vendor's `text-4xl` line height (1.111) can still beat `leading-tight` (1.25) on the
  display heading while its 36px size holds. Recorded, not repaired here.

## The test

`packages/grammar/src/core/primitive/Heading/index.spec.tsx` gains one case, titled exactly the plan's
regression assertion (`renders the font size each FONT stamp claims from the family's own sheet, per
level and scale`), under `// @vitest-environment jsdom` (jsdom 30 is hoisted at the workspace root,
as `react-dom` already is for the package's other specs). It renders levels 1–4 and `scale="display"`
with `renderToStaticMarkup` inside `.grammar-common-root[data-grammar-family="core"]`, reads the
`FONT-n` id off `data-contract`, and measures `getComputedStyle` font-size, line-height, weight and
letter-spacing against the `font.md` scale at a 16px root. Before the repair the nodes measure the UA
defaults (h1 32px under `FONT-4`); after it, 20/28, 16/24, 14/20, 12/16 and 36 / 1.25. The
before-proof failed on exactly that title, the after-proof and the full package suite passed, and the
0.4.11 stamp-versus-render specs (`scrollable-surfaces`, `Tabs`) are in the regression command and
green on both sides.

Two measurement facts the next spec author needs, both recorded in the spec:

- jsdom parses `@layer` blocks into `CSSLayerBlockRule` but its cascade never visits the rules inside
  one, so the spec lifts the shipped sheet's rules out of their layer (walk `cssRules`, recurse into
  `CSSLayerBlockRule.cssRules`, join `cssText`) into a flat `<style>` before measuring. What is
  measured is still the shipped sheet, declaration for declaration.
- `new URL("../x.css", import.meta.url)` is rewritten by Vite's asset handling and under the jsdom
  environment resolves to `http://localhost:3000/...`, so `readFileSync` throws `The URL must be of
  scheme file`; the spec reads through `fileURLToPath(import.meta.url)` + `resolve` instead
  (`Heading/index.spec.tsx:23`).
