## The doctrine that must not be broken

- The owner decides; the runtime prepares. A recommendation is provisional, never an answer.
- A credential is never invented, stubbed, defaulted or silently skipped, and **no secret value is ever written
  anywhere** except the tree's encrypted custody. Never "allow secret" on a GitHub push protection warning.
- Custody is `<work tree>/_resources/identity/<slug>/secrets.enc.yaml`, sops-encrypted, written only by
  `starci identity set|fill` (value from stdin) and read only through `sops exec-env`. An environment variable
  is not custody.
- Never touch another worktree, never touch a product repository outside the sanctioned flow, never push `main`
  of a product repository, and never message or type into a running Orca agent. Fix the kernel instead.

## What was deployed today

All of it is on `main` and on the live `.claude`. In the order it landed:

1. **The ask op decides what the question is.** The keyword heuristic only chooses which tab opens; what the op
   reports decides how it ends (`answered-from`, `decision:`, `credential: … present`). Either ask kind may end
   either way (`ask-reclassified`). Two asks on one decision folder never queue behind each other.
2. **A dead dispatch leaves its last words.** Orca's `worker-show` `last_failure` becomes the op's own report
   (`dispatch-last-words`); a failure the environment caused counts against `infraRestarts`, never the op.
3. **One owner list.** `ownerItems(state)` renders `## Owner (n)` first in the status page, the final report and
   `workflow-status`. Mechanical lines are dropped while an author op is on them.
4. **The kernel reads the tab before calling an op stalled** (`kernel/tab.mjs`): five verdicts - prompt-missing,
   asked, finished-unreported, working, idle - plus a grace window for long contracts.
5. **A credential is a prompt to fill, not a command to compose.** A `provision.ask` for a credential is never
   launched as an agent. The kernel prints one line with the exact command; the owner runs
   `starci identity fill <slug> --name A --name B`, which asks `Fill A:` with the echo off and writes custody;
   the kernel settles the ask by presence at the next tick (`provision-filled`).
6. Four repairs found while watching it run: `redactSecrets` no longer masks variable NAMES (it ate
   `RECOVERY_CUSTODY_SECRET_KEY` and lost the presence marker); `sopsEnv` names `~/.starci/master.identity` when
   nothing names a key file; the supervisor and the kernel now revive each other (both died at once and the
   workflow sat an hour with nine ops "running"); a fill-waiting ask with no command yet is asked again every
   tick until its custody is knowable.

## If the workflow looks frozen

1. `workflow-status` first: it prints whether the kernel process is gone and how long the supervisor has been
   silent.
2. The supervisor is started by hand only when both are dead - it now revives the kernel and the kernel revives
   it, so this should be rare:
   `node <skill root>/bin/starci.mjs workflow-supervise --host <skill root>` run detached from the product
   worktree.
3. A deploy to `.claude` restarts every kernel by design (`build changed` → `run-resumed` within a minute).
   Deploying twice in a minute costs a tick, nothing more.
