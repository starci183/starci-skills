# Code style: i18n (translation and multiple languages)

Scope: how to WRITE translation code in the FE app — the real library, the hook, key namespacing,
the ban on hard-coded user-facing strings, locale, interpolation. Not the design or the content of
the translations themselves.

Grounded by scanning the FE app's `src`. `useTranslations` appears in **474 files**;
`react-i18next` in **0**. The idiom is **next-intl**, not i18next or react-i18next.

---

## 0. The real library is `next-intl` — and here is how to be sure

`package.json` lists `i18next`, `react-i18next`, and `next-intl` alike. Do not trust
`package.json`; grep the source:

```bash
grep -rl "useTranslations" src | wc -l   # 474  -> next-intl
grep -rl "useTranslation\b" src | wc -l  # 0    -> react-i18next is dead here
```

**STRICT:** all new code translates through `next-intl`. Importing from `"react-i18next"` or
`"i18next"` is banned, even though both sit in the dependency list.

---

## 1. The client hook is `useTranslations` from `"next-intl"`

```tsx
// src/components/blocks/cards/CourseCard/index.tsx
import { useLocale, useTranslations } from "next-intl"
const t = useTranslations()
// ...
{t("courses.viewCourse")}
```

```tsx
// Wrong on both counts: a library this repo does not use, and the wrong destructure.
import { useTranslation } from "react-i18next"
const { t } = useTranslation()
```

`t` is the return value DIRECTLY — `const t = useTranslations()` — never destructured as `{ t }`.

---

## 2. Namespace: empty `useTranslations()` with a full dotted key is the dominant idiom

The repo uses two shapes. Both are valid, but **empty plus full key dominates, 435 of 474**:

```tsx
// Dominant — no namespace, the key is the full path (CourseCard)
const t = useTranslations()
t("courses.learners", { count })
t("course.continueLearning")
```

```tsx
// Accepted — scope to a namespace when one component sits entirely on one key branch
// src/components/features/blog/BlogList/CategoryFilter/index.tsx
const t = useTranslations("blog")
t("title")                       // = blog.title
t(`categories.${filter}`)        // = blog.categories.<filter>
```

**STRICT:** pick one shape per file and stay with it. Keys are always `camelCase.dotted`, and every
key must exist in **BOTH** `src/messages/en.json` and `src/messages/vi.json` — the two files mirror
each other.

---

## 3. No hard-coded user-facing strings

Every word a user reads goes through `t(...)` with a key in `messages/{en,vi}.json`. A Vietnamese or
English literal in JSX is banned.

```tsx
// src/components/blocks/cards/CourseCard/index.tsx
const viewLabel = isEnrolled ? t("course.continueLearning") : t("courses.viewCourse")
```

```tsx
// Wrong: hard-coded copy.
const viewLabel = isEnrolled ? "Tiếp tục học" : "Xem khoá"
<Button>Xem khoá</Button>
```

There is an anti-pattern still present in the repo that must not spread: an inline locale ternary,
in `src/app/[locale]/contact/page.tsx` and `.../status/page.tsx`.

```tsx
// Do not multiply this — move the copy into the messages JSON.
title: locale === "vi" ? "Liên hệ" : "Contact"
```

It survives in about seven older route and config files. NEW code uses a key, never a string
ternary.

---

## 4. Interpolation and plurals are ICU in the JSON, never string concatenation

Variables are passed as the second argument:

```tsx
// CourseCard
t("courses.learners", { count: course.enrollmentCount })
t("course.priceUsdHint", { amount: formattedPriceUsd })
```

```jsonc
// messages/en.json
"learners": "{count} learners"
// plurals use ICU syntax in the JSON — never an if/else in the TSX
"resources": "{count, plural, =0 {No resources} one {# resource} other {# resources}}"
```

```tsx
// Wrong: concatenation, and plural logic climbing into the component.
t("courses.learners") + " " + count
count === 1 ? t("one") : t("many")
```

Rich text — JSX embedded inside a translation — uses `t.rich` with a chunk callback
(`landing.hero.headline` and friends):

```tsx
t.rich("landing.hero.headline", { accent: (chunks) => <span className="text-accent-soft-foreground">{chunks}</span> })
```

---

## 5. Locale and routing come from `@/i18n/*` — do not roll your own

The current locale is `const locale = useLocale()` (160 call sites). The single source of truth for
configuration is `src/i18n/routing.ts`: `locales: ["en","vi"]`, `defaultLocale: "vi"`, cookie
`LOCALE`.

- In a server component or in metadata, use `getTranslations` from `"next-intl/server"`
  (`src/app/[locale]/privacy/page.tsx`):

  ```tsx
  const { locale } = await params
  const t = await getTranslations({ locale })
  ```

- `requestLocale` is read in `src/i18n/request.ts` via `getRequestConfig` — do not read the cookie
  or the param by hand.
- `useLocale()` is for choosing a format or a data branch — `locale === "vi" ? "vi-VN" : "en-US"` —
  never for choosing between two UI strings. That is `t`'s job.

**Navigation keeps the locale prefix:** use the localised wrappers in `src/i18n/navigation.ts` —
`Link`, `useRouter`, `usePathname` from `@/i18n/navigation`. The repo is currently MIXED: several
places still reach for `next/navigation` or the vendor `Link`. When a link must preserve `/vi` or
`/en`, prefer `@/i18n/navigation`.
