# Upgrading an installed runtime to 5.0.0-plus

This page is for the person who operates an installed runtime — the `.claude` directory of a host — rather
than for someone reading the source. It says what changed under you, what you have to run once, and what is
safe to leave alone.

`starci update --dir <host>` moves the payload, rebuilds and verifies `.dist`, and records the new version.
Everything below is what that update does **not** do for you.

## Do this once, after the update

**Stop and start a running supervisor with the new command line.** The supervisor is the only long-running
process of the runtime, and it was started from a module path that no longer exists. A supervisor left
running from the old path keeps executing the code it started with and will fail as soon as it tries to start
a kernel.

```
# stop the running supervisor (the process you started with the old launcher path)
# then start it again, from the one entry:
node <host>/.claude/bin/starci.mjs workflow-supervise --host <host>/.claude
```

Nothing else needs restarting. A kernel that is mid-workflow notices that the runtime's own modules moved,
ends its loop cleanly and is started again by the supervisor on the new code; that is the ordinary
build-follows behaviour and it needs no hand.

**Use the one entry everywhere else too.** Every command of the workflow kernel is now
`node <host>/.claude/bin/starci.mjs <command> ...`, which forwards its arguments unchanged to the launcher.
Any script, alias, cron entry or note of yours that names a module path inside the runtime has to be changed
to that form — the old `.dist/execution/orca-supervised-launch.mjs` path is gone, along with the rest of the
old `execution` tree the kernel lived in.

## What changed under you

**The tree is laid out by concept.** The runtime source inside `.claude` moved: the declared data the runtime
runs on is now `model/` (it was `profiles/`), and what used to be one `execution/` folder is now `kernel/`
(the control loop, one file per concern), `hosts/` (the host adapters), `models/` (the model functions) and
`checks/` (the machine checks that read bytes). `.dist` mirrors that same shape, so a path you may have read
in a log or a contract has moved with it. The installer removes the old roots it owned and preserves anything
it did not.

**Three declaration files are versioned.** The operation catalog is `kinds@2`: each kind now declares `reads`
and `writes` over a closed catalog of record kinds, where 5.1 had one `mutates` list. The record catalog
itself is new (`records@1`), and so is the host profile (`hosts@1`), which is where a host's capabilities and
whether it runs operations in parallel are now declared. You do not edit these to upgrade; they ship with the
runtime. They matter to you because a validation error now names one of them.

**A new node kind: `integration`.** An external system a business or design record declares is a record in
its own right, and the tree owes one node per declared system, with its own completion profile. Until such a
node exists for a declared integration, the tree reads as incomplete and the runtime opens the work to author
it. See the new fields below.

**An unclear requirement or design no longer stops the work, and you are told what it decided.** A record that
is confusing, contradictory or silent used to reach you as a blocked operation. It no longer does: the runtime
revises the record itself towards its most reasonable reading — by your accepted records, the decided records
of your other features and the product's own conventions — states why, bumps the record's `rev` and carries
on. A requirement gap is the new blocker `srs-gap` and is repaired by the new kind `business.revise` on the
business node that owns the record, exactly as `sds-gap` has always been repaired by `architecture.revise` on
the architecture node. You read what it decided in `extensions.work3.decisionLog` on the record and overturn it
there if you disagree; the proof digests reopen whatever was built on the old reading. **The one exception**:
when the readings differ in an observable outcome about money, authority or customer data, the runtime does
not choose silently — it prepares a decision record with numbered options and one recommendation, asks you,
and carries the work on that recommendation until you answer. The same split runs on the goal page: a hidden
decision the critic calls decisive is put to you before the work of its feature starts, and one it does not is
left to the record repair.

**The goal page now tells you what only you can provide.** Under `### The owner provides`, and in
`workflow-status` as `## The owner provides (n)`: credentials, sandbox or test accounts on external systems,
real datasets or samples, and the legal or consent authority to act for real — read from the whole product
before anything is planned, rather than discovered one stuck operation at a time. It is a heads-up, not a
queue: nothing waits on that list, and the operation that needs one asks you in its own tab with the exact
name at the moment it needs it.

**A heavy node is cut up and built in parallel.** A node whose write scope names more than 12 files, that
states more than 8 assertions, or whose design references 3 or more components is no longer approved and run
as one long build. The runtime plans one `implementation.plan` operation first — a new operation kind, on the
existing `work.author` operator — which splits that node into child nodes with disjoint write scopes: the
**seam** (the one child that owns the module wiring, the dependency registration, the migrations and the
shared contracts and types every other child would otherwise touch) is built first and alone, then the rest
run at once, up to nine of them on the ten parallel slots. The node you authored becomes a **derived parent**:
its `state` and its write scope are removed, and its assertions are kept as the group's acceptance under
`extensions.work3.groupAssertions`, which is exactly what the group's one proof is judged against. The proof
runs once for the whole group on a runtime none of the children used — `e2e.verify` then `review.verify` for
backend work, one `uat.verify` walking every flow for frontend work — never once per piece, and a review
finding is repaired in the child whose write scope holds the file it names. A node that really is one
observable behaviour is not split: the operation reports `cut: none` and the node runs as it is. Nothing about
this needs a decision from you; you will see it on the goal page as `1 implementation.plan -> seam ->
N backend.implement -> 1 e2e.verify -> 1 review.verify` instead of a single large operation, and the bound on
how wide one node may fan out is `allocation.fanOut` in `model/runtimes.yaml`.

**You are asked for less, and the work no longer waits on you.** The runtime now stops for exactly two things:
something only you can provide, and something that cannot be undone. *Only you can provide* is a class, not a
key — a credential, a **sandbox or test account** on an outside system (a payment gateway, a bank, an e-invoice
provider, a tax authority, an SMS or e-mail provider, an identity provider, storage), a **real dataset** the
product must be verified against (a bank statement export, a sample of production invoices), or your
**authority** to act (may we message these users, may we charge this card). *Cannot be undone* is a message to
real customers, a payment, a deletion of real data, a publish. Everything else the records do not settle — a
conflict, money, customer data, a rule a review keeps arguing about — the runtime now decides **provisionally**
on its own recommendation and carries on. `workflow-status` prints those under `## Provisional decisions (n)`,
separately from `## Needs you`, and a workflow can finish `done` with some open. You answer them whenever you
like, with the same `workflow-answer --id <id> --op <ask op> --choice <n>`: the same option confirms what was
built, a **different** option reopens every node that was built on it. You can also just type the number in
the operation's own terminal while it is asking. And a bound the runtime set for itself — review rounds, the
depth of a shared change, launch attempts, a record path an operation asked for — never reaches you as a
question any more; it is settled inside the runtime.

**A credential now lives in the tree, encrypted — not in an environment variable.** An environment variable
belongs to whichever terminal exported it, is gone on the next machine, and the tree cannot say who set it.
Custody is `.starciwork/_resources/identity/<slug>/`: a readable `resource.yaml` (the alias, who the identity
is on the provider, what it may do, the variable **names**) beside `secrets.enc.yaml`, encrypted with
[sops](https://github.com/getsops/sops) under this host's own age or GPG key — your product repositories
already carry a `.sops.yaml`. You put a value in with one command, which reads it from stdin and never prints
it:

```
node <skill root>/bin/starci.mjs identity set <slug> --name <VAR>
```

An accounting example: your e-invoice provider's sandbox key goes into `identity:e-invoice` as
`EINVOICE_API_KEY`, the integration record declares
`credential: {name: EINVOICE_API_KEY, providedBy: owner, custody: identity:e-invoice}`, and every check that
needs it runs inside `sops exec-env`, so the value exists in one process and is copied into no file, log or
report. The 5.1 `where:` field is retired and still read, as the finding `credential-custody-missing`, so an
older record is told what to change rather than failing on a rule it predates.

**New fields your records may carry.** All of them are written by the runtime, not by you:

- `extensions.work3.integrations` — on a business or design record, the external systems it talks to, each
  with the exact variable the **owner** provides the credential in and the `custody: identity:<slug>` that
  holds it. The value is never recorded anywhere; only the variable's name and the custody travel.
- `extensions.work3.kernel.provisional` — on a completed node, the decisions its proof rests on that you have
  not answered yet. It is what lets a different answer later find exactly the nodes that were built on the
  runtime's own recommendation, and reopen those and nothing else.
- `extensions.work3.reconciliation` — on a feature's module record, one typed row per decided record the
  feature touches: what it cites, what conflicts and is waiting on your decision, and what is new.
- `extensions.work3.kernel.contractDigest` — on a completed node, the digest of the rules that completion was
  accepted under, with the kind it was taken for.
- `extensions.work3.decisionLog` — on a requirement or design record a repair revised, one append-only entry
  per revision: `{rev, at, gap, chosen, why, alternatives}`. Nothing ever rewrites or deletes an entry, so the
  log is the whole history of what the runtime decided for you and why.
- `proof` in an evidence manifest — what a run actually proved against: a live external system, or the
  product's own interface with the outside systems it faked named.
- `extensions.work3.groupAssertions` — on a node that was cut, the assertions it stated before it became a
  derived parent. They are the acceptance the group's one proof is judged against, so nothing you wrote is
  lost when the node stops being a leaf.

## What is safe, and stays as it is

**Your workflow stores.** Everything under `.starciwork/_local/workflows` is unchanged by this update. An
approved, unfinished workflow resumes from its own `state.json` and event log with the same counters, the
same ledger and the same operations — start it again (or let the supervisor do it) and it carries on.

**Your product records.** No record is rewritten, converted or migrated by this update. The new fields above
appear only as the runtime writes them, on nodes it touches from now on.

**Proofs you already have.** A completion recorded before this build carries no digest of the rules it was
taken under. Those are **left exactly as they are and are not reopened**: reopening every earlier proof would
be a whole product's work you never asked for. They are reopened only when you ask for it. From now on, a
completion records its rules, and a node whose rules later change is reopened on its own — which is the
behaviour this field exists for.

## What was already on your list

A workflow that was running before this build may carry items an older rule put on your list: a review
"still fails after 3 rounds", a shared change "2 levels deep", a request "the kernel will not delegate", an
op "restarted 4 times". None of those is yours under this rule. The first kernel start after the update
judges them again (`parked-rejudged` in the log) and routes each where the rule routes it now: the review
is escalated inside the runtime, the deep change is authored as a Work node, the record paths are refused
and the code paths carry on, the spent launch cools and comes back. What stays on your list is what only
you can give: a credential, an account, a dataset, an authority, an irreversible effect.

## One Work tree, two repositories working in it

A project has one Work tree and the backend repository owns it, so the frontend's records and the backend's
records are written into the same tree, at the same time. Two rules that did not know that have been fixed.
A `todo` node's declared assets are pending work, not a broken tree: a drawing operation records the six
images its own next step will render, and until they land the validator reports the warning
`NODE_ASSET_PENDING` and the tree stays valid, so a frontend drawing no longer reddens every backend proof
beside it. Once a node is done - or is a branch deriving from its children - it must hold every asset it
declares, and an absent one is the error it always was. And a file another workflow left dirty in the shared
worktree is never counted as an operation's product: an operation answers for the files it reported itself,
over every attempt it made, so a record a frontend lane was writing is no longer a finding against a backend
build that happened to have it inside its write scope. Nothing to run; both take effect at the next kernel
start.

## Quota and downgrade

The only budget is the one your provider actually keeps. The supervisor reads those windows — the session, the
week, Fable's own week — and a runtime whose window is at ninety-five per cent is set aside until that window
resets, then picked up again on its own. The daily caps the runtimes profile used to carry are gone: one of
them once stopped a migration late in the evening while the provider still had most of its week left, and that
is the kind of stop this update removes.

Under every tier there is now another one. The runtimes that decide and plan no longer end at Fable and Astra:
Fable hands work down to Opus, Astra to Sol, and the launch chains say so. Nothing moves down while the top is
free — the top tier is still preferred whenever it has a slot, and the next operation returns to it the moment
one frees — but a top tier that is full, cooling or out of window now passes the work on instead of holding it.

## The validator judges what the operation claimed

Two decision drafts share one `policy-decisions/**` allowlist, and the second ask was rejected twice for the
first ask's record that was dirty beside its own. The validator now judges the files the operation reported
and git confirms (`validator-scope-attributed`); an op that claimed nothing is still judged on everything it
could have changed. An op an older build blocked that way is re-admitted at the next start
(`validator-readmitted`).

## The question stays on screen

A prepared decision's tab used to close with its report, so the question was printed and gone within a
minute. The `decision.prepare` tab is now kept open (`ask-tab-kept`) until the owner answers or the
workflow finishes; the op stays in it and relays a number the owner types there through `workflow-answer`.

## A question is a prompt to fill, not a command to type

Asking you for a credential used to mean an agent in a terminal tab: it printed a wall of text with a command
for you to compose, then polled you for the word `set`. You looked at that tab and asked whether it was even
asking you anything. It was not, so no agent is launched for a credential any more.

The kernel prints ONE line instead - in its own tab, in `## Owner` on `workflow-status`, and in the final
report: `Fill ZALO_OA_ACCESS_TOKEN, ZALO_OA_SECRET for identity:zalo-oa: copy and run  node <skill
root>/bin/starci.mjs identity fill zalo-oa --name ZALO_OA_ACCESS_TOKEN --name ZALO_OA_SECRET --work-root
<tree>`. You copy it, run it, and it asks: `Fill ZALO_OA_ACCESS_TOKEN:` with the echo off, one variable at a
time, putting each answer straight into the tree's encrypted custody. An empty answer is a skip, never a blank
credential.

Nothing is replied to and nothing is clicked. The ask waits with no runtime, no slot and no deadline
(`provision-fill-waiting`), and the kernel settles it itself the moment the custody holds every variable -
checked the way the contract checks it, `sops exec-env <secrets.enc.yaml> 'node -e
"process.exit(process.env.<VAR>?0:1)"'`, so presence is all that is ever read (`provision-filled`). The
variable names and the slug come from your integration record's `credential: {name, providedBy: owner, custody:
identity:<slug>}`, or from the question's own words when the tree declares none. `workflow-answer --op <ask>
--note set` runs the same check immediately and refuses, naming what is missing, if the custody is still
empty. An account, a dataset, an authority or an irreversible effect is unchanged: there is nothing to type
into a prompt for those, so they are still asked in their own tab.

## Two kinds instead of `owner.ask`

The one kind that put things to you is two now, split on the one thing that matters - whether the runtime
waits. `decision.prepare` prepares a decision (the question, the sides, the numbered options, one
recommendation), prints it in its tab and reports at once; the runtime carries the recommendation into the
work and you overturn it later with `workflow-answer`. `provision.ask` names the one thing only you can give
- a credential, an account, a dataset, an authority, the go-ahead for an irreversible effect - and waits in
its tab. A workflow written before the split has its `owner.ask` ops renamed on the first kernel start
(`kind-renamed`); the events keep their `owner-ask-*` names.

## Migrating a tree

`starci workflow-goal --migrate all --lane migrate-v5 --job "..."` plans one intake per feature, in
parallel, that adds what this model makes explicit to your decided records - the typed reconciliation, the
integrations with `custody: identity:<slug>`, the integration nodes - and re-decides nothing. Approve it
like any workflow; the intakes never touch `implementation/` or `ui/`, so a workflow building code at
the same time is not disturbed.

## If something looks wrong

Run `starci doctor --dir <host>` first: it runs the installed copy's own contract tests and reports local
drift. A file you changed by hand is kept by the update and listed as kept; pass `--force` only when you
intend to take the package's version of it.
