# Upgrading to StarCi 1.0

This version names the durable engine by what it is, keeps only what a workflow needs to continue, and stops
before it fills a disk. It is not an npm publication or proof of a complete live product delivery. Read
[the execution contract](../docs/execution-contract.md).

## Prerequisites and version identity

Use Node.js 22.13.0 or newer; the runtime uses the built-in `node:sqlite` API without an experimental CLI flag.
The local operational journal defaults to SQLite DELETE journal mode and FULL synchronization. WAL is
explicit only, with SQLite 3.51.3 or newer; older bundled SQLite releases may contain the WAL reset defect.
The journal is local to this machine, shared by enrolled workflows, and is not placed on a network share. Its
default location is `<local app data>/StarCi/runtime/journal.sqlite`; candidates and probation ledgers live
beside it.

Historical tags describe earlier package history and are preserved. The package version is `1.0.0`, the engine
version in a workflow's state is the package version, and the engine's identity is a schema,
`engine.schema: starci/engine@1`, not a number. Neither identity is inferred from tag order. Do not silently
downgrade an installation from a historically higher package version. Select this build deliberately. Do not
publish or retag it as an automatic registry upgrade.

The install manifest carries `installProtocol: {schema: starci/install-protocol@2, engine: starci/engine@1}`
independently of public package semver. A receipt written before public 1.0 - a numbered marker under the
earlier protocol schema, or no marker at all - is the pre-release protocol, ranked below every public engine:
updating such a host is a major upgrade and needs `--upgrade-major`. A malformed marker is refused instead of
guessed, and installer writes refuse an engine newer than this build supports. Doctor remains read-only.

Agent-led coordination is explicit. Only a retry that records `engine.coordination: agent-v1` enables the
manager decision function. It receives a bounded digest-bound snapshot and may order only executable action IDs
supplied by the kernel. The kernel remains the sole state writer, rechecks preconditions, and keeps owner
choices, authority, evidence acceptance and product meaning outside the manager. Its host-local pool is
`models.nonOperation.kernelManager: opus-sol` in `config.json`; `planner: fable-astra` and
`validator: fable-astra` serve the other two non-operation roles with separate typed inputs and contexts.
Admission chooses an eligible, qualified pool member using known quota and capacity before calling it.

## Build, test, pin, retry

1. Build and test a private copy of the complete source. Never publish an intermediate `.dist` to a running
   workflow. Run the complete test suite, relocated CLI checks, provider validation, build reproducibility,
   and both documentation sites before accepting the build.
2. Seal the accepted `.dist`, launcher and operation template with `kernel/runtime-pin.mjs`'s build helper into
   `<skill root>/runtime/engine/builds/<digest>`. This is maintenance tooling; agents still use only
   `bin/starci.mjs`. Keep the returned pin record locally.
3. Pause the approved workflow using `node <runtime>/bin/starci.mjs workflow-stop --id <id>` and wait for its
   kernel to exit. A pause does not prove its native operation workers stopped.
4. Run `node <runtime>/bin/starci.mjs workflow-retry --id <id> --runtime-pin <pin-record.json>` with the same
   host, worktree and ledger binding. This command settles live dispatches, refuses unknown effects, preserves
   the approved goal and accepted Work, increments the execution generation and gives unfinished active
   operations fresh contexts. It does not delete product branches or edit accepted specs. The pin and journal
   must be visible to both the supervising process and the execution host. When their user-local storage
   namespaces differ, place the pin in a shared local runtime directory and pass
   `--journal-file <shared-local-journal.sqlite>`. All enrolled workflows on that machine must use the same
   journal to share the global capacity limit. Relocation requires all former-generation jobs settled.
5. The supervisor verifies the pin before starting the next kernel. A changed/missing pin fails closed.
   Observe operation, owner-input, job and acceptance events. A resumed workflow trial is distinct from a
   fresh end-to-end trial with a clean scenario and held-out assertions.

Retain the previous runtime pin, Git history and workflow evidence. A rollback must first settle every job and
dispatch; never point a live journal at an older engine or delete its leases to recover capacity. The upgrade
does not move `.starciwork`, custody, Orca worktrees or source repository ownership.

## Migrating a workflow enrolled by an earlier build

A workflow enrolled by an earlier build carries the engine as a numbered marker, every engine-owned operation
field prefixed with that number, and the candidate manifests (the file inventory of the whole repository, with
digests) whole inside `state.json`. Such a state is never edited by hand and never started by this build:
`workflow-run` refuses it by name and points at the retry. The one boundary is the same stop, seal and retry as
above, and the retry migrates the record on the record:

- `engine-state-migrated` renames the prefixed fields to their names (`lease`, `pending`, `candidate`,
  `candidateDigest`, `workerSettled`, `retryReconciled`, `ownedBaselinePaths`, `resolvedReferences`, ...),
  writes each inline candidate under its own control root and leaves a small record in its place (a candidate
  whose control root is gone is dropped; the next attempt begins a new one), and gives the engine its schema.
  The number is read from the record; this build knows no numbered engine.
- the usual retry fences then run against the former journal: live dispatches are settled through the host,
  stale lease fields are cleared with the journal's own proof, and unsettled model or check jobs block the retry.
- `journal-relocated` moves the workflow to this build's default journal unless `--journal-file` names one:
  the former journal must hold nothing live of the workflow, its settled rows are retired there, and the
  probation ledgers beside it are copied beside the new journal when the new root has none. Until every
  workflow on the machine has moved, the two journals hold two global ceilings of ten; move them together.
- `events-rotated` closes the retired generation's event log as `events.g<n>.jsonl` beside a fresh live log.
  History stays readable; `readEvents` replays the segments before the live log, and the seq counter continues.
- the startup lock (`kernel-startup.sqlite`) needs no migration: the retry requires the former kernel to be
  gone, and the supervisor's next reservation reclaims a dead owner.

The supervisor of this build starts a workflow still on the earlier record through the sealed build its state
names, so nothing changes for a workflow until its owner retries it. A former journal that no state names any
more is removed with `journal-retire` (below); its orphaned rows die with it.

## What the journal and the store keep

The admission journal keeps what a workflow needs to continue and nothing it has settled. The policy is one
record, `RETENTION` in `kernel/journal.mjs`, and it is tested:

- the bound generation keeps one state body (the recovery state), every `transition:` and `bind:` checkpoint
  row (so a replayed transition is still recognised, body or not) and only the latest `save:` checkpoint;
- a retired generation keeps no snapshot rows, no settled jobs and none of their events; the kernel retires them
  when it binds the next generation (`journal-generations-retired`);
- a finished workflow retires every row it holds (`journal-workflow-retired`); a finished workflow that still
  holds a reservation keeps them and says so (`journal-workflow-retained`);
- live reservations, unsettled jobs and their events are never touched, whatever their generation;
- a journal created by this build gives freed pages back to the filesystem on its own; a journal created earlier
  shrinks only under `journal-prune --vacuum true` while no kernel holds it.

`state.json` keeps a candidate record - identity, roots and digests - and the manifests stay under the
candidate's control root on disk (`bridge.json`, `snapshot.json`, `candidate.json`), so a state is a few hundred
kilobytes where it was several megabytes and every checkpoint body with it.

Two operator commands act on a journal a kernel never acts on for another workflow:

- `journal-prune --journal-file <file> [--store-root <root,..>] [--retire <id,..>] [--vacuum true] [--dry-run]`
  retires the rows of every workflow the named stores prove settled - finished, bound to another journal, or
  named with `--retire`. A workflow with live rows is kept by the journal itself; an id no store knows is
  reported and left alone. A dry run opens the file read-only and changes nothing.
- `journal-retire --journal-file <file> --store-root <root,..> [--delete true]` removes a whole journal that no
  state under the named stores binds and that nothing wrote to within the last thirty minutes. Rows still live
  in it belong to workflows no state names and are reported as what dies with the file. Without `--delete true`
  the command only reports.

## Disk headroom

Before its first tick and before every tick the kernel measures the free space of the volumes it writes to - the
workflow store, the worktree and the journal - against one threshold, one gibibyte unless
`STARCI_DISK_HEADROOM_BYTES` says otherwise. Below it the kernel records `disk-headroom-exhausted` with the
measured bytes and the threshold, saves nothing, and exits with code 3. A write the disk refused mid-stage
(`database or disk is full`, `ENOSPC`) is recorded as `disk-full` and ends the kernel the same way; it is not
one more kernel error on the way to a crash loop. The supervisor measures the same volumes every round, leaves
a workflow alone while its volume is exhausted (`disk-headroom-exhausted` once, in its log), and starts the
kernel again when room returns (`disk-headroom-restored`).

## What the live trials taught this build

The first live retry exposed an already-closed-terminal case. Settlement uses the worker's actual stop/release
receipts even when closing its terminal again fails; unknown worker effects still block retry. For enrolled
workflows, the owner-input helper launches from the same sealed pin as the kernel while retaining the original
host binding for project routing and local language configuration.

An Orca kernel must execute inside its own live coordinator terminal. A detached process carrying an old
terminal handle is not an attested coordinator. The supervisor prepares the native terminal and the kernel
proves its Run binding before launching operations. A failed binding is an infrastructure condition, not
evidence that the chosen model failed its task. Retry must account for every prior native reservation,
including a blocked operation with no recorded dispatch; unknown effects cannot be skipped by advancing
the generation.

Review counters and findings belong to their execution epoch. Retry preserves accepted Work and actual
owner answers, and requires fresh review of unfinished groups. Unlaunched, unanswered questions derived
solely from a retired review epoch can be superseded with an audit record. Qualification refusals identify
missing evaluation evidence and unmet probation prerequisites; runtime maintenance does not manufacture
certificates or lower required machine checks to obtain a launch.

Failed native launches retain their Task, Dispatch and settlement receipts. A retry can recover a missing
Dispatch reference only by matching the exact Task and Run and verifying the exited worker's released
terminal resource. Worker termination settles reservations; it does not erase possible filesystem effects
or prove that the model never ran. Probation is refunded only for an independently recorded pre-task
rejection that proves execution and input never began. Late prompt consumption remains a spent attempt.

The host can revoke a Codex dispatch before the native CLI finishes starting, then the CLI consumes the input
after revocation. Such a worker cannot be accepted. Attaching a prestarted terminal is not a substitute unless
the host also attests its effective model identity.

The kernel prepares an actual canonical Work gate before admitting a declared Work writer. Independent
acceptance still validates the resulting candidate; absent or contradictory validator output and pathless
validation failures remain blocking. A reviewer reports `partial` with findings, and `done` only after all
required checks pass with no findings. Retained failed worker prose is explicitly diagnostic when its
structured findings were lost; it is not an accepted verification receipt.

The owner page shows preparation progress while workflow-owned prerequisites remain pending. This does not
open credential inputs early or certify the provider. Authenticated owner decisions remain available during
preparation. The single owner renderer reconciles polling and authenticated submit: polling retains draft text
and focus for the same request identity, revision, options digest and status, and a changed binding invalidates
that draft. `preparing` and `answered` rows cannot be entered, and polling itself never submits an answer.

Durable recovery retains the current validated invocation's coordinator and host lifecycle binding. A
checkpoint restores workflow progress, not the identity of a terminal that no longer exists; the current kernel
stays alive while the old terminal is retired. Pending worker reports are preserved and their dispatches are
settled through the retry boundary.

Operation admission records an `intent-v1` reservation before any native launch. If Windows temporarily
denies the atomic state-snapshot rename, the store retries the rename for at most 775 ms without deleting the
old snapshot. An exhausted write keeps the exact durable reservation and its probation charge; the next tick
may continue it mechanically only while the job identity, lease, resources, runtime, target and role are still
live and no launch-intent event exists. The kernel records launch intent immediately before the host call and
will not infer no effect after that point. A failed-launch settlement additionally requires a durable
task/dispatch observation bound to that exact job attempt and generation, so an older failure receipt cannot
release a newer reservation. Legacy reservations created before the observation protocol may have no bound
launch receipt; a missing worker id or Dispatch is not proof that the worker never began, so retry remains
blocked until the host supplies genuine settlement evidence. Maintenance must not manufacture a pre-effect
receipt or clear the lease to advance the generation.

The goal phase refreshes the provider budget through the host probe before selecting its pools; a quota nobody
can read selects nothing and is recorded as such. Scope entries are normalized to the feature tree and
intersected with the approved scope. A goal records its grounds and a first approval fails closed on a goal
with no definition of done or one nobody was asked to critique; criteria and verdicts are never hand-written
into the record. A plan-ledger goal may only plan the kernel's operation kinds that write code, the runtime or
evidence (`PLAN_OP_KINDS`); the Work gate holds only where a canonical tree is bound (`needsWorkGate`);
external `file:` inputs are staged under the worktree's `.starciwork/_local/inputs/<workflow>/` and a decisive
decision on a plan ledger stays the owner's.

The Claude screen table reads the status line of any turn (glyph, verb, elapsed time, token counter,
`thinking`); only the prompt box says idle; a screen with neither falls through to the silence rule. An
allocation the admission deferred is `deferred`: the slot and the day's count come back and nothing cools.
A refusal is a provider error sentence only. Before a tab its heuristics call idle is nudged or closed, a cheap
model reads the same rendered frame (`classifyScreen`, through the same admission as every model call) and a
`working` answer makes the kernel wait; a worker still settled for `stalled-idle` is a runtime-perception
settlement whose probation attempt is refunded against the exact job its lease named. Goal assessments and
critiques carry a twenty-minute window and the whole quota-ordered pool.

The protected proof is a gate only for a kind that writes code and only when an oracle was sealed for the
operation; otherwise it is recorded as `proof-skipped`. A partial, failed or blocked report settles its attempt
through the typed stopped-worker path before the report is applied (`attempt-settled`), and retry clears a
lease the journal no longer backs on the record (`stale-lease-cleared`). The retry binds a stopped lease
through the candidate identity and takes Orca's worker record - a terminal state and an exited process stage
on the exact worker - as the proof of no live process. A retry refunds, against the exact job of each receipt,
the probation of every unfinished operation's attempts from the generations it retires
(`retired-generation-probation-refunded`). A path a prior attempt owned that is clean now is dropped from
ownership on the record (`owned-baseline-dropped`).

The kernel command sent into an Orca coordinator terminal can die before it acquires startup; the reservation the
supervisor made names the terminal the command went into (`launching-native`), a reservation the ten-minute launch
window has outlived - its reserving process gone, or for a native launch no kernel holding the lock - is reclaimed
by the next round with its reason (`startup-reservation-reclaimed`), and the terminal that launch left behind is
closed. A kernel acquires startup first, before it binds a run or writes state, so a reservation still unacquired
after the window belongs to no running kernel.

Orca re-titles an exited kernel's tab to its shell, so a title sweep never sees a dead kernel tab. The supervisor
records every coordinator terminal it opens beside the store (`coordinator-terminals.json`); a start - no kernel is
alive then - closes every recorded terminal by handle before it opens the new one (`stale-kernel-terminals-closed`),
and a running kernel's sweep closes every recorded terminal but its own. A terminal Orca no longer lists is dropped
from the record; one whose close fails stays for the next pass.

The kernel's own model functions - the manager, the planner, the validator, the screen sense - are not
operation work and no longer draw the workflow's operation probation budget. The first alpha workflow spent that
budget (six per operation) on twenty-five manager decisions, one per decision id, and then had no eligible model
for anything: no manager, so nothing was dispatched; no screen sense (`classifyScreen` was not even a model kind),
so a worker twenty minutes into a turn was settled as idle, its settlement could not be proved and the writer fence
stayed held. Each kernel function still has its bounded per-call scope; the budget again means what it says: how
many native worker attempts a workflow may spend under probation.

Two more fences the first 1.0.0 migration met. A worker whose own tab the kernel had already closed (a blocked
operation's sweep closes it) could never be settled: Orca answered the release with `release_unknown` /
`closed_agent_terminal`, honestly unable to confirm a process it no longer held, and the retry refused the
workflow for good. Orca's worker record is the proof now: a stop in a terminal state, the worker's process stage
`process_exited`, and its tab no longer listed in the worktree settle the attempt to `none` with the record kept
(`exitedWorker`). A tab still listed is closed by exactly that handle first; one that outlives even that (Orca's
pty stop unverifiable) is read: an idle or finished prompt with a dispatch heartbeat older than fifteen minutes is
a finished worker whose tab nobody can kill, settled with the tab recorded as residual. A drawing turn, a question,
a fresh heartbeat or a stage short of exited stays unknown. And a queued job that never
launched - no lease, no receipt of any kind - is cancelled by the retry whatever its generation or kind; before,
only the current generation's model and check jobs were, and nine such operation rows from retired generations
bound a workflow to its old journal and refused the relocation.

The owner reads the tabs in the language of the host's `config.json` (`language`): the kernel's own terminal lines
(`[Kernel] ...`) are spoken in it (`PROGRESS_MESSAGES`), and every operation contract carries a `## Language` section
telling the worker to address the owner in it. Nothing in the files changes: event kinds, operation ids, runtimes,
paths, identifiers, commit messages, check names and report fields stay as the tree spells them, in English, so a
line in any language still matches its record. The kernel's sweep now also seeds the coordinator record from the
supervisor log, so kernel tabs opened before the record existed are closed without a restart, and a quarantine
for a candidate that could not be sealed names the mismatches.

A close Orca answers `ok` for is not a closed tab: a pty it cannot stop keeps the tab listed, and the sweep asked
again every twenty-seven seconds, an Orca call and an event line each time, while the log seed put the handle back
on the record after every drop. The record now keeps the closes it was answered (`closed`), the seed never re-adds
them, a tab still listed after its close is reported once (`terminals-unclosable`) and asked again only after
`UNCLOSABLE_RETRY_MS` (thirty minutes), and one that finally leaves the listing is forgotten.

The owner page (`kernel/inputs-ui.mjs`) is one column read top to bottom in the shadcn idiom - neutral tokens,
1px borders, badges, one primary button per card, light and dark by the system - and its words follow
`config.json`'s language while every record it shows stays as recorded. A decision with options is a choice: option
cards with radios, the recommended one badged, a free answer only behind "another answer" or when no option
exists; credentials stay stacked fields with a reveal toggle. A decision still queued behind the canonical writer
is listed as preparing, with one line and no control, so the owner sees every question the workflow will ask.
`debug: true` in `config.json` adds to the kernel tab how each runtime was allocated to an operation, which
model a kernel function was given (`model-selected`), and on every accepted operation what it did and an outlook
(open operations, an estimate from the durations accepted so far); off by default. The page is built from one
component set (`kernel/inputs-components.mjs`: card, badge, button, input, secret, textarea, radio group, checkbox,
meta, field) with one system type stack and fixed sizes per role; the page owns only its layout.

A migrated record whose first relocation was refused (the former journal still held the stopped attempt's rows)
was treated by every later retry as a current record that "stays where it is", so two workflows never left the
former journal. A retry now brings the journal to this build's default unless the operator named `--journal-file`
- a choice the record remembers (`journalChosen`) - and the former journal is left as soon as a retry finds
nothing live of the workflow in it.

The owner reads the question itself in the configured language: an ask ends its report summary with
`presentation (<lang>): <question> 1. <option> 2. <option>` (the Language section of its contract says so), the
kernel keeps it on the ask as `question.presentation` with the recommendation (`recommended: <n>`), and the page
shows that text and those option labels - the record and the numbered options stay English, one fold away. And a
kernel function's provider filter keeps every eligible pool member: the validator pool had been narrowed to the
one runtime that happened to hold the scope's first probation entry, which was not in that pool, so no validator
was ever eligible again for that operation.

An existing goal written before these repairs is not migrated: run `workflow-goal` again under a new id and
keep the old store as evidence.

## Whole-application stacks

Application deployment work loads the same `application-stacks` knowledge from authoring, architecture,
implementation, runtime, deployment and relevant verification contracts, including their replacing execution
modes. The single manifest describes the complete application in dev Docker Compose and Ubuntu VPS Docker Swarm
environments, its per-environment managed/external/excluded components, encrypted credential custody,
lifecycle commands and verification obligations. Kubernetes remains explicitly deferred.

Existing deployment fragments are inputs to reconciliation, not a second competing deployment authority.
Preserve useful Dockerfiles, encryption and application checks; update affected manifests, runbooks and
consumers together. VPS keeps Swarm as its default; it is not silently converted to Compose. Installing the
runtime does not migrate an app, deploy a VPS, import credentials or change its accepted Work. Apply the
standard only within the selected application's authorized stack scope.

`starci stacks check` is a read-only structural check of an application manifest and caller-supplied rendered
deployment YAML/JSON. It does not invoke Docker or authenticate the model's provenance. Compose file mounts and
versioned external Swarm secrets use distinct validation policies. SOPS envelope recognition is not decryption
or recovery proof. The synthetic `examples/application-stacks/tiny-stateful` kit illustrates lifecycle
behavior; its passing tests cannot certify a real application or an untested Ubuntu host.

## Limits that must remain visible

Native operation liveness belongs to the exact Orca Dispatch. The model-process reconciler never classifies a
native worker from an absent owned child PID, including jobs already marked `effect_unknown`. For a stopped
unreported attempt, the kernel requires typed host settlement bound to its durable job, attempt, generation,
lease and launch receipt. It then freezes the observed file delta while retaining the writer reservation. Only
a sealed in-scope delta may become the next attempt's provenance baseline; unsealable or out-of-scope effects
remain quarantined. Stopping a process never proves its earlier file effects absent and never refunds
input-accepted probation.

A prompt-shaped screen alone cannot close an exact worker whose typed native running observation and heartbeat
are fresh. Stale or mismatched observations still require reconciliation; the operation deadline and deliberate
rate-limit settlement remain in force.

Interactive kernels print bounded transition and wait summaries to stderr, leaving stdout JSON unchanged.
Accepted manager decisions include a short validated decision rationale; this is an explicit decision summary,
not hidden model reasoning. The workflow view distinguishes selected models from model attestation and counts
actual transitions as progress. These observations make stalls visible; they do not constitute product
acceptance or proof of complete unattended delivery.

Kernel startup ownership is acquired before binding an Orca Run or writing workflow state. The supervisor and
kernel share a transactional local SQLite ownership record using DELETE journal mode and FULL synchronization.
The supervisor passes its exact launch token; a competing launch cannot replace the current coordinator. An
unresolved native launch is not expired into permission to launch again while its launch window stands; a
reservation the window has outlived, whose reserving process is gone and whose store no kernel holds, is a dead
launch and is reclaimed with its reason on the record. Stop the old supervisor before installing the accepted
supervisor build, and retain any unknown worker effects. Local kernel launches bind their exact child PID before
acquisition; a late child close cannot release a running kernel's newer ownership.

Detached jobs persist redacted wrapper/executor lifecycle receipts and retry terminal commits without calling
the provider again. Completed results are staged privately with their exact job, attempt, generation, lease
and payload bindings. A terminal-commit failure may replay that same validated result; it does not rerun the
provider or grant a new admission. Missing, mismatched or unwritable staging keeps the effect unknown. An
owner-authorized fresh workflow uses a new identity, preserves the failed run and its reservations, and
revalidates current inputs; deleting a UI row does not clear capacity or certify earlier filesystem effects.

The npm payload explicitly includes the compiled .dist tree. Verification packs the real tarball, installs it
without development dependencies and invokes a compiled command; static launcher help alone cannot prove that
an installed package contains its runtime.

The current Orca native agent API does not attest a filesystem write sandbox. Native writers therefore share a
single writer reservation for a canonical root and are checked for drift. A Docker mount probe validates only
the container primitive, not an Orca worker adapter. Full parallel writers require that adapter and its
adversarial tests. All admitted model functions and other eligible jobs share the global ceiling of 10; the
manager uses one of those slots while it runs.

No capability certificates ship with the package. Scoped local probation is not a certificate and cannot
authorize higher-risk external operations. Credential presence is not provider validity. Missing or
inconclusive required evidence cannot make an operation or the workflow complete.

The owner reads every open question in the language `config.json` names, from the moment the question opens and
not only once its ask reports. A planner-pool presenter renders the question and, when they arrive, its options;
the rendering lives on the ask as `question.presentation` and the record itself keeps its English words. An ask
that reports its own presentation keeps it. A presenter that cannot answer is noted on the ask and asked again
half an hour later, never turned into a kernel error, and an English page asks no presenter at all.

One canonical writer serves a worktree. While an operation that writes is running, a ready operation that also
writes cannot be admitted, so it waits out of the manager's action list instead of buying a decision that
admission defers a tick later. The kernel names the waiting operations once, when the set changes, not on every
round.

An ask that has already written its decision record holds everything the owner needs: the record and its numbered
options. Whatever else that operation is still blocked on, a tree layout only another operation may repair or a
spent retry budget, the question goes onto the owner page with its choices and the operation stops being
dispatched. Repeating an attempt that can only earn the same refusal produces no better question, and a decision
with options never reaches the owner as an empty text box. The blocker stays on the owner's list in its own right.

The allocation algorithm stays as authored: each role has a preference order, a ready operation takes the first
preferred runtime with a free slot and no cooldown, and a saturated or exhausted one overflows to the next. What
the owner may now set is the order of providers for a run. `providers` in config.json names them, best first, and
every role preference, every tier and the non-operation model pools are sorted so runtimes of an earlier-named
provider come first. Providers the owner does not name keep their authored order behind the named ones. Nothing is
removed and no window is ignored: a preferred provider that is out of window, cooling or saturated overflows
exactly as before, so naming a provider can never stall a workflow. A workflow reads the list from the config it
is pinned to, so the choice travels with the sealed runtime rather than with whatever the host file says today.

The same rule is read once per tick, not only when an operation reports. An ask that went quiet in an earlier
generation still holds its record and its numbered options in the report it already wrote, and no further attempt
of it will ever be made, so the kernel puts that question on the owner page from what is on the ask rather than
leaving an answered-looking empty box behind a blocker nobody will clear.
