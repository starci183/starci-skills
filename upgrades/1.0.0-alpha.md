# Upgrading to StarCi v1-alpha

This version changes the execution protocol for explicitly enrolled workflows. It is not an npm publication
or proof of a complete live product delivery. Read [the execution contract](../docs/runtime-v6.md).

## Prerequisites and version identity

Use Node.js 22.13.0 or newer; the runtime uses the built-in `node:sqlite` API without an experimental CLI flag.
The local operational journal defaults to SQLite DELETE journal mode and FULL synchronization. WAL is
explicit only, with SQLite 3.51.3 or newer; older bundled SQLite releases may contain the WAL reset defect.
The journal is local to this machine, shared by enrolled workflows, and is not placed on a network share.

Historical tags, including `v6.1.1`, describe earlier package history. They are preserved. StarCi v1-alpha
uses package version `1.0.0-alpha` while retaining internal compatibility identity `engine.major = 6`; neither
identity is inferred from tag order.
Do not silently downgrade an installation from a historically higher package version. Select this build
deliberately. Do not publish or retag it as an automatic registry upgrade.

The install manifest carries `installProtocol: {schema: starci/install-protocol@1, major: 6}` independently
of public package semver. Installer receipts created before this marker infer their historical protocol from
their package major only for compatibility. A malformed current marker is refused instead of guessed, and
installer writes refuse a protocol newer than this build supports. Doctor remains read-only; it uses the
marker to detect an incomplete current installation without rewriting or downgrading it.

Agent-led coordination is also explicit. Only a retry that records `engine.coordination: agent-v1` enables
the manager decision function. It receives a bounded digest-bound snapshot and may order only executable
action IDs supplied by the kernel. The kernel remains the sole state writer, rechecks preconditions, and
keeps owner choices, authority, evidence acceptance and product meaning outside the manager.
Its host-local pool is `models.nonOperation.kernelManager: opus-sol` in `config.json`. The other canonical
non-operation roles are `planner: fable-astra` and `validator: fable-astra`; their functions retain separate
typed inputs and contexts. Admission chooses an eligible, qualified pool member using known quota and capacity
before calling it. This config never overrides operation-agent selection or bypasses admission.

## Build, test, pin, retry

1. Build and test a private copy of the complete source. Never publish an intermediate `.dist` to a running
   workflow. Run the complete test suite, relocated CLI checks, provider validation, build reproducibility,
   and both documentation sites before accepting the build.
2. Seal the accepted `.dist`, launcher and operation template with `kernel/runtime-pin.mjs`'s build helper.
   This is maintenance tooling; agents still use only `bin/starci.mjs`. Keep the returned pin record locally.
3. Pause the approved workflow using `node <runtime>/bin/starci.mjs workflow-stop --id <id>` and wait for its
   kernel to exit. A pause does not prove its native operation workers stopped.
4. Run `node <runtime>/bin/starci.mjs workflow-retry --id <id> --engine 6 --runtime-pin <pin-record.json>`
   with the same host, worktree and ledger binding. This command settles live dispatches, refuses unknown
   effects, preserves the approved goal and accepted Work, increments the execution generation and gives
   unfinished active operations fresh contexts. It does not delete product branches or edit accepted specs.
   The pin and journal must be visible to both the supervising process and the execution host. When their
   user-local storage namespaces differ, place the pin in a shared local runtime directory and pass
   `--journal-file <shared-local-journal.sqlite>`. All enrolled workflows on that machine must use the same
   journal to share the global capacity limit. Relocation requires all former-generation jobs settled.
5. The supervisor verifies the pin before starting the next kernel. A changed/missing pin fails closed.
   Observe operation, owner-input, job and acceptance events. A resumed workflow trial is distinct from a
   fresh end-to-end trial with a clean scenario and held-out assertions.

Retain the previous runtime pin, Git history and workflow evidence. A rollback must first settle all v6 jobs
and dispatches; never point a live v6 journal at an older engine or delete its leases to recover capacity.
The upgrade does not move `.starciwork`, custody, Orca worktrees or source repository ownership.

The first live retry exposed an already-closed-terminal case. Settlement now uses the worker's actual
stop/release receipts even when closing its terminal again fails; unknown worker effects still block retry.
For enrolled workflows, the owner-input helper launches from the same sealed pin as the kernel while
retaining the original host binding for project routing and local language configuration.

An Orca kernel must execute inside its own live coordinator terminal. A detached process carrying an old
terminal handle is not an attested coordinator. The supervisor prepares the native terminal and the kernel
proves its Run binding before launching operations. A failed binding is an infrastructure condition, not
evidence that the chosen model failed its task. Retry must account for every prior native reservation,
including a blocked operation with no recorded dispatch; unknown effects cannot be skipped by advancing
the generation.

Review counters and findings belong to their execution epoch. Retry preserves accepted Work and actual
owner answers, and requires fresh review of unfinished groups. Unlaunched, unanswered questions derived
solely from a retired review epoch can be superseded with an audit record. Qualification refusals identify
missing evaluation evidence and unmet probation prerequisites; runtime maintenance does not manufacture
certificates or lower required machine checks to obtain a launch.

Failed native launches retain their Task, Dispatch and settlement receipts. A retry can recover a missing
Dispatch reference only by matching the exact Task and Run and verifying the exited worker's released
terminal resource. Worker termination settles reservations; it does not erase possible filesystem effects
or prove that the model never ran. Probation is refunded only for an independently recorded pre-task
rejection that proves execution and input never began. Late prompt consumption remains a spent attempt.

The live Orca trial also exposed a startup race: the host can revoke a Codex dispatch before the native CLI
finishes starting, then the CLI consumes the input after revocation. Such a worker cannot be accepted.
Attaching a prestarted terminal is not a substitute unless the host also attests its effective model identity.

The resumed trial exposed incomplete Work-writer gate preparation and contradictory review instructions.
The kernel now prepares an actual canonical Work gate before admitting a declared Work writer. Independent
acceptance still validates the resulting candidate; absent or contradictory validator output and pathless
validation failures remain blocking. A reviewer reports `partial` with findings, and `done` only after all
required checks pass with no findings. Retained failed worker prose is explicitly diagnostic when its
structured findings were lost; it is not an accepted verification receipt.

The owner page shows preparation progress while workflow-owned prerequisites remain pending. This does not
open credential inputs early or certify the provider. Authenticated owner decisions remain available during
preparation. Deploy these corrections through the same private build, seal, settlement and fresh-context
retry boundary above; an existing owner decision is never answered by the migration.

The former polling renderer rebuilt owner controls on every refresh, while the authenticated submit path
already bound actions to request revision and options digest. The single owner renderer now reconciles both
consumers: polling retains draft text and focus for the same request identity, revision, options digest and
status, and a changed binding invalidates that draft. `preparing` and `answered` rows cannot be entered, and
polling itself never submits an answer. Server-side request validation and owner authority remain unchanged.

Durable recovery must retain the current validated invocation's coordinator and host lifecycle binding.
A checkpoint restores workflow progress, not the identity of a terminal that no longer exists. Previously,
restoring the old coordinator after rebinding a new native kernel caused stale-terminal cleanup to close the
kernel's own current terminal. The recovery regression keeps the current kernel alive while retiring the
old terminal. Preserve pending worker reports and settle their dispatches through the retry boundary.

Operation admission now records an `intent-v1` reservation before any native launch. If Windows temporarily
denies the atomic state-snapshot rename, the store retries the rename for at most 775 ms without deleting the
old snapshot. An exhausted write keeps the exact durable reservation and its probation charge; the next tick
may continue it mechanically only while the job identity, lease, resources, runtime, target and role are still
live and no launch-intent event exists. The kernel records launch intent immediately before the host call and
will not infer no effect after that point. A failed-launch settlement additionally requires a durable
task/dispatch observation bound to that exact job attempt and generation, so an older failure receipt cannot
release a newer reservation.

Legacy reservations created before the observation protocol may have no bound launch receipt. A missing
worker id or Dispatch is not proof that the worker never began, so retry remains blocked until the host
supplies genuine settlement evidence. Maintenance must not manufacture a pre-effect receipt or clear the
lease to advance the generation.

## Limits that must remain visible

The current Orca native agent API does not attest a filesystem write sandbox. Native writers therefore share
a single writer reservation for a canonical root and are checked for drift. A Docker mount probe validates
only the container primitive, not an Orca worker adapter. Full parallel writers require that adapter and its
adversarial tests. All admitted model functions and other eligible jobs still share the global ceiling of 10. The manager uses
one of those slots while it runs; it does not add an eleventh model execution.

No capability certificates ship with the package. Scoped local probation is not a certificate and cannot
authorize higher-risk external operations. Credential presence is not provider validity. Missing or
inconclusive required evidence cannot make an operation or the workflow complete.
