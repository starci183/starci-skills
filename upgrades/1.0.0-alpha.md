# Upgrading to StarCi v1-alpha

This version changes the execution protocol for explicitly enrolled workflows. It is not an npm publication
or proof of a complete live product delivery. Read [the execution contract](../docs/runtime-v6.md).

## Prerequisites and version identity

Use Node.js 22.13.0 or newer; the runtime uses the built-in `node:sqlite` API without an experimental CLI flag.
The local operational journal defaults to SQLite DELETE journal mode and FULL synchronization. WAL is
explicit only, with SQLite 3.51.3 or newer; older bundled SQLite releases may contain the WAL reset defect.
The journal is local to this machine, shared by enrolled workflows, and is not placed on a network share.

Historical tags, including `v6.1.1`, describe earlier package history. They are preserved. StarCi v1-alpha
uses package version `1.0.0-alpha` while retaining internal compatibility identity `engine.major = 6`; neither
identity is inferred from tag order.
Do not silently downgrade an installation from a historically higher package version. Select this build
deliberately. Do not publish or retag it as an automatic registry upgrade.

The install manifest carries `installProtocol: {schema: starci/install-protocol@1, major: 6}` independently
of public package semver. Installer receipts created before this marker infer their historical protocol from
their package major only for compatibility. A malformed current marker is refused instead of guessed, and
installer writes refuse a protocol newer than this build supports. Doctor remains read-only; it uses the
marker to detect an incomplete current installation without rewriting or downgrading it.

Agent-led coordination is also explicit. Only a retry that records `engine.coordination: agent-v1` enables
the manager decision function. It receives a bounded digest-bound snapshot and may order only executable
action IDs supplied by the kernel. The kernel remains the sole state writer, rechecks preconditions, and
keeps owner choices, authority, evidence acceptance and product meaning outside the manager.
Its host-local pool is `models.nonOperation.kernelManager: opus-sol` in `config.json`. The other canonical
non-operation roles are `planner: fable-astra` and `validator: fable-astra`; their functions retain separate
typed inputs and contexts. Admission chooses an eligible, qualified pool member using known quota and capacity
before calling it. This config never overrides operation-agent selection or bypasses admission.

## Build, test, pin, retry

1. Build and test a private copy of the complete source. Never publish an intermediate `.dist` to a running
   workflow. Run the complete test suite, relocated CLI checks, provider validation, build reproducibility,
   and both documentation sites before accepting the build.
2. Seal the accepted `.dist`, launcher and operation template with `kernel/runtime-pin.mjs`'s build helper.
   This is maintenance tooling; agents still use only `bin/starci.mjs`. Keep the returned pin record locally.
3. Pause the approved workflow using `node <runtime>/bin/starci.mjs workflow-stop --id <id>` and wait for its
   kernel to exit. A pause does not prove its native operation workers stopped.
4. Run `node <runtime>/bin/starci.mjs workflow-retry --id <id> --engine 6 --runtime-pin <pin-record.json>`
   with the same host, worktree and ledger binding. This command settles live dispatches, refuses unknown
   effects, preserves the approved goal and accepted Work, increments the execution generation and gives
   unfinished active operations fresh contexts. It does not delete product branches or edit accepted specs.
   The pin and journal must be visible to both the supervising process and the execution host. When their
   user-local storage namespaces differ, place the pin in a shared local runtime directory and pass
   `--journal-file <shared-local-journal.sqlite>`. All enrolled workflows on that machine must use the same
   journal to share the global capacity limit. Relocation requires all former-generation jobs settled.
5. The supervisor verifies the pin before starting the next kernel. A changed/missing pin fails closed.
   Observe operation, owner-input, job and acceptance events. A resumed workflow trial is distinct from a
   fresh end-to-end trial with a clean scenario and held-out assertions.

Retain the previous runtime pin, Git history and workflow evidence. A rollback must first settle all v6 jobs
and dispatches; never point a live v6 journal at an older engine or delete its leases to recover capacity.
The upgrade does not move `.starciwork`, custody, Orca worktrees or source repository ownership.

The first live retry exposed an already-closed-terminal case. Settlement now uses the worker's actual
stop/release receipts even when closing its terminal again fails; unknown worker effects still block retry.
For enrolled workflows, the owner-input helper launches from the same sealed pin as the kernel while
retaining the original host binding for project routing and local language configuration.

An Orca kernel must execute inside its own live coordinator terminal. A detached process carrying an old
terminal handle is not an attested coordinator. The supervisor prepares the native terminal and the kernel
proves its Run binding before launching operations. A failed binding is an infrastructure condition, not
evidence that the chosen model failed its task. Retry must account for every prior native reservation,
including a blocked operation with no recorded dispatch; unknown effects cannot be skipped by advancing
the generation.

Review counters and findings belong to their execution epoch. Retry preserves accepted Work and actual
owner answers, and requires fresh review of unfinished groups. Unlaunched, unanswered questions derived
solely from a retired review epoch can be superseded with an audit record. Qualification refusals identify
missing evaluation evidence and unmet probation prerequisites; runtime maintenance does not manufacture
certificates or lower required machine checks to obtain a launch.

Failed native launches retain their Task, Dispatch and settlement receipts. A retry can recover a missing
Dispatch reference only by matching the exact Task and Run and verifying the exited worker's released
terminal resource. Worker termination settles reservations; it does not erase possible filesystem effects
or prove that the model never ran. Probation is refunded only for an independently recorded pre-task
rejection that proves execution and input never began. Late prompt consumption remains a spent attempt.

The live Orca trial also exposed a startup race: the host can revoke a Codex dispatch before the native CLI
finishes starting, then the CLI consumes the input after revocation. Such a worker cannot be accepted.
Attaching a prestarted terminal is not a substitute unless the host also attests its effective model identity.

The resumed trial exposed incomplete Work-writer gate preparation and contradictory review instructions.
The kernel now prepares an actual canonical Work gate before admitting a declared Work writer. Independent
acceptance still validates the resulting candidate; absent or contradictory validator output and pathless
validation failures remain blocking. A reviewer reports `partial` with findings, and `done` only after all
required checks pass with no findings. Retained failed worker prose is explicitly diagnostic when its
structured findings were lost; it is not an accepted verification receipt.

The owner page shows preparation progress while workflow-owned prerequisites remain pending. This does not
open credential inputs early or certify the provider. Authenticated owner decisions remain available during
preparation. Deploy these corrections through the same private build, seal, settlement and fresh-context
retry boundary above; an existing owner decision is never answered by the migration.

The former polling renderer rebuilt owner controls on every refresh, while the authenticated submit path
already bound actions to request revision and options digest. The single owner renderer now reconciles both
consumers: polling retains draft text and focus for the same request identity, revision, options digest and
status, and a changed binding invalidates that draft. `preparing` and `answered` rows cannot be entered, and
polling itself never submits an answer. Server-side request validation and owner authority remain unchanged.

Durable recovery must retain the current validated invocation's coordinator and host lifecycle binding.
A checkpoint restores workflow progress, not the identity of a terminal that no longer exists. Previously,
restoring the old coordinator after rebinding a new native kernel caused stale-terminal cleanup to close the
kernel's own current terminal. The recovery regression keeps the current kernel alive while retiring the
old terminal. Preserve pending worker reports and settle their dispatches through the retry boundary.

Operation admission now records an `intent-v1` reservation before any native launch. If Windows temporarily
denies the atomic state-snapshot rename, the store retries the rename for at most 775 ms without deleting the
old snapshot. An exhausted write keeps the exact durable reservation and its probation charge; the next tick
may continue it mechanically only while the job identity, lease, resources, runtime, target and role are still
live and no launch-intent event exists. The kernel records launch intent immediately before the host call and
will not infer no effect after that point. A failed-launch settlement additionally requires a durable
task/dispatch observation bound to that exact job attempt and generation, so an older failure receipt cannot
release a newer reservation.

Legacy reservations created before the observation protocol may have no bound launch receipt. A missing
worker id or Dispatch is not proof that the worker never began, so retry remains blocked until the host
supplies genuine settlement evidence. Maintenance must not manufacture a pre-effect receipt or clear the
lease to advance the generation.

## First live trial of the goal phase

The first fresh trial on this build started three workflows with `workflow-goal` while the last written
`runtime-budget.json` was hours old. The quota-aware selector rightly refused the stale file, but the goal phase
then went on with an empty planner and validator pool: no model was called, the assessment "failed" with zero
attempts, the critique was "unavailable" because no critic was given, and two goals were still written as
`ok:true` with an empty definition of done. A scope spelled `features/<f>/<layer>` also produced an intake over
`features/features/<f>/<layer>`, and a `--reintake <f>` beside a two-layer scope produced an intake holding the
whole feature. Three repairs, deployed through the same private build, seal and fresh-goal boundary:

- the goal phase refreshes the provider budget through the host probe before selecting its pools; a quota
  nobody can read selects nothing and is recorded as such, never replaced by stale numbers or a forced provider;
- scope entries are normalized to the feature tree and intersected with the approved scope, so an intake owns
  exactly the approved layers, never the module record of a layer-restricted feature, and a reintake outside
  the scope is refused;
- a goal records its grounds (what assessed it, whether a critic was asked) and a first approval fails closed on
  a goal with no definition of done or one nobody was asked to critique. The repair is to run `workflow-goal`
  again with a readable quota; criteria and verdicts are never hand-written into the record;
- a plan-ledger goal may only plan the kernel's operation kinds: the second trial's stacks plan was assessed with
  `inventory`, `effect` and `integrate` ops, every runtime rejected them ("Unknown skill/operator route") and the
  workflow cooled and stalled without one launch. The goal form now carries the closed kind list with what each
  kind is for, and the phase refuses any other kind before writing the page;
- a Claude Code worker seven minutes into a turn was read as `stalled-idle`, nudged with a "Continue" line typed
  into its input, and settled and closed with a partial effect on disk. The Claude screen table knew one busy
  signature (`esc to interrupt`) and treated the footer `bypass permissions on` - present on every Claude screen
  - as idle. The table now reads the status line of any turn (glyph, verb, elapsed time, token counter,
  `thinking`), only the prompt box says idle, and the kernel's tab classifier knows Claude's spinner glyphs. A
  screen with neither falls through to the silence rule: slower than a wrong idle, never a closed turn;
- an allocation the admission deferred (the canonical writer was busy) was released as a finished run: the slot
  came back, the day's count did not, and three deferrals per tick inflated it without one launch. The allocator
  now has `deferred`, which refunds the slot and the count and cools nothing;
- on a plan ledger, a `file:` input named by an absolute path outside the worktree became an op reference no
  candidate could resolve, the critique's decisive decisions became `decision.prepare` ops the Work gate refused
  (a plan ledger binds no canonical Work), and the model wrote absolute allowlists. The goal phase now stages such
  inputs under the worktree's `.starciwork/_local/inputs/<workflow>/` and refers to the copy (`inputs-staged`),
  a decisive decision on a plan ledger stays the owner's under Questions (`decision-unplanned`), and the plan
  form refuses any allowlist or reference that is not worktree-relative;
- the same plan then carried `decision.prepare` and `implementation.plan` ops, and its `runtime.operate` and
  `integration.verify` ops would have met the canonical Work gate for writing "runtime" and "evidence" records into a
  tree a plan ledger does not have. The plan form now allows only the kinds that write code, the runtime or
  evidence (`PLAN_OP_KINDS`), and the Work gate holds only where a canonical tree is bound (`needsWorkGate`);
- the rate-limit detector matched the words `quota` and `billing` anywhere on a screen - in the contract of a
  commerce feature and the agent's prose about it - so a working worker was settled as refused, its runtime cooled
  for twenty minutes and the cooldown shared to every other kernel. A refusal is now a provider error sentence
  only: a status code, "rate limit reached", "exceeded your quota", "credit balance is too low", an `_error` type;
- the kernel gained a sense. Before a tab its heuristics call idle is nudged or closed, a cheap model reads the same
  rendered frame (`classifyScreen`, the easy tier's verify-capable runtimes, through the same admission as every
  model call) and a `working` answer makes the kernel wait (`perception`); any other answer changes nothing. A
  worker still settled for `stalled-idle` is a runtime-perception settlement (`runtime-incident`): its probation
  attempt is refunded against the exact job its lease named, and its runtime is not avoided. A silent, dead or
  refused worker is still the model's own attempt;
- a plan-ledger goal assessment of a long job died at the headless call's ten-minute default ("exited null") and
  the goal phase had handed the call one provider, so the goal ended. Goal assessments and critiques carry a
  twenty-minute window, a killed process is named a timeout, and the goal phase hands the whole quota-ordered pool
  to the call so a peer whose process died is followed by the next one;
- the protected proof (a spec the operation added must fail on the code it started from) was planned for every v6
  operation, and the first intake that reported `done` was refused as "no protected oracle covers work.author". The
  proof is a gate only for a kind that writes code and only when an oracle was sealed for the operation; otherwise
  it is recorded as `proof-skipped` and the re-run checks, the Work validator and the independent validator carry
  the acceptance.

An existing goal written before these repairs is not migrated: run `workflow-goal` again under a new id and
keep the old store as evidence.

## Whole-application stacks

Application deployment work now loads the same `application-stacks` knowledge from
authoring, architecture, implementation, runtime, deployment and relevant verification
contracts, including their replacing execution modes. The single manifest describes
the complete application in dev Docker Compose and Ubuntu VPS Docker Swarm environments, its per-environment
managed/external/excluded components, encrypted credential custody, lifecycle commands
and verification obligations. Kubernetes remains explicitly deferred.

Existing deployment fragments are inputs to reconciliation, not a second competing
deployment authority. Preserve useful Dockerfiles, encryption and application checks;
update affected manifests, runbooks and consumers together. Nivo's existing Swarm and
Compose layouts supplied read-only evidence for this standard. VPS keeps Swarm as its
default; it is not silently converted to Compose. Installing the runtime
does not migrate an app, deploy a VPS, import credentials or change its accepted Work.
Apply the standard only within the selected application's authorized stack scope.

`starci stacks check` is a read-only structural check of an application manifest and
caller-supplied rendered deployment YAML/JSON. It does not invoke Docker or authenticate
the model's provenance. Compose file mounts and versioned external Swarm secrets use
distinct validation policies. SOPS envelope recognition is not decryption or recovery proof.
The synthetic `examples/application-stacks/tiny-stateful` kit illustrates lifecycle
behavior; its passing tests cannot certify a real application or an untested Ubuntu
host. Acceptance still requires actual application, credential, persistence, update
and recovery evidence for the selected environment.

## Limits that must remain visible

Native operation liveness belongs to the exact Orca Dispatch. The model-process reconciler no longer
classifies a native worker from an absent owned child PID, including jobs already marked `effect_unknown`.
For a stopped unreported attempt, the kernel requires typed host settlement bound to its durable job,
attempt, generation, lease and launch receipt. It then freezes the observed file delta while retaining the
writer reservation. Only a sealed in-scope delta may become the next attempt's provenance baseline;
unsealable or out-of-scope effects remain quarantined. Stopping a process never proves its earlier file
effects absent and never refunds input-accepted probation.

A prompt-shaped screen alone cannot close an exact worker whose typed native running observation and
heartbeat are fresh. Stale or mismatched observations still require reconciliation; the operation deadline
and deliberate rate-limit settlement remain in force. Apply this repair through the same accepted-build
retry boundary, preserving historical incident evidence rather than clearing the old lease manually.

Interactive kernels now print bounded transition and wait summaries to stderr, leaving stdout JSON
unchanged. Accepted manager decisions include a short validated decision rationale; this is an explicit
decision summary, not hidden model reasoning. The workflow view distinguishes selected models from model
attestation and counts actual transitions as progress, not repeated admission waits. These observations
make stalls visible; they do not constitute product acceptance or proof of complete unattended delivery.

Kernel startup ownership is acquired before binding an Orca Run or writing workflow state. The supervisor
and kernel share a transactional local SQLite ownership record using DELETE journal mode and FULL
synchronization. The supervisor passes its exact launch token; a competing launch cannot replace the
current coordinator. An unresolved native launch is not expired into permission to launch again. Stop the
old supervisor before installing the accepted supervisor build, and retain any unknown worker effects.

Local kernel launches bind their exact child PID before acquisition. The synchronous supervisor loop
can reclaim a confirmed-dead local child without depending on a delayed JavaScript close callback;
an unresolved native terminal launch retains its reservation until host reconciliation proves cleanup.
A late child close cannot release a running kernel's newer ownership.

Detached jobs persist redacted wrapper/executor lifecycle receipts and retry terminal commits without
calling the provider again. Completed results are staged privately with their exact job, attempt,
generation, lease and payload bindings. A terminal-commit failure may replay that same validated result;
it does not rerun the provider or grant a new admission. Missing, mismatched or unwritable staging keeps
the effect unknown. A duplicate wrapper cannot reopen a terminal job. Missing historical process receipts
are not created retrospectively by this upgrade. An
owner-authorized fresh workflow uses a new identity, preserves the failed run and its reservations, and
revalidates current inputs; deleting a UI row does not clear capacity or certify earlier filesystem effects.

The npm payload explicitly includes the compiled .dist tree. Verification packs the real tarball, installs
it without development dependencies and invokes a compiled command; static launcher help alone cannot
prove that an installed package contains its runtime.

The current Orca native agent API does not attest a filesystem write sandbox. Native writers therefore share
a single writer reservation for a canonical root and are checked for drift. A Docker mount probe validates
only the container primitive, not an Orca worker adapter. Full parallel writers require that adapter and its
adversarial tests. All admitted model functions and other eligible jobs still share the global ceiling of 10. The manager uses
one of those slots while it runs; it does not add an eleventh model execution.

No capability certificates ship with the package. Scoped local probation is not a certificate and cannot
authorize higher-risk external operations. Credential presence is not provider validity. Missing or
inconclusive required evidence cannot make an operation or the workflow complete.
