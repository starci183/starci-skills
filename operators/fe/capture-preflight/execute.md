# Execute `fe/capture-preflight`

Validate capture mechanics before AI review. Bind and apply
`knowledge/runtime-capture-readiness.md`. Freeze the exact matrix fingerprint and owner-partition
fingerprint. First prove the runtime origin and exact routed worktree, a contained dependency graph
that passes the required build/load path, the separately recorded repository-reproducibility status,
and viewport controls whose requested dimensions equal observed content dimensions.
Then check real data, skeleton/loading/steady identity, state content, control effects, page and bounded
scroll restoration, zoom restoration, probe completeness, raster uniqueness, and the unmodified host
handoff surface. Reject duplicate responsive rasters even when an automation tool reports a successful
viewport change.

Every `reuse` partition must carry dependency proof that the latest mutation cannot affect it. Every
shared sentinel is recaptured. Do not infer visual quality and do not call a reviewer. Do not create an
escaping `node_modules` symlink/junction or mutate product manifests/lockfiles to heal the harness. A
Repository lock drift blocks clean-install/release proof but does not alone block capture when the
contained runtime passes production build and exact target load. A product implementation defect may
route to source repair, missing backend data may route to backend
authority, and a broken runtime/worktree/capture harness blocks with exact evidence. Round purposes are
fixed: 1 discovery, 2 verification, 3 regression.

When live records are missing, emit `backend-required` first with a typed
`starci-backend-process` handoff in `prove` mode. Backend mutation being frozen does not forbid this
read-only capability/data proof. Resume the same FE mission only after consuming its canonical RETURN.
If that RETURN proves the backend capability exists but routed live data is still unavailable, a
frontend-only `new` or `reconstruct` calibration may accept `dataEvidence.mode=contract-fixture` with a
content-addressed, contract-derived, non-product fixture, the retained `backendGapRef`, and the exact
consumed `backendProofReceiptRef`. A fixture without that receipt is a routing defect, not ready data.
This makes visual capture ready, not backend ready. Never use it for live integration or completion
proof, and never let later visual or circuit-breaker findings erase the retained backend obligation.

If the active capture tool exposes no effective zoom capability, do not misclassify that tool-model
limit as a product defect. After one bounded native attempt and one fresh-context confirmation,
preserve both failure receipts and mark only `zoom-restored` as `not-applicable` with an exact
`capability://zoom/...` evidence reference. Keep all three zoom lifecycle cells in the frozen matrix
as `tool-capability-unavailable` with no raster. Every other readiness check and applicable probe
remains mandatory. This exception proves neither zoom behavior nor restoration; it only permits the
remaining latest-source pixels to reach blind review.
