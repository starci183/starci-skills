Use case: ui-mockup
Asset type: proposed visual direction for the Todo web product; representative invite / invalid-email refused state with existing collaborators; desktop-1280
Primary request: Render a polished collaborator-management page after the owner entered an invalid invite email, while the existing collaborator list remains unchanged. This is a proposed design direction, not a screenshot and not proof of a running product.

Scene/backdrop: Light neutral application canvas, centred product PageContainer, no browser chrome, device frame, sidebar, illustration, logo, mascot, or decorative art. One page header leads into two regions: an invite SurfaceCard and a separate collaborator collection below it.

Brand: Inter, white (#FFFFFF) surfaces, #2F6BFF reserved for the single primary invite action and focus accents, dark readable text, quiet neutral separators. No low-contrast copy on primary and no unapproved saturated hues.

Grammar anatomy: Follow installed @starci/grammar 0.4.13 Common family on HeroUI v3 using the README, public declarations, renderer JavaScript, and Common CSS. Use PageContainer, SectionHeader/Heading, SurfaceCard(label Invite collaborator), Input(id invite-email, kind email, isError, errorMessage), an application-owned native radio group labelled “Role” with exactly the peer choices “Viewer” and “Editor”, Button(type submit, variant primary), then SurfaceListCard(label Collaborators, fact 2). Each application-owned collaborator row contains email Text, role Text, a Badge for live status, and a labelled Button(variant outline) for “Revoke”. The collection is a section/container, never a second generic card and never one card per collaborator.

Composition and hierarchy: Surface class is console. “Share this task” is the page focal point. The invite form is the primary decision region; the invalid-email correction stays on the Email Input per FEEDBACK-1. Existing collaborators remain visible as a stable second region. Exactly one filled accent action: “Send invite”. Row revoke actions are visibly weaker and do not use the primary colour as destructive authority. Align region edges and keep region gap greater than internal form and row gaps.

Responsive intent: At mobile-390 keep header, invite form, then collaborator list in the same reading and focus order. Stack email, role choices, and Send invite; let long email addresses break safely and row actions wrap without clipping.

Avoid: no existing frontend implementation as a source, no extra roles, no permissions beyond Viewer and Editor, no avatar photos, no card per collaborator, no nested cards, no icon-only controls, no custom red destructive button, no coloured custom alert banner, no gradients, no glassmorphism, no excessive shadows, no watermark, no extra copy, no misspelled text.
