# StarCi 4.1 — supervision protocol plan

> Superseded by [v5-plan.md](v5-plan.md): the supervisor layers described here are replaced by the workflow kernel. Kept for the failure analysis that motivated 5.0.

Status: landed 2026-09-12 (`report`, `wait`, `notify`, `start-coordinator`, staged-prompt recovery, typed report schemas, supervision templates); R14 restarted on it the same day. Supersedes the supervision clauses of `v4-plan.md`; the Orca call
contract, chain walking and Qwen command-terminal launch from 4.0 stay as they are.

## Why 4.1

R14 ran for a day on 4.0 and every stall traced to the same three gaps, none of them in the operation work itself:

1. **Downward messages are lost.** Orca fences a terminal to the one Run it consumes. A Monitor bound to its nested
   Run never reads parent-Run mail (`consumer_fenced`), so every Coordinator decision, reply and contract change
   silently missed all four Monitors. Typed input into the Monitor's terminal is the only channel that worked.
2. **Nobody owns the wait.** `check --wait` timeouts were treated as "nothing happened"; an operation parked on a
   prompt, a dead pty or a lost delivery looked identical to "still working". Monitors ended turns before the
   workflow goal; the Coordinator sent `worker_done` while four workflows were live and lost its send capability.
3. **Outcomes are prose.** Operation reports were free text, so a Monitor could not tell `done` from `partial`,
   an unanswered `ask` from a failure, or a check that was run from a check that was claimed.

## Roles (one verb each)

- **Helper session** (human-side Claude): reads logs, transcripts and screens; compares runtime behavior with the
  contracts; changes `.claude`. Never creates Tasks, Dispatches or terminals; never injects operations. It reaches
  the Coordinator only through `notify` with a pointer to a runtime-change note.
- **`[Monitor] <Plan>`** inside the `[Coordinator] <Plan>` worktree: manages **workflows** — starts, replaces and
  closes workflow Monitors, receives workflow-level `failed | ask | blocked`, repairs by re-spec or re-dispatch,
  integrates branches, runs the plan gates. Never performs operation work. Never sends `worker_done` before the
  integration gate passes.
- **`[Monitor] <Workflow>`** inside `[Workflow] <X>`: manages **operations** — starts, retries, replaces and settles
  `[Op]` agents along the operation DAG until the workflow goal (`review.verify` passed, branch committed). Never
  writes product code.
- **`[Op] <operation> - <scope>`**: executes one contract and reports **exactly one** typed outcome.

## Typed outcome (`starci/op-report@1`)

Every operation ends with one report, written as a file and signalled once:

```
outcome: done | partial | failed | ask | blocked
files:   [paths inside the allowlist]
checks:  [{name, command, exitCode, evidence}]     # only checks that were actually run
open:    [items the next operation must pick up]  # required for partial
question:{text, options?}                         # required for ask
blocker: {kind: shared-change | sds-gap | environment | authority, detail}   # required for blocked
```

Mapping to Orca signals: `done|partial → worker_done`, `failed → worker_failed`, `ask → question`,
`blocked → escalation`. The file is the source of truth; the mailbox is only the wake-up. A Monitor validates the
report against the schema before accepting it (`checks` non-empty for `done`, files inside the allowlist, outcome
consistent with the signal). Workflow Monitors report to the Coordinator with the same envelope
(`starci/workflow-report@1`: same outcomes, plus `branch`, `head`, `gates`).

The launcher gains `report` so no agent hand-writes the envelope:
`orca-supervised-launch.mjs report --outcome <o> --task <t> --dispatch <d> [--files ..] [--checks-file ..] [--question ..] [--blocker ..]`
— writes `.starciwork/_local/runtime/<run>/reports/<dispatch>.json`, sends the matching Orca message, verifies
`ok:true`, and refuses to send twice.

## Channel (file + signal, never mailbox-only)

- **Downward** (Coordinator → Monitor, Monitor → Op): write the message file under the recipient's runtime directory,
  then `orca-supervised-launch.mjs notify --terminal <recipient> --file <message>`. `notify` types a pointer into the
  recipient's agent terminal and proves delivery from the screen (`queued | staged | submitted`), because a busy agent
  queues input and Orca answers `agent_prompt_stalled` for a message that is in fact staged. Landed in 4.0.1.
- **Upward** (Op → Monitor, Monitor → Coordinator): `report` (file + `send`). The receiver never depends on the
  delivery alone: every wait tick also scans the reports directory, so a lost delivery cannot stall a workflow.
- **Ack**: the receiver acknowledges by `--ack` on the next `check`; the sender re-`notify`s a downward message that is
  not reflected in the recipient's next heartbeat within 10 minutes.

## The wait is owned (`wait` command)

Monitors and the Coordinator stop improvising loops. One launcher command owns the wait and returns typed events:

`orca-supervised-launch.mjs wait --run <nested-or-parent> --from <me> --worktree . --timeout-ms 900000`

On each tick it: (1) `check --wait` for `worker_done, worker_failed, question, escalation`; (2) scans the reports
directory for files newer than the last tick; (3) for every live Dispatch of the Run runs `worker-show` and a screen
read: idle at the prompt with no report → `stalled-idle` (the caller `notify`s "report now"); no output for longer
than `stalledAfterMs` → `stalled-silent`; pty gone → `dead`; (4) sweeps dead terminals and re-canonicalizes drifted
titles; (5) sends the caller's heartbeat to its parent. It returns `{event: report | stalled-idle | stalled-silent |
dead | timeout, ...}`; `timeout` is an instruction to call `wait` again, never a reason to end the turn. The turn ends
only on the workflow goal or on a `blocked` escalation that needs the parent.

## Naming

- Task `display_name` stays canonical (`[Op] <operation> - <scope>`, `[Monitor] <X>`, `[Coordinator] <Plan>`).
- The launcher verifies the label Orca shows (worker-show `terminal.title` / sidebar label) after the worker is
  `ready`, not immediately after `worker-start`, and `wait` re-canonicalizes on every tick. `worker-task_<id>` on a
  sidebar is a launch that never reached the verified-rename step; it is reported as `titleDrift` with the observed
  label, never as success.
- Investigate suppressing the native title writes of managed Claude (`CLAUDE_CODE_DISABLE_TERMINAL_TITLE`) at
  `worker-start` if Orca exposes an environment hook; otherwise drift stays cosmetic and re-canonicalized.

## Lifecycle rules that move into the templates

- Coordinator spec ≤ 4 KB of instructions plus pointers to files (long specs stall the managed Claude prompt).
- Coordinator never `worker_done` before the integration gate; it reports `partial` at checkpoints instead.
- A Monitor commits its own child branch after `review.verify` passes and before its `done` report.
- Qwen: working operations `yolo`, reasoning `plan` (4.0.1). A terminal whose close returns `ptyKilled:false` is sent
  `/quit` then closed again; still alive → reported as `residualTerminal` with the pid pattern for the user.
- Sweep after every settlement and inside every `wait` tick.
