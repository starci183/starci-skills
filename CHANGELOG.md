# Changelog

All notable changes to StarCi are documented here. The runtime is on the `1.0.0-alpha.N` line: contracts are provisional
until every S* row in `docs/goal.md` holds with fresh evidence, then `1.0.0` freezes them.
`package.json` `version` is the only version authority.

### Changed

### Added
- SSE is the third door of the `realtime` pattern (alpha.30 item C, owner decision 2026-10-24): slot `be.feature.realtime.sse`, a hub-only `@Sse` controller with heartbeat comment frames and `Last-Event-ID` resume, the lite edition may serve it (R212 amended), the FE reads it through a fetch-based event-stream reader, and the lite-app `booking-status` example proves it.

Rule BE-TYPING-8; R304 `BE_SCHEMA_PLACE` (zod only in a `<name>.schema.ts` of a domain, platform or integrations owner, never in a feature, door or `dto/`, never beside `class-validator`); R305 `BE_SCHEMA_BOUNDED` (every string, array, set, record and map bounded, no `z.any()`, `z.unknown()` or `z.json()`). The slot manifest declares the `schema` role suffix (a measured logic role, covered through its reader's spec). The `zod` canon pin is `side: both` (4.6.7) and a new app's starter dependencies carry it. Reference readers: full-app `integrations/sepay` (provider response) and lite-app `domain/calendar-inbox` (inbox payload read back). No schema is shared with the front end and `nestjs-zod` is not adopted.

### Added
- `starci runtime check --only export-used` also reports `RT_IMPORT_UNBOUND`: a runtime module that imports or re-exports a name a relative module of the tree does not export, which Node refuses at link time. Dropping an export can no longer leave an importer behind.
- `starci sonar project rekey` moves a declared project to its new key in place (`api/projects/update_key`, the target's `previousKey` to its `projectKey`): its analyses, issues and quality gate stay with it. Idempotent; verified when the new key reads back and the old key returns 404; `sonar-project-rekey-*` codes name a conflict (both keys hold a project), a missing source or an undeclared previous key.
- A SonarCloud operations target may take its admin credential from the runtime's untracked secret.env by name (`hostConnection: sonar-runtime-secret-env`, `env: SONAR_TOKEN`), read through the same `runtimeSecretEnv` reader as `starci gate sonar up`; the value is never printed or written, and an absent or empty variable refuses with `sonar-host-credential-unavailable`. No sealed secret enters the public runtime repository.
- The three examples declare the operations target `sonarcloud` (organization `starcidapride`, project `starcidapride_starci-example-<app>`, the organization and key the examples workflow scans with), so `starci sonar project ensure --target sonarcloud` puts ecommerce-app and shape-slot on `starci-quality` and lite-app on `starci-quality-lite` with the conditions of `knowledge/sonar-gate.yaml`.
- `starci workflow start` works from a shell Orca did not open (the owner's chat, an agent's tool shell), where it was refused `no_active_sender_terminal`: an owner or Supervisor start without `ORCA_TERMINAL_HANDLE` opens one plain PowerShell terminal in the runtime's worktree (it launches no agent), runs the same start there through the start relay, waits for its receipt and answers with the start's output and exit code. A booted Kernel keeps that terminal as its entry coordinator; a refused start closes it. `--plan` and the watchdog's launches are unchanged.
- The runtime may create plain Orca shells: `terminal create` leaves `api.yaml` `forbiddenForStarciOrchestration` and `check-host-boundary` no longer scans for it (the owner's ruling to drop the ban rather than keep an exception). Agents are still launched only by `orchestration worker-start`, `check-host-boundary` still refuses an agent CLI spawned as a child process, and the `RAW_TERMINAL_CREATE` guard still refuses an agent typing `orca terminal create`.

### Fixed
- Front ends type-check unused locals and parameters (`@starci/tsconfig` 2.0.5 `next.json`): Sonar S1481 is left to the compiler by the lint canons, and only the back-end preset enabled it.
- `starci app release gate --sonar` no longer fails a release on one transient read: a network error or HTTP 5xx while polling `api/ce/task` or reading `api/qualitygates/project_status` is retried up to 5 times with backoff (2, 4, 8, 16 s) inside the same 600 s wait (NIVO's `RELEASE_SONAR_GATE_UNREADABLE: fetch failed` after a healthy upload). Only OK passes; ERROR, FAILED and CANCELED stay red, a 4xx is unreadable at once, and a failure that persists through every try is still `RELEASE_SONAR_GATE_UNREADABLE`.

- The usage sweep cuts a Kernel or Supervisor session at its wake events by the timestamps of the usage records and tags every row with the wake that owns it (`turn_ref ...#w<wake seq>`), so a short wake reads exactly its own turns and tokens. `starci debug digest` reports a Supervisor wake over its token budget as the `supervisor-wake-budget` departure of the Supervisor.

The nine ops with the read-knowledge proof (architecture.decide, brand.decide, business.decide, decision.prepare, docs.author, knowledge.repair, scope.define, scope.finish, work.author) filed `knowledge/**` as their standard: 260 to 290 mandatory files and a 88 to 95 KB prompt that the worker read and carried in its context for every later turn (up to 13 percent of the 3 to 13 million tokens a decision leg cost in the real usage rows). Each now files the law inputs and the knowledge its own READ step names (19 to 45 files, a 21 to 28 KB prompt); `knowledge/op-gate.yaml` `readSet` bounds the file count and the prompt, and a spec holds it.
- Wakes and launch or follow-up prompts share `allocation.promptFile.maxChars`, owned by `scripts/agent/prompt-file.mjs`; the separate wake cap is removed. The transition, ask-answered, stall, supervisor and watchdog wakes keep their opener, the runtime-rev sentence when it fits and the seat identity, and point at `starci kernel status` for the rest (`scripts/kernel/wake-bound.mjs`). The watchdog wording is shortened while retaining its menu, yield, scope and revision duties.
- The `TERMINAL_COUNT_DRIFT` clock counts only the tabs the runtime titled (`[Kernel]`, `[Op]`, `[Worker]`, `[Supervisor]`), not the owner's own terminals, and a violated clock runs the dedupe pass once per SLA window; before, it counted every Orca terminal, stayed open for twenty hours and named an auto-action nothing performed (`scripts/reconciler/terminal-drift.mjs`).
- A Kernel launch that fails for the same cause is bounded. The StarCi Kernel was started 303 times in three hours, each launch failing at `workflow-worktree-install`: every start ran a full `npm ci`, which deletes `node_modules` first, and a running process holding a native `.node` file of the tree stopped it with EPERM half way, leaving a tree without `react`; the next start did the same, and a failed start was never counted against the seat. Now a start-up install skips a tree that is a finished install of the current lockfile (a marker written after npm finishes and cleared before it runs, so a half tree reads as incomplete), a file lock is the typed failure `workflow-worktree-install-locked` naming the path and the processes inside the tree, and the launch of one cause backs off (`seats.kernel.startRetryMs`), is held after `startSameCauseMax` failures and quarantines the seat with one `seat-unrecoverable` item that names the cause (hold `kernel-start-held`).
- `starci supervisor start --rotate` (and `--replace`, `--restart`) is the watchdog's call of the seat script, not a CLI option. The verb declares them as `internalFlags` and the CLI refuses each with a pointer instead of the bare `unknown option`.
- The wake prompt tells the Kernel to answer its menu and yield when it is empty.
- `--field <path>[,<path>...]` on `starci kernel status`, `survey`, `logs` and `decisions`: the answer reduced to the named fields.
- A Kernel launch no longer fails its seat publication for the size of the admission decision: an event that carries a launch admission decision or an admission refusal keeps a bounded summary inline and the whole payload behind `payload_sha` (`engine/db/event-compact.mjs`, which also declares the 16 KiB event bound once), and a publication failure of any cause stops and releases the started worker with proof (`rollbackUnpublishedKernel`).

### Class 4: updating `.claude` while workflows run
A deploy was a hand sequence that knew nothing of the roles it touched: replacing a seat lost both Kernels, a Kernel re-read 103 files for one line of documentation. Now what a change asks of each role is declared once in `modules/kernel/revision-scope.yaml` and refused when a tracked path has no row (`revision-scope`, R237); `starci runtime deploy` is the one gated carry; what the runtime installs outside its tree is declared and migrated (`installed-artefacts`); a seat has one revision acknowledgement.
- What a change of the runtime tree asks of each role is one declared table, `modules/kernel/revision-scope.yaml`, checked against the tracked tree by the `revision-scope` self-check (R237): docs, tests and CLI code cost no seat anything, guards bite on the next command, the engine restarts only for the files its process imports (derived from the import graph), a live Kernel or Supervisor is updated in place (woken once per set of owed files, even with an empty menu; the Kernel attests its complete current READ set, including required contracts and the owed changes; the runtime settles a change that does not concern it as `not-concerned` with the diff hash) and is replaced by a fresh seat at its next yield, with the distinct reason `contract-changed`, only when a rule of its contract was removed or reversed, when the files its launch prompt is built from changed, or folded into a rotation it is already due for. A commit may declare an edit wording-only with the trailer `Revision-Wording: <path>`; the declaration holds only for a file that keeps its structure. An Op is never updated or restarted inside an attempt.
- `starci kernel revision-ack` and `starci supervisor revision-ack` (`--plan`, then `--rev <sha> --read-manifest <file>`) list the files a revision change sends the seat, with their hashes, and attest them. The Kernel records `runtime-rev-acked`, bound to its current incarnation and complete required READ manifest; the Supervisor records its attestation as `runtime-rev-noticed`. Long event payloads use the shared blob spill path. `starci kernel status` (field `revisionNotice`), `starci supervisor status` and `starci debug digest` print one line per seat: the revision it acked, whether the last change concerns it, the files it owes.
- The roles standard requires a `revisionAck` declaration for every role; `starci kernel settle` records `settle-revision-recorded`: per proof the op owes, the revision the attempt was admitted under and whether the files of the judge that decides it moved since.
- The generated package runtime copies follow the runtime: a new engine process regenerates the copies that drifted from their sources before it leads (recorded in its swap as `runtime-copies-synced`; it does not lead with the typed cause `runtime-copies-stale` when it cannot), and `starci git land` regenerates them after main moved.
- `starci runtime deploy --from <clone-or-ref> [--plan] [--json]`: the one verb that carries a runtime revision onto the running host, replacing the hand sequence (fast-forward the live checkout, `starci reconciler restart`, read the digest). It refuses unless the source is committed and clean, a fast-forward of the host tree and proven by a verify receipt bound to that exact commit and the host base (or a land note carrying its `Affected:` proof); it refuses while a release cut holds the host lock and waits for the settles, Critic runs and prepared decisions in flight (it stops none); a tip several commits ahead is one revision change; after the restart it verifies the new revision with a fresh heartbeat, unchanged controller modes and no dead seat, and on a failure names the host state and the non-destructive way back. Each refusal has a code in `modules/kernel/failure-codes.yaml`; one `runtime-deployed` event (from, to, areas, who, the file list as a blob, `roleActions` for the role notification) is journalled. It requires the complete `starci test affected --run --base <host head>` proof from the source clone and refuses `deploy-affected-red` unless the affected receipt is ok, clean and on the source tip (no bypass); the receipt and the event carry `affected: {base, tip, passed, total}`; `--plan` states the set size and budget. The affected run is judged from a receipt FILE (`starci test affected --run --receipt-file`; every clean run also leaves the proven receipt of its base..tip pair, which the deploy accepts instead of repeating it); the child's output and progress go to files, its timeout is the declared budget plus `allocation.deploy.affectedMarginMs`, the progress is printed while it runs, and a refusal names the red files, the unfinished files, the budget that ended or how the child died with its last lines. Declared waits: `allocation.deploy` of `modules/models/runtimes.yaml`.
- `modules/kernel/installed-artefacts.yaml` declares every artefact the runtime installs outside its own tree (the history and work hooks of workflow trees, the runtime repository hooks, the generated package copies, the job guard files, the worktree records); `starci runtime artefacts [--migrate]` judges and migrates them to the revision of the tree, verified and idempotent, and the deploy runs it from the new tree for every live workflow. The engine runs the same migration at start for anything the deploy could not reach. The `installed-artefacts` self-check refuses a declared row without its writer or handler and a new installer that is not declared.

### Class 5: the judge's law differs from the admission's law
The settle read its rules from the tree that was running, so a Critic gate born later refused jobs admitted before it, and a turn that failed could not be judged again. A mapped missing-proof refusal becomes `gate-newer-than-admission` only when the declared judge is proven to have changed since admission and the admitted dispatch contract did not teach that proof, every op declares who judges its product and a contract with no judge is refused (`op-judge`, R242), the Critic is the runtime's and never the maker's, and an attempt whose tree moved is judged from its own placement.
- The maker never supplies its own judge's verdict. `scope.define` and `architecture.decide` no longer run, write, attach or block on a Critic: when one reports done the settler runs the Critic itself (another provider than the maker), once per version of the records, and the settle judges only that run (`runtime-critic-run`). A verdict file an op attaches is ignored and recorded once as `runtime-critic-op-verdict-ignored`. The run is bounded (`tail.maxAttempts` per digest, then a Supervisor item through the checker-unavailable path) and visible: who, model, dispatch, duration, tokens (measured from the Critic session by the usage sweep and unmeasured until its session is indexed), try and verdict, in `starci kernel status --full` (`runtime-critic:` lines) and `starci debug digest` (`co-critic-independent`). The menu's `settle-fail` recorded its refusal as a bare array that `record-checks` refused (`checks-invalid`), so it never ran; it now records the `{checks: [...]}` envelope. A job admitted before the Critic gate, or one whose own run held, is judged by the same run, once per product digest, through the same picker, guard and rubric: a pass passes, a failing critique is the op's error-work, a Critic that cannot judge holds the settle (the checker-unavailable path).
- `scripts/kernel/gate-admission.mjs` is the shared seam for judged settle phases. It maps a declared missing-proof refusal to `gate-newer-than-admission` only when revision comparison proves its judge changed and the admitted dispatch contract lacks the teaching step; unknown history, unrecognized proof codes and red judgments retain their original result; the settler holds the settle bounded and tells the Supervisor, and the Kernel menu offers nothing for it.
- The runtime's own Critic launches from the workflow's Kernel terminal (Orca refused its run-create with `no_active_sender_terminal`, so every run was a hold), a settle the runtime owes (the Critic verdict, a job held for a checker that could not run) is no choice of the Kernel's, and an item the Kernel hands up with `none-fits` is not asked again inside the snooze: an unanswerable menu item woke the Kernel every minute and rotated two Kernels in 30 minutes. `starci work brand` and `starci work shell-conformance` are re-runnable read-only checks (a first done `brand.decide` was handed over `check-not-reverifiable`), and the budget-overrun item of a running attempt closes when its job reports.
- A prepared fail decision whose apply never completed no longer blocks every later settle of its attempt: the settler withdraws a receipt whose reset target is not the workflow's gate base (journalled `prepared-settlement-withdrawn`, the half-reset index put back) and judges the report afresh; the gate base follows the newest checkpoint of the workflow's chain when the registry record lost its pointer (it fell back to the merge-base with main, behind settled ops); a refusal for an unapplied prepared decision is the runtime's, not a Kernel menu item, and a new refusal code under the same reason is recorded as a new handover (the failing Critic verdict was never shown to the Kernel).
- The runtime's own rewind of a workflow branch to its last checkpoint is allowed by the history hook (version 8, `STARCI_BRANCH_REWIND`) while the commit it leaves is kept under `refs/heads/preserved`, and `preserveAndReset` refreshes the hook of the tree first: the settle-fail of a failed op whose files the worktree collector had committed on the branch died `workflow-reset-failed`.
- The native observations of a rebound attempt are one subject across its trees: the newest run stands, so the runs of the lost tree no longer make the settle refuse `op-gate-tool-failed` after the placement was rebound.
- The READ judgment of a rebound attempt reads the op's filed digest root and captured target files through its placement-rebound events, so the re-judgment of a job whose tree was put back at another path no longer reads the filed READ as a foreign target. A gate `workaround` (a new dispatch of the same op) is refused (the refusal that names the re-judgment still owed) while the done report the gate holds has not been judged under the live runtime revision.
- Every op declares who judges its product (principle P2). The contract of each of the 38 ops carries the required field `judge` (machine, critic, owner, next-leg, each with a one-line why); `nobody` cannot be declared. `modules/kernel/op-judges.yaml` holds the vocabulary, the measures a machine judge may cite (only measures the runtime owns and re-runs at settle: a test file the same attempt wrote is never one), the owner gates and the reviewing legs, and the `op-judge` self-check (R242 `RT_OP_JUDGE_UNDECLARED`) holds the contracts to the runtime's own tables (op-gate and sonar-gate ops, opProofs, proof media, the Critic coverage), so they cannot drift. `starci kernel status --full` tags each leg `[judge:...]` and the op prompt carries one `judged_by:` line. The judge declarations follow each op's actual judging mechanism. This release adds the approved runtime Critic for `business.decide`. Acceptance-trace runs in report mode and does not act as a pass gate; declaring a judge alone does not prove product substance. The remaining judge gaps are listed under Deferred.

### Class 6: content inside ledger rows
Each writer decided what to put in a ledger row: an event passed the 16 KiB bound twice, a dispatch prompt row held 334 KB. Now an event payload that grows with its input goes through the one path of `appendEvent` into the blob store (`event-spill`, R238) and readers resolve it; the storage convention (R239, `storage-convention`) declares every text column of both stores as a scalar, a bounded value, a reference, a spill or a migration. The convention and readers do not complete storage-writer conversion; the ledger migration with mandatory backup and the blob collector remain deferred.
- The Kernel's READ attestation (`kernel-ack-rev`) keeps a manifest over the inline event bound in the blob store; its readers resolve it (`engine/db/event-payload.mjs`). A 103-file plan was refused `STARCI_EVENT_PAYLOAD_TOO_LARGE`, so the StarCi Kernel could not open a new leg.

### Class 7: reading or writing the wrong tree
Each call site worked out for itself which directory it meant: a brand record read from the wrong checkout, an app server started by hand against the wrong host, a read verb writing the ledger as its caller, a decision item run against the runtime root. Now a read verb runs on a read-only connection and a spec holds the verbs of effect `read`, one verb renders a layout, an item whose ledger resolves to no repository is refused (`ledger-root-is-runtime`), an admitted attempt follows its tree by a recorded rebind, one module names every root of the runtime and which tree wins (`scripts/lib/roots.mjs`), a new runtime file that spells `process.cwd()` or the Work directory name itself is refused (`root-adhoc`, R240), and every CLI verb declares whether it acts on the tree that owns the bin or on the host. This check prevents new ad hoc root derivation; the remaining legacy root conversions are deferred.
- `starci work layout-render`: the one way an op gets a real browser render of a product layout. The runtime serves the app itself (`next dev` on a free port with no host pin, every URL on `localhost`, the scaffold's public-origin variables set), keys the page slot #FF00FF, captures the viewport at the tree's breakpoint size, stops the server it started and, with `--write`, records the capture as `layout-tree capture` does. A render it cannot produce prints `SHELL_RENDER_UNAVAILABLE` with a typed cause, the failing URL and the redirect chain.
- `brand.decide` looped on `SHELL_RENDER_UNAVAILABLE` in a fresh workflow tree: the op started `next dev --hostname 127.0.0.1` by hand, the product's i18n proxy rewrites to `localhost`, and a server pinned to another host answers that rewrite with 307 for ever. The command policy now refuses a hand-started app server (`next`, `node …/next`, `npm run dev`) and names the verb; the op prompt and `brand.decide` name it (`renders.layoutRender` in `command-policy.yaml`).
- `starci kernel status` is a read verb and no longer writes the ledger as its caller. It opened the ledger writable and ran six writes (resolve a met typed wait, sweep the autopilot, renew leases, record a provider outage, send the blocking heads-up, drain the Runs) as whoever called it, so Debug, a monitor or a person left ledger writes under their own identity. A verb spec now declares `reads: true` and runs on a read-only connection whose every write fails the call with `read-verb-write`; `reacts: true` reopens it writable only for the roles that own the reactions (the Kernel seat, the Supervisor, a reconciler, settler or api child). Anyone else gets the projection with `readOnly: true`, a met typed wait shown as met and left to its owner. The same holds for the other read-looking Kernel verbs: `survey`, `usage`, `observe`, `logs`, `questions`, `messages`, `hierarchy`, `artifacts`, `coverage`, `peers`, `foundations`, `extensions`, `decisions` and `inbox` run on the read-only ledger connection like `status`: a verb with writing flags (`inbox --ack`, `decisions --open/--claim/--resolve/--escalate`) opens the ledger writable only when one is given, and the ones with a reaction of their own (`logs` sync, `questions`/`messages` drain, `observe` record, `decisions` sweep) run it only for the roles that own the reactions. `logs` wrote the ledger's logs table through its own connection as whoever called it; a read-only caller now reads the rows as they stand. The read-only handle carries the pure read accessors (`eventsHead`, `getJob`, ...), so `survey` runs on it.
- The eleven catalog verbs with `effect: read` (`check run`, `docker ps`, `harness status`, `lint run`, `supabase status`, `task list/show`, `typecheck run`, `worker list/read/show`) are held by a spec: the function the dispatcher calls opens no ledger or machine store for writing.
- An admitted attempt survives the loss of its workflow tree: when the tree is put back at another path (`starci workflow start`, `starci workflow custody --apply`, the settler's pass), every admitted, unsettled attempt whose recorded path is lost is rebound by a `placement-rebound` ledger event that settle, the checks and the op gate read (its worker gone, its report filed, every report file in the tree) or ended by the runtime as `placement-lost` (an environment cause: no business attempt spent, the failed-no-step route queues the next attempt). The admission stays immutable.
- `workflow-custody-busy` refuses only while an op has a live worker (or one whose liveness cannot be read): a reported job whose worker is gone no longer holds the repair of its own workflow tree.
- The Supervisor's gate item resolves its repository whichever way its refs name the ledger (id or registered name), and a choice whose `kernel` step cannot bind its repository or workflow is not offered; the item lists it under `unanswerable` with what is missing, so no choice can run against the runtime root (`ledger-root-is-runtime`).
- A Decision Item or Supervisor gate item whose ledger resolves to no repository is refused where it is applied (`ctx.openDecision`, code `decision-item-without-repo`), in every mode, instead of running its verbs against the runtime root (`ledger-root-is-runtime`).
- Every CLI verb declares its side (`runtimeSide: tree | host`, set per group in `_group.yaml` and overridable per verb; the catalog refuses a group without one). A tree-side verb is about the runtime tree that owns the running bin (`runtime check`, `test affected`, `release …`, `gate …`, the regenerations): it runs this checkout even when the per-user record points at another tree, unless `STARCI_RUNTIME` or its own `--root` chose one, and says so on stderr; a host-side verb runs the located runtime as before. The affected-specs receipt names the root it judged, and the deploy gate refuses a receipt whose specs ran in another tree.
- One module names the roots of the runtime: `scripts/lib/roots.mjs` holds the runtime tree, the state directory, the temp root, the invocation directory and the Work directory, and says which tree wins when two hold one record (the workflow tree first, then the product's main checkout) and where a tool is looked up (the tree the work happens in, the runtime's own install last). The grammar context, the autopilot direction and draw gates and the render tools use it, and the `root-adhoc` self-check (rule R240, `RT_ROOT_ADHOC`) refuses a new runtime file that spells `process.cwd()` or the Work directory name itself; a file keeps the count it had when the check landed and only loses it as it is converted.

### Class 8: work with no owner
The routing table and the dispatcher contradicted each other, so work had no one to do it: a rework was blocked by the dispatcher that the table queued, an approved step lacked its proposed file scope, a refusal repeated every minute, a cause was classified by its wording. Now the Job controller performs the moves with one right answer and the Kernel's menu holds only judgments, each choice one the runtime can carry out; a blocker kind is read before wording; a refusal for one cause is remembered and retried on a doubling interval.
- `starci kernel status` prints the Kernel's menu (`menu[]` in the JSON) as its only actionable section: the open decision points of the workflow, built by one function from the Decision Items, the reported blocks, the worker questions, the peer messages and the next actions the runtime does not yet perform, with the options that answer each (`modules/kernel/kernel-menu.yaml`). `frontier.actionable` follows the menu, so the watchdog wakes a Kernel only while its menu has an item.
- `starci kernel decide --item <id> --choice <choice> --reason <why> [--text <input>]` answers one item: the choice is validated against the current menu, recorded in the decision log and executed in-process through the verb's own code path. A choice off the menu is refused with the menu; `none-fits` records the reason and escalates the item to the Supervisor (`menu-escape` Decision Item). The decision-log modes (`--hypothesis`, `--close`, `--list`) are unchanged.
- The Kernel seat's shell is `starci`: the read verbs, `log`, `decide` and `kernel-ack-rev`, plus pure read programs. Every other `starci kernel` verb is the runtime's and is refused to a Kernel seat (`KERNEL_USE_DECIDE`) with the seat's menu; any other program is refused (`KERNEL_STARCI_ONLY`). The table is `kernel` in `modules/kernel/command-policy.yaml`.
- The Job controller performs the retry of a job whose gate resolved, whose owner wait filed no ask, whose ask was answered or whose provisional acceptance the owner re-opened (`scripts/reconciler/mechanical-moves.mjs`); a refused retry opens the `retry-decision` item. Every next action carries an `origin` classified in the menu catalog, and a retry its typed `move`.
- The Job controller also performs the next actions that had one right answer: the enqueue of an approved leg whose plan declares its write set, the rework of a red node (a failed last job is retried, a passed one reopened), the re-run of a stale proof or attempt (a passed unit is reopened with its reason, the move the old menu choice could not make), the `interface.asset` leg, the end-of-flow credential ask, the owner's redraw of a named job and the redo of a cut ordinal that does not reconcile with its seam. A move is built from the ledger (`scripts/kernel/next-moves.mjs`), made once per engine process, skipped while a gate or peer-wait holds it, and a refused move opens Decision Item `move-refused` (`retry-decision` for a failed job nothing follows). The menu kinds `node-rework`, `stale-redispatch`, `asset-slots` and `credential-step` are gone; `leg-ready`, `draw-redraw` and `seam-duty` stay as judgments (the write set the plan leaves open, a redraw that names no job, the checks that reconcile a stub sibling and the re-cut of a slipped seam), and `move-unbuilt` holds a move the ledger could not build. Origins are classed `mechanical` (with a `fallback`) or `judgment` (with its `why`); the origin class that left a next action unclassified is retired.
- A defect the owner reports on the handover is routed by typed choices of the `handover-step` item: `route-fix-<job>` for each slice the workflow built (the passed unit of a build-family op, reopened under the note) and `route-requirement-gap`, `route-design-gap`, `route-interface-gap` with the record in `--text`; a slice the workflow did not build is refused by `decide` before anything is enqueued. The Kernel role's `does` and `decidesAlone` now name the judgments only.
- The Job controller enqueues `handover.review` itself when the handover is due and when the owner answered its ask approve or question (a delegate's approve included): next action origin `handover-review` (`scripts/kernel/handover-move.mjs`). The `handover-step` item now holds only the typed routing of a reported defect.
- `kernel-prompt.md` and `driver-loop.yaml` shrink to the menu loop; the ranked-actions, decisions-first and nextActions procedures are retired from the instructions (removed-vocabulary).
- A `retry-decision` item lives while its job has no later try (it was closed as soon as it was read).
- The budget-overrun item's replace option is `starci kernel enqueue --retry-of <job> --switch-agent` (the old text named a `kernel settle` call the verb cannot take); `--switch-agent` demotes the pool of the attempt being retried for that retry's route.
- The budget-overrun item of an attempt that is still running offers one option, `let-finish` (a snooze: asked again after it, and the settled attempt's usage rows open a second item with the retries), under its own subject `attempt-<id>-running`; the three retries are refused `unit-in-flight` while a try is open and no Kernel verb stops a live worker, so a stop-and-replace is not offered.

### Class 9: integration discipline

- App gates and slice coverage resolve Jest through its declared executable export, including a root-hoisted one-app install; missing tools and failing assertions retain their existing refusal semantics.
- Queue adapters and scaffolded queue templates preserve the declared Redis database for both Queue and Worker. The example test world passes its leased database through the same typed options, preventing queues from silently sharing DB 0 across isolated test worlds; adapter regressions cover a nonzero database without changing scheduler assertions or timeouts.

Nothing stood before a merge or before the host: 28 branches were merged on `npm run check`, which runs no spec, and `npm ci` deleted a package folder in use. Now a release is cut under `release.suite` with a host check that refuses in seconds, a schedule of rows that resumes from its own ledger, the affected specs of the range and the live smokes; a workflow tree that holds its install is marked, not wiped; the examples and the packages are proven against the registry before a tag.

- The release affected row reads the selector's `large` field and uses per-commit selection for a range above its bound, preserving commit reuse and the explicit `notRun` list.
- The cut's default L4 runner receives the selected plan instead of rebuilding a local plan. A CI cut therefore keeps its affected and live-smoke rows without starting the delegated root suite or Linux parity; local mode and row carry retain their declared behavior. The replay exercises the real adapter and runner with private fixture commands.
- `starci release publish --plan` explicitly selects the read-only publication plan; combining it with `--publish` is refused before host or registry effects.
- A UAT slot records its lessee (the attempt's scratch directory and terminal, and the identity of the run, the process that launched it and the held command), and the run ends with it. The Host pass (`host:processes`; shadow only lists) and `starci uat slots collect [--dry-run]` end every slot whose attempt ended, whose launcher is gone, whose holder died with its command alive, or that recorded no lessee and was held past `allocation.uatSlot.unknownHoldMs`; a process is stopped only while its recorded pid, creation time and command line still match, and each stop is a `uat-slot-collected` event. `starci uat slots status` lists the slots it would end as `collectable`. Cause of the 21-hour-old `next start -p 3919/3920` servers that failed 1670 Kernel launches at `npm ci`.
- The install of a workflow tree first ends the UAT slot servers that run from it (`workflow-worktree-install-slot-held` names the lease when one cannot be ended), and a tree that already holds its lockfile's install without a completion marker is marked instead of wiped by `npm ci`.
- A locked tree names its holders by what the platform shows beyond the command line: working directory and mapped files on Linux, loaded modules on Windows (`holders[].via`).
- `config.yaml` `release: {suite: local | ci}` (shipped default `local`): under `ci`, the owner's recorded choice of 2026-10-09 (`release-suite-ci`), `starci release cut` plans no root suite and no Linux parity row (listed as `delegated` in `--plan`, the result and the release record), runs `npm run check`, `npm run test:packages`, the affected specs of the release range (commit by commit when the range is over the bound, with per-commit evidence), the live Orca smokes and the example rows, and the pre-push gate accepts the record only while the checked-out config says `ci` too (`RELEASE_SUITE_MODE`). `starci release ci-status [--tag] [--wait]` reads the `ci` workflow and the Codecov and Sonar checks through `scripts/api/gh/**`, records a red run of a `ci` release as `runtime-defect:release-ci-red-<tag>`, and `starci debug digest` and `starci reconciler up --check` show the last release CI.

- `modules/kernel/op-incident-policy.yaml`: one policy table for every hold on a job, seat or workflow, with a matrix of hold kinds against eight invariants. A launch refusal, quota or readiness failure demotes then excludes that agent for the job so the next chain member takes it; a job with every member spent opens one job-scoped escalation; a running worker's rate limit waits or is replaced by the reset time; an overdue Supervisor Decision Item climbs to the owner. A `supervisor-gate` needs a typed cause and a tried workaround (or a typed reason none exists), carries a machine-checked release condition where its cause allows, enters the same ladder, and takes one of three Supervisor resolutions: `fixed`, `workaround`, `not-runtime-fault`.

- A Kernel waiting on a named machine condition was replaced as idle; an unattended Kernel restart had no sender terminal and retried forever; a failed Kernel launch left a `launch-unknown` signal no later start could reconcile; a disconnected terminal with no tagged process could not be proven closed.
