# Changelog

All notable changes to StarCi are documented here. The runtime is on the `1.0.0-alpha.N` line: contracts are provisional
until every S* row in `docs/goal.md` holds with fresh evidence, then `1.0.0` freezes them.
`package.json` `version` is the only version authority.

## [1.0.0-alpha.8] — in preparation

### Changed
- Every CLI verb declares its side (`runtimeSide: tree | host`, set per group in `_group.yaml` and overridable per verb; the catalog refuses a group without one). A tree-side verb is about the runtime tree that owns the running bin (`runtime check`, `test affected`, `release …`, `gate …`, the regenerations): it runs this checkout even when the per-user record points at another tree, unless `STARCI_RUNTIME` or its own `--root` chose one, and says so on stderr; a host-side verb runs the located runtime as before. The affected-specs receipt names the root it judged, and the deploy gate refuses a receipt whose specs ran in another tree.
- One module names the roots of the runtime: `scripts/lib/roots.mjs` holds the runtime tree, the state directory, the temp root, the invocation directory and the Work directory, and says which tree wins when two hold one record (the workflow tree first, then the product's main checkout) and where a tool is looked up (the tree the work happens in, the runtime's own install last). The grammar context, the autopilot direction and draw gates and the render tools use it, and the `root-adhoc` self-check (rule R240, `RT_ROOT_ADHOC`) refuses a new runtime file that spells `process.cwd()` or the Work directory name itself; a file keeps the count it had when the check landed and only loses it as it is converted.
- The replay world is host-independent: every host reading the runtime takes (free RAM, CPU, disk, the worker census) comes from the injected sample `STARCI_HOST_RESOURCES_JSON`, and a trap preload in every process of the world logs any read of the real host (`os.freemem`, `os.cpus`, `fs.statfsSync`, ...); `tests/replay/host-independence.spec.mjs` proves a starved host leaves `allowed: 0` (the cause of a replay that failed on a loaded machine) and that a replayed pass reads none. New replay specs `ready-not-dispatched` (a worker-start refused `consumer_fenced`, a grammar context read from the workflow tree) replay the fixes of lane fix/a8-live-ready-not-dispatched; the second push of the fence sequence still lost one launch to `attempt-released` (open registry entry, `todo` test).
- A fix for a defect found on a live host is done when a replay spec built from the sequence that showed it passes. The replay harness (`tests/helpers/replay-*.mjs`) builds a throwaway world from a reduced, neutral fixture of a real ledger (`replay-extract.mjs`, hygiene scan `replay-hygiene.mjs`; five fixtures under `tests/fixtures/replay/`, a few KB each), drives the real reconciler engine (a fresh process per call, so every call is an engine restart), the settler, the Kernel verbs and the menu builders through a bound Kernel seat, crosses a runtime revision change (`world.reviseRuntime`), stubs only the Orca binary and the Critic agent launch, and runs a spec against an older revision (`replay-on-revision.mjs`) to show it fail where the bug lived. Six replay specs under `tests/replay/` cover today's live cases (a handed-over job refused for a missing Critic verdict, a prepared fail decision left by a failed rewind, a none-fits whose item id the redaction filter rewrites, a read attestation over the inline event bound, a retry the shape guard skipped, an escalated item answered by the Supervisor). The edge-case registry marks a case found live with `found: live`; the `edge-case-registry` self-check refuses a covered live case that names no `replay:` spec of `tests/replay/` built on the harness. The rule is in `skills/starci/references/debug-loop.md` and the Debug role (`roles.yaml`, ruling `debug-replay-before-done`).
- `starci kernel status` prints the Kernel's menu (`menu[]` in the JSON) as its only actionable section: the open decision points of the workflow, built by one function from the Decision Items, the reported blocks, the worker questions, the peer messages and the next actions the runtime does not yet perform, with the options that answer each (`modules/kernel/kernel-menu.yaml`). `frontier.actionable` follows the menu, so the watchdog wakes a Kernel only while its menu has an item.
- `starci kernel decide --item <id> --choice <choice> --reason <why> [--text <input>]` answers one item: the choice is validated against the current menu, recorded in the decision log and executed in-process through the verb's own code path. A choice off the menu is refused with the menu; `none-fits` records the reason and escalates the item to the Supervisor (`menu-escape` Decision Item). The decision-log modes (`--hypothesis`, `--close`, `--list`) are unchanged.
- The Kernel seat's shell is `starci`: the read verbs, `log`, `decide` and `kernel-ack-rev`, plus pure read programs. Every other `starci kernel` verb is the runtime's and is refused to a Kernel seat (`KERNEL_USE_DECIDE`) with the seat's menu; any other program is refused (`KERNEL_STARCI_ONLY`). The table is `kernel` in `modules/kernel/command-policy.yaml`.
- The Job controller performs the retry of a job whose gate resolved, whose owner wait filed no ask, whose ask was answered or whose provisional acceptance the owner re-opened (`scripts/reconciler/mechanical-moves.mjs`); a refused retry opens the `retry-decision` item. Every next action carries an `origin` classified in the menu catalog, and a retry its typed `move`.
- The Job controller also performs the next actions that had one right answer: the enqueue of an approved leg whose plan declares its write set, the rework of a red node (a failed last job is retried, a passed one reopened), the re-run of a stale proof or attempt (a passed unit is reopened with its reason, the move the old menu choice could not make), the `interface.asset` leg, the end-of-flow credential ask, the owner's redraw of a named job and the redo of a cut ordinal that does not reconcile with its seam. A move is built from the ledger (`scripts/kernel/next-moves.mjs`), made once per engine process, skipped while a gate or peer-wait holds it, and a refused move opens Decision Item `move-refused` (`retry-decision` for a failed job nothing follows). The menu kinds `node-rework`, `stale-redispatch`, `asset-slots` and `credential-step` are gone; `leg-ready`, `draw-redraw` and `seam-duty` stay as judgments (the write set the plan leaves open, a redraw that names no job, the checks that reconcile a stub sibling and the re-cut of a slipped seam), and `move-unbuilt` holds a move the ledger could not build. Origins are classed `mechanical` (with a `fallback`) or `judgment` (with its `why`); the class `pending` is retired for next actions.
- A defect the owner reports on the handover is routed by typed choices of the `handover-step` item: `route-fix-<job>` for each slice the workflow built (the passed unit of a build-family op, reopened under the note) and `route-requirement-gap`, `route-design-gap`, `route-interface-gap` with the record in `--text`; a slice the workflow did not build is refused by `decide` before anything is enqueued. The Kernel role's `does` and `decidesAlone` now name the judgments only.
- The Job controller enqueues `handover.review` itself when the handover is due and when the owner answered its ask approve or question (a delegate's approve included): next action origin `handover-review` (`scripts/kernel/handover-move.mjs`). The `handover-step` item now holds only the typed routing of a reported defect.
- `kernel-prompt.md` and `driver-loop.yaml` shrink to the menu loop; the ranked-actions, decisions-first and nextActions procedures are retired from the instructions (removed-vocabulary).
- The wake prompt tells the Kernel to answer its menu and yield when it is empty.
- The roles contract names exactly two classes of error, happy error and bug; Debug's goal is a workflow with no bug. The Kernel role declares a per-wake budget (20 turns, 6 million tokens, from the usage rows of the first real workflows) and the digest reports a wake over it as a departure.
- A `retry-decision` item lives while its job has no later try (it was closed as soon as it was read).
- The budget-overrun item's replace option is `starci kernel enqueue --retry-of <job> --switch-agent` (the old text named a `kernel settle` call the verb cannot take); `--switch-agent` demotes the pool of the attempt being retried for that retry's route.
- The budget-overrun item of an attempt that is still running offers one option, `let-finish` (a snooze: asked again after it, and the settled attempt's usage rows open a second item with the retries), under its own subject `attempt-<id>-running`; the three retries are refused `unit-in-flight` while a try is open and no Kernel verb stops a live worker, so a stop-and-replace is not offered.

### Added
- `starci runtime verify [--base <ref>]` is what "verified" means: it runs `starci runtime check` and then `starci test affected --run --base` on one committed, clean tree and writes ONE receipt (`starci/verify-receipt@1`, `<runtime state dir>/verify/<sha>.json`) bound to the exact commit, with `check p/p` and `affected N/N for <base>..<tip>`; its last line is `verified <sha>: check p/p, affected N/N of <base>..<sha>` or `NOT VERIFIED <sha>: ...` listing the red files. Twenty-eight branches had been merged and deployed on `npm run check exit 0` alone, which never starts a spec.
- The verify receipt names the root the specs ran in (one rule, `judgedIn`, shared with the deploy receipt) and is honest about a partial run: `PARTIAL <sha>: check p/p, affected N/T passed, 0 failed, M not started (budget)` (exit 3) when nothing is red and every spec the change touched ran (they run first); `starci git land` accepts it and writes `Affected-Not-Started: M (budget)` into the note, `starci runtime deploy` and the release need N/N. The affected run samples the host again every `resampleMs` (`modules/supervisor/test-concurrency.yaml`) instead of keeping the concurrency of its first second.
- `starci git land` refuses a tip that has no verify receipt for its exact commit and the land base (step `0-verify-receipt`, before the gate, the check and the specs) and writes `Affected: N/N <base>..<tip>` into the land note; `starci runtime deploy` takes the verify receipt of the source clone, or a land note that carries the `Affected:` line for the host head, and no longer takes a land note with the check alone.
- The last line of `starci runtime check` reads `check: ok — HFS clean; self-checks N of N; specs NOT run (starci runtime verify)`; the debug loop, the Debug role ruling, `CONTRIBUTING.md` and the lane documents tell a lane to report the verify line.
- `starci test affected --run` keeps a per-spec result cache under the runtime state dir (`spec-cache/`): a spec whose key is unchanged since a green run is not run again and the receipt counts it as `reused`. The key is the spec, its import closure, the data its modules name, the generated outputs of a generator in the closure, the whole runtime (or tree) for a spec that starts the CLI or scans folders, node, platform, the preload closure and the lockfiles; `--no-cache` runs every file; the `spec-cache-key` self-check changes one file of every input class the selector knows and refuses a key that does not move.
- `starci workflow purge --repo <repo> --workflow <id> [--plan | --apply [--ledger] [--expect <sha>]]` (owner role) removes what an archived workflow left on the host: its worktrees (through the Orca home with its held-file retry, or the git home), its branches `wf-<id>`, `wf-<id>-2` and its `preserved/<id>/*` refs (only with the proof that the runtime made them; the plan prints every tip so one is recovered by sha), the Orca workers and terminals the ledger ties to it (through `worker-close` and the terminal close; anything it cannot tie is listed and never touched), its job guards, spilled dispatch prompts and machine Decision Items. The plan is the default and changes nothing; `--apply` runs under the host lock and the gc lock, stores the plan first so a crash resumes, and writes one `workflow-purged` event (plan sha, counts, each deleted ref with its tip). The ledger rows stay unless `--ledger` archives them to a verified zip and drops them. Refusals are catalogued (`workflow-purge-not-archived`, `-live-job`, `-live-seat`, `-worker-live`, `-orca-unreadable`, `-host-busy`, `-plan-changed`). `starci workflow stop` names it as the next step, and the debug digest skips a purged workflow.
- What a change of the runtime tree asks of each role is one declared table, `modules/kernel/revision-scope.yaml`, checked against the tracked tree by the `revision-scope` self-check (R237): docs, tests and CLI code cost no seat anything, guards bite on the next command, the engine restarts only for the files its process imports (derived from the import graph), a live Kernel or Supervisor is updated in place (woken once per set of owed files, even with an empty menu, with exactly the changed files; the runtime settles a change that does not concern it as `not-concerned` with the diff hash) and is replaced by a fresh seat at its next yield, with the distinct reason `contract-changed`, only when a rule of its contract was removed or reversed, when the files its launch prompt is built from changed, or folded into a rotation it is already due for. A commit may declare an edit wording-only with the trailer `Revision-Wording: <path>`; the declaration holds only for a file that keeps its structure. An Op is never updated or restarted inside an attempt.
- `starci kernel revision-ack` and `starci supervisor revision-ack` (`--plan`, then `--rev <sha> --read-manifest <file>`) list the files a revision change sends the seat, with their hashes, and attest them; the record (`runtime-rev-noticed`) carries the two revisions, a count and the diff hash, and the file list lives in the blob store, so an attestation of any number of files stays under the event payload limit. `starci kernel status` (field `revisionNotice`), `starci supervisor status` and `starci debug digest` print one line per seat: the revision it acked, whether the last change concerns it, the files it owes.
- The roles standard requires a `revisionAck` declaration for every role; `starci kernel settle` records `settle-revision-recorded`: per proof the op owes, the revision the attempt was admitted under and whether the files of the judge that decides it moved since.
- A UAT slot records its lessee (the attempt's scratch directory and terminal, and the identity of the run, the process that launched it and the held command), and the run ends with it. The Host pass (`host:processes`; shadow only lists) and `starci uat slots collect [--dry-run]` end every slot whose attempt ended, whose launcher is gone, whose holder died with its command alive, or that recorded no lessee and was held past `allocation.uatSlot.unknownHoldMs`; a process is stopped only while its recorded pid, creation time and command line still match, and each stop is a `uat-slot-collected` event. `starci uat slots status` lists the slots it would end as `collectable`. Cause of the 21-hour-old `next start -p 3919/3920` servers that failed 1670 Kernel launches at `npm ci`.
- The install of a workflow tree first ends the UAT slot servers that run from it (`workflow-worktree-install-slot-held` names the lease when one cannot be ended), and a tree that already holds its lockfile's install without a completion marker is marked instead of wiped by `npm ci`.
- A locked tree names its holders by what the platform shows beyond the command line: working directory and mapped files on Linux, loaded modules on Windows (`holders[].via`).
- `config.yaml` `release: {suite: local | ci}` (shipped default `local`): under `ci`, the owner's recorded choice of 2026-10-09 (`release-suite-ci`), `starci release cut` plans no root suite and no Linux parity row (listed as `delegated` in `--plan`, the result and the release record), runs `npm run check`, `npm run test:packages`, the affected specs of the release range (commit by commit when the range is over the bound, with per-commit evidence), the live Orca smokes and the example rows, and the pre-push gate accepts the record only while the checked-out config says `ci` too (`RELEASE_SUITE_MODE`). `starci release ci-status [--tag] [--wait]` reads the `ci` workflow and the Codecov and Sonar checks through `scripts/api/gh/**`, records a red run of a `ci` release as `runtime-defect:release-ci-red-<tag>`, and `starci debug digest` and `starci reconciler up --check` show the last release CI.
- The release host check (`starci release cut`, also under `--plan`) refuses in seconds when a provider the live settle smokes launch has no fresh Orca quota poll (it names the provider, the age of the poll and the fix: focus the Orca window until the usage panel refreshes), when the provider cannot be admitted, or when the checkout is outside `launchTrust` (`scripts/supervisor/release-host-live.mjs`). A provider the host cannot admit is a red row, never a skip.
- `starci work layout-render`: the one way an op gets a real browser render of a product layout. The runtime serves the app itself (`next dev` on a free port with no host pin, every URL on `localhost`, the scaffold's public-origin variables set), keys the page slot #FF00FF, captures the viewport at the tree's breakpoint size, stops the server it started and, with `--write`, records the capture as `layout-tree capture` does. A render it cannot produce prints `SHELL_RENDER_UNAVAILABLE` with a typed cause, the failing URL and the redirect chain.
- The role standard (`standard:` in `modules/kernel/roles.yaml`): every role block declares the same fields, its happy errors (each naming a policy row), its bug surface, a guard binding or `noSeat`, a budget or the reason it has none, and stands in the reporting chain. The `roles-contract` check prints the role by requirement table and is red for a missing requirement unless the role block carries a dated `pending:` entry naming the lane that builds it. `starci runtime check --only roles-contract -- --table` prints the five roles by scope, function, happy errors and what each does on a bug; `docs/workflow-kernel.md` carries the generated copy.
- `modules/reconciler/operating-standard.yaml`: the standard path of a workflow as ordered steps (actor, precondition, observable done-state, bound, evidence, probe), the departure table (role, broken duty, registry entry) and the happy errors that are only counted. `starci debug digest` judges every running workflow against it step by step and names the first departure.
- `modules/reconciler/debug-questions.yaml`: the nine groups of Debug's questions, each answerable today by a digest check or a documented gap with the signal it needs; `starci debug digest --questions` lists them.
- `starci debug digest` prints a verdict per role (Supervisor, each Kernel, each Op attempt, the Critic runs, the Runtime) as no error, happy error (counted) or BUG, and Debug's standing against its end condition. Only a BUG is a problem line; the digest schema is `starci/debug-digest@2`.
- Three signals: a `reconciler.boot` row at every engine start (boot instant, uptime, boot id), the directory, commit and tree of every check on the `op-settled` event (`checkedIn`), and a `ledger-written-outside-seat` event for a ledger write by a person at a shell.
- The Op's token budget is measured: each settled attempt is summed from its usage rows, `starci kernel status` lists the attempts over budget whose job waits on the Kernel (`budgetOverruns`), and the Workflow controller opens a Kernel Decision Item `budget-overrun` with the options continue-once, replace and re-scope.
- All 34 of Debug's questions are answerable (`modules/reconciler/debug-questions.yaml` has no gap). The last five read signals recorded where the fact occurs: `provider_health_events` keep the end of the circuit (`circuitOpenUntil`) beside the failing job, step and kind (`pl-network-loss`); `signal.runtime-change-applied` is written when an engine starts on a new revision and when a land re-looks at the running workflows (`cu-live-state-untouched`); the redaction module reports which rule still finds a secret in a stored text (`redactTracked`, `survivingSecrets`) and the digest re-scans its log rows, seat snapshots, Supervisor reports and attempt transcripts with it, naming the artifact and the rule and never the text, and lists a survivor as a problem of the runtime (`co-secret-in-transcript`); `signal.host-ledger-drift` is written by the SLA pass for every clock whose code names a `driftKind` in `modules/reconciler/sla.yaml` when it outlives its bound and when it clears (`rr-claimed-vs-observed`); `signal.port-claim` is written by `starci gate env-health` for each claim, adoption, replacement, refusal and release of a port, and a port nobody lists but a connect to 127.0.0.1 reaches is a stranger's (`cc-port-claims`).
- `--field <path>[,<path>...]` on `starci kernel status`, `survey`, `logs` and `decisions`: the answer reduced to the named fields.
- The role standard is complete for all five roles: Op, Kernel, Supervisor and Debug now declare their happy errors (each naming a row of the incident policy), their bug surface (the typed refusal or digest signal and the file that reads it) and their guard binding and budget, so the roles-contract table prints `present` in every cell and no `pending:` marker remains. Debug declares `noSeat: true` with a `noSeatReason` (an explicit form the check accepts only with its reason); the Kernel's budget is its `wakeBudget`; the Supervisor's `tokenBudget` is provisional, declared from 55 measured `supervisor-turn` rows. A `pending:` entry may name an open edge-case registry entry instead of a lane; two entries are open: `supervisor-wake-budget-unmeasured` and `supervisor-menu-escape-has-no-policy-row`.

- The release cut runs its L4 rows as a schedule (`scripts/supervisor/release-l4-schedule.mjs`, `release-l4-graph.mjs`, `modules/supervisor/release-cut.yaml`): the Linux parity container starts first and runs beside the root suite, the example apps' row chains and their three SonarCloud proofs run together once the suite has ended (bounded by the declared pool sizes and the host's free threads and RAM), and a red row cancels nothing. From the row times of the second alpha.7 cut that is about 1800 to 2200 s instead of 4240 s.
- A cut that resumes (`scripts/supervisor/release-reuse.mjs`): each cut leaves a ledger of its green rows per commit with a digest of each row's declared input set; a later cut reuses a row whose inputs are byte-identical (the example apps' rows and proofs) and lists it in the record with `reusedFrom`; `--plan` prints run, carry or reuse with the reason per row; `--no-reuse` runs all. The three rows the pre-push gate requires (`npm test`, `npm run test:packages`, `npm run check`) are never reused: the gate counts them only when they RAN on the pushed commit.
- `starci release cut --rows <row,row>` re-runs named rows alone on the same commit (an env-only red row) and completes the record when every other row is green there; `rows-unknown` and `rows-incomplete` refuse before anything runs.
- The reconciler engine reads the answer of a verb whole: `starci kernel status --json` prints indented over many lines and the engine parsed only the last line, so every status read of the real workflows was "no JSON" since 2026-10-07 (238 status-unreadable items) and the Job controller never ran `dispatch-ready` (a ready StarCi `brand.decide` waited 20 hours). The Job controller names an unreadable status instead of reporting the workflow ended.
- An open supervisor-gate always has its Supervisor item: the Workflow controller reads the open gates from the ledger when the status cannot be read, at any ladder step, and offers a runtime-defect gate again under every new runtime revision with the commits since it was raised that touch its cause (`fixed --text <commit>`). A green re-judgment of the job a gate holds settles it and resolves the gate as `fixed` by the runtime with the revision as proof; a red one is recorded on the gate (`gate-rejudged`).
- The native observations of a rebound attempt are one subject across its trees: the newest run stands, so the runs of the lost tree no longer make the settle refuse `op-gate-tool-failed` after the placement was rebound.
- A Kernel boot is a cut of its session's usage with its own budget (`kernel.wakeBudget.perBoot`): the contract and rev-ack reading of a new session is no longer counted as a 22-turn wake of the session it replaced.
- The Supervisor's gate item resolves its repository whichever way its refs name the ledger (id or registered name), and a choice whose `kernel` step cannot bind its repository or workflow is not offered; the item lists it under `unanswerable` with what is missing, so no choice can run against the runtime root (`ledger-root-is-runtime`).
- The READ judgment of a rebound attempt reads the op's filed digest root and captured target files through its placement-rebound events, so the re-judgment of a job whose tree was put back at another path no longer reads the filed READ as a foreign target. A gate `workaround` (a new dispatch of the same op) is refused (`gate-rejudge-pending`) while the done report the gate holds has not been judged under the live runtime revision.
- A report whose outcome is `ask`, `blocked`, `failed` or `partial` is settled by the settler within its bound (the Job controller plans the settle for every report but the owner's own act), instead of waiting for a Kernel menu item that never existed; a StarCi `brand.decide` that asked the owner a question sat `reported` for 16 minutes.
- The settler runs the decision Critic itself for a done report of a covered kind (`scope.define`, `architecture.decide`) that attaches no verdict (a job admitted before the Critic gate, or an op whose own run held), once per product digest, through the same picker, guard and rubric, and the settle gate judges that verdict: a pass passes, a failing critique is the op's error-work, a Critic that cannot judge holds the settle (the checker-unavailable path). A refusal for a gate newer than the job's admission is `gate-newer-than-admission` and offers the Kernel no choice. The menu's `settle-fail` recorded its refusal as a bare array that `record-checks` refused (`checks-invalid`), so it never ran; it now records the `{checks: [...]}` envelope.
- A Supervisor gate item closes when its gate is answered: the Supervisor's own closing verb is allowed for the item it answered (the item listed only the controller's `starci kernel incident`, so the closure was refused and only noted), the Workflow controller closes the items of its workflow's resolved gates every pass (it ran only in the Workers controller's notifier, in shadow mode), and the older item of a gate offered again under a newer runtime revision closes when the newer one stands.
- The generated package runtime copies follow the runtime: a new engine process regenerates the copies that drifted from their sources before it leads (recorded in its swap as `runtime-copies-synced`; it does not lead with the typed cause `runtime-copies-stale` when it cannot), and `starci git land` regenerates them after main moved.
- The runtime's own Critic launches from the workflow's Kernel terminal (Orca refused its run-create with `no_active_sender_terminal`, so every run was a hold), a settle the runtime owes (the Critic verdict, a job held for a checker that could not run) is no choice of the Kernel's, and an item the Kernel hands up with `none-fits` is not asked again inside the snooze: an unanswerable menu item woke the Kernel every minute and rotated two Kernels in 30 minutes. `starci work brand` and `starci work shell-conformance` are re-runnable read-only checks (a first done `brand.decide` was handed over `check-not-reverifiable`), and the budget-overrun item of a running attempt closes when its job reports.
- A prepared fail decision whose apply never completed no longer blocks every later settle of its attempt: the settler withdraws a receipt whose reset target is not the workflow's gate base (journalled `prepared-settlement-withdrawn`, the half-reset index put back) and judges the report afresh; the gate base follows the newest checkpoint of the workflow's chain when the registry record lost its pointer (it fell back to the merge-base with main, behind settled ops); a refusal for an unapplied prepared decision is the runtime's, not a Kernel menu item, and a new refusal code under the same reason is recorded as a new handover (the failing Critic verdict was never shown to the Kernel).
- A ready job the dispatch push refuses for its shape (the op, owned paths and params of a failed job of its unit) is a Kernel menu item `shape-refused` with a `widen` choice, instead of a skip inside a successful push that nobody owned (a StarCi `work.author` retry sat ready for 25 minutes).
- `starci runtime deploy --from <clone-or-ref> [--plan] [--json]`: the one verb that carries a runtime revision onto the running host, replacing the hand sequence (fast-forward the live checkout, `starci reconciler restart`, read the digest). It refuses unless the source is committed and clean, a fast-forward of the host tree and proven by a check receipt bound to that exact commit (the verb runs `starci runtime check` in the clean source itself, or reads the land note); it refuses while a release cut holds the host lock and waits for the settles, Critic runs and prepared decisions in flight (it stops none); a tip several commits ahead is one revision change; after the restart it verifies the new revision with a fresh heartbeat, unchanged controller modes and no dead seat, and on a failure names the host state and the non-destructive way back. Each refusal has a code in `modules/kernel/failure-codes.yaml`; one `runtime-deployed` event (from, to, areas, who, the file list as a blob, `roleActions` for the role notification) is journalled. After the check it runs `starci test affected --run --base <host head>` in the source clone and refuses `deploy-affected-red` unless the affected receipt is ok, clean and on the source tip (no bypass); the receipt and the event carry `affected: {base, tip, passed, total}`; `--plan` states the set size and budget. The affected run is judged from a receipt FILE (`starci test affected --run --receipt-file`; every clean run also leaves the proven receipt of its base..tip pair, which the deploy accepts instead of repeating it); the child's output and progress go to files, its timeout is the declared budget plus `allocation.deploy.affectedMarginMs`, the progress is printed while it runs, and a refusal names the red files, the unfinished files, the budget that ended or how the child died with its last lines. Declared waits: `allocation.deploy` of `modules/models/runtimes.yaml`.
- `modules/kernel/installed-artefacts.yaml` declares every artefact the runtime installs outside its own tree (the history and work hooks of workflow trees, the runtime repository hooks, the generated package copies, the job guard files, the worktree records); `starci runtime artefacts [--migrate]` judges and migrates them to the revision of the tree, verified and idempotent, and the deploy runs it from the new tree for every live workflow. ## [1.0.0-alpha.6] — 2026-10-08

Theme: the first two real workflows run end to end through their first gates; model picking moves to capability tiers; every hold on a job gets one declared policy.

### Changed
- Model picking is by capability tier and ordered chain (`modules/models/tiers.yaml`: `frontier`, `high`, `medium`, `low`, and the call-only `imagegen`), one picker for every seat and op: hard filter, owner bias, keep a live seat, balance, then chain order by tokens. Provider pools, shares, `kernel.group`, `models.pools` and the `require` bias are removed and refused by name; the bias key is `only`.
- Image generation is a headless call (`starci work imagegen`), not a seat: drawing ops run on their difficulty tier and call it for raster regions.
- Workflow debug is a loop of the calling chat (`starci debug digest`, read-only); the Orca core-debug seat, `debug pass`, the `--caller-*` flags and the `coreDebug`/`debug` config keys are removed and refused by name. The Codex loop syntax in the skill reference is unverified.
- `/starci` checks the runtime on every invocation.
- The land gate holds the host lock only around the publish step and verifies the tree it lands; its spec selection is bounded.
- The Codex command guard is registered in the Codex home a worker starts in (the owner's `~/.codex` and Orca's managed home), not in the worktree's project layer, which Codex ignores in a linked worktree.

### Added
- `modules/kernel/op-incident-policy.yaml`: one policy table for every hold on a job, seat or workflow, with a matrix of hold kinds against eight invariants. A launch refusal, quota or readiness failure demotes then excludes that agent for the job so the next chain member takes it; a job with every member spent opens one job-scoped escalation; a running worker's rate limit waits or is replaced by the reset time; an overdue Supervisor Decision Item climbs to the owner. A `supervisor-gate` needs a typed cause and a tried workaround (or a typed reason none exists), carries a machine-checked release condition where its cause allows, enters the same ladder, and takes one of three Supervisor resolutions: `fixed`, `workaround`, `not-runtime-fault`.
- `roots.temp` and `resources.{minFreeDiskGb,minFreeDiskPct,minFreeRamPct}` in `config.yaml`: the runtime temp root and the host floors are the owner's to set.
- A generic retry budget (`scripts/lib/retry-budget.mjs`) for the reconciler work queue, stale terminals and the host lock; a provider-reservation reaper; a leftover-worker sweep.
- Host rows `command guard resolvable`, `drift-modes` and `drift-rev`; `reconciler status` leads with a `DRIFT:` line.
- Checks: `undeclared-identifiers`; the failure-code catalogue covers the new refusals.

### Fixed
- The command guard hook resolved through the per-user launcher on PATH, which bash does not find as `starci.cmd`, so every guarded Bash call of a Windows seat ran unguarded behind a non-blocking hook error. The hook command now names the launcher by absolute path, `starci runtime install` and `runtime link` write an extensionless POSIX launcher beside `starci.cmd`, launch trust refuses a launch whose guard command no shell can run (`guard-command-unresolvable`), and the host check has a required row `command guard resolvable`.
- An autopilot budget gate held every job of a workflow whenever a finished attempt was not yet metered, and nothing released it; only an exceeded cap raises it now and the runtime releases it when its condition is gone.
- A Kernel waiting on a named machine condition was replaced as idle; an unattended Kernel restart had no sender terminal and retried forever; a failed Kernel launch left a `launch-unknown` signal no later start could reconcile; a disconnected terminal with no tagged process could not be proven closed.
- An op that had read its knowledge was settled failed for a READ proof nothing produced; a job's checks were re-run in the main checkout instead of its workflow worktree; `status` showed a superseded red as the reason.
- The reconciler engine recorded an unreadable `config.yaml` as every controller `off` and could not reload onto a new revision; it keeps its last good modes, reloads without reading the new config through old code, and reports drift.
- Kernel and Supervisor token usage was not metered behind the Orca worker preamble.
- Linux: the Windows launcher path, file-time rounding, temp-root and path-key assumptions in specs; `starci kernel route` dropped the per-member rejections when every member was refused.
- SonarCloud findings: from 5,701 code smells down to 59 smells and 2 bugs on the last scan, each of which this release addresses in code.

### Known limitations

## [1.0.0-alpha.5] — 2026-10-06

Theme: host prompts move under the public entry, host state lives under the runtime root, and the runtime gains artifact, install-sandbox and Sonar proof.

### Changed
- The host startup and maintenance prompts live at `skills/starci/references/host-startup.md` and `host-maintenance.md`; the `.starci/` source directory is gone.
- Host state and artifacts live under `<runtime root>/.runtime`, which is git-ignored and never packaged; nothing is relocated from earlier per-user locations.
- The machine store has one schema and no upgrade path: a store that is not the current schema is refused unchanged.
- The entry check validates the bootstrap files of the hosts an install selected.
- The runtime repository's CI runs on every push to `main` as well as on `v*` tags and by hand (static checks, coverage, Codecov, and the SonarCloud scan on `main`), the runtime artifact is built on every main push, and a fast-forward push of `main` needs no release tag; rule R221 allows the `main` push in the runtime's own workflows only, and app CI templates keep the tag-only law.

### Added
- A `runtime-artifact` workflow (manual dispatch) packs the runtime with version, SHA and hash metadata plus an inventory, and refuses host-local or secret material.
- An `install-sandbox` workflow and `scripts/gates/install-sandbox.mjs` prove a clean-machine install on Windows and Linux.
- Runtime coverage (`npm run test:coverage`, Codecov flag `runtime`, informational) and a SonarCloud analysis of the runtime in the tag run.
- A packed-import guard in the runtime package proof.

### Fixed
- SonarCloud bug and vulnerability findings across `engine/`, `scripts/`, `ui/` and `packages/`: explicit code-unit sort comparators, regexes without catastrophic backtracking, secret redaction in the assisted-UAT runner, a quiet-since fallback in progress RCA, tightened file modes, GitHub Actions pinned by commit SHA and `npm ci --ignore-scripts` in workflows.
- The packed runtime no longer imports modules absent from the package.
- The installer names a missing or unsupported `age-keygen`.

### Known limitations
- Sonar, Linux parity, the L3 and L4 ladders, UAT and the full unit and e2e suites did not run for this release; only targeted specs and checks did.
- The two product workflows are not yet proven running; `1.0.0` waits for that proof.
